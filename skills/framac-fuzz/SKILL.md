# /framac-fuzz

Dynamic bug-hunting stage that pairs **Frama-C RTE + E-ACSL** with **Clang LibFuzzer** across module slices before any static proof effort is spent.

## Why This Runs Before Eva and WP

1. **Zero Human ACSL Required:** `-rte -rte-initialized @all` automatically injects `\valid` / `\valid_read` (`mem_access`), `initialization`, `signed_overflow`, `division_by_zero`, and shift bounds across every C expression in the slice. `--warn-unsigned-downcast` adds unsigned downcasts. Unsigned overflow and signed downcasts are **not** checked while fuzzing: intentional wrap-around (hashes, checksums) and narrowing casts (byte encoders) would stop every campaign on its first input. Eva and WP check those kinds statically.
2. **Sub-Object Precision:** Unlike ASan (which only places redzones between top-level allocations), E-ACSL checks exact array/field sub-object bounds (catching `pkt.header[16]` overflowing into `pkt.is_admin` inside the same struct). Its per-byte initialization tracking backs the `initialization` checks without full-program MSan rebuilds.
3. **Coverage-Guided ACSL Exploration:** E-ACSL compiles ACSL predicates into explicit C `if` branches before calling `__e_acsl_assert()`. Clang's `-fsanitize=fuzzer` instruments those generated branches, actively steering mutations toward RTE and security contract boundaries.

## Step 1 — Load Module Slices from Phase 0

Read `workspace/reports/callgraph_dag.json` and `workspace/harnesses/`. If Phase 0 has not been run yet, execute `/framac-slice <target-dir>` first.

Campaigns run per **harness module**: a link unit, or a sub-module of one (`unit` in `harness_<mod>.json`). Each one's reports, corpus and crashes stay under its own name and credit its unit's functions. Select all harness modules whose tier has `run_eacsl_fuzz: true` (or the specific `--module <name>` passed by the user). `pipeline_make.py gen` lists them; under `quick`, Tier 3 modules are excluded with a reason.

Everything below runs in the analysis image (the wrapper's default). The target's headers and libraries come from the run's snapshot (`workspace/snapshot/`, written by the build capture): builds add `-idirafter` for its headers and link its libraries with an RPATH, so fuzz, replay and coverage binaries run without the target's packages and without `LD_LIBRARY_PATH`. Never pass `-TargetPackages` here.

## Step 1b — Verify the E-ACSL Toolchain (once per image / Frama-C version)

The `selftest` Make target (a prerequisite of `fuzz`) runs it; for a one-off check:

```powershell
# Windows (PowerShell)
& ".\wrappers\framac-docker.ps1" `
  -TargetDir "<target-dir>" -RunDir "<run-dir>" `
  "python3 /opt/framac-pipeline/scripts/run_eacsl_fuzz.py selftest"
```

```bash
# Linux / macOS (POSIX)
./wrappers/framac-docker.sh \
  --target "<target-dir>" --run-dir "<run-dir>" \
  -- "python3 /opt/framac-pipeline/scripts/run_eacsl_fuzz.py selftest"
```

`selftest` builds `templates/eacsl_canary/canary.c` through the exact production E-ACSL path and writes `workspace/reports/eacsl_selftest.json`. Its checks are `compiled`, `no_gmp_only`, `instrumented_binary`, `benign_input_clean`, `detects_overflow`, `detects_uninitialized`, and `attributes_line` (the last one is informational). `benign_input_clean` matters because a replay counts any non-zero exit as a reproduction: a binary that fails on every input (uninitialized runtime, false `\valid` alarms) would otherwise pass `detects_overflow`. Every canary input also goes through each step the build adds to E-ACSL's output (formal init, the contract-wrapper result init on a struct `\result`, the `isnan` shim, the errno stub and shim), so taking one out fails `benign_input_clean` (the `isnan` shim fails `compiled`). If it fails, `campaign --engine auto` skips E-ACSL for every module with `engine_fallback_reason: eacsl_selftest_failed: ...` instead of failing each compile. Read `checks` and the canary `compile_log` before touching harnesses: a failing canary is a toolchain problem, not a target problem.

## Step 2 — Fuzz Every Module with Make (no subagents)

Campaigns need no judgment, so they run from the generated Makefile, not from one LLM subagent per module. Make admits each campaign by CPU and memory and gives it as many LibFuzzer workers as the measured budget allows (`docs/guides/resources-and-caching.md`). The wrapper commands below are the same on POSIX (`framac-docker.sh`). `S=/opt/framac-pipeline/scripts`.

1. Generate the Makefile once, in the foreground: `python3 /opt/framac-pipeline/scripts/pipeline_make.py gen`. Its JSON lists the runnable modules and any module excluded with a reason (no harness sidecar, or a flag outside the allowlist).
2. Compile every module: `python3 /opt/framac-pipeline/scripts/pipeline_make.py run build`. Builds are cached by content, so repeating this after a harness repair rebuilds only what changed. Under `FRAMAC_FUZZ_EXPLORE_JUDGE=on` with `--engine auto`, `build` compiles and caches both `<out-bin>.e-acsl` and `<out-bin>.san` and records them in `workspace/build/<mod>.build.json` (`binaries`, `sanitizer_compile`), so `fuzz`, `judge`, and `eacsl-fuzz` consume pre-built binaries via `--build-json` without compiling inside fuzz/replay leases. Write this command exactly as shown, with the full path: only this exact command line may also fill the shared cross-run cache (`docs/guides/resources-and-caching.md`, Section 5).
3. **Smoke gate (`FRAMAC_HARNESS_SMOKE=on`, default `off`):** run `python3 /opt/framac-pipeline/scripts/pipeline_make.py run smoke` (or `smoke-<mod>`) before fuzzing and before Eva. `smoke-<mod>` executes `harness_smoke.py run` and records the result via `phase0_gates.py record-smoke` into `workspace/reports/phase0_gates.json`. `fuzz-<mod>` and `eacsl-fuzz-<mod>` then check `phase0_gates.py check --module <mod> --need smoke` and pass `--smoke-report workspace/reports/smoke/<mod>.json` so quarantined cases (`quarantined_cases`) are skipped via `FRAMAC_FUZZ_SKIP_CASES` and recorded in `smoke_skipped_cases`.
4. Fuzz every module: `python3 /opt/framac-pipeline/scripts/pipeline_make.py run fuzz`. **No Fuzz/Eva overlap (P4):** run Fuzz stages to completion before starting `/framac-eva` (`build -> smoke -> fuzz -> judge/coverage -> reach-dynamic/eacsl-fuzz -> eva`) so fuzzing and Eva never compete for CPU/memory leases or cache mounts.
5. **Judge & Coverage:**
   - Under `FRAMAC_FUZZ_EXPLORE_JUDGE=on` (default `off`), run `python3 /opt/framac-pipeline/scripts/pipeline_make.py run judge coverage` (they run in parallel after `fuzz`), then `python3 /opt/framac-pipeline/scripts/pipeline_make.py run reach-dynamic` (and under `--profile deep`, `python3 /opt/framac-pipeline/scripts/pipeline_make.py run eacsl-fuzz`).
   - With `FRAMAC_FUZZ_EXPLORE_JUDGE=off`, run `python3 /opt/framac-pipeline/scripts/pipeline_make.py run coverage`, then `python3 /opt/framac-pipeline/scripts/pipeline_make.py run reach-dynamic` (see Step 3).
6. Tune per module only where needed, then re-run the target. Options: dictionaries, budgets, `--fuzz-max-time`, `--fuzz-engine`. Setting `pipeline_make.py params set --module <mod> --fuzz-engine eacsl` emits a warning (in JSON `warnings` and on stderr) that it disables the fast sanitizer explorer (ASan+UBSan) and runs E-ACSL alone, and names `--fuzz-engine auto` to restore dual-engine mode. When no `--dict` / `--fuzz-dict` is configured (and `--no-auto-dict` is not passed), `run_eacsl_fuzz.py campaign` runs `scripts/fuzz_dictionary.py` in-process on the module's target sources (the harness excluded): it writes their string literals plus fixed 8/16/32/64-bit boundary tokens (decimal, hex and byte forms) to `workspace/dicts/<mod>.dict` and passes it to LibFuzzer as `-dict=`. The report's `dictionary` field records `{path, auto, entries}`; when extraction finds no readable source or fails, the campaign runs without a dictionary and `dictionary.reason` says why. You can also generate or inspect a dictionary standalone with `python3 /opt/framac-pipeline/scripts/fuzz_dictionary.py --sources <files...> --out-dict workspace/dicts/<mod>.dict`.
   ```text
   python3 /opt/framac-pipeline/scripts/pipeline_make.py params set --module <mod> --fuzz-dict <file> --fuzz-budget <cpu-seconds>
   ```
   With the module's flags (`--cppflags`, as `make` passes them), the auto dictionary also holds the values of the object-like macros the project defines, read from `cc -E -dD` on the preprocessed sources: integers as decimal text and little- and big-endian bytes, strings as their content. Macros of system headers, the compiler and Frama-C are left out.

Each campaign writes only its own module's corpus, crash directory, and report (`workspace/reports/fuzz/<mod>.json`).
- **Default budgets (`FRAMAC_FUZZ_EXPLORE_JUDGE=off`):** the fuzz budget is CPU-seconds per harness case from the profile (`quick` 60, `standard` 120, `deep` 900): a dispatch harness with `N` cases gets `N` shares, any other harness one. The campaigns of one link unit together get at most `480 / 1200 / 7200` CPU-seconds (`quick / standard / deep`); above that each is scaled down in proportion, never below 30.
- **Sublinear fuzz budgets (`FRAMAC_FUZZ_EXPLORE_JUDGE=on`):** per-case budgets are `60 / 600 / 3600` CPU-seconds (`quick / standard / deep`) with a sublinear link-unit cap `min(3 * base_cap, round(base_cap * sqrt(max(1, cases / 12))))` where `base_cap` is `480 / 7200 / 43200` CPU-seconds (`quick / standard / deep`), never below 30. Effective workers are clamped to `max(1, min(lease_workers, budget // 30))` so the 30 s wall-time floor never inflates CPU spent.
- `gen` records `fuzz_cases` and `fuzz_budget_source` (`cases`, `unit_cap`, or `params` when `params set --fuzz-budget` fixed it).

Wall time = budget / workers, at least 30 s, so a larger node finishes sooner at equal or greater effort. `-rss_limit_mb` stays fixed at 2048 on every machine, so `oom_found` means the same thing everywhere.

### Explore / Judge Split (`FRAMAC_FUZZ_EXPLORE_JUDGE=on`, default `off`)

When `FRAMAC_FUZZ_EXPLORE_JUDGE=on` and `--engine auto`, Phase 1 separates fast sanitizer exploration from E-ACSL judgement instead of splitting wall time evenly inside one campaign:
- **Explore (`fuzz` / `fuzz-%`):** runs `run_eacsl_fuzz.py campaign --build-json workspace/build/<mod>.build.json --profile <profile>` on the pre-built `.san` (ASan+UBSan) binary with `discovering_step: "explore"`, spending 100% of the module's fuzz budget in `quick`/`standard` and 4/5 in `deep`. Round budgets charge only pure LibFuzzer execution time (`fuzz_s`), excluding post-exit replay and attribution (the report records `build_s`, `fuzz_s`, `replay_s`, and `telemetry` series). Dispatch harnesses run a single-case floor pass via `FRAMAC_FUZZ_ONLY_CASE` and load any `--smoke-report` quarantined cases into `FRAMAC_FUZZ_SKIP_CASES` (`smoke_skipped_cases`).
- **Judge (`judge` / `judge-%`):** runs standalone `run_eacsl_fuzz.py judge --module <mod> --build-json workspace/build/<mod>.build.json --corpus-dir workspace/corpus/<mod> --extra-corpus workspace/seeds/<mod> workspace/imported_corpus/<mod> --explore-report workspace/reports/fuzz/<mod>.json [--smoke-report workspace/reports/smoke/<mod>.json] --profile <profile> --sources ... --out-json workspace/reports/judge/<mod>.json` (validated against `schemas/judge_report.schema.json`). It replays mandatory seeds, imported corpora, explorer crashes, and a case-stratified SHA-256 deterministic sample of the grown corpus (profile caps: 512 / 2048 / 4096) on the pre-built `.e-acsl` binary in O(N) batches. Every batch culprit is re-verified in a fresh standalone process: failures that reproduce only inside a batch are separated into `batch_state_only` (not filed as candidates), while confirmed witnesses carry `discovering_step: "judge"` and cross-engine links. Unreplayed inputs are accounted for under `not_judged` and `not_judged_breakdown` (`cap`, `smoke`, `timeout`, `blinded`, `error`).
- **Deep-profile E-ACSL fuzzing (`eacsl-fuzz` / `eacsl-fuzz-%`):** active under `--profile deep` only (skipped under `quick`/`standard`). Runs `run_eacsl_fuzz.py eacsl-fuzz` for the remaining 1/5 CPU-second share on the pre-built `.e-acsl` binary (`discovering_step: "eacsl_fuzz"`, report `workspace/reports/eacsl-fuzz/<mod>.json`), skipping cases quarantined by smoke or blinded by `judge`. If `judge` blinded every active case, `eacsl-fuzz` exits early with `status: unspent_blinded` (`fuzz_unspent_blinded` ledger evidence).
- **Per-case blinding (`K_case = 16`):** in dispatch Explore and Judge runs, a case that triggers `K_case = 16` consecutive 0-pass crashes is blinded so a broken case cannot starve the module; the report records `partial_blinded: true`, `status: partial_blinded` (or `status: blinded` if every active case blinds), and `blinded_remedies`. Non-dispatch fork mode stops early at 64 crashing jobs with `corp == 0`.

**Seeds from the tests.** Phase 0 records the API calls the target's tests make (`/framac-slice` Step 1e: `seed_harvest.py record`, build image, scratch volume; without a test command, the project's non-test executables run once with no arguments instead):
- each test executable is relinked with `-Wl,--wrap` recorders for the model's API functions and run in the sandbox (no network, capped time) under `strace`;
- the arguments of each outermost API call (buffers with their length, strings, scalars, pointees, `{ptr, len}` struct members) go to `workspace/seed_records/calls.jsonl`, with up to 64 small data files the tests opened.

Before each campaign, `seed_harvest.py write --module <mod>` turns them into `workspace/seeds/<mod>/seed-*` in the harness's own case format, read from `harness_<mod>.c`: the dispatch selector byte (two bytes, little-endian, above 256 cases), the fixed-size slots in order, then the data. Data files become whole-input seeds for the cases that take the whole buffer. `workspace/reports/seeds/<mod>.json` says what each case got. The `seeds` Make target writes them for every module.

The campaign and `coverage` read the seeds as a read-only extra corpus (`--extra-corpus`). No test command and no executable that calls the API, a failing test suite, or no recorded call just means fewer or no seeds, never an error. Calls made through header `static inline` functions are not recorded, so their harness cases start from an empty corpus.

**The target's own corpus.** Phase 0 imports the fuzz corpora the target ships (`/framac-slice` Step 1f). Before each campaign, `fuzz_assets.py write --module <mod>` writes them to `workspace/imported_corpus/<mod>/imp-*`:
- a target fuzz module (`tf_<id>`, sidecar `target_fuzzer`) gets the corpora mapped to its fuzzer as they are: they are that fuzzer's own input format;
- any other module gets each mapped corpus in the cases that take the whole buffer and call one of the corpus's functions (its mapped `--function`s, or its fuzzer's `direct_api_calls`), with the dispatch selector byte (or two) in front;
- inputs longer than the module's `max_input_size` are dropped and counted, and a module gets at most 20,000 inputs.

`workspace/reports/imported_corpus/<mod>.json` says what each case got. The campaign and `coverage` read the folder as a second read-only extra corpus. When the fuzzer ships a dictionary, its valid entries go to `workspace/dicts/<mod>.extra.dict` and are appended to the auto dictionary (the report's `dictionary.extra_entries`); an explicit `--dict` is used alone. Imported inputs are named `imp-`, not `seed-`, so guardrails do not replay them all.

**Did the seeds get written?** Both writes record each module's outcome in `workspace/reports/seed_status/{seed_harvest,fuzz_assets}/<mod>.json`, and the campaign report carries it as `seeds`: `{status, reason, writers: {seed_harvest: {status, reason, inputs, generated_at}, fuzz_assets: {...}}}`. `status` is `ok` (a write produced inputs), `skipped` (nothing to write: no records, no mapped corpus, no case that takes them; `reason` says which) or `failed` (a write raised, or recorded no status although the campaign reads `--extra-corpus`; `reason` has the exception, and the module's seed folder may hold part of the new inputs). A failed write exits 1 but never stops the campaign. Read `seeds.status: failed` before tuning a module whose cases start from an empty corpus: fix the write (or the records) and re-run `fuzz-<mod>`.

**Lifecycle cases.** An `--api` harness has one case per opaque handle type with a constructor and a destructor (sidecar `api_cases`, `kind: lifecycle`): it builds the handle, then while the input lasts makes up to 8 calls on it, each picked by one input byte among the functions in `methods`, then releases it. Single cases build a fresh handle per call, so only these reach use after free, double free and call after error. A crash in one is skipped as a whole case; when one of its functions changes the fuzzing process itself (libseccomp's `seccomp_load`), skip the case by hand as for the single case.

**Inputs that reach nothing stay out of the corpus.** A generated harness returns `-1` from `LLVMFuzzerTestOneInput` (libFuzzer's input rejection, clang 19 in the analysis image) for an input longer than `MAX_INPUT_SIZE`, and, in a dispatch harness, for an empty input and an input whose case the round skips. A hand-written dispatch case whose own length guard turns the input away before any call writes `FRAMAC_FUZZ_REJECT();` there (empty in `eva_main`). The generated `--api` cases have no such guard: a short input leaves the remaining arguments zeroed and still makes the call, so it is kept.

A campaign keeps going after a crash, so one shallow bug does not hide the others in its module:
- **The dispatch selector.** A dispatch harness's first input byte is the index of the case it runs; a byte at or above the case count runs no case, and libFuzzer drops that input. Appending a case therefore never changes the case an existing corpus input, seed or crash file selects. A harness with more than 256 cases selects with the first two input bytes, little-endian (`dispatch_selector: "identity16"`, switch marker `dispatch selector: identity16, <n> cases`), and the case gets the input after them; a harness with 256 cases or fewer keeps the one-byte selector, its text and its `harness_digest`. Two bytes select at most 4096 cases, the most a campaign skips at run time: `generate_harness.py` refuses a harness with more and says to split the module into sub-module harnesses (`--scope-file`); an `--api` harness keeps its first 4095 cases and lists the functions left out in `api_skipped` (`more than 4095 cases`). The sidecar records the encoding as `dispatch_selector` (`identity` or `identity16`), and seeds, imported corpus inputs and crash decoding use that many selector bytes. A dispatch harness whose sidecar has no `dispatch_selector` was generated with the older selector (the first byte modulo the case count) and every tool still decodes it that way; once it is regenerated, its stored inputs whose first byte is at or above the case count select nothing, so fuzz the module again.
- **Dispatch harnesses** run in rounds. Each case an input crashed (or timed out) in (the case its selector bytes select) is skipped from the next round on. A harness that carries the runtime skip marker skips the cases through `FRAMAC_FUZZ_SKIP_CASES` in the environment of the same binary (`keep_going.runtime_skip`). Otherwise the skip uses a rebuild with the same engine and the mask in 64-bit words: `-DFRAMAC_FUZZ_SKIP_CASES=<mask>` for cases 0..63 and `-DFRAMAC_FUZZ_SKIP_CASES_<k>=<mask>` for cases 64k..64k+63, so every case of a dispatch harness can be skipped. The E-ACSL runtime empties `environ` unless the build links its `environ_keep` shim; when an E-ACSL build has no shim, its rounds rebuild with `-DFRAMAC_FUZZ_SKIP_CASES` instead, and `keep_going.runtime_skip_unavailable` says why. Rounds are bounded by CPU-seconds: the campaign's wall time times its LibFuzzer workers, so the same campaign runs the same rounds on any worker count. The rounds end when a round finds no new crashing case (`stopped: no_new_case`), every case is skipped, less than 10 CPU-seconds are left (`MIN_ROUND_CPU_S`) or less than one whole wall second, or a rebuild fails. A round's wall budget (`-max_total_time`) is the wall time the campaign has left, rounded down to whole seconds, so no round overruns the campaign; the first round gets the campaign's wall time (`campaign_wall_time`). `keep_going.stopped` is the last round's reason, one of `no_new_case`, `insufficient_memory`, `every_case_skipped`, `time_budget_spent`, `unskippable_case`, `rebuild_failed` and `crash_in_skipped_case`. `keep_going.cpu_seconds_spent` is the CPU-seconds the rounds used, and `keep_going.workers` the worker count they ran with. A skipped case is not fuzzed for the rest of the campaign, so a second bug in the same case can still be hidden; the report's `keep_going.rounds` lists what each round skipped and found. `keep_going.status: error` (a round with `stopped: crash_in_skipped_case`) means the rounds stopped because a case that was skipped still crashed: the listed crashes are real, the remaining cases were not fuzzed, and the ledger records `fuzz_keep_going_error`. Report it as a pipeline problem.
- **Cases that cannot be skipped.** A dispatch harness generated before every case became skippable (its guard lacks the `every dispatch case skippable` marker) can skip cases 0..63 only. When a round's only new crashing cases cannot be skipped, the round records `stopped: "unskippable_case"` with `unskippable_cases`; after that, or after `rebuild_failed`, the time left runs in fork mode with `-ignore_crashes=1` on the last binary (`keep_going.fork_fallback`). Regenerate such a harness to get rounds for every case.
- **Other harnesses** (and dispatch harnesses generated before the skip macro existed) run in libFuzzer fork mode with `-ignore_crashes=1` (`keep_going.mode: fork`). The same bug is then saved many times: at most 64 crash inputs are replayed, and at most 3 artifacts are listed per fingerprint (`artifacts_omitted` counts the rest).
- **Single-process campaigns.** libFuzzer starts its `-jobs`/`-workers`/`-fork` processes through `system()`. A module that defines `system` or `popen` itself (an LD_PRELOAD interposer such as sudo's `sudo_noexec.c`, read from the binary with `nm`; sanitizer interceptors do not count) runs in one process with `-print_funcs=0`. So does a multi-process campaign that ends `fuzzer_error` with no artifact before any input ran (its workers never started, e.g. a seccomp filter denying `execve`): it is rerun once in one process, and `multi_process_attempt` keeps the first attempt's returncode and log tail. The engine's later rounds stay single-process. The engine's result and `keep_going` carry `single_process_reason`; `keep_going.workers` is then 1 and `cpu_seconds_spent` counts one CPU, so the campaign used less CPU than its budget. Without fork mode a single process stops at its first crash (`keep_going.stops_at_first_crash`). Fuzz binaries run with SIGPIPE ignored, so a crash is still saved when the target keeps the symbolizer from starting (its frames then stay unsymbolized).
- `--stop-on-first-crash` restores the old behavior: one campaign that ends at the first crash.

For a single module in guidance mode, check the module's Phase 0 gate first, then run the underlying command:

```text
python3 /opt/framac-pipeline/scripts/phase0_gates.py check --module <mod> --need reach,build_check
python3 /opt/framac-pipeline/scripts/seed_harvest.py write --module <mod>
python3 /opt/framac-pipeline/scripts/fuzz_assets.py write --module <mod>
python3 /opt/framac-pipeline/scripts/run_eacsl_fuzz.py campaign --module <mod> --sources <sidecar sources> workspace/harnesses/harness_<mod>.c --out-bin workspace/harnesses/fuzz_<mod> --corpus-dir workspace/corpus/<mod> --artifacts-dir workspace/crashes/<mod> --extra-corpus workspace/seeds/<mod> workspace/imported_corpus/<mod> --workers auto --fuzz-budget <cpu-seconds> --engine auto --cppflags='<sidecar cppflags> -I/opt/framac-pipeline/templates/acsl' --out-json workspace/reports/fuzz/<mod>.json
```

The gate check exits 1 with the reasons when the module failed the reach gate or build-check, or its harness or the DAG changed since the reach check: repair the harness and re-run the gate (`/framac-slice` Steps 4b and 5); never fuzz around it. `campaign --module <mod>` enforces the same check itself whenever the run directory has a gate stamp (`workspace/reports/phase0_gates.json`): it refuses the module with the reasons and writes no report. A campaign outside a run directory is not gated.

`run_eacsl_fuzz.py` supports `--engine {auto,eacsl,sanitizers}` (default `auto` in `campaign` mode):
- **Two-stage E-ACSL build.** Stage 1 instruments only (`e-acsl-gcc -n -F <frama-c flags> -E <frontend>`). It receives all preprocessor flags (`-I`, `-D`, `-include`), the `fc_stubs` directory first, `fc_compat_types.h`, `-D__FRAMAC_EACSL__`, and for glibc's floating-point classification macros (`isnan`, `isinf`, `fpclassify`, `signbit`, ...) `-D__SUPPORT_SNAN__` with the `fc_stubs/eacsl` `math.h` shim, since Frama-C knows neither the `__builtin_*` forms nor glibc's `_Generic` dispatch. Without `-n`, `e-acsl-gcc` also links the original main-less harness and fails. Stage 2 compiles the self-contained `<out-bin>.instrumented.c` with `e-acsl-gcc -C -e <codegen flags only>`. Two printer and E-ACSL gaps are handled on the way. Full memory tracking takes the address of every local, which Frama-C refuses for a `register` local, so stage 1 also gets `-Dregister=` (`compile.full_mtracking_defines`; never in the harness cppflags, which Eva and WP read). The Frama-C printer puts a member's `_Alignas(N)` after its declarator, which clang rejects, so between the stages each one becomes `__attribute__((__aligned__(N)))`, which keeps the alignment (`compile.alignas_rewrites`). The kernel also prints a global array sized from a later object at its header declaration, above that object (sudo: `unsigned int sudoers_subsystem_ids[sizeof(sudoers_subsystem_names) / ...]` before the static table), which clang rejects as an undeclared identifier: those earlier declarations become `extern T ids[];` and the sized declaration follows the object, so the size and the checks are kept (`compile.forward_array_sizes`). Printing several files, the kernel drops a forward tag declaration the sources have (sudo_nss.h's `struct passwd;`) and prints the definition after a struct whose member names the tag in a parameter list, where it declares a type of its own; clang then rejects `.query = & sudo_file_query` ("incompatible function pointer types ... 'int (*)(..., struct passwd *)' with ... 'int (*)(..., struct passwd *)'"). Each tag defined at file scope that is first named in a parameter list or a function body gets `struct T;` at the start of the file, line numbers unchanged (`compile.forward_tag_declarations`). The printer also puts a goto label before `default:` (sudo: `FALLTHROUGH; default: print_word:` printed as `__attribute__((__fallthrough__)); print_word: default:`), which clang rejects ("fallthrough annotation does not directly precede switch label"): a fallthrough attribute not directly followed by a `case` or `default:` label is removed and its `;` kept; it only silences a warning, so control flow and checks are unchanged (`compile.misplaced_fallthrough`). A module that compiles another link unit's file (a link repair adds it) gets that file's own `-I`/`-iquote` directories from the build capture (`compile.source_include_dirs`). E-ACSL cannot mark a const union read-only (pub/frama-c#2795), so the stage-1 preprocessor drops `const` from every `static const union` object in the E-ACSL frontend's text only (`compile.const_union_rewrites`; E-ACSL then does not check those objects as read-only, and REPORT.md names the modules). A const union form it does not cover shows in `build_check.json` as `eacsl_static_const_union` with `rewrite_missed: true`: record the gap in `docs/troubleshooting/harnesses-and-seeds.md`, then continue with the row's `next_step` sanitizers command.
- **Runtime initialization.** Harnesses have no `main()`, so the build uses `-e-acsl-full-mtracking` and links `templates/eacsl_runtime/fuzz_init.c`. It initializes the E-ACSL runtime the way an instrumented `main()` would, from the executable's `.preinit_array`: before any shared library's constructor and the target's own constructors, so target constructors and libc functions the target replaces (a `getenv` a library's constructor calls) run tracked. Its `LLVMFuzzerInitialize` does it if the preinit entry did not run (`runtime_init` in the build record). It also registers the `environ` pointer array, which the runtime leaves out. Stage 2 links a position-dependent binary (`-fno-pie`/`-no-pie`), so the library data the target references (`environ`, `__progname`, `stdout`, `optarg`, ...) is copied into the executable's own tracked globals; `position_dependent.copied_library_globals` lists it. When that link fails, the build falls back to a PIE and records `fallback_reason`; such a binary still crashes in `__e_acsl_globals_init` if the slice registers library data. Without full tracking, valid writes to a caller's stack buffer fail `\valid`; without the hook, every input crashes in `shadow_alloca`. A harness must therefore not define its own `LLVMFuzzerInitialize` (`reason: eacsl_init_hook_conflict`). Never force-include headers into stage 2 (it redefines `timeval`, `fd_set`, ...), so boundary stub headers do not need E-ACSL-specific branches. The full transcript is in `<out-bin>.compile.log`.
- **Initialization checks.** Stage 1 adds `-rte-initialized @all`, so every read of a local or pointed-to value must be initialized. libFuzzer writes the input buffer outside instrumented code, so target code must never read `data` directly: generated harnesses copy it into their own buffer (`fuzz_buf`) first. Reads of memory filled by other uninstrumented code, such as external libraries behind `fc_stubs` or `read`/`recv`, can raise false `initialization` alarms. Measured on one harness, the checks roughly halve throughput (3.3k vs 7.5k exec/s). `--no-rte-initialized` (campaign and guardrail) turns them off; in a run, set it per module with `pipeline_make.py params set --module <mod> --no-fuzz-rte-initialized`. That opt-out is recorded in `reduced_checks` and in the ledger's evidence note, and Eva still reports uninitialized reads statically. E-ACSL registers formal parameters without marking them initialized, so the build marks each one initialized at function entry (`compile.formal_inits`); otherwise the first read of a by-value struct field would fail `\initialized` on every call. The cost: E-ACSL does not report uninitialized struct members passed by value. An `initialization` alarm on a formal (`\initialized(&s.len)` at a function's first statement) means the build skipped that step: rebuild, do not opt out.
- **libc and format-string checks.** Both stages get `--libc-replacements` and `--validate-format-strings` (`compile.check_options`). E-ACSL then checks the buffers passed to `memcpy`, `memmove`, `memset`, `strcpy`, `strcat`, `strlen`, `strcmp` and their `n` variants (overflow, overlap, unterminated string), and the arguments of printf-family calls against their format directives. RTE alone checks none of these. E-ACSL's runtime compares a directive's type with the argument's type exactly, so a promoted `unsigned char` passed to `%u` would stop every input. Stage 2 therefore compiles the runtime from a patched copy of E-ACSL's share directory (`compile.runtime_patches.format_runtime`), which lets a signed/unsigned argument of one rank through when its value fits both types, as C11 allows. The same copy reads the argument of a `%s`, `%p` or `%n` after a floating-point argument from the right slot. A stop on such a pair still happens when the value does not fit, for example a negative `int` for `%u`. The failure then carries `format_mismatch` `signedness`. If `runtime_patches` says `not_applied`, the stop may be the promotion false alarm. Such a failure is one bare line followed by an abort, for example `memcpy: overlapping memory areas` or `printf: directive 1 ('%s') expects argument of type 'char*' ...`, with no file or line. The failure gets `kind` `eacsl_libc_error` or `eacsl_format_error`, `file` `unknown` and `line` 0. Its `function` is the target function that made the call, taken from libFuzzer's stack, and `instrumented_location` is that call's line in `<out-bin>.instrumented.c`. With no line, the campaign replays the input on its ASan+UBSan build. ASan locates the memory errors there, but not the format errors, which keep `file` `unknown`. To find the call, open the instrumented file at `instrumented_location` and look for the matching call in that function in the source. E-ACSL does not track memory libc keeps in its own storage. For the functions of `EACSL_LIBC_EFFECTS` (`strerror`, `strsignal`, `gmtime`, `ctime`, `inet_ntoa`, ...), the libc shim (below) hands the target a tracked copy instead, so `fprintf(f, "%s", strerror(e))` runs clean. A stop on a pointer from any other libc or library call is a false alarm, for example `... attempt to access unallocated memory via directive ...` or `... source string string unallocated`. When a module's seeds stop on one, add the function to the table, or run `pipeline_make.py params set --module <mod> --no-fuzz-libc-checks`. It is recorded as `-no-libc-checks` in `reduced_checks`, and the guardrail follows it. `--temporal` stays off: with full tracking it aborts on any call that passes a function's address.
- **Argv contract.** `e-acsl-gcc` splits flag values on spaces and re-parses standalone short options (a bare `-g` becomes `--gmp`). The script joins `-I dir` into `-Idir`, rewrites `-g` to `-gline-tables-only`, and refuses other standalone single-letter tokens or paths containing spaces (`reason: eacsl_argv_unsafe`).
- **Instrumented binary only.** The fuzzed binary is `<out-bin>.e-acsl`, and it must contain E-ACSL instrumentation (`reason: eacsl_binary_not_instrumented` otherwise). The guardrail refuses uninstrumented binaries instead of reporting a vacuous `passed_dynamic_oracle`.
- **Function scoping.** `-rte-select` / `-e-acsl-functions` come from the preprocessed slice sources, so functions disabled by `#if` are excluded. Functions Frama-C still reports as unknown are dropped once and listed in `rte_select_dropped`.
- **Variadic fallbacks.** Undefined `<fn>_fallback_<N>` symbols are defined in a generated, link-only `<out-bin>_fallbacks/eacsl_fallbacks.o`, which forwards to the real libc function when possible. `variadic_fallbacks` lists each one; `mode: enosys` entries always fail with `ENOSYS`, which is a coverage caveat for the code behind them. `--no-variadic-translation` asks Frama-C not to emit them at all.
- **errno shim.** In E-ACSL builds `errno` is a tracked global (`templates/fc_stubs/errno.h`): libc's thread-local errno is outside the memory E-ACSL shadows, and every write to it would abort the runtime. When the slice reads errno, the build links a generated, link-only `<out-bin>_errno_shim/eacsl_errno_shim.o` with `-Wl,--wrap=<fn>` for each errno-setting libc function it calls (`strtol`, `read`, `recv`, ...); each wrapper copies libc's errno into the global after the call, and the Variadic fallbacks do the same. `compile.errno_shim` lists the wrapped functions (`status: built`), or `status: failed` with the `unsynced` ones. It is a coverage caveat: after a libc call outside the list, or in a failed build of the shim, the target reads the last errno it wrote and can take the wrong branch.
- **libc shim: what libc wrote or returned.** E-ACSL does not see libc write memory, so with `-rte-initialized` the first read of an out-parameter fails `\initialized` (`strtol`'s `endptr`, `getsockname`'s address, the buffer `recvmsg` filled). The same wrappers therefore also tell the runtime what the call wrote, for the functions of `EACSL_LIBC_EFFECTS` in `scripts/eacsl_toolchain.py` the slice calls, whether or not it reads errno. They mark exactly the bytes written as initialized (`r` bytes of a `read` buffer, at most the caller's length of a socket address, nothing on failure), and only in memory the runtime tracks. A function returning libc's static storage gets a tracked copy in a buffer of the shim. One buffer per function, as in libc: the next call overwrites it, and a string is cut at 1023 bytes. `compile.errno_shim.eacsl_effects` lists these functions. When they fail to compile against the host libc, the errno wrappers are built alone and `effects_error` says why. The effects start once `fuzz_init.c` has initialized the runtime. A real uninitialized read next to such a call still stops, for example a byte past what `read` returned or a failed `getsockname`. With `-rte-initialized`, the `\initialized` checks on a `va_list` are dropped (`va_list_init_checks_skipped`): `va_start` is a builtin E-ACSL does not see, so every `va_arg` failed.
- **Sanitizer fallback.** With `--engine auto`, an E-ACSL failure (or a failed selftest) falls back to Clang LibFuzzer + ASan + UBSan (`-fsanitize=fuzzer,address,undefined -fno-sanitize-recover=all`). The report then has `engine_used: sanitizers` and `engine_fallback_reason`, and ledger evidence notes that no E-ACSL contract checks or intra-object bounds checks ran.
- **Both engines.** With `--engine auto` and a working E-ACSL build (under default `FRAMAC_FUZZ_EXPLORE_JUDGE=off`), the campaign fuzzes twice, half the wall time each: ASan+UBSan first, then E-ACSL on the grown shared corpus. (Under `FRAMAC_FUZZ_EXPLORE_JUDGE=on`, `fuzz` runs the pre-built `.san` Explore campaign and `judge` replays the corpus on the pre-built `.e-acsl` binary; see "Explore / Judge Split" above.) The engines catch different bugs: ASan intercepts libc calls (an overlapping `memcpy`, for example), which E-ACSL does not check, while E-ACSL checks initialization, intra-object bounds and contracts. On libmnl, ASan alone found 4 of 5 known bugs and E-ACSL alone 2. The report has `engine_used: eacsl+sanitizers`, each engine's own outcome under `engines`, and an `engine` on every artifact; candidate replay uses that engine. `--engine eacsl` or `--engine sanitizers` (`params set --fuzz-engine`) fuzzes with one engine only; choosing `--fuzz-engine eacsl` warns that it disables the fast sanitizer explorer and names `--fuzz-engine auto` to restore dual-engine mode. A module whose unit E-ACSL cannot build fuzzes with the sanitizers only, by the DAG's choice (`fuzz_engine_reason`): a unit on the GCC fallback, or one that includes `setjmp.h` or calls setjmp/longjmp. If the sanitizer build fails, the campaign fuzzes with E-ACSL only and records `dual_engine_skipped`.
- **Link repair.** When the link stops on `undefined reference to 'X'`, the build adds the source defining `X` and links again. That source comes from the DAG's functions, else from its `build_only_functions`: code the compiler builds and Frama-C's parse lacks, such as libpng's `png_target_init` under `__SSE2__`. The report records the repair under `link_repair`. When several files define `X` (each program its own, as sudo's `open_sudoers`), the repair links the one the build already has, else the one of the module's link unit or a unit it links; when none is, it never picks one: `X` becomes an aborting stub in `link_stubs.c`, listed in `link_repair.stubbed_functions` with its `reason` and `definers` (a call to it at runtime is a `link_stub_aborts` entry, never a finding). A target fuzz module never gets back a file its sidecar's `target_fuzzer.link.excluded_sources` leaves out: what that file defines is stubbed the same way (globals in `link_globals.c`). Nor does any module get a file that also defines a name the build already defines (the DAG's functions and the model's globals of the linked files, and a target fuzzer's own definitions, `main` included): linked, it would fail on "multiple definition" (sudo: cvtsudoers.c, the only definer of `log_warnx`, also defines the fuzzer's `open_sudoers`), so `X` is stubbed with a `reason` naming each clash. A defining file that does not exist is never added: `link_repair.missing_sources` names it, and its `reason` names the Phase 0 step that should have kept it. For a C file the build generated, that step is the build capture, which keeps it in the snapshot and installs it in `workspace/work`. A run captured before generated sources were kept must redo the capture. After a repair, `build_attempts` keeps every attempt's failure and its logs (`<log>.attempt<N>.log`), so an earlier failure stays visible when a later attempt fails for another reason. `killed` means a SIGKILL was seen directly. `killed_suspected` means Frama-C stopped with only `aborted by Frama-C` and no error of its own: most likely out of memory, which `docker events` (`oom`) can confirm.
- **Crash attribution.** When an E-ACSL crash has no usable location (for example the RTL crashed in `unsafe_initialize`), the input is replayed on a sanitizer build of the same slice. The artifact then has `attribution` and `failure_source: sanitizer_replay`. Disable with `--no-attribution-replay`.
- **E-ACSL's heap limit.** The E-ACSL runtime tracks a fixed heap zone of `EACSL_HEAP_ZONE_MB` (1024 MiB; stage 2 gets `--zone-sizes heap:1024`, recorded as `compile.eacsl_zone_sizes`). A larger block aborts the runtime with `Exceeded heap allocation limit of 1024MB`, so a target that allocates a size read from its input (mpack's `*_alloc` functions) stops there on a legitimate input. The limit is fixed because it decides results. Each tracked MiB costs about one MiB of RSS in shadow memory, so 1024 is the largest zone that stays inside the fixed `-rss_limit_mb` 2048. The runtime cannot go to 2048: its `int` size product overflows and every input segfaults. Such an artifact keeps `kind: crash`, so keep-going skips its case, and has `failure: null` and `eacsl_resource_abort: {resource, limit_mb, message, caller, sanitizer_replay}`. The input is replayed on the sanitizer build first: a failure located there becomes the artifact's failure and a candidate. Otherwise the ledger makes no candidate and gives the module's units `fuzz_eacsl_resource_limit` evidence listing the inputs. Read that evidence as a gap, not a pass: E-ACSL checked nothing after that allocation for those inputs. `sanitizer_replay: unavailable` means no sanitizer build could replay them. An `oom-` artifact is replayed the same way and keeps `kind: oom`. It gets the marker only from its own replay, never from the campaign log, and not when the sanitizer build of the input runs out of memory too. An OOM left without a failure or a marker becomes a candidate keyed by its input.
- Phase 3 `/framac-wp` `guardrail` mode always uses E-ACSL (`compile_eacsl_binary`), because its purpose is to execute candidate ACSL annotations against the corpus.
- `compile.undeclared_functions` lists functions called without a prototype. Add them to the matching `templates/fc_stubs/` header (see `templates/fc_stubs/README.md`).

### MetAcsl security properties in the E-ACSL build

When `workspace/reports/security_props.json` lists `eacsl` in `meta_engines` (`security_props.py run --meta-engines eacsl`, `docs/guides/security-properties.md`), the E-ACSL build of a module also compiles the module's MetAcsl properties into run-time checks, so an input that violates one stops the binary like any other failed check. `gen` then writes `FUZZ_SECURITY_PROPS_<mod>` into `modules.mk`, the `build-<mod>` and `fuzz-<mod>` recipes pass `--security-props=<file>`, and `build-<mod>` depends on the file. By hand, the `build`, `campaign`, `replay`, `minimize`, `replay-candidates` and `minimize-candidates` subcommands take `--security-props PATH`, else `$FRAMAC_SECURITY_PROPS`, else `workspace/reports/security_props.json` when it exists; `--security-props none` turns it off. Without `eacsl` in `meta_engines` the Make output, the commands and the reports are the ones of a run without the option.

- **What the build loads.** The properties with an instance in a function of the module's sources, written to `<out-bin>.security_meta.c` with a sidecar `<out-bin>.security_meta.json` (property to class and instances, function to file, the harness's functions). MetAcsl runs in a Frama-C stage of its own before RTE and E-ACSL. The sanitizer build, the guardrail (`guardrail` mode), the selftest canary and the loop-seed check never load them.
- **The cache.** A build with properties is cached under its own key: the meta file's text, the MetAcsl stage flags and what the sidecar is written from. The path of `security_props.json` is not in the key, so in one run directory Make's build, the campaign and a replay share one entry, however each names the file. A build in another directory is another entry, as for any build. A hit restores the meta file and the sidecar with the binary. The key of a build without properties is made of what it always was.
- **Read `security_props` and `security_props_warnings`** at the top of the build, campaign and replay reports (each warning is also printed on stderr as `security props [<mod>]: ...`):
  - `status: loaded` with no warning: every loaded property has a run-time check.
  - `dropped`: the E-ACSL build failed with the properties and was redone without them. The binary checks **no** MetAcsl property; `log` names the failed build's log (`<out-bin>.security_meta.log`). Not cached: the next build tries again. Never read such a campaign as evidence about a MetAcsl unit: `ingest-fuzz` writes `fuzz_meta_not_checked` on the module's units of those classes.
  - `error`: the file could not be read. `skipped` with a reason other than "no property has an instance in a function of these sources": the toolchain or the module cannot take the properties (no target function listed, an old `e-acsl-gcc`). Both are treated as `dropped`.
  - `rejected`: MetAcsl could not type a property in this module (a global the module does not declare); the others are checked.
  - `left_out`: a `\precond` property whose protected function the harness names. The harness could break it on a correct target, so it is not compiled. WP still proves it.
  - `not_translated`: no run-time check exists (MetAcsl decided it, or it has no instance in the instrumented functions).
  - `unplanned_instances`: MetAcsl checks the property in a function `security_props.json` does not list as an instance. A violation there is a candidate that links no unit. Report it: the model and MetAcsl disagree on where the property applies.
  - `libc_contracts`: the E-ACSL build parses libc from the host headers, which carry no contract, so the meta file adds `assigns` for `memcpy`, `memmove`, `memset` and `strncpy`: a write through one of them into a protected location is checked. `loaded` lists them. `dropped` (warning `libc contracts dropped`): the build failed with them and was redone without them, the properties still loaded; `log` names the failed build's log (`<out-bin>.security_meta_libc.log`). Record it as a pipeline bug.
  - `libc_unchecked`: the libc functions that write or read through a pointer and have no contract in this build (`strcpy`, `sprintf`, `read`, `recv`, `fgets`, ...), each with the module's functions that call it (warning `libc unchecked`). No `\writing` or `\reading` property is checked on what those calls write or read in this binary; WP and Eva check them. Do not read a clean campaign as evidence that such a call respects the property.
- **A violation.** Its failure has `meta_property`, `obligation_class`, `line: 0` and `meta_location` (the property's line in the meta file); its fingerprint is `<file>#<function>::meta_<property>::<hash>` and does not depend on where the meta file was written, so a replay built in another directory gives the same fingerprint. So does a replay with `--binary` from another working directory: the sidecar is looked for next to the binary first.
- **A failed precondition** (`kind: precondition`) is reported in the protected function and carries `caller`. With `harness_induced: true` the caller is harness code: the campaign report lists it under `security_props_harness_induced`, and it is not a finding against the target. Fix the harness (pass the gate first) or accept that the property is checked by WP only.
- **A failed guard** (`meta_guard`): E-ACSL could not evaluate the property's predicate (an invalid read, an uninitialized value). It is an ordinary alarm at that function, not a violation of the property.

The fuzzer, and every crash replay, runs inside the hardened container through `sandbox_exec.py` (rlimits, env allowlist, timeout with process-group kill). There is no filesystem isolation inside the container. If the report says `sandbox_unavailable`, the command was not run inside the container (non-POSIX host); stop and rerun it through the wrapper rather than running it unsandboxed.

*(Never pass `-fsanitize=address` alongside E-ACSL's memory tracking runtime in the same binary, as both intercept `malloc`/`free` and map conflicting shadow memory.)*

For E-ACSL behaviour not covered here, start with `docs/references/e-acsl-quickref.md`, which covers `e-acsl-gcc` and `-e-acsl-*` options, runtime output and limitations. Then grep the E-ACSL plug-in manual (Frama-C 33.0) in `docs/references/` (see `docs/references/README.md`). The manual's examples mix old and new option spellings, so check any flag against `e-acsl-gcc -h` in the container.

## Step 3 — Read Outcomes and Ingest

`workspace/reports/fuzz/<mod>.json` has one of these statuses:

| Status | Meaning |
| :--- | :--- |
| `crash_found` | At least one `crash-*` artifact in any round. Each listed artifact was replayed once (`reproducible`), its failure parsed (`failure`: file, line, function, kind, alarm_kind, predicate), and fingerprinted. A sanitizer failure has `kind` `asan_<kind>` or `ubsan_runtime_error`. A LeakSanitizer leak has `kind` `lsan_direct_leak` or `lsan_indirect_leak` and `alarm_kind` `memory_leak`: it is a candidate with `property.kind` `memory_leak`, verified by its allocation stack (CWE-401), and it links no ledger unit, since no obligation class covers leaks. |
| `timeout_found` / `oom_found` | Per-input timeout or RSS limit hit. A termination/DoS lead, not a memory-safety bug. |
| `clean` | No failure within the time budget. The corpus in `workspace/corpus/<mod>/` becomes the dynamic anti-hallucination corpus for `/framac-wp`. Fuzzing is not proof. The ledger reads the coverage report (below) per function: a function with `executions: 0`, or one the report does not list, gets `fuzz_not_executed` evidence instead, which says no replayed input ran it and is not evidence of anything. Without a usable coverage report (missing, a status other than `ok` or `partial`, or a `partial` report with inputs not replayed), the units get `fuzz_clean` and its note says which functions ran was not measured. Under `FRAMAC_FUZZ_EXPLORE_JUDGE=on`, E-ACSL `fuzz_clean` is granted only for dynamically executed functions whose reaching cases were judged cleanly by `workspace/reports/judge/<mod>.json` without blinding or `not_judged` gaps (otherwise the ledger records `fuzz_not_judged`, `judge_partial_blinded`, or `judge_batch_state_only`). |
| `partial_blinded` / `blinded` / `unspent_blinded` | Under `FRAMAC_FUZZ_EXPLORE_JUDGE=on`, one or more dispatch cases hit `K_case = 16` consecutive 0-pass crashes and were blinded (`partial_blinded`), every active case blinded (`blinded`), or `eacsl-fuzz` skipped because `judge` blinded the module (`unspent_blinded`). Never read blinded cases as clean; inspect `blinded_remedies` and `smoke_skipped_cases`. |
| `fuzzer_error` / `compile_error` / `sandbox_unavailable` | The campaign did not run to completion. Never read this as clean. Startup/runtime-init aborts (`toolchain_startup_error`) and smoke-quarantined artifacts (`quarantined_by_smoke` or in `smoke_skipped_cases`) are filtered out of candidate creation and recorded as `fuzz_startup_error` or `harness_smoke_quarantined` unit evidence instead. |
| `engine_errors` (any status) | A merged report whose engine did not run to completion lists it here as `{engine: {status, reason}}`, even when the other engine crashed or was clean. The module's units get `fuzz_fuzzer_error` evidence naming that engine: the other engine's results are ingested too. |
| `insufficient_memory` | The job's memory lease is below what LibFuzzer needs at the fixed `-rss_limit_mb` (the report's `error_summary` gives both numbers). Nothing ran; never read this as clean. Give the container engine more memory, or lower the pool's concurrency. |
| `not_run` | No report was produced for an expected module (the job was killed or excluded). Written by `ingest` so the gap is recorded, never silent. |

`workspace/reports/coverage/<mod>.json` says which of the target's functions and code regions the corpus executes, measured by replaying `workspace/corpus/<mod>/` on a plain Clang source-coverage build (`run_eacsl_fuzz.py coverage`, no E-ACSL and no sanitizers). That build gets the same link repair as the fuzz build, so `sources` is what it compiled last and `link_repair` (with any `missing_sources`) says what the repair added. `functions[]` has `executions`, `regions` and, for a function that ran, `uncovered_lines`. `make` replays the corpus as it stands, so run `coverage` again after a corpus changes.

| Status | Meaning |
| :--- | :--- |
| `ok` | Every input replayed. |
| `partial` | Some inputs failed or were not replayed (`failed_inputs`, `inputs`), so the counts are lower bounds. A failing input is a lead to replay on the fuzz binary, not a candidate. Failures no longer stop the replay: only the time budget does (`inputs.not_replayed`). `failed_inputs` details the first 16 failures, `failed_inputs_unlisted` counts the rest, and inputs matching a crash artifact of the module replay last (`inputs.known_crash`). |
| `no_inputs` / `compile_error` / `coverage_error` / `sandbox_unavailable` | Nothing was measured. Never read this as no reach. |

When llvm-cov rejects the build with "truncated coverage data" (LLVM 19 writes an unreadable mapping when a header is included inside a function body), `coverage` rebuilds once with those headers included first and lists them in `pre_included`.

`reach-dynamic-<mod>` (after `coverage-<mod>`) is the dynamic half of the reach gate: an entry point the gate holds the module to, and that its corpus never executed, records the gap in `phase0_gates.json` (`dynamic: entry points never executed by the corpus`; rows in `workspace/reports/harness_reach_dynamic.json`). A dynamic gap stops no fuzz, coverage or Eva target of the module, since those are what can close it. It holds the module's planned units out of WP instead: `ledger.py gate-reach` (run by `wp-replay` and by `wp_scheduler.py init`) blocks them with the reason `dynamic_reach_gap: <entry points>` and returns them to `planned` once the gap is gone (a unit blocked for another reason stays blocked). `reach-gate` keeps the gap while the harness is the one coverage measured. The static gate (`/framac-slice` Step 4b) is the stricter one on calls: the harness must call each entry point itself, so an entry point the corpus executes only inside another function passes here and is still a static gap. A reproducible crash counts as execution of an entry point only when it was found under the current harness (the same `harness_digest` and `dispatch_case_count` as the harness now has) and its replay shows the entry point ran: a stack frame of it, a sanitizer failure or a postcondition in it, or a failure in its callees (and none of its case's init helpers') for the single dispatch case its first byte selects. A crash at an unknown location, or an E-ACSL failure under the entry point's name with no stack, counts for nothing. After a harness change, fuzz again. `crash_notes` in the reach report say why a crash did not count. Repair the harness (its digest changes), or exempt the entry point with `harness_reach.py exempt --module <mod> --function <fn> --reason <why>`, naming it by its DAG key (`file#name` when the name collides) or by its plain name when no other DAG function has it; the static and the dynamic gate match it the same way. `--function` can be repeated. `exempt` re-checks the gate itself and prints the result under `gate` (`rechecked`, and `still_failing` with the gaps left): an exemption clears only the entry points it names. After a harness repair, re-run the reach gate (`pipeline_make.py run reach-gate`) before the module's targets: they refuse a harness whose digest changed since the gate ran. The gate's failure message names both commands. A whole-run `reach-gate` exits 1 while another module still has a gap, but it records this module's row.

Gaps are only trusted on a complete replay. A `partial` report with `inputs.not_replayed > 0` is treated as unmeasured (`partial coverage: N of M inputs not replayed`): the printed row keeps `executions` and lists its gaps as `gaps_lower_bound`, but the gate is not reopened. When every input was replayed and only some failed, the measurement counts and the row records `failed_inputs`. A module that moves from a failed dynamic check to passing or unmeasured has the stale `dynamic:` failure lifted from its gate row.

A module whose coverage measured nothing (the statuses above, or no report) gets no row: it is listed with its reason under `unmeasured` in `harness_reach_dynamic.json`, and `reach-dynamic-<mod>` exits 2 without reopening the gate, so its fuzz and Eva go on. Read the reason. When every input crashes, the corpus can never grow (oscs-qlz: a misaligned store at `quicklz.c:161` on every input, the empty one included): the crash is the finding and goes to the Crash Verification Gate. There is nothing to repair in the harness, and the module's reach stays unmeasured; do not exempt its entry points for it.

A function a public header defines (`static inline`) has no global symbol, so it is not an entry point and neither reach gate counts it: a passing gate does not mean the header API ran (QCBOR run-6: 171 of 171 entry points executed, 383 of 440 public header functions never). When the Phase 0 model lists the unit's `header_api`, the dynamic row reports them, deciding nothing: `header_api_functions` (those of the unit, or of the sub-module's scope) and `header_api_unexecuted` (`count`, and the first 20 names, sorted: those with no execution or not in the coverage report). A row measured by its crashes keeps only `header_api_functions`. The run report lists each module with unexecuted public header functions under "Public header functions the corpus never executed".

Exemptions are for entry points that cannot be driven from bytes, not for a corpus that did not get deep enough:
- **Valid reasons:** the function needs a live kernel socket or a real file descriptor; it reads a process-global the harness cannot set up safely; it is a callback only the platform calls.
- **Not reasons:** "30 s of fuzzing did not reach it"; "behind a parser check"; "reached only through `parse_x509_cert`". Those are reach gaps to work on, in this order: recorded seeds (`/framac-slice` Step 1e), the target's own corpus mapped to the function (`/framac-slice` Step 1f), a dictionary (`params set --fuzz-dict`), a larger budget (`--fuzz-budget`), then a dispatch case that calls the function directly with fixed-size slots. Exempt only what still cannot be driven, and say what you tried in the reason.
- **Not a repair:** a case that calls the function with constant arguments only to tick the gate. The gate then passes, but fuzzing exercises nothing.

Read `executions: 0` before tuning. The harness may simply not call that function, which a better dictionary or budget cannot fix: repair the harness instead. If the harness does call it, the corpus is stuck behind an input check, and `uncovered_lines` on the callers shows where. This report is reach only: it is not proof, the ledger does not read it, and a reached function is not a safe one.

Then ingest (parent only), after both fuzz and Eva have finished:

```text
python3 /opt/framac-pipeline/scripts/pipeline_make.py run ingest
```

`ingest` ingests only reports it has not seen before, matched by content digest. Fuzz reports (plus `workspace/reports/judge/<mod>.json` via `ledger.py ingest-judge` and `deep` `workspace/reports/eacsl-fuzz/<mod>.json` when present) go before Eva reports. Every expected module gets a report, or a `not_run` record. Then it runs `validate_artifacts.py run-dir .`.

Each statement site becomes one entry in `candidates.json`. A site is a source line of a function, keyed by the normalized text of the line and, among identical lines of one function, its occurrence, so a line that moves down with edits above it keeps its site. Several crash inputs with the same failing predicate collapse into one candidate, and so do the detections of one site from the sanitizers, E-ACSL and Eva. The candidate's `observations` lists every detection that landed on it (engine, origin, message, reproducer), and its `property` is the E-ACSL or Eva reading when a sanitizer saw the site first. `replay-candidates --cross-engine` replays each reproducer on the other engine, and `ledger.py link-related` records the candidates that one reproducer makes on both engines as `related`; the verifier then rejects the second as `duplicate`. A leak links no ledger unit (D5). The matching ledger units become `candidate` (including any `deferred` Tier 3 helper functions reached via cross-module calls), which excludes them from WP. A crash is a candidate until a verifier confirms that the fault is in target code and that the harness respected the entry function's contract.

With MetAcsl on for E-ACSL, `ingest-fuzz` files a violated property by these rules:

- **A violation** links the unit `file#function::<class>` of the property's class (the failure's `obligation_class`), which becomes `candidate`. Each property is its own candidate, even when several fail in one function.
- **A failed precondition** links the unit of its `caller`, where WP and Eva place the same obligation. The candidate's location stays the protected function. Without a caller in the report, it links nothing.
- **`harness_induced: true`** makes no candidate and touches no unit. It is listed in the command's output under `meta_harness_induced`.
- **An unplanned instance** (the report's `security_props.unplanned_instances`) is a candidate that links no unit.
- **A failed guard** (`meta_guard`) is a candidate of class `rte` at the function, never against the property's unit.
- **A campaign whose build lost the properties** (`dropped`, `error`, a toolchain `skipped`) gives the module's units of the MetAcsl classes `fuzz_meta_not_checked` evidence, and the command's output repeats the report's warnings under `security_props_warnings`.

To scaffold a schema-valid `crash_verifier` JSON record for any candidate in `candidates.json` (pre-populating `sha256`, `size_bytes`, `linked_units`, and `refingerprint_reason`), run:

```text
python3 /opt/framac-pipeline/scripts/ledger.py scaffold-verifier --fingerprint <fp> --decision confirmed --agent-id verifier-1 --out agents/verifier-1/scratch/result.json
```
