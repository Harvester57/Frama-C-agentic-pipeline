# MetAcsl: `-meta-fold` drops the location of the folded instances

Draft for the **MetAcsl** issue tracker (https://git.frama-c.com/pub/meta/-/issues, project id
869), not for `pub/frama-c`. **Not filed.** Issue 48 of this folder, drafted on 2026-11-20.

**Package:**
[issue text](./filing/48-metacsl-fold-annotation-location-issue.md),
[MR text](./filing/48-metacsl-fold-annotation-location-mr.md),
[patch](./patches/48-metacsl-fold-annotation-location.patch),
[reproducer](./repro/48-metacsl-fold-annotation-location.sh) with its
[C file](./repro/48-metacsl-fold-annotation-location.c).

## Summary

With `-meta-fold`, each instance of a property becomes an assertion that calls a generated global
predicate. That assertion has no source location: the report and WP show it as "generated by
Frama-C kernel", and E-ACSL records `file = "<unknown>"`, `line = 0`, so a failure prints
`<unknown>:0`. The same property unfolded keeps the line of its predicate. The location is also
lost without `-meta-fold`, when an instance is wrapped in the `\forall` of `-meta-quantify-range` or
in the implication from a callee behavior's `assumes`.

## Where the pipeline meets it

Measured on 2026-11-19 (`docs/plans/metacsl-exploitation-plan.md`, section "`-meta-fold` and
`-meta-quantify-range` in the E-ACSL build"): with `-meta-fold`, a meta failure in the E-ACSL build
is reported at `<unknown>:0`, and its `pred_txt` is the call (`meta_L4_auth_state_login(dst + i)`).
`failure_identity.py` maps a meta failure to its file through the meta file's line, so the
fingerprint loses its file part (`unknown#...`) and its hash changes. That is one of the reasons
the plan keeps both options off. A fix upstream removes the line problem; the plan's other
condition (map by property name and function through the sidecar) stands on its own.

`pred_txt` is not a separate defect: E-ACSL prints the predicate of the assertion, which for a
folded instance is the call. The property name (`name`) is the same in both modes.

## Evidence

Run on 2026-11-20 in `framac-analysis:latest` (Frama-C 34.0~beta, MetAcsl 0.12~beta), with
[`./repro/48-metacsl-fold-annotation-location.sh`](./repro/48-metacsl-fold-annotation-location.sh):

```
34.0~beta (Selenium)

report auth_unfolded: - Assertion 'meta' ("48-metacsl-fold-annotation-location.c", line 35)
e-acsl auth_folded:   <unknown>:0: Error: Assertion failed:
e-acsl auth_unfolded: 48-metacsl-fold-annotation-location.c:35: Error: Assertion failed:
RESULT: the folded instance has no location
```

The same output with MetAcsl `master` (`4f43801390`) built and installed in place of 0.12~beta
(see [Builds](#builds)). With the patch on that build:

```
34.0~beta (Selenium)
report auth_folded:   - Assertion 'meta' ("48-metacsl-fold-annotation-location.c", line 30)
report auth_unfolded: - Assertion 'meta' ("48-metacsl-fold-annotation-location.c", line 35)
e-acsl auth_folded:   48-metacsl-fold-annotation-location.c:30: Error: Assertion failed:
e-acsl auth_unfolded: 48-metacsl-fold-annotation-location.c:35: Error: Assertion failed:
RESULT: the folded instance has the location of its property
```

The patch also moves E-ACSL's warning "no assigns clause generated for function meta_auth_folded"
from `<generated by Frama-C kernel>` to `fold.c:30`.

Without `-meta-fold`, the report gives `("fold.c", line 30)` for `auth_folded` (run on the issue's
`fold.c`, which has the same lines), so line 30 is what an unfolded instance of that property gets.

`-print` does not show locations, so the printed code is the same before and after. MetAcsl's own
oracles record the bug: `tests/meta-wp/oracle_fold/typing.0.res.oracle` has
`Goal Assertion 'test,meta' (generated by Frama-C kernel):` where the default configuration's
oracle has `("typing.c", line 22)`.

before and after the patch):

| :-- | :-- | :-- | :-- |
| `\writing`, callee `assigns p[0 .. n-1]` | none | `range.c`, 18 | same |
| same | `-meta-quantify-range` | `<unknown>`, 0 | `range.c`, 18 |

only there; the other "before" cells come from the `master` build. Every "after" cell comes from
the patched `master` build.

## Cause

All in `meta_annotate.ml` of `master` `4f43801390`:

- `create_call` (lines 118 to 131) builds the call with `Logic_const.papp (li,labels,args)`.
  `papp` passes `?loc` to `Logic_const.pred`, whose default is `Kernel.gen_loc`.
- `context_visitor#create_instance` (lines 282 to 326) returns that call for every folded instance
  (line 319). The unfolded branch returns `ump.ump_property kf ~stmt assoc_list`, a predicate that
  keeps the location of the parsed property.
- `writing_visitor#external_assigns` (`post` and `post_fold`, lines 658 to 673) and
  `reading_visitor#passthrough_from` (lines 795 to 810) wrap the instance with
  `Logic_const.pimplies` and `Logic_const.pforall`, both without `~loc`.
- `\precond`, `\postcond`, `\weak_invariant` and `\conditional_invariant` go through
  `weak_inv_visitor#add_to_contract`, which uses `ump_property` directly and never folds; that is
  why the 2026-11-19 measurement saw them keep their location. `\calling`, `\writing`, `\reading`
  and `\strong_invariant` go through `instantiate` and can be folded.

## Patch

[`./patches/48-metacsl-fold-annotation-location.patch`](./patches/48-metacsl-fold-annotation-location.patch),
one commit on `pub/meta` `master` `4f43801390`, subject prefix `[fold]` as in the commits of the
`-meta-fold` series (`6e83cce7`, "[fold] avoid having qualifier in parameters of predicates"):

- `create_call` takes `~loc`; `create_instance` passes `inst.pred_loc`, the location of the instance
  the call stands for.
- `post` and `post_fold` in both visitors give `pimplies` and `pforall` the location of the
  predicate they wrap (`prop.pred_loc`). With that, `inst.pred_loc` is the property's location even
  when `post` applies.
- `tests/meta-wp/oracle_fold/typing.0.res.oracle`: the goal line now has `("typing.c", line 22)`.
  This oracle is the regression test; no new test file.

Checked: `git apply --check --cached` on a pristine clone of `4f43801390`, no CR in the patch.
Not run: `make lint`, the header check.

### Builds

- MetAcsl `master` declares `frama-c {>= "34.0~" & < "35.0~"}` but does not build on 34.0~beta:
  `meta_parse.ml` line 483 matches `PLpointer_comparable`, which the installed `Logic_ptree` does
  not have (most likely from the merge `4f43801390` itself, "pointer-comparable-const", a sync with
  frama-c!6051; the clone is shallow, so this was not checked with `git blame`). Every `master` build here removed that line first, in a throwaway container only.
- Before: the installed 0.12~beta, and `master` with that line removed. After: `master` with that
  line removed and the patch. Each build was `dune build @install && dune install` in a
  `docker run --rm` container of `framac-analysis:latest`.
- Suites: `meta`, `meta-wp` and `meta-deduce`, default and fold configurations, on `master` and on
  `master` with the patch. The two sets of result logs are identical except
  `meta-wp/result_fold/typing.0.res.log`, and the updated oracle has the same blob id as the patched
  log (`b17e019`). `meta-deduce` failed the same way in both: SWI-Prolog is not
  installed in the image (`env: ‘swipl’: No such file or directory`, after the CRLF line ends of the
  Windows checkout were stripped from `deduce/` in a rerun of that suite alone), so its deduction
  checks were not exercised. The image lacks a few files listed in frama-c's `dune-package` (doc and
  man pages); they were created empty in the container so that dune would run the tests.

## Not in this report

- **A folded predicate can capture a caller's variable.** With `assumes.c` (`set(&auth_ok, n)` in
  `caller(int n)`, callee behavior `assumes n > 0`), `-meta-fold -meta-no-simpl -print` gives the
  global predicate `meta_auth_assumes{Before}(int *_written) = n > 0 ⇒ \separated(_written,
  &auth_ok);`: `post` is applied when the predicate body is built, so the first instance's
  `assumes`, written over the caller's formal `n`, becomes part of a global predicate shared by
  every instance of the same type signature. Seen once, not analysed further, not filed.
