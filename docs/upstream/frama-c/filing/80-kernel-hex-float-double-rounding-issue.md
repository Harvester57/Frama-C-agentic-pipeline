# [Kernel] Hexadecimal floating-point literals with f/f32 suffix suffer double rounding through double precision

<!-- Everything below this line is the issue description. -->

### Summary

`Typed_float.parse_hexadecimal` (`src/lib/floating_point/typed_float.ml`) parses hexadecimal
floating-point constants by first converting the string to an OCaml 64-bit `float` (`double`) via
`float_of_string_opt` and then rounding that intermediate `double` to the target format (`Single` /
`Float32`). For literals with more than 53 bits of significand (for example
`0x1.0000010000000001p0f`, `0x1.0000000000000001p-150f`, or `0x1.fffffeffffffffffffp127f`), this
causes double rounding in violation of ISO C11 6.4.4.2p3 and IEC 60559, producing the wrong single-precision value in the AST and causing Eva/WP to evaluate valid checks as invalid.

### Steps to reproduce the issue

`hex_double_round.c`:

```c
void main(void) {
  float f_up = 0x1.0000010000000001p0f;
  float f_neg = -0x1.0000010000000001p0f;
  float f_sub = 0x1.0000000000000001p-150f;
  float f_tie_even = 0x1.000001p0f;
  float f_tie_odd = 0x1.000003p0f;
  /*@ check f_up == 0x1.000002p0f; */
  /*@ check f_neg == -0x1.000002p0f; */
  /*@ check f_sub == 0x1p-149f; */
  /*@ check f_tie_even == 0x1.000000p0f; */
  /*@ check f_tie_odd == 0x1.000004p0f; */
}
```

```sh
frama-c -eva hex_double_round.c
```

### Expected behaviour

In IEEE 754 single precision (round-to-nearest-even, single rounding, matching `gcc 14.2.0`):

- `0x1.0000010000000001p0f` is strictly greater than the midpoint `0x1.000001p0`, so it rounds up to
  `0x1.000002p0f` (`1.00000011921`).
- `-0x1.0000010000000001p0f` rounds to `-0x1.000002p0f`.
- `0x1.0000000000000001p-150f` is strictly greater than half the smallest single-precision subnormal
  (`2^-150`), so it rounds up to `0x1p-149f` (`1.40129846432e-45`).

All 5 `check` assertions should be proven valid (`Assertions 5 valid 0 unknown 0 invalid 5 total`).

### Additional information (optional)

**Cause.** In `src/lib/floating_point/typed_float.ml`, `parse_hexadecimal` (lines 424-437) parses
the literal string with `float_of_string_opt s` (rounding to IEEE 754 `binary64` first, which drops
bits beyond position 53) and then calls `represents ~float:... ~in_format:format` (rounding a second
time to `binary32`). For `0x1.0000010000000001p0f`, the trailing bit at `2^-64` is lost during the
`binary64` step, leaving the exact midpoint `0x1.000001p0`, which ties-to-even rounds down to `1.0f`
instead of up to `0x1.000002p0f`. The same issue affects subnormal single-precision constants
(`0x1.0000000000000001p-150f` -> `0.0f` instead of `0x1p-149f`) and the `FLT_MAX` overflow boundary
(`0x1.fffffeffffffffffffp127f` -> `+inf` instead of `0x1.fffffep127f`). In addition,
`is_hexadecimal` (line 421) only checked for an unsigned `"0x"`/`"0X"` prefix.

**Fix.** Parse hexadecimal floating-point literals directly with arbitrary-precision integers
(`Z.of_string_base 16`) and binary exponents (`p`/`P`), computing `lower`, `nearest`, and `upper`
directly in the target `format` with a single exact rounding (using `Z.log2`, `Z.trailing_zeros`, and
`Z.testbit` for round-to-nearest-even ties, subnormals, overflow, and underflow, and applying signs
via `apply_sign` just like decimal literals). A merge request with this fix and a regression test
(`tests/misc/hex_float_rounding.c`) is ready.

The analysis and fix were prepared with LLM assistance; I reviewed them and ran the reproducer and
tests described above.
