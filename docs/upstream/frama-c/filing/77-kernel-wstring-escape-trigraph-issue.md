# [Kernel] Wide-string printer emits invalid `\u` escapes, crashes above 2^32, and loses trigraph protection

<!-- Everything below this line is the issue description. -->

### Summary

`Escape.escape_wchar` and `Escape.escape_wstring` (`src/lib/utils/escape.ml`, lines 54-82) have
five defects when pretty-printing C wide string literals (`L"..."`):

1. Code points in `0o1000..0xFFFF` (such as `L"\x20AC"`) are printed as `\uXXXX`, which Frama-C's
   own C lexer rejects (`Unrecognized escape sequence: \u`), so `-print -ocode` output cannot be
   re-parsed by Frama-C.
2. UTF-16 surrogates (`0xD800..0xDFFF`, such as `L"\xD800"`) are printed as `\ud800`, which
   violates ISO C11 6.4.3p2 and is rejected by GCC and Clang (`not a valid universal character`).
3. Code points in `0x10000..0xFFFFFFFF` (such as `L"\x1F600"`, `L"\x1F600""A"`, `L"\x110000"`) are
   printed with lowercase `\u` followed by 5 to 8 hex digits instead of `\UXXXXXXXX`. C11 6.4.3
   defines `\u` as taking exactly 4 hex digits (and forbids values above `0x10FFFF`). GCC and
   Clang silently consume 4 digits as the character and treat the remaining digits as literal
   characters (often without any warning), silently corrupting the string under both `-print -ocode`
   and `e-acsl-gcc`.
4. Code points `>= 2^32` (such as `L"\x100000000"`, which Frama-C's C front end accepts and GCC
   compiles with only a warning) crash Frama-C during printing with an uncaught
   `Invalid_argument("Cprint.escape_string_intlist")` (exit 125).
5. `escape_wchar` calls `escape_char`, which allocates a fresh `maybe_trigraph = ref false` per
   character instead of threading trigraph state across the wide string as `escape_string` does.
   Consequently, `L"a?\?!b"` is printed as `L"a??!b"`, which GCC/Clang under `-std=c99` (including
   `e-acsl-gcc`) silently turns into `L"a|b"`.

### Steps to reproduce the issue

#### 1. Silent miscompilation of `> 0xFFFF`, `> 0x10FFFF`, and trigraphs

`wstr.c`:

```c
#include <stddef.h>
#include <stdio.h>
wchar_t a[] = L"\x20AC";
wchar_t b[] = L"\x1F600";
wchar_t c[] = L"\x1F600" "A";
wchar_t e[] = L"\x110000";
wchar_t t[] = L"a?\?!b";
int main(void) {
  printf("a=%x b=%x/%zu c=%x,%x/%zu e=%x t=%zu:%x,%x,%x,%x,%x\n",
         (unsigned)a[0], (unsigned)b[0], sizeof(b),
         (unsigned)c[0], (unsigned)c[1], sizeof(c),
         (unsigned)e[0], sizeof(t) / sizeof(t[0]),
         (unsigned)t[0], (unsigned)t[1], (unsigned)t[2],
         (unsigned)t[3], (unsigned)t[4]);
  return 0;
}
```

```sh
gcc -std=c99 wstr.c -o wstr_gcc && ./wstr_gcc
frama-c -machdep gcc_x86_64 -no-frama-c-stdlib wstr.c -print -ocode wstr_out.c
gcc -std=c99 wstr_out.c -o wstr_out && ./wstr_out
e-acsl-gcc -c wstr.c -o wstr.gen.c -O wstr_e && ./wstr_e.e-acsl
```

#### 2. Surrogate rejected by GCC and `\u` rejected by Frama-C on re-parse

`surrogate.c`:

```c
#include <stddef.h>
wchar_t a[] = L"\x20AC";
wchar_t d[] = L"\xD800";
```

```sh
frama-c surrogate.c -print -ocode surrogate_out.c
frama-c surrogate_out.c
gcc -c surrogate_out.c
```

#### 3. Crash on code points `>= 2^32`

`huge.c`:

```c
#include <stddef.h>
wchar_t huge[] = L"\x100000000";
```

```sh
OCAMLRUNPARAM=b frama-c -debug 1 huge.c -print
```

Host headers are used with `e-acsl-gcc` / `-no-frama-c-stdlib` on Debian 13 (trixie; glibc 2.41,
gcc 14.2.0, clang 19.1.7).

### Expected behaviour

1. `wstr_out` and `wstr_e.e-acsl` print the exact same values as `wstr_gcc`:
   `a=20ac b=1f600/8 c=1f600,41/12 e=110000 t=6:61,3f,3f,21,62`.
2. `surrogate_out.c` re-parses cleanly in Frama-C and compiles cleanly with `gcc -c`.
3. `frama-c huge.c -print` exits 0 without raising an internal exception.

### Additional information (optional)

**Cause.** In `src/lib/utils/escape.ml` (lines 54-82):

- Lines 66-69 print both `fits_universal_4` (`< 0x10000`) and `fits_universal_8` (`< 0x100000000`)
  using the identical format `"\\u%04Lx"`, where `\U%08Lx` was intended for the second branch;
  even `\U` would still fail C11 6.4.3p2 for surrogates (`0xD800..0xDFFF`) and values above
  `0x10FFFF`, and Frama-C's C lexer does not parse `\u`/`\U`.
- Line 71 raises `invalid_arg "Cprint.escape_string_intlist"` for any code point `>= 2^32`, and
  `limit` (line 56) converts `Int64.sub` to `float`, mishandling negative `int64`.
- Line 63 calls `escape_char`, creating a fresh `maybe_trigraph` ref on every wide character, so
  consecutive `?` characters are never escaped as `\?`.

**Fix.** In `src/lib/utils/escape.ml`:

- Thread `maybe_trigraph` across `escape_wstring` via `escape_wchar_internal` (matching
  `escape_string`).
- For code points `>= 0o1000` (or negative `int64`), emit hexadecimal escapes (`\x%Lx`), which C11
  6.4.4.4 allows for arbitrary `wchar_t` values (including surrogates and `> 0x10FFFF`) and which
  both GCC/Clang and Frama-C's C lexer accept.
- Whenever a `\x` escape is immediately followed by a hexadecimal digit (`0-9`, `a-f`, `A-F`),
  split the adjacent wide string literal (`" L"`) so the following digit is not absorbed into the
  `\x` escape.

A merge request with this fix, the single updated oracle line in
`tests/spec/oracle/string.0.res.oracle`, and regression test
`tests/pretty_printing/wstring_escape.c` is ready.

The analysis and fix were prepared with LLM assistance; I reviewed them and ran the reproducer and
tests described above.
