# [Kernel] Narrow character constants with out-of-range octal/hex escapes ('\777', '\x1ff') are silently accepted

<!-- Everything below this line is the issue description. -->

### Summary

Frama-C rejects out-of-range octal and hexadecimal escape sequences in narrow string literals (such
as `"\777"` or `"\x1ff"`) with `User Error: integral literal 0x1ff too big`, but silently accepts
the exact same out-of-range escapes in narrow character constants (`'\777'`, `'\x1ff'`, `'a\x100'`),
turning them into `511` (`511UL`) or `25088` without any diagnostic. This violates ISO C11
6.4.4.4p9, which constrains each octal or hexadecimal escape sequence in an ordinary character
constant to the range of `unsigned char`.

### Steps to reproduce the issue

`char_oob.c`:

```c
int bad_oct = '\777';
int bad_hex = '\x1ff';
int bad_multi = 'a\x100';
```

```sh
frama-c -no-autoload-plugins -print char_oob.c
```

### Expected behaviour

Each out-of-range escape in a narrow character constant (`'\777'`, `'\x1ff'`, `'a\x100'`) should be
rejected with `User Error: integral literal 0x... too big` (exit 1), matching Frama-C's existing
rejection of `"\777"` and `"\x1ff"` in narrow string literals, while valid narrow escapes
(`'\377'`, `'\xff'`, `'ab'`) and wide character constants (`L'\777'`, `L'\x1ff'`) remain accepted.

### Actual behaviour

Frama-C silently accepts all three declarations with zero warnings or errors (exit 0):

```text
[kernel] Parsing char_oob.c (with preprocessing)
/* Generated by Frama-C */
int bad_oct = 511;
int bad_hex = 511;
int bad_multi = 25088;
```

The same silent acceptance occurs on both `35.0~~dev` (`189053d4a2`) and `34.0~beta` (Selenium).
By contrast, `gcc -Wall` warns (`octal/hex escape sequence out of range`) and truncates to `unsigned
char` (`-1` on signed `char`).

### Contextual information

- Frama-C installation mode: from source (`master`) and opam (Docker image based on `framac/frama-c:dev`)
- Frama-C version: 35.0~~dev (Bromine), `master` at `189053d4a2`; also `34.0~beta` (Selenium)
- Plug-in used: kernel (C parser, `cparser.mly`)
- OS name: Debian GNU/Linux
- OS version: 13 (trixie; glibc 2.41, gcc 14.2.0)

### Additional information (optional)

**Cause.** In `src/kernel/internals/parsing/cparser.mly`, `string_constant` (lines 751-754) calls
`intlist_to_string`, which validates every element of the lexed `int64 list` through `int64_to_char`
(lines 185-190), rejecting values outside `0..255` with `Errorloc.parse_error ~loc "integral literal
0x%Lx too big" value`. However, the `CST_CHAR` production in `constant` (line 742) passes `fst $1`
directly to `CONST_CHAR` without checking element bounds, so `Cil.interpret_character_constant`
receives `[511L]` and promotes it to `511UL` (`CInt64 (511, IULong, None)`).

**Fix.** Validate every element of `CST_CHAR` in `cparser.mly` via `int64_to_char ~loc` before
constructing `CONST_CHAR (fst $1), loc`, leaving `CST_WCHAR` untouched. A merge request with this
fix and a regression test (`tests/syntax/char_escape_range.c`) is ready.

The analysis and fix were prepared with LLM assistance; I reviewed them and ran the reproducer and
tests described above.
