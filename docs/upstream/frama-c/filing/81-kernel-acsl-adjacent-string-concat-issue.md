# [Kernel] Adjacent string literals in ACSL annotations are concatenated as raw text before unescaping

<!-- Everything below this line is the issue description. -->

### Summary

In `src/kernel/internals/parsing/logic_parser.mly`, the `string` production concatenates adjacent
ACSL string literals as raw text (`prefix ^ suffix`) before escape sequences are decoded in
`Logic_typing`. Consequently, a trailing hexadecimal or short octal escape sequence in the first
literal absorbs leading digits from the next literal: `"\x4" "1"` becomes `"\x41"` (`"A"`) instead
of `"\0041"`, and `"\01" "2"` becomes `"\012"` (`"\n"`) instead of `"\0012"`, violating ISO C11
5.1.1.2p1 phase 6 and disagreeing with Frama-C's C parser on identical literals.

### Steps to reproduce the issue

`acsl_concat.c`:

```c
void main(void) {
  const char *a = "\x4" "1";
  const char *b = "\01" "2";
  /*@ check c1: ("\x4" "1")[0] == 4; */
  /*@ check c2: ("\01" "2")[0] == 1; */
  /*@ check c3: ("\\" "n")[0] == '\\'; */
  /*@ check c4: (L"\x4" "1")[0] == 4; */
  /*@ check c5: (L"\01" "2")[0] == 1; */
}
```

```sh
frama-c -no-autoload-plugins -print acsl_concat.c
```

### Expected behaviour

Adjacent ACSL string literals should decode escapes within each token before concatenation (matching
the C side):

- `"\x4" "1"` should represent the 2-byte string `"\0041"` (`0x04`, `'1'`), not `"A"` (`0x41`).
- `"\01" "2"` should represent the 2-byte string `"\0012"` (`0x01`, `'2'`), not `"\n"` (`0x0A`).
- `L"\x4" "1"` and `L"\01" "2"` should similarly preserve the escape boundary (`0x04` followed by
  `'1'`, and `0x01` followed by `'2'`).

### Actual behaviour

The C parser produces `"\0041"` and `"\0012"`, while the ACSL annotations collapse them to `"A"`
and `"\n"`:

```text
[kernel] Parsing acsl_concat.c (with preprocessing)
/* Generated by Frama-C */
void main(void)
{
  char const *a = "\0041";
  char const *b = "\0012";
  /*@ check c1: (\let tmp = "A"; tmp[0]) ≡ 4; */ ;
  /*@ check c2: (\let tmp = "\n"; tmp[0]) ≡ 1; */ ;
  /*@ check c3: (\let tmp = "\\n"; tmp[0]) ≡ '\\'; */ ;
  /*@ check c4: (\let tmp = L"A" ; tmp[0]) ≡ 4; */ ;
  /*@ check c5: (\let tmp = L"\\n" ; tmp[0]) ≡ 1; */ ;
  return;
}
```

The same output is produced on both `35.0~~dev` (`189053d4a2`) and `34.0~beta` (Selenium).

### Additional information (optional)

**Cause.** In `src/kernel/internals/parsing/logic_parser.mly` (lines 677-684):

```ocaml
string:
| STRING_LITERAL { $1 }
| string STRING_LITERAL
    { let (is_wide,prefix) = $1 in
      let (is_wide2,suffix) = $2 in
      (is_wide || is_wide2, prefix ^ suffix)
    }
;
```

Because `Logic_lexer` returns raw (un-unescaped) string contents in `STRING_LITERAL` and
`Logic_typing` unescapes the combined string only later, concatenating `prefix ^ suffix` merges any
trailing hexadecimal (`\x...`) or 1-/2-digit octal (`\01`, `\7`) escape in `prefix` with leading
digits in `suffix`.

**Fix.** Add `concat_string_literal` in `logic_parser.mly` so that when `prefix` ends with a
trailing hex escape (`\xH+`, value `<= 0xff`) followed by a hex digit in `suffix`, or a trailing
1-/2-digit octal escape followed by a digit in `suffix`, the trailing escape is normalized to a
3-digit octal escape (`\NNN`) before concatenation. A merge request with this fix and a regression
test (`tests/spec/string_concat_escape.c`) is ready.

The analysis and fix were prepared with LLM assistance; I reviewed them and ran the reproducer and
tests described above.
