# [Kernel] Custom YAML machdep with non-positive type size or alignment crashes Frama-C with Z.shift_left Invalid_argument

<!-- Everything below this line is the issue description. -->

### Summary

Passing a custom YAML machdep file whose type size is zero or negative (such as `sizeof_int: 0` or
`sizeof_long: -1`) crashes Frama-C during machdep header generation with an uncaught
`Invalid_argument("Z.shift_left: count argument must be positive")` exception instead of reporting a
user error. Non-positive alignments for concrete scalar/pointer types (such as `alignof_ptr: 0`) are
likewise accepted without validation.

### Steps to reproduce the issue

`empty.c`:

```c
int main(void) {
  return 0;
}
```

```sh
sed 's/^sizeof_int: .*/sizeof_int: 0/' "$(frama-c -print-share-path)/machdeps/machdep_x86_64.yaml" > zero_int.yaml
frama-c -no-autoload-plugins -machdep zero_int.yaml empty.c
```

### Expected behaviour

Frama-C should reject any YAML machdep whose concrete scalar/pointer `sizeof_*` or `alignof_*`
field is `<= 0` with a clean user error (`[kernel] User Error: Error during machdep parsing: ...`,
exit code 1), while continuing to allow negative/zero sentinel values on optional/unsupported fields
(`sizeof_void`, `sizeof_fun`, `alignof_void`, `alignof_fun`, `alignof_aligned`,
`alignof_max_align_t`, `max_extended_alignment`, `gcc_alignof_*`).

### Actual behaviour

Frama-C crashes with exit code 125:

```text
[kernel] Unexpected error (Invalid_argument("Z.shift_left: count argument must be positive")).
  Please report as 'crash' at https://git.frama-c.com/pub/frama-c/issues
  Your Frama-C version is 35.0~~dev (Bromine).
```

The same crash occurs on `34.0~beta` (Selenium). Setting `alignof_ptr: 0` is silently accepted
(exit 0).

### Contextual information

- Frama-C installation mode: from source (`master`) and opam (Docker image based on `framac/frama-c:dev`)
- Frama-C version: 35.0~~dev (Bromine), `master` at `189053d4a2`; also `34.0~beta` (Selenium)
- Plug-in used: kernel (`Machdep` YAML parser / `File.get_machdep`)
- OS name: Debian GNU/Linux
- OS version: 13 (trixie; glibc 2.41, gcc 14.2.0)

### Additional information (optional)

**Cause.** `Machdep.mach_of_yaml` (`src/kernel/internals/runtime/machdep.ml`, derived by
`[@@deriving yaml]` at line 102) and `File.get_machdep` (`src/kernel/services/ast_queries/file.ml`,
lines 303-318) accept any integer value for `sizeof_*` and `alignof_*`. Later,
`Machdep.gen_std_min_max` (line 538) passes `8 * mach.sizeof_int` to `Machdep.max_val` (line 451),
which computes `to_shift = bitsize - 1 = -1` and calls `Z.shift_left Z.one (-1)`, crashing with
`Invalid_argument`.

**Fix.** Validate in `Machdep.mach_of_yaml` that the 16 concrete scalar/pointer size and alignment
fields (`sizeof_short`, `sizeof_int`, `sizeof_long`, `sizeof_longlong`, `sizeof_ptr`,
`sizeof_float`, `sizeof_double`, `sizeof_longdouble`, and the corresponding 8 `alignof_*` fields)
are strictly positive (`> 0`), returning `Error (`Msg ...)` so `File.get_machdep` reports a clean
user error. Optional/sentinel fields (`sizeof_void`, `sizeof_fun`, `alignof_void`, `alignof_fun`,
`alignof_aligned`, `alignof_max_align_t`, `max_extended_alignment`, `gcc_alignof_*`) remain
unrestricted (for example `machdep_msvc_x86_64.yaml` uses `sizeof_void: 0` and `-1` sentinels). A
merge request with this fix and Cram regression tests in `tests/misc/machdep.t/run.t` is ready.

The analysis and fix were prepared with LLM assistance; I reviewed them and ran the reproducer and
tests described above.
