# [Kernel] ACSL lexer splits hexadecimal escapes into byte pairs, crashes with `Char.chr` on octal escapes above `\377` (including valid `L'\777'`), and does not truncate `L'...'` to `wchar_t`

<!-- Everything below this line is the issue description. -->

### Summary

In ACSL annotations, character constants, wide character constants, and narrow string literals
share `Logic_lexer.chr`, which decodes escapes into a byte `Buffer`. This causes three related
defects:

1. **Hexadecimal escapes are split into pairs of digits:** `'\x041'` is decoded as two bytes
   `'\x04'` and `'\x01'` (value `1025` instead of `'A' = 65`), `L'\x20AC'` is decoded as two wide
   units `0x20` and `0xAC` (value `137438953644` instead of `0x20AC = 8364`), and `"\x041"`
   becomes a two-byte string `"\004\001"` instead of `"A"`.
2. **Octal escapes above `\377` crash with `Invalid_argument("Char.chr")`:** valid ISO C wide
   character constants such as `L'\777'` (value `511`, accepted by GCC and Frama-C's C front end)
   and out-of-range narrow literals such as `'\777'` abort with
   `Failure: Unknown error (Invalid_argument("Char.chr"))` (exit 4), while `"\777"` crashes with
   `Unexpected error (Invalid_argument("Char.chr"))` (exit 125).
3. **Wide character constants are not truncated to `wchar_t`:** `Logic_typing.parseInt` folds
   multiple units with `Cil.reduce_multichar` without truncating to `Machine.wchar_kind ()` (unlike
   `cabs2cil.ml:5749-5751`), so `L'ab'` evaluates to `416611827810` (`0x6100000062`) in ACSL where
   C gives `98`.

### Steps to reproduce the issue

`acsl_hex_oct.c`:

```c
#include <stddef.h>
#include <string.h>

int main(void) {
  char c = '\x041';
  wchar_t w = L'\x20AC';
  wchar_t w2 = L'ab';
  //@ check c_hex: '\x041' == 'A' && c == '\x041';
  //@ check w_hex: L'\x20AC' == 0x20AC && w == L'\x20AC';
  //@ check w_multi: w2 == L'ab';
  //@ check s_hex: strlen("\x041") == 1;
  return 0;
}
```

```sh
frama-c -print acsl_hex_oct.c
frama-c -eva acsl_hex_oct.c
```

For the `Char.chr` crashes:

`acsl_oct_wchar.c`:

```c
#include <stddef.h>
int main(void) {
  wchar_t w = L'\777';
  //@ check o1: w == L'\777';
  return 0;
}
```

`acsl_oct_str.c`:

```c
#include <string.h>
int main(void) {
  //@ check o2: strlen("\777") == 1;
  return 0;
}
```

```sh
frama-c -debug 1 acsl_oct_wchar.c

```

### Expected behaviour

According to the ACSL manual, character and string literals are adopted from C without
modification (ISO C11 6.4.4.4, 6.4.5):

- On `acsl_hex_oct.c`: `'\x041'` equals `'A'` (`65`), `L'\x20AC'` equals `0x20AC` (`8364`), `L'ab'`
  equals `w2` (`98`), and `strlen("\x041") == 1`; all 4 assertions are valid in Eva.
- On `acsl_oct_wchar.c`: `L'\777'` is valid C (value `511`); Frama-C parses it cleanly and `o1` is
  valid.
- On `acsl_oct_str.c` (and narrow `'\777'` / `"\x1ff"`): out-of-range narrow escapes produce a
  clean user error (exit 1) instead of an internal `Invalid_argument("Char.chr")` crash.

### Additional information (optional)

**Cause.**

1. `src/kernel/internals/parsing/logic_lexer.mll:525-552` (`chr`) splits `hex_escape` into 2-digit
   bytes via `add_one_char` and passes octal values up to `0o777 = 511` directly to `Char.chr`.
2. `logic_lexer.mll:440-446` calls `chr` at lex time on both `'...'` and `L'...'`, forcing wide
   character escapes through an 8-bit `Buffer`.
3. `src/kernel/services/ast_queries/logic_typing.ml:1155-1167` (`parseInt`) explodes the byte
   string and passes it to `Cil.reduce_multichar (Machine.wchar_type ())` without truncating to
   `Machine.wchar_kind ()` (unlike `src/kernel/internals/typing/cabs2cil.ml:5749-5751`).

**Fix.**

- Keep the raw char/wchar literal in `INT_CONSTANT` at `logic_lexer.mll:440-446`.
- Add `Logic_lexer.chr_codes : Lexing.lexbuf -> int64 list` decoding each escape sequence into a
  single code unit (like `clexer.mll`), and use it in `Logic_typing.parseInt` (truncating `L'...'`
  with `Cil.truncateInteger64 (Machine.wchar_kind ())` and reporting clean out-of-range user errors
  for narrow `'...'` values `> 255`).
- In `Logic_lexer.chr` (used for narrow strings), decode the full `hex_escape` / `oct_escape`
  value, check `<= 255` (raising `lex_error` instead of `Invalid_argument("Char.chr")`), and catch
  `Logic_lexer.Error` in `logic_typing.ml` to emit a clean `C.error` annotation error.

A merge request with this fix and regression tests (`tests/spec/char_hex_oct_escapes.c` and
`tests/spec/char_hex_oct_escapes_err.c`) is ready.

The analysis and fix were prepared with LLM assistance; I reviewed them and ran the reproducer and
tests described above.
