# [E-ACSL] Real constants that are not exactly a double: Frama-C stops on an unexpected error with an exponent (`1e-9`), and a `long double` one (`0.1L`) is 0 at run time

<!-- Everything below this line is the issue description. -->

### Summary

When a real constant of an annotation is exactly a `double`, E-ACSL takes its value from the kernel. Otherwise it gives the text of the constant to GMP as a fraction, and the conversion (`Gmp.Q.normalize_str`) only knows plain decimal expansions such as `0.1`. Two results follow:

1. **With an exponent or in hexadecimal notation** (`1e-9`, `1.5e-3`, `0x1.00000000000000001p0`): Frama-C stops with `Unexpected error (E_ACSL__Gmp.Q.Not_a_decimal("1e-9"))`. A tolerance such as `x - y <= 1e-9` is enough.
2. **With a suffix, that is for a `long double` constant** (`0.1L`): no message, and the constant is 0 at run time. `0.1L > 0.05` (true) fails, and `0.1L == 0` (false) holds.

Constants with an exponent that are exactly a `double` (`1e5`, `25e-2`) are not concerned, which is probably why this went unnoticed.

### Steps to reproduce the issue

`exp.c`:

```c
int main(void) {
  double x = 0.5;
  /*@ assert x - 0.5 <= 1e-9; */
  return 0;
}
```

`ld.c`:

```c
int main(void) {
  /*@ assert 0.1L == 0; */
  return 0;
}
```

```
$ frama-c -e-acsl exp.c -then-last -print
$ e-acsl-gcc -c ld.c -O ld && ./ld.e-acsl
```

### Expected behaviour

`1e-9` is the rational 1/1000000000: the assertion of `exp.c` should be translated, and hold at run time. For `ld.c`, either the assertion fails (0.1L is not 0), or E-ACSL says that it does not support the constant and ignores the annotation, as it does for other unsupported constructs.

### Actual behaviour

`exp.c`:

```
[kernel] Parsing exp.c (with preprocessing)
[e-acsl] beginning translation.
[kernel] Parsing FRAMAC_SHARE/e-acsl/e_acsl.h (with preprocessing)
[kernel:backtrace]
  Current location was: <generated by Frama-C kernel>
[...]
[kernel] Unexpected error (E_ACSL__Gmp.Q.Not_a_decimal("1e-9")).
  Please report as 'crash' at https://git.frama-c.com/pub/frama-c/issues
  Your Frama-C version is 35.0~~dev (Bromine).
```

`ld.c`: the program is built without any warning and runs to the end (exit code 0), although the assertion is false. The generated code is:

```c
    __gmpq_set_str(__gen_e_acsl_,"0.1L",10);
    __gmpq_set_str(__gen_e_acsl__2,"0",10);
```

`__gmpq_set_str` rejects `"0.1L"` (its result is not checked) and the rational stays 0. With `/*@ assert 0.1L > 0.05; */` instead, the program aborts:

```
ld2.c: In function 'main'
ld2.c:2: Error: Assertion failed:
	The failing predicate is:
	0.1L > 0.05.
```

### Contextual information

- Frama-C installation mode: from source (`master`) and opam (Docker image based on `framac/frama-c:dev`)
- Frama-C version: 35.0~~dev (Bromine), `master` at b80fcac74f; also 34.0~beta (Selenium), same results
- Plug-in used: E-ACSL
- OS name: Debian GNU/Linux
- OS version: 13 (trixie)

### Additional information (optional)

Cause, on `b80fcac74f`, `plugins/e-acsl/src/code_generator/gmp.ml`, module `Q`:

- `decimal_to_fractional` (lines 258-307) reads a sign, digits and one dot. On any other character it raises `Not_a_decimal`, except on a suffix letter, where it returns the text unchanged.
- `normalize_str` (lines 312-316) calls it under `with Invalid_argument _ -> Error.not_yet "number not written in decimal expansion"`. That handler has caught nothing since 11b9381ab0 (2019), which changed the two `raise (Invalid_argument str)` into `raise (Not_a_decimal str)` and left the handler as it was. So the intended "not yet supported" message became an unexpected error.
- `tests/arith/rationals.c` still lists `/*@ assert 3 != 1e5; */` and a `long double` case under "Not yet", commented out.

Fix: convert a constant with an exponent or in hexadecimal notation with Zarith's `Q.of_string`, which reads both exactly, and report a constant that still has its suffix as not yet supported, since its value depends on the `long double` format of the target. A merge request follows.

Not covered: a unary minus on a rational (`-1e-2`) is still reported as not yet supported (`reals: Neg | BNot`), which is a separate, clean limitation.

The analysis and fix were prepared with LLM assistance (Claude Code); I reviewed them and ran the reproducer and tests described above.
