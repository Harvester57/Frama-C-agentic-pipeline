# [Kernel] ACSL lexer silently keeps unknown escape sequences and \e/\E as two raw characters

<!-- Everything below this line is the issue description. -->

### Summary

In `src/kernel/internals/parsing/logic_lexer.mll`, the `chr` rule omits the GCC `\e`/`\E` escape
sequence supported by Frama-C's C lexer (`clexer.mll:277`) and falls through to a catch-all
`| _ { Buffer.add_string buffer (lexeme lexbuf); chr buffer lexbuf }` (line 570) on any unrecognized
escape sequence. As a result, `'\e'` in ACSL silently evaluates to the two-character integer `23653`
(`'\\' * 256 + 'e'`) instead of `27` (`'\033'`), disagreeing with C, and invalid escapes such as
`'\z'` or `"\z"` are silently accepted (`'\z'` becomes `23674`) instead of reporting a lexical error.

### Steps to reproduce the issue

`acsl_esc.c`:

```c
void main(void) {
  int c_e = '\e';
  int c_E = '\E';
  /*@ check c_e == '\e'; */
  /*@ check c_E == '\E'; */
  /*@ check '\e' == 27 && '\E' == 27; */
}
```

```sh
frama-c -eva acsl_esc.c
```

For an unknown escape (`acsl_unknown.c`):

```c
void main(void) {
  /*@ check '\z' == 0; */
}
```

```sh
frama-c -no-autoload-plugins -print acsl_unknown.c
```

### Expected behaviour

In `acsl_esc.c`, `'\e'` and `'\E'` in ACSL should decode to `'\033'` (`27`), matching C (`clexer.mll`),
so Eva proves all 3 checks valid (`Assertions 3 valid 0 unknown 0 invalid 3 total`).

In `acsl_unknown.c` (and similarly for `"\z"`), the ACSL lexer should reject the unknown escape
sequence with `[kernel:annot-error] ... lexical error, unrecognized escape sequence: \z` (and abort
with exit 1 under `-kernel-warn-key annot-error=abort`).

### Additional information (optional)

**Cause.** In `src/kernel/internals/parsing/logic_lexer.mll`:

1. `let escape` (lines 386-388) and `chr` (lines 553-568) omit `'e'` and `'E'`, whereas
   `src/kernel/internals/parsing/clexer.mll` (line 277) maps `'e' | 'E'` to `'\027'`.
2. In `chr`, any unrecognized `\c` sequence fails to match `hex_escape`, `oct_escape`, and `escape`,
   so the catch-all `| _ { Buffer.add_string buffer (lexeme lexbuf); chr buffer lexbuf }` (line 570)
   silently copies the literal `'\\'` and then `c` into the buffer instead of calling `lex_error`.
3. Narrow `STRING_LITERAL` tokens (line 460) defer unescaping to `Logic_typing.unescape`, where an
   uncaught `Logic_lexer.Error` would not be handled by `parse_from_position`.

**Fix.** In `src/kernel/internals/parsing/logic_lexer.mll`:

- Add `'e' | 'E'` to `escape` and map `'e' | 'E' -> '\027'` in `chr`.
- Add `| '\\' _ { lex_error lexbuf ("unrecognized escape sequence: " ^ lexeme lexbuf) }` before
  `| eof` / `| _` in `chr`.
- Validate narrow `STRING_LITERAL` contents through `chr` during lexing so unknown escapes in ACSL
  strings are caught cleanly by `parse_from_position` (`annot-error`) rather than escaping
  `Logic_typing.unescape`.

A merge request with this fix and a regression test (`tests/spec/acsl_escape_char.c`) is ready.

The analysis and fix were prepared with LLM assistance; I reviewed them and ran the reproducer and
tests described above.
