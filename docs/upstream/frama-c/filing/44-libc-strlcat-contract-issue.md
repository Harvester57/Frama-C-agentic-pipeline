# [Libc] `strlcat`: the result is stated against the destination after the call, and `assigns` covers a byte past `n`

<!-- Everything below this line is the issue description. -->

### Summary

Two clauses of the contract of `strlcat` in `share/libc/string.h` are wrong:

- `ensures bounded_result: \result == strlen(dest) + strlen(src);` reads the length of `dest`
  after the call. `strlcat` returns the length of the string it tried to create: the length of
  `dest` before the call (or `n`, when `dest` has no NUL within its first `n` bytes) plus the
  length of `src`. Eva then computes a wrong result, and WP proves a postcondition that the
  compiled program violates.
- `assigns dest[strlen(dest)..n]` includes `dest[n]`, one byte past the `n` bytes the function may
  write, and every byte up to it whatever the length of `src`. Eva considers the object that
  follows the buffer modified, and WP cannot prove a caller that only owns `n` bytes.

### Steps to reproduce the issue

`cat.c`:

```c
#include <string.h>

struct s {
  char d[4];
  char next;
};

int main(void)
{
  char f[8] = "abcdef";
  size_t rf = strlcat(f, "x", 3); /* no NUL within 3 bytes: returns 3 + 1 */
  //@ check no_nul_within_n: rf == 4;

  char d[8] = "ab";
  size_t r = strlcat(d, "cd", sizeof d); /* "abcd": returns 4 */
  //@ check appended: r == 4;

  struct s v = {"a", 'Z'};
  strlcat(v.d, "b", sizeof v.d); /* writes v.d[1] and v.d[2] */
  //@ check next_kept: v.next == 'Z';
  return 0;
}
```

`append.c`:

```c
#include <string.h>

/*@ requires valid_string(d) && \valid(d + (0 .. 15)) && valid_read_string(s);
    requires strlen(d) + strlen(s) < 16;
    requires \separated(d + (0 .. 16), s + (0 .. strlen(s)));
    assigns d[0 .. 16];
    ensures \result == strlen(d) + strlen(s);
*/
size_t append(char *d, const char *s)
{
  return strlcat(d, s, 16);
}
```

```
$ frama-c cat.c -eva
$ frama-c append.c -wp
```

### Expected behaviour

- `cat.c`: the three checks are valid. Compiled with gcc and glibc 2.41, the program has
  `rf == 4`, `r == 4` and `v.next == 'Z'`.
- `append.c`: the postcondition is not proved. With `d` holding `"ab"` and `s` pointing to `"cd"`,
  the compiled function returns 4, and `strlen(d) + strlen(s)` is 6 after the call.

### Additional information (optional)

- **What the function does.** The BSD manual and glibc (2.38 and later) agree: `strlcat` returns
  the initial length of `dest` plus the length of `src`; if it finds no NUL in the first `n` bytes
  of `dest`, it writes nothing and returns `n` plus the length of `src`; otherwise it writes from
  `dest[strlen(dest)]` to `dest[\min(n-1, strlen(dest)+strlen(src))]`, the last byte being the
  NUL.
- **Proposed clauses.**

  ```
  assigns dest[strlen(dest)..\min(n-1, strlen(dest)+strlen(src))]
    \from indirect:n, src[0..strlen(src)];
  assigns \result \from indirect:dest[0..], indirect:src[0..], indirect:n;
  ensures bounded_result:
    \result == \old(\min(strlen(dest), n) + strlen(src));
  ```

  The upper bound of the frame is the one the `separation` precondition already uses. The
  dependencies of the result now name the bytes of `dest` and all the bytes of `src`: the result
  depends on both lengths.
- **How I checked the new clauses.** WP proves a byte-loop implementation of `strlcat` against the
  patched contract, with one admitted fact (the two lengths do not add up past `SIZE_MAX`). With
  the current contract the same proof stops on `bounded_result`. That implementation returns the
  same result and leaves the same bytes as glibc 2.41's `strlcat` for every destination length and
  source length from 0 to 10 and every `n` from 0 to 14 (1815 calls).
- **Your own test.** `tests/libc/string_h.c` has `//@ check imprecise: strlcat_res == 6;` after
  appending `"cat"` to `"dog"`. It is unknown today and valid with the new clause.
- **Not changed.** The preconditions, and the contract of `strlcpy`, whose result clause is right.
- **Seen, not changed: the `separation` precondition.** It covers `src+(0..strnlen(src, n-1))`,
  but the function reads `src` up to its NUL to compute the result. With
  `char buf[32] = "0123456789abcdefghij";`, the call `strlcat(buf + 16, buf, 8)` has its four
  preconditions valid, and it writes `buf[20..23]`, which holds the NUL of `src`. The BSD manual
  says the behaviour is undefined when the strings overlap. Requiring
  `src+(0..strlen(src))` to be separated would reject that call. It is a stronger precondition
  for existing users, so I left it out; I can add it to the merge request if you want it.

A merge request with the three clauses and a test follows.
