# [Kernel] `Cil.isExactFloat` drops `(float)` casts on `double`-exact literals in ACSL logic, causing false WP proofs and lost Eva alarms

<!-- Everything below this line is the issue description. -->

### Summary

In ACSL annotations, an explicit `(float)` cast applied to a floating-point literal that is exact
as a `double` but not as a single-precision `float` (such as `16777217.0`, `2147483647.0`, or
`1e11`) is silently dropped during typing. As a result, WP proves false properties such as
`(float)16777217.0 == 16777217.0`, and Eva marks true assertions such as
`assert (float)16777217.0 == 16777216.0` invalid, stopping propagation and silently hiding
downstream alarms (such as a sure division by zero).

### Steps to reproduce the issue

`float_cast_exact.c`:

```c
/*@ check lemma exact_float: (float)16777216.0 == 16777216.0;
    check lemma inexact_float: (float)16777217.0 == 16777216.0;
    check lemma wrong_float: (float)16777217.0 == 16777217.0; */

int g;
void dead(int z) {
  //@ assert (float)16777217.0 == 16777216.0;
  g = 10 / z;
}

int main(void) {
  float lim = 2147483647.0f;
  float big = 1e11f;
  //@ check true_1: lim <= (float)2147483647.0;
  //@ check true_2: big == (float)1e11;
  //@ check true_3: (float)1e11 == 99999997952.0;
  dead(0);
  return 0;
}
```

```sh
frama-c -print float_cast_exact.c
frama-c -eva float_cast_exact.c
frama-c -wp -wp-prover none -wp-print float_cast_exact.c
```

### Expected behaviour

- `-print` keeps the `(float)` cast on `16777217.0`, `2147483647.0`, and `1e11` (which are not
  representable as single-precision `float`), while still simplifying exact single-precision casts
  such as `(float)16777216.0` to `16777216.0`.
- `-eva` validates all four assertions (`true_1`, `true_2`, `true_3`, and the `assert` in `dead`)
  and reports the sure division-by-zero alarm at `g = 10 / z;`.
- `-wp -wp-prover none -wp-print` proves `inexact_float` and refutes `wrong_float` (`Prove: false.`).

### Actual behaviour

`-print` drops every `(float)` cast:

```c
/*@ check lemma exact_float: 16777216.0 ≡ 16777216.0;
 */
/*@ check lemma inexact_float: 16777217.0 ≡ 16777216.0;
 */
/*@ check lemma wrong_float: 16777217.0 ≡ 16777217.0;
 */
```

`-eva` marks the true checks and assertion invalid, stops propagation in `dead`, and reports zero
alarms:

```text
[eva:alarm] float_cast_exact.c:14: Warning: check 'true_1' got status invalid.
[eva:alarm] float_cast_exact.c:15: Warning: check 'true_2' got status invalid.
[eva:alarm] float_cast_exact.c:16: Warning: check 'true_3' got status invalid.
[eva:alarm] float_cast_exact.c:7: Warning:
  assertion got status invalid (stopping propagation).
...
  0 alarms generated by the analysis.
```

`-wp -wp-prover none -wp-print` proves the false lemma `wrong_float` and refutes the true lemma
`inexact_float`:

```text
Goal Check Lemma 'inexact_float':
Prove: false.
Goal Check Lemma 'wrong_float':
Prove: true.
```

### Additional information (optional)

**Cause.** `Logic_utils.numeric_coerce` (`src/kernel/services/ast_queries/logic_utils.ml:332-333`)
drops `(TFloat fk)` on `TConst (LReal r)` whenever `Cil.isExactFloat fk r` holds. However,
`Cil.isExactFloat` (`src/kernel/services/ast_queries/cil.ml:2494-2495`) only checks:

```ocaml
let isExactFloat fk r =
  r.r_upper = r.r_lower && isFiniteFloat fk r.r_nearest
```

`r.r_upper = r.r_lower` only tests exactness as an OCaml `double`, and `isFiniteFloat` only tests
that rounding to `fk` remains finite — it never checks that rounding `r.r_nearest` to `fk` leaves
the value unchanged. The only other caller (`plugins/aorai/src/aorai_utils.ml:393`) is affected by
the same predicate.

**Fix.** In `Cil.isExactFloat` (`src/kernel/services/ast_queries/cil.ml`), require that rounding
`r.r_nearest` to `fk` produces a finite value equal to `r.r_nearest`:

```ocaml
let isExactFloat fk r =
  r.r_upper = r.r_lower &&
  let f = Floating_point.round_if_single_precision fk r.r_nearest in
  Floating_point.is_finite f && Float.equal f r.r_nearest
```

A merge request with this fix and a regression test (`tests/spec/float_cast_exact.c`) is ready.

The analysis and fix were prepared with LLM assistance; I reviewed them and ran the reproducer and
tests described above.
