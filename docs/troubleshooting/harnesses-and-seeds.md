### Symptom: `seed_harvest.py record` Reports `status: "not_relinked"` and 0 Calls Because Every Test Unit Is `no_api_function`
- **Seen on:** libmodbus run-1 (2026-11-18, `standard` profile). `workspace/reports/seed_harvest.json` had `status: "not_relinked"`, `calls.recorded: 0`, and `relink.<exe>.status: "no_api_function"` for all 9 test executables (`unit-test-server`, `unit-test-client`, `proxy-test-server`, ...), although the test command succeeded and the library exports the 71 API functions.
- **Cause:** pipeline gap. `seed_harvest.plan_recorder` builds one wrapper plan per model API function, but the relink loop keeps only `mine = [p for p in plans if p["name"] in defined_functions(exe)]`, where `defined_functions` is `nm --defined-only` on the test executable. libmodbus builds its tests against the shared library (`src/.libs/libmodbus.so.5.1.0`), so the tests reference the API as undefined symbols and define none of it; every executable is skipped. The check works for a target whose tests link the library statically into the executable, where the API functions are defined there.
- **Fix:** **fixed** in [`../../scripts/seed_harvest.py`](../../scripts/seed_harvest.py), commit `6212e3b` on branch `sup/libmodbus-seed-shared-lib`, merged live into `phase1-remediation` as `5ef9ea4` (2026-11-18). New `undefined_functions()` (`nm -D --undefined-only`, version suffix cut); the relink wraps the API an executable defines or references undefined, since `ld --wrap` redirects undefined references too and `__real_<fn>` resolves to the `.so` at run time. libmodbus's libtool wrappers run `.libs/<exe>` directly (`relink_command=""`, `LD_LIBRARY_PATH` set to `src/.libs`), so the relinked binary is the one the tests run. On libmodbus in the build image: before `not_relinked`, 0 calls; after `ok`, 9 of 10 executables relinked, 321 calls (189 unique) over 46 API functions. The test command exits 255 on the unmodified build too (target-side, not diagnosed). Tests: `tests/test_seed_harvest.py::test_record_wraps_api_functions_the_executable_calls_from_a_shared_library`, `::test_undefined_functions_reads_the_dynamic_symbol_table`, and the Linux-only compiled `tests/test_seed_harvest_shared_lib.py::test_recorder_wraps_calls_into_a_shared_library`. This is not a target defect.
- **Fixed (was open; commit `6dfe3c0d`, `shared_library_dirs` in `scripts/seed_harvest.py`):** without a test command, `_run_executables` ran `tree/<unit>` (`.libs/<exe>`) directly, without the libtool wrapper's `LD_LIBRARY_PATH`: such an executable is now relinked but cannot load the project's `.so`, so it records nothing.
- **Open pipeline gap:** a libtool build whose wrapper runs `.libs/lt-<exe>` (fast-install relink) rebuilds that binary from its own `relink_command` without the wraps, and the report says `relinked` with 0 calls. Checked only on libmodbus, which is not affected.
- **Open test gap:** no local image ships pytest, so the Linux-only compiled seed-recorder tests skip on the Windows host; they were run in `framac-analysis:latest` with pytest copied from the host.

### Symptom: `--api` Harness Skips Every Function That Takes an Opaque Handle Built by `<lib>_new_<kind>` (`no constructor for opaque handle struct _modbus *`)
- **Seen on:** libmodbus run-1 (2026-11-18, `standard` profile), module `libmodbus_so_5_1_0` after the generated `config.h` force-include fix. `generate_harness.py --api` produced 20 cases and put 51 of the unit's 71 entry points in `api_skipped`, each with `no constructor for opaque handle struct _modbus *`. The skipped set is the security-relevant surface: `modbus_reply`, `modbus_reply_exception`, `modbus_receive`, `modbus_receive_confirmation`, `modbus_proxy`, every `modbus_read_*`/`modbus_write_*`, and every context setter/getter. `harness_reach.py check` then listed the same 51 functions as `gaps` and exited 1.
- **Cause:** pipeline bug in [`../../scripts/api_harness.py`](../../scripts/api_harness.py). `handle_functions` takes a function returning the handle as its constructor only when `_INIT_NAME_RE` matches its name, and that regex accepted `new`/`create` only as a suffix (`_new$`, `_create$`). The `<lib>_new_<kind>` constructors `modbus_new_tcp`, `modbus_new_tcp_pi` and `modbus_new_rtu` were therefore never candidates. Parameters were never the problem: the rule already allowed them. The docstring's "returns the handle type and takes none" meant no handle parameter, and the run's model read it as "no parameters" (a first diagnosis that turned out wrong). The three internal entry points (`_modbus_receive_msg`, `_modbus_init_common`, `_error_print`) are skipped separately, because their `struct _modbus *` parameter needs `modbus-private.h`.
- **Fix:** **fixed**, commit `08bec6c` on branch `sup/libmodbus-new-ctor-name`, merged live into `phase1-remediation` as `c8484c6` (2026-11-18). `_INIT_NAME_RE` now matches `init`/`new`/`create` as a whole word anywhere (`(?:^|_)(?:init|new|create)(?:$|_)`; not `modbus_renew`, `newline_count`, `recreate_x`), so `modbus_new_tcp` is the constructor (fewest parameters, then the name) and `modbus_free` the destructor. The `handle_functions` docstring and the `/framac-slice` skill now say a constructor takes no handle and no path parameter, other parameters coming from the input. Regression test: `tests/test_api_harness_lifecycle.py::test_a_lib_new_kind_constructor_builds_the_handle`. A run already past step 4 regenerates its `--api` harness. Before the fix the run stopped at the reach gate rather than write about 51 `--dispatch-case` cases.
- **Open pipeline gap:** a `char *device` parameter is not a file-system path for `path_parameter` (`_PATH_WORDS`). On libmodbus `modbus_new_rtu` loses to `modbus_new_tcp` and its own case never calls `modbus_connect`, so no fuzzed device string reaches `open()`; a library whose only constructor takes a device string could, through a connect-style method in the lifecycle case. Likewise a TCP handle built from fuzzed address and port can `bind`/`listen` on loopback (the containers run `--network none`), and `modbus_tcp_accept`/`modbus_receive` on such a handle may block: watch for libFuzzer timeouts in the `modbus_t` lifecycle case.

### Symptom: `validate_artifacts.py` Fails With `$.api_cases[<n>].rest: expected type null` After a Parameterized Constructor Creates a Lifecycle Case
- **Seen on:** libmodbus run-1 (2026-11-18, `standard` profile), module `libmodbus_so_5_1_0`, immediately after the constructor-name fix `08bec6c`. `pipeline_make.py run seed` ran `validate_artifacts.py run-dir .` and exited 1 with:
  ```text
  "workspace/harnesses/harness_libmodbus_so_5_1_0.json: $.api_cases[67].rest: expected type null",
  "workspace/harnesses/harness_libmodbus_so_5_1_0.json: $.warnings: the producer recorded a schema problem: schema: $.api_cases[67].rest: expected type null"
  ```
- **Cause:** pipeline bug. `modbus_new_tcp(const char *ip, int port)` is now the `modbus_t` constructor, so `api_harness.lifecycle_case` synthesizes a lifecycle case whose constructor takes a string. The generator records the port in `slots` but the string in `rest`, as `{"call": 0, "param": 0, "kind": "string"}`. [`../../schemas/harness_sidecar.schema.json`](../../schemas/harness_sidecar.schema.json)'s `lifecycle_case` requires `rest` to be `null` (a lifecycle case's constructor arguments are its `slots`; only `single_case` carries a `rest`, and `slot.kind` has no string member). `generate_harness.py` writes the schema problem into the sidecar's `warnings` but still exits 0, so the failure surfaces later, at the seed target's validation.
- **Fix:** fixed by `8e0472b` and `f40993b`, fast-forwarded into `phase1-remediation` during the run. In `scripts/api_harness.py`, `_lifecycle_case` now binds the constructor with the rest reserved (`_RESERVED_REST`), as `_construct` does.
  - Under a reserved rest, an unsized input string becomes a `STRING_SLOT_BYTES` (16-byte) `bytes` slot whose last byte is forced to 0. It is not a zeroed buffer, because `modbus_new_tcp` returns NULL on an empty IP and the case would never run a method.
  - An unsized input byte pair becomes a zeroed spare buffer with a clamped length.
  - Tests: `tests/test_api_harness_lifecycle.py::test_a_lifecycle_constructor_string_is_a_bounded_slot_never_the_rest`, `::test_an_out_parameter_lifecycle_constructor_string_is_a_bounded_slot_never_the_rest`, `::test_a_lifecycle_constructor_byte_pair_never_takes_the_rest`, `::test_an_out_parameter_constructor_string_in_a_single_case_is_a_slot_and_the_call_keeps_the_rest`.
  - A run that has already generated its harness must regenerate it, because rerunning the validation alone still fails.
  - The generator only records its own schema problems as a warning. That is deliberate (R5): the failure shows at `validate_artifacts.py run-dir`.
  - Still open, narrow:
    - a loop method's unsized string or byte pair reads at `fuzz_off` without advancing it;
    - a returning constructor inside a single case still takes the rest;
    - a lifecycle constructor's unsized byte pair is always zero data.

### Symptom: The Generated Harness Enables a Documented Infinite-Retry Mode (`MODBUS_ERROR_RECOVERY_LINK`), and the Crash Gate Confirms the Resulting libFuzzer Timeout
- **Seen on:** libmodbus run-1 (2026-11-18, `standard` profile). The generated `modbus_set_error_recovery` case, and the `modbus_t` lifecycle case's method for it, copy the fuzzed enum argument and can set `MODBUS_ERROR_RECOVERY_LINK`. A later send in the same lifecycle case then enters the documented infinite close/connect loop in `send_msg`, and libFuzzer's 10 s alarm records a timeout (`timeout-246633d0...`, 71 bytes). The independent crash verifier confirmed it as a medium-severity DoS.
- **Cause:** **Open pipeline gap.** The generator clamps a fuzzed enum argument to the declared constants, but it has no notion of a value the API documents to block. The target's own `docs/modbus_set_error_recovery.md` (in the libmodbus checkout, outside this repository) says of `MODBUS_ERROR_RECOVERY_LINK`: "This mode will try an infinite close/connect loop until success on send call ... The reconnection attempt can hang for several seconds if the network to the remote target unit is down." The crash-verifier brief's rejection classes have no "documented behaviour" basis for a hang, so a documented infinite retry can be confirmed as a target DoS. The harness call is otherwise legitimate (public API, declared enum value).
- **Fix:** none in the pipeline yet. Suggestions: let the sidecar mark blocking enum values or functions so the generator does not feed them to the target, and add a verifier rejection basis for behaviour the target documents. Workaround used in this run: after regenerating the harness for the A/B/C repair, the parent clears the LINK bit from the fuzzed argument (`value & ~MODBUS_ERROR_RECOVERY_LINK`) with a comment citing the doc, recorded in the repair reason. The confirmed record is left as the gate wrote it and is reported as a false positive, not a target bug. Not a target defect.

### Symptom: LeakSanitizer Direct Leaks From the Handle Constructor of Every API Case (`modbus_new_tcp`, `modbus_mapping_new_start_address`) and an Invalid `free` in `modbus_mapping_free`
- **Seen on:** libmodbus run-1, 2026-11-18, Phase 1 fuzz (`crash_found` after 165 s, 63 artifacts). Eva also reports `modbus_mapping_free` (modbus.c:2328, precondition of `free`) Invalid.
- **Cause:** pipeline bug.
  - `api_harness.handle_functions` took the alphabetically first destructor-named function. That was `modbus_close`, which only closes the socket, not `modbus_free`. So every single case and the lifecycle case released `modbus_t` with `modbus_close`, and each execution leaked the context.
  - A constructor returning a complete struct (`modbus_mapping_t *modbus_mapping_new_start_address(...)`) is not a handle, so its result was dropped as `(void)`.
  - The `modbus_mapping_free` single case passed a zeroed stack struct to a function that calls `free` on its members.
- **Fix:** fixed by `f59649e` and `8385bd1`, merged into `phase1-remediation` as `5a9ff81` during the run. The crash verification gate had rejected these crashes as harness-induced and opened a harness repair, which regenerates the harness with the fixed generator.
  - A destructor named for freeing wins (`_FREEING_DTOR_RE`).
  - A destructor-named `close` of the same handle runs before it (`handle_closers`).
    - The `close` is chosen by name only.
    - One that reaches `free` through direct call sites is excluded.
    - A `close` that frees through an indirect call (a vtable) would still be a double free; that remains open.
  - A constructor-named, allocating function returning `struct S *` has its result released by S's freeing destructor (`_made_struct`, `struct_freers`).
  - A freeing struct destructor of a struct with no initializer gets no single case.
  - Tests: `tests/test_api_harness_lifecycle.py::test_the_destructor_that_frees_wins_over_close_and_close_runs_first`, `::test_a_struct_made_by_a_constructor_is_released_by_its_freeing_destructor`, `::test_a_close_that_frees_the_handle_is_no_closer`.
  - The libmodbus harness drops from 69 to 68 cases, and selectors 39 and up shift down by one.

### Symptom: ASan SEGV / global-buffer-overflow in `modbus_get_byte_from_bits`, `modbus_set_bits_from_byte`, `modbus_set_bits_from_bytes` (Unbounded `idx`, `nb_bits`)
- **Seen on:** libmodbus run-1, 2026-11-18, Phase 1 fuzz.
- **Cause:** pipeline bug. The index (`idx`) and count (`nb_bits`, `nb`, `write_nb`, `read_nb`) that index a buffer with no length beside it were read from the input unbounded.
  - `_ARRAY_COUNT_RE` did not know `nb`.
  - The array/count logic only handled a count that follows its array, but libmodbus puts the count before the buffer.
- **Fix:** fixed by `f59649e`, merged into `phase1-remediation` as `5a9ff81` during the run.
  - `nb` as a word is now a count name.
  - In a call with no (buffer, length) pair, count- and index-named integers are clamped to half of the smallest buffer of no length (`_indexed_scalars`, `_index_rules`). Values within the bound pass as read.
  - Tests: `tests/test_api_harness_array_count.py::test_an_index_and_a_count_stay_within_a_buffer_of_no_length`, `::test_an_nb_count_before_its_buffer_is_bounded_by_it`, `::test_an_index_of_a_call_with_a_length_is_left_to_the_callee`.
  - Still open: a limit named otherwise (`modbus_report_slave_id`'s `max_dest`) stays unbounded.

### Symptom: `generate_harness.py --api` Fails With `field has incomplete type 'struct in6_pktinfo'`
- **Seen on:** nginx 1.31.9 run-3, 2026-11-19, modules `nginx__ngx_files` and `nginx__ngx_event_openssl`.
  - With `--header`: `the harness does not compile outside its cases: workspace/work/src/event/ngx_event_udp.h:46:27: error: field has incomplete type 'struct in6_pktinfo'`.
  - Without `--header`, every automatic header attempt failed the same way. The generator reported `the build capture's headers do not compile in the harness, dropping ...`, then `unresolved identifiers after automatic prelude resolution: ngx_array_t`.
- **Cause:** pipeline bug.
  - glibc's `features.h` reads the feature-test macros once, at the first system header. `struct in6_pktinfo` in `<netinet/in.h>` exists only under `__USE_GNU`, which `_GNU_SOURCE` turns on.
  - nginx defines `_GNU_SOURCE` and `_FILE_OFFSET_BITS 64` in `src/os/unix/ngx_linux_config.h`, before its first system header. They are not on its command line, so the DAG's cppflags do not have them.
  - The harness includes `<stdint.h>`, `<stddef.h>`, `<stdlib.h>` and `<string.h>` before the module header. Eva and E-ACSL also force-include `fc_compat_types.h`, which includes host headers on the E-ACSL side. `features.h` was therefore read without the macros, and nginx's later `#define _GNU_SOURCE` came too late. A `#define` written in the harness would come too late as well: only a command-line `-D` reaches the compiler before `-include`.
  - Frama-C's libc declares `in6_pktinfo` unconditionally, so the Frama-C parse of the model never saw the problem.
- **Run-side workaround on run-3:** the agent added `-D_GNU_SOURCE` to `--cppflags` by hand. It is hard-coded and omits `_FILE_OFFSET_BITS=64`, which nginx also sets (no layout change on x86_64, but a different `off_t` on a 32-bit target).
- **Fix:** commit `50310f6` and its follow-up (a compile that cannot be preprocessed is reported), on branch `sup/nginx-harness-feature-macros`, stacked on `sup/nginx-stub-check-include-context`. Both were merged into `phase1-remediation` in `aa65c16` and into main in `fd40b66`.
  - New shared module [`../../scripts/include_context.py`](../../scripts/include_context.py). It holds the `gcc -E -dD` scan that `stub_check.py` used for its include context, and adds the feature-macro scan.
  - **Which macros:** a macro the target defines (command line, its own files, or its generated headers) before the first system header that a target file enters, and that some system header the compile enters tests in an `#if`/`#ifdef`/`#ifndef`/`#elif`. Include guards of target files are never kept, nor are function-like macros or values with spaces or quotes. Nothing is hard-coded.
  - **Which compiles decide:** the build capture's compiles of the module's sources that include the harness's header (all of them when none does). A macro is carried when every scanned compile defines it with the same line. A source that defines it only after a system header (nginx's `ngx_event_quic_bpf_code.c`) agrees and is listed under `late`. A disagreement is not carried and is reported under `differing`.
  - **How it reaches the compiler:** `generate_harness.py` appends the macros to the harness cppflags as `-DNAME=value` before the first probe. The prelude probe, the `--api` layout and case probes, every automatic header attempt, and the Eva, E-ACSL and LibFuzzer builds all read those cppflags, and gcc applies every `-D` before any `-include`.
  - **Failures:** a compile that `gcc -E` cannot preprocess (no gcc, a missing include directory, a timeout) is said on stderr and listed under `failed`; the macros then come from the other compiles only, and with none left nothing is added.
  - **Given flags:** a macro already given in `--cppflags` with the same value is kept as is (listed under `given`); `-DX` agrees with an empty value or `1`. A different value, or a `-U`, is kept and reported on stderr and under `conflicts`. Nothing is added twice.
  - **Sidecar:** `harness_<mod>.json` gets `feature_macros` (`source`, `compiles`, `command`, `macros`, `flags`, and when non-empty `headers`, `late`, `given`, `conflicts`, `not_carried`, `differing`, `failed`); see [`../../schemas/harness_sidecar.schema.json`](../../schemas/harness_sidecar.schema.json). A target that sets no such macro, or a run without a build capture, gets a byte-identical harness and sidecar.
  - `stub_check.py` passes the same macros to its three probes as `-D` flags (`include_context.feature_flags`); see [`./kernel-and-stubs.md`](./kernel-and-stubs.md).
- **Tests:**
  - `tests/test_harness_feature_macros.py::test_an_api_harness_compiles_when_the_target_defines_gnu_source_in_its_config_header` (Docker), with a small non-nginx fixture whose config header defines `_GNU_SOURCE` before `<stddef.h>` and whose module header has a `struct in6_pktinfo` field. On `f029b86` it fails with run-3's error (`workspace/work/src/fm.h:5:22: error: field has incomplete type 'struct in6_pktinfo'`). After the fix the harness generates, and clang, E-ACSL's preprocessing and the Eva parse accept it.
  - `::test_an_api_harness_of_a_target_without_feature_macros_gets_no_flag` (Docker).
  - Unit: `::test_the_harness_flags_get_the_targets_feature_macros`, `::test_a_compile_that_cannot_be_preprocessed_is_said_and_recorded`, `::test_a_given_flag_is_kept_and_a_conflicting_one_is_reported`, `::test_only_the_compiles_that_include_the_harness_headers_decide`, `::test_a_source_that_defines_them_after_a_system_header_agrees`, `::test_a_target_without_feature_macros_gets_the_same_harness_and_sidecar`, `::test_the_scan_keeps_what_the_target_defines_before_its_first_system_header`, `::test_a_macro_becomes_the_flag_that_defines_it_identically`.
- **Recovering run-3:** regenerating the two harnesses with the fix derives `_GNU_SOURCE` and `_FILE_OFFSET_BITS 64` for both. With the hand-added `-D_GNU_SOURCE` still in `--cppflags`, only `-D_FILE_OFFSET_BITS=64` is added and `_GNU_SOURCE` is listed under `given`; without it, both are added. The `-D_GNU_SOURCE` workaround is no longer needed. The harness `.c` text does not change. Checked read-only with `clang -fsyntax-only` on run-3's harnesses: the exact error without the macros, a clean parse with the derived flags.
- **Open pipeline gap:** a function-like feature macro, or one whose value has spaces or quotes, is listed under `not_carried` and must be given in `--cppflags` by hand (none seen so far).
- **Verified on nginx run-4 (2026-11-19):** both nginx harnesses got `feature_macros` with `_GNU_SOURCE` and `_FILE_OFFSET_BITS=64` from 8 compiles, with no hand-written `-D`, and the manual prelude compiled. The automatic header path still failed on `nginx__ngx_files`, for another reason: see "The Automatic Prelude Cannot Resolve nginx's `ngx_files` Module" below.

### Symptom: A Harness Line Like `break int main(void);`, or `too many arguments to function call, expected 0, have 2` on `main`
- **Cause:** the `main` prototype synthesizer read a statement keyword from a preceding macro continuation (`png-fix-itxt.c`'s `GETBREAK`) as the return type; and the default `argv` entry style calls `main(2, argv)` on a `main(void)` (libpng `pngfix-itxt`, `pnggetset`; defects B and C of `docs/progress/2026-11-09-libpng-harness-generation-bugs.md`).
- **Fix:** B is **fixed** in `scripts/generate_harness.py`: preprocessor continuations are stripped and statement keywords cut from the head. C is handled by failing early (`_check_argv_entry`) with what to do: `--entry-style stdin` for a program that reads stdin, `harness_reach.py exempt` for one that reads no input, else `--entry-style custom` with `--call-expr`.

### Symptom: An `--api` Harness Never Finds a Use After Free, Double Free or Call After Error on an Opaque Handle
- **Seen on:** H2 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), from `scripts/api_harness.py` (2026-11-10).

## Reach Gates, Coverage & `build-check`

### Symptom: The Reach Gate Fails (`harness_reach.py check` Exit 1, or `make` Stops at `reach-gate`)
- **Cause:** a harness does not reach one of its module's API entry points, a Tier 1A/1B/2 module has no harness (`no_harness`), or a harness changed after the check ran (its digest no longer matches `phase0_gates.json`). On multi-binary/plugin codebases such as `sudo`, legacy Rule 1 also marked internal convenience archives (`libparsesudoers_a`, `libsudo_eventlog_a`, `libsudo_iolog_a`), plugin shared objects (`sudoers_so`), and executable internal headers as public API entry points, and shipped `tf_*` fuzzers did not credit their link unit's reachability.
- **Fix:** add a `--dispatch-case` per unreached entry point and rerun `check`, or record a reason with `harness_reach.py exempt` (`/framac-slice` Step 4b; `--function` is repeatable in a single batch invocation with one regate). A sub-module is checked only against the unit's entry points in its own scope; entry points no harness's scope holds are reported as the unit's gaps.
- **P1 scoping & `tf_*` credit (`FRAMAC_HARNESS_SCOPE_V2=on`, default `on`, `=off` for A/B rollback; commits `3ab114a` and `1d81171` across [`../../scripts/build_capture.py`](../../scripts/build_capture.py), [`../../scripts/trust.py`](../../scripts/trust.py), [`../../scripts/build_callgraph_dag.py`](../../scripts/build_callgraph_dag.py), and [`../../scripts/harness_reach.py`](../../scripts/harness_reach.py)):** non-test link units are classified by `unit_visibility` (`executable`, `plugin_so`, `public_lib`, `internal_convenience`), Rule 1 restricts default trust-boundary marks to `public_lib` exports and `plugin_so` vtable callbacks (aligned with `THREAT_MODEL.md`), `check_unit()` and `run_dynamic()` credit passing `tf_*` target-fuzzer modules to their link unit (`covered_by_target_fuzzers`), and P2A `api_auto_exempt` reasons are accepted automatically. Tests: `tests/test_p1_capture_scoping.py` and `tests/test_p1_dag_reach.py`.

### Symptom: A Companion Sub-Module Harness (`--scope-file`) Does Not Close Another Harness Module's Reach Gap
- **Seen on:** ptf-original run-2 (2026-11-10): `ExternalInterfaces__Logger` (dispatch case for the by-value `EventEntry_T` helpers) left the main `ExternalInterfaces` module failing on the same three functions, and itself failed on every other `Logger.c` entry point.
- **Cause:** not a defect, but easy to misread: `harness_reach.py check` tests **each module against the entry points in its own scope**. The main module's scope also holds `Logger.c`, so it must reach those functions itself; the companion only adds obligations for its own scope. Coverage does not aggregate across a unit's harness modules for gate purposes.
- **Fix:** exempt the unreachable entry points on the module whose scope holds them, with a recorded reason; do not add companion harnesses to close another module's gaps.

### Symptom: `dynamic: entry points never executed by the corpus` in `phase0_gates.json`
- **Cause:** after `coverage-<mod>`, `reach-dynamic-<mod>` found an entry point the gate holds the module to that no input executed. Fuzz and Eva of that module stop at the gate until it is fixed.
- **Fix:** read `executions: 0` in `workspace/reports/coverage/<mod>.json`. If the harness never calls the function, add a case. If it does, the corpus is stuck behind an input check: try, in order, recorded seeds, a dictionary (`params set --fuzz-dict`), a larger budget (`params set --fuzz-budget`), and a dispatch case that calls the function directly. The gap stays while the harness is unchanged.
- **Exemptions:** exempt only an entry point that cannot be driven from bytes (a live socket, a real file descriptor, process-global state). "30 s of fuzzing did not get deep enough" is not a reason: try the steps above first, and exempt only what still cannot be driven.
- **After a repair:** rerun the reach gate (`pipeline_make.py run reach-gate`) before rerunning the module; after an exemption this is not needed (`harness_reach.py exempt` re-checks the gate, see the next entry). `build-<mod>` and `fuzz-<mod>` refuse a harness whose digest changed since the gate ran. A whole-run `reach-gate` exits 1 while another module still has a gap, but it still records this module's row.
- **No row for the module:** a module whose coverage could not be measured (coverage status `no_inputs`, `compile_error` or `coverage_error`, or no coverage report) gets no row. It is listed with its reason under `unmeasured` in `workspace/reports/harness_reach_dynamic.json`; `harness_reach.py dynamic` exits 2 and `reach-dynamic-<mod>` fails, but the gate is not reopened: fuzzing and Eva of the module continue. The usual cause is that every input crashes, so the corpus stays empty (qlz: a misaligned store at `quicklz.c:161`). Then the crash is the finding: verify it. There is nothing to repair in the harness, and the module's reach stays unmeasured; do not exempt entry points for it. Seen again on ptf-original run-2 (2026-11-10): `PtfHandler` (`no_inputs`, its one crash artifact is the finding) and `libXmlHandler_a__ClkInternComparData` / `__NetworkParam_3` (`coverage_error: no input replayed to completion`, every corpus input crashes or times out in the coverage replay).
