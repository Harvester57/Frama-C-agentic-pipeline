## Harness Generation (`generate_harness.py`, `api_harness.py`)

### Symptom: `lib/getopt.c:45: fatal error: gettext.h: No such file or directory` in a Harness Build (nettle getopt)
- **Fixed pipeline bug** (`scripts/build_callgraph_dag.py`, commit `d71b255`): 9 executable modules of nettle run-3 (`base16dec`, `base16enc`, `base64dec`, `base64enc` and the tools) failed `build-check` with this error.
- **Cause:** Frama-C parses with its own libc, which has no `__GLIBC__`; the build and every harness build use glibc. nettle's root `getopt.c` includes `lib/getopt.c` only when `ELIDE_CODE` is unset, and sets it under `__GLIBC__ >= 2`. The glibc build therefore compiled `getopt.c` to an empty object: in `build_capture.json` it has `headers: []` and `defined_functions: []`, and `lib/getopt.c` is no compiled source. The model took the other branch and put `_getopt_internal`, `getopt_long`, and the rest in `lib/getopt.c`. The DAG took `required_sources` from the model's defining files, so the argv harnesses compiled `lib/getopt.c` on its own.
- **Fix:** a module's `required_sources` now hold only compiled sources (`compiles[].source`). Any other file becomes the compiled source whose `cc -M` list (`compiles[].headers`) includes it, or is dropped when none does. A function the real build does not define carries `model_only` with the reason, and the DAG lists these per file under `model_only_functions` with a warning. A function is marked when no compile compiles or includes its file, or when it is non-static and no object of its units defines it (statics are never marked: the compiler may inline them). Marked functions are never harness sources or reach-gate entry points (`harness_reach.built_entries`). Eva and WP may still analyse them; the ledger shows `bookkeeping.model_only` and REPORT.md lists them. `build_capture.py` now records `compiles[].probe_errors`, so an empty `headers` or `defined_functions` list is no longer confused with a failed probe. A capture that predates it trusts only non-empty symbol lists. `build_only_functions` no longer reports the functions of an included `.c` (nettle's `eccdata.c` including `mini-gmp.c`).
- **Check:** after `build_callgraph_dag.py`, no `required_sources` names a file outside `compiles[].source`. Each `model_only_functions` warning names code only Frama-C's configuration compiles. Report it to the user: Eva and WP results there describe code the shipped binary does not contain.

### Symptom: A Harness Misses a Build Flag (`-include config.h`, a Quoted `-D`, `-std=`)
- **Cause:** harnesses take the unit's flags from the DAG. The unit's `-include` files are kept apart (`force_includes`) and applied by `generate_harness.py`. Quoted `-D` values (`-DLOG_PATH="log.txt"`) and the build's `-std=` are not copied. Later stages split and re-join flag strings, and a pre-C99 `-std` rejects both the C99 harness and E-ACSL's printed code.
- **Fix:** state quoted `-D` flags in the harness's `--cppflags` yourself.
  - A `-std=` of C99 or later given there is kept.
  - A pre-C99 one got through until the fix described in the next entry, which drops it.

### Symptom: `tf_<id>` (or Any Harness) Fails build-check With `instrumented.c:<N>: error: expected ')'` at `fd_set * restrict`

- **Cause:** pipeline bug.
  - c-ares builds with `-std=gnu90`, and the `framac-slice` skill passes the unit's cppflags to `generate_harness.py --target-fuzzer`.

- **Fix:** commit `2f22b2c`, from branch `sup/c-ares-tf-std-flag`, fixed and merged into `phase1-remediation` (2026-11-16).

  - `phase0_model.framac_file_flags` uses the same predicate.
  - The skill's target-fuzzer paragraph says the generator drops the flag.
  - In Docker, the fixture's E-ACSL build fails before the fix and builds after it, with either the new or the old sidecar flags.
  - Tests:

    - `tests/test_eacsl_toolchain.py::test_flag_sets_never_compile_instrumented_code_before_c99`

It links at the pipeline's `-O1`, and `-fgnu89-inline` would restore it. The E-ACSL build is not affected. c-ares has no plain `inline`.

### Symptom: A Harness Line Like `break int main(void);`, or `too many arguments to function call, expected 0, have 2` on `main`
- **Cause:** the `main` prototype synthesizer read a statement keyword from a preceding macro continuation (`png-fix-itxt.c`'s `GETBREAK`) as the return type; and the default `argv` entry style calls `main(2, argv)` on a `main(void)` (libpng `pngfix-itxt`, `pnggetset`; defects B and C of `docs/progress/2026-11-09-libpng-harness-generation-bugs.md`).
- **Fix:** B is **fixed** in `scripts/generate_harness.py`: preprocessor continuations are stripped and statement keywords cut from the head. C is handled by failing early (`_check_argv_entry`) with what to do: `--entry-style stdin` for a program that reads stdin, `harness_reach.py exempt` for one that reads no input, else `--entry-style custom` with `--call-expr`.
- **Stdin entry style:** **fixed** by O10 of [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md) (`ot/o10-stdin-entry`, not merged yet).
  - Before it, a program reading stdin could not be harnessed: the refusal said "no stdin entry style yet" and the module had to be exempted.
  - `generate_harness.py --entry-style stdin` calls `main` (renamed and declared as for `argv`) as `main()`, `main(1, argv)` or `main(1, argv, envp)`, by its parameter count.
  - Fuzz side: `framac_stdin_feed`, which the generator writes after the harness's headers (`STDIN_FEED_PRELUDE`), purges stdio's buffer of the previous input and its EOF flag, then makes the input the whole of fd 0 through a fresh pipe. `read(0, ...)` and stdio both see it, on every input of one process. An input above the pipe's capacity (64 KiB on Linux) is rejected.
  - Eva side: `main` reads Frama-C's libc model of stdin.
  - The reach gate counts the entry points of a `stdin` harness as for `argv`.
  - Tests: `tests/test_harness_stdin.py`. An `fgets` and a `read(0, ...)` program reach their parser on three consecutive inputs, built by a plain driver and by the pipeline's E-ACSL libFuzzer build. The Eva harness parses, and Eva reaches both parsers. These tests need a POSIX host compiler or `FRAMAC_DOCKER_TESTS=1`.
  - Not handled: a target that calls `fclose(stdin)` leaves the next input's purge on a closed stream.

### Symptom: A Repaired Harness's Sidecar Still Lists the Pre-Repair `dispatch_cases`, So a Verifier That Trusts It Concludes the Harness Is Unrepaired
- **Seen on:** mpack run-3 (2026-11-17), `libmpack_a__mpack_expect` after two repairs. `workspace/harnesses/harness_libmpack_a__mpack_expect.c` initialises each reader over the fuzz buffer and passes a real two-element enum table, while `harness_libmpack_a__mpack_expect.json`'s `dispatch_cases` still describes the generated shape (`const char * c0a1` zeroed, unclamped count, no `mpack_reader_init_data`). Verifier `verify-mpack_expect_enum_3389461b8c` flagged it; another verifier replayed a *stale* module binary and read case indices that the current harness does not have.
- **Cause:** `generate_harness.py --record-repair` records the attempt and leaves the sidecar's case descriptions from the last generation. A repair by hand (the documented path for a harness a prover/verifier proved wrong) therefore makes the sidecar misdescribe the `.c` it is the manifest for. The `harness_digest` itself is a composite over the sidecar **and** the `.c` and source (`sha256` over `.json`+`harness .c`+source, `ignore_exempt`), so report digests do track the repaired file; the misleading part is only the human-readable `dispatch_cases`. A module binary built before a `.c` repair stays on disk (builds are content-addressed, so a new run rebuilds) and replays against it show old case tables.
- **Fix:** none yet; **open pipeline gap** (documentation/consistency). Suggested: have `--record-repair` mark the case list `stale: true` (or drop it), and have `refresh` rebuild the module binary before a verifier can replay it. Run-local check before trusting a verifier's replay: compare the module binary's mtime with the `.c`'s, and read `harness_<mod>.c` rather than the sidecar's `dispatch_cases`.

### Symptom: Coverage and Sanitizer Builds Fail With `clang: error: cannot specify -o when generating multiple output files` (Headers in the Sidecar `sources`)
- **Seen on:** mpack run-3 (2026-11-17), every module. `workspace/reports/coverage/<mod>.json` has `status: compile_error`, `compile.stderr` = `clang: error: cannot specify -o when generating multiple output files`; every campaign report has `dual_engine_skipped: sanitizer build failed` for the same reason, and every `cross_engine` entry of `workspace/reports/replay/index.json` is `build_failed`. `modules.mk` shows the cause directly, e.g. `SOURCES_libmpack_a__mpack_common := ... mpack-common.h ... mpack-reader.h ...`.
- **Cause:** `scripts/api_harness.py` builds the sidecar's `sources` from the entry functions' `file` field plus the unit's `required_sources`. When an entry point is a header `MPACK_INLINE` function (mpack's tag/load/store accessors, `mpack_reader_ensure`), its file is a `.h`, so a header lands in `sources`. `pipeline.mk` then passes it to every engine: E-ACSL/Frama-C accepts a header as a translation unit, but clang does not (it builds a precompiled header per `.h`, which conflicts with `-o`), so the source-coverage build and the ASan+UBSan build fail while the E-ACSL build succeeds.
- **Fix:** **fixed** by `sup/mpack-harness-sources-and-fd-leak` (`7dc1be4`), merged into `phase1-remediation` on 2026-11-17 (merge `7cb53a7`); see the supervisor's entry for the same defect in [`./eacsl-and-fuzzing.md`](./eacsl-and-fuzzing.md). The run-local workaround used before the merge: run `run_eacsl_fuzz.py coverage` by hand per module with the `.h` entries dropped from `--sources` and the same flags as the Make recipe (the reports are identical in shape), then `harness_reach.py dynamic --module <mod>` by hand, since `reach-dynamic-%` depends on `coverage-%`. Consequence to report: the sanitizer engine is unavailable for the whole run, so Phase 1 has E-ACSL evidence only, and header-inline functions show `executions: 0` in the coverage report even when their dispatch case runs (they are compiled into the `.c` files, and the report lists the 140 `.h` functions it does attribute — so check the report before calling such a gap a measurement artifact).

### Symptom: `signed_downcast` RTE Alarms on a Byte Encoder's Deliberate `(char)0xC2` Narrowing, Every One Needing a Verifier Run
- **Seen on:** mpack run-3 (2026-11-17), modules `libmpack_a__mpack_writer_2` and `libmpack_a__mpack_writer`. Eva reports `rte,signed_downcast` Invalid at `src/mpack/mpack-writer.c:655,659,663,667` (`mpack_write_nil` `0xc0 <= 127`, `mpack_write_bool` `(int)(0xc2 | tmp) <= 127`, `mpack_write_true` `0xc3 <= 127`, `mpack_write_false` `0xc2 <= 127`), each becoming a `needs_validation` candidate and a full Crash Verifier run.
- **Cause:** `mpack_write_byte_element` takes the byte as `char` and stores it into a `char*` byte buffer (`mpack-writer.h:173-175`), so the MessagePack tag constants 0xC2/0xC3 (and 0xC0) are narrowed to a signed `char`. That conversion is **implementation-defined**, not undefined (ISO C11/C23 6.3.1.3p3), and it stores the intended byte on every two's-complement target — the target's own unit test pins `"\xc2"`/`"\xc3"` (`test/unit/src/test-write.c:320-325`). `scripts/run_eva_slice.py` passes `-warn-signed-downcast` unconditionally (Frama-C leaves it off by default), so the pipeline asks the encoder to keep its own wire byte inside `[-128,127]`, a property it neither needs nor can have. Verifier `verify-mpack_write_bool_da7350c06e` rejected it as `contract_overconstraint`, showed the alarm is identical on a correctly `mpack_writer_init`-ed writer (so it is not harness-induced), and that the E-ACSL fuzz build carries no `signed_downcast` assertion at all, so no campaign can ever reproduce it.
- **Fix:** none yet; **open pipeline gap** (an overconstraint, not a target defect). Options: do not enable `-warn-signed-downcast` for modules that encode bytes, record a `contract_overconstraint` / `implementation_defined_downcast` rejection class the verifier can use without a run (the crash verifier already returns it, but the scheduler still spends one verifier per site), or teach the generator/ledger to treat a downcast to a byte buffer as a documented assumption. Target-side hardening that keeps the encoding identical: narrow through `uint8_t`, `(char)(uint8_t)(0xc2 | ...)`, or declare the writer buffer `unsigned char`.

### Symptom: `--api` Cases Pass a Zeroed Struct or a `static unsigned char[]` Cast to a Target Struct Type, so Every Case Is Harness-Induced
- **Seen on:** mpack run-3 (2026-11-17), modules `libmpack_a__mpack_writer*`, `_mpack_node_4`, `_mpack_common`. Three independent symptoms, one cause:
  - **No initializer:** `harness_libmpack_a__mpack_writer_2.c` never calls an `mpack_writer_init*` function, so every writer argument is an all-zero `mpack_writer_t` (`buffer == position == end == NULL`). A zero-length write then takes `mpack_memcpy(writer->position, p, 0)` with `dest == NULL` at `mpack-writer.c:536`, and Eva reports `valid_dest: valid_or_empty(dest, n)` Invalid for the libc `memcpy`. Crash Verifier `verify-memcpy_4c6a5720c0` reproduced it and showed that one `mpack_writer_init(&w, buf, sizeof buf)` makes the same call site `Valid`.
  - **Wrong storage class:** the `mpack_realloc` case passes `static unsigned char c0a0[4024]` to `mpack_realloc`, which forwards to `realloc` (`mpack-platform.h:1844-1847`), so Eva reports the `realloc` `freeable` precondition Invalid (`FRAMAC_SHARE/libc/stdlib.h:644`). Crash Verifier `verify-realloc_b7e9ed487a` replayed the two 17-byte crashers on the module binary (abort in `unsafe_realloc`, returncode 77) and on a rebuild whose only change is a `malloc`'d block (returncode 0).
  - **Alignment:** the shadow buffers are `static unsigned char[4024]`, cast to `mpack_writer_t *` / `mpack_tree_t *` / `mpack_node_t *`. C gives them alignment 1, so WP cannot discharge `\aligned(tree, alignof(mpack_tree_t))` and Eva reports unaligned-pointer alarms; the breakers for `mpack_node_data_alloc` and `mpack_tree_init_stdfile_noclose` showed the addresses are aligned at runtime and that a control harness with `c0a0.data + 1` does fire the assert.
- **Cause:** `scripts/api_harness.py` builds a case argument for a pointer to a struct the API knows by value: it `memset`s a stack struct (or a byte array it casts) and only calls the API's initializer when the entry point of the case *is* the initializer. It also declares buffers as `unsigned char[]` rather than with the struct type or `_Alignas`, and it does not model allocator-owned arguments (`mpack_realloc`). The cases compile and pass the static reach gate, but they exercise an invalid object, so Phase 1/2 report [harness-induced] alarms and Phase 3 breakers stall on goals no input can move.
- **Fix:** none yet; **open pipeline gap.** The three verified repairs for a run: call the documented initializer (`mpack_writer_init(&w, buf, sizeof buf)`, `mpack_reader_init_data(&r, data, len)`) before every case whose argument is that struct; pass a `malloc`'d block (and free the result) to allocator entry points; declare the shadow buffers as the struct type or `_Alignas(struct) unsigned char[]`. In this run the affected candidates were rejected as `harness_induced` by their verifiers with a repaired-harness replay as evidence.

### Symptom: An `argv` Harness Does Not Compile: `call to undeclared function '__framac_target_main'`
- **Seen on:** mpack run-3 (2026-11-17), module `sax_example`. The entry is `main` in `examples/sax-example.c` and the module header is `examples/sax-example.h`. `generate_harness.py --entry-style argv` wrote a harness that failed under clang/E-ACSL with `harness_sax_example.c:...: error: call to undeclared function '__framac_target_main'; ISO C99 and later do not support implicit function declarations`.
- **Cause:** pipeline bug in `scripts/generate_harness.py`.
  - A program's `main` is rarely declared in its module header, but the generator synthesized the entry's declaration from the sources only when no `--header` was given.
  - With a header that lacks `main`, the harness called `main(argc, argv)` undeclared; `-Dmain=__framac_target_main` renames that call. A comment in `_build_invocations` claimed a "synthesized declaration" that did not exist on this path.
  - Related gap: `_check_argv_entry` read only the sources, so an `int main(void)` visible only in the header was not refused.
- **Workaround used in the run:** a run-directory header holding `int main(int argc, char **argv);`, passed with `--extra-include` (`workspace/harnesses/include/sax_main.h`).
- **Fixed:** `a13e149`, `2e1fc93` from `sup/mpack-argv-main-prototype`, merged into `phase1-remediation` on 2026-11-17 (merge `4e947ba`).
  - `_argv_entry_declaration` writes `main`'s declaration into the argv harness when no included header declares it. It goes after the headers and before the Eva and fuzz calls, and the `-Dmain=` rename covers it. The declaration is copied from the target's definition, or else is `int main(int argc, char **argv);`.
  - `_check_argv_entry` also consults the included headers, so `main(void)` is refused there too.
  - Tests are in `tests/test_harness_argv.py`, e.g. `test_argv_harness_declares_main_when_the_module_header_does_not` and `test_argv_style_refuses_a_main_void_seen_only_in_the_module_header`.
  - Still not handled: a three-parameter `main(argc, argv, envp)` still gets a two-argument call.

### Symptom: `--api` Says `no API entry point the generator can call: {}` for an Executable Module
- **Cause:** an executable's only API entry point is `main`, which `--api` does not drive (no signature it can fill from bytes).
- **Fix:** use the argv style: `generate_harness.py --module <m> --unit <unit> --sources <required_sources...> --header none --entry-fn main --entry-style argv --cppflags='<DAG cppflags>'`. Modules that take no attacker input (table generators such as nettle's `desdata`/`eccdata`, benchmarks) get `harness_reach.py exempt --module <m> --reason '<why>'`.

### Symptom: `--api` Harness Fails With `unresolved identifiers after automatic prelude resolution: jmp_buf, FILE`, or Leaves Partial `harness_<mod>.{c,json}` After Exit 1
- **Cause:** the auto-prelude knew no header for standard-library names the target's headers use without including them; a failed generation left its half-written files, which `gen` and the reach gate can pick up; the case probe stopped at clang's 20-error cap, so more failing cases needed several rounds (libpng `pngwutil`, `pngset`, `pngget*`; defect E and "partial files" of `docs/progress/2026-11-09-libpng-harness-generation-bugs.md`).
- **Fix:** **fixed** in `scripts/generate_harness.py` and `scripts/api_harness.py`: the prelude includes the standard header of such names (`_STD_HEADER_OF`); generation restores the previous harness files on any failure (`harness_files_kept_on_failure`) and fails on a harness that still does not compile after the prelude (`fail_on_compile_error`); the probe lifts the error cap and fails on errors outside the cases instead of dropping cases for them. **Open pipeline bug:** `--api` still does not default `--header` to the unit's `public_headers` from the build capture; give `--header` by hand (O4 in [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md)).

### Symptom: Auto-Prelude Reports Identifiers Unresolved That a Manually Provided Prelude Header Already Defines
- **Seen on:** ptf-original run-2 (2026-11-10), `libXmlHandler_a__XmlUtil`: with `--extra-include xmlhandler_prelude.h` (which includes `<libxml/tree.h>`, `XmlParser.h`, ...) on the `-I` path, `resolve_prelude_headers` still reported `xmlNodePtr, xmlXPathParserContextPtr, xmlXPathContextPtr, XML_ERROR, xmlDocPtr` as unresolved, although a manual `clang -fsyntax-only` of a file including only that prelude compiles cleanly with the same flags.
- **Cause (from the code, reproduced with a modelled clang, not confirmed on ptf):** the harness includes the module header first and the `--extra-include` headers after it, so the module header is compiled before the header that defines its types; and the definition search reads only the `*.h` files directly in each `-I` directory, so a definition reached through `<libxml/tree.h>` is never found. The manual check compiled the prelude alone, which does not show the order.
- **Fix (fixed 2026-11-11, uncommitted, `scripts/generate_harness.py` `resolve_prelude_headers`):** before reporting `unresolved`, each `--extra-include` header is moved in turn before the module header and clang runs again; the move is kept only when identifiers are resolved, none is new and fewer errors remain. The moved headers are recorded as `extra_includes_first` in the sidecar, and their line carries `/* auto-prelude: moved before the header that needs it */`. Harnesses with nothing unresolved, and `--no-auto-prelude`, are unchanged. Tests: `tests/test_harness_prelude_extra_include.py` (clang modelled by a fake runner, plus a real-clang test that is skipped without clang and passes in `framac-analysis:latest`, 2026-11-11). Not run on ptf.
- **Workaround (still valid):** the documented manual form — `--no-auto-prelude` with an explicit prelude header that includes every definer in dependency order (`PtfUtil.h` before `ExtCommonDefs.h`, `XmlParser.h` before `XmlUtil.h`, `Logger.h` before `LogFiles.h`, ...). The skeleton compile still fails loudly if something is genuinely missing.

### Symptom: `--api` Skips Cases With `invalid application of 'sizeof' to an incomplete type` or `call to undeclared function`
- **Cause:** the harness was generated with `--header none`, so it includes no project header. The auto-prelude only searches for headers that define identifiers the module header uses, and there is none. Internal headers (`aes-internal.h`, `ghash-internal.h`...) are not found either. Found on nettle: 22 of 35 libnettle clusters failed outright and libhogweed skipped 109 cases.
- **Fix:** pass the headers explicitly, one `--extra-include <hdr>.h` each (the public headers of the unit and the internal ones its API uses), and regenerate. On nettle this took the gaps from 245 to 70.
- **Seen again:** c-ares run-1, 2026-11-16 ([`../runs/2026-11-16-c-ares-run1-supervision.md`](../runs/2026-11-16-c-ares-run1-supervision.md)). An `--api` run without `--header` made 19 cases, and the compile probe dropped 18 with `call to undeclared function`. Without a header, the harness declares only its first entry point, and the skill's `--api` text did not say a header is needed.
  - Commit `2424b9b` (branch `sup/c-ares-api-outparam-ctor`, fixed and merged into `phase1-remediation` (2026-11-16)) makes `--api` without `--header` print `api_harness: warning: --api without --header: ...` and add `api_warnings` to the result, naming the build capture's public headers.
  - It also makes `skills/framac-slice/SKILL.md` say to pass `--header <public header>` plus `--extra-include` for the rest.
  - The public headers are not used as a default, because their recorded paths (`/framac-scratch/install/include/...`) do not map reliably to an include path.
  - Workaround (still the way to call it, since the header is not defaulted): `--header ares.h --extra-include ares_dns_record.h`.

### Symptom: Every `--api` Case of a Module Is Dropped (`no API case compiles`) on Opaque Handles (`png_const_structrp`)
- **Cause:** the generator declared an opaque struct, reached through a pointer typedef, as a by-value stack object (libpng `pngget*` clusters; defect A of `docs/progress/2026-11-09-libpng-harness-generation-bugs.md`).
- **Fix:** **open, not re-verified on libpng.** `18bc5e9` (initializer calls for struct pointers, layout probing) may cover it; re-run Phase 0 Step 4 on libpng to check before closing (O6 in [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md)).

### Symptom: `--api` Skips Cases With `pointer to an anonymous struct` (GMP `mpz_t`)
- **Cause:** `mpz_t` is `__mpz_struct[1]` with an anonymous struct, which the layout probe cannot fill. Every bignum API (RSA, DSA, ECC, PKCS#1, PSS, key parsers) is skipped and shows up as a reach gap (nettle libhogweed: 62 gaps after the header fix).
- **Fix:** write a dispatch sub-module by hand, which is the documented route for contracts the model does not know: a freely named sub-module (`libhogweed_a__mpz`) with `--scope-file` for the defining sources, `--entry-style dispatch` and one `--dispatch-case` per API family. Build the `mpz_t` values from `fuzz_buf` (`mpz_import`, `nettle_mpz_set_str_256_u`), initialise and clear everything, never `return`, and give sign/decrypt cases a fixed valid private key plus a deterministic random callback (a harness that violates the contract is rejected as harness-induced). A sub-module is checked only for its own scope, so the **unit's** harness still lists those entry points as gaps: record `harness_reach.py exempt --module <unit harness> --function <fn> --reason 'covered by sub-module <name>'` for exactly the functions the sub-module reaches, and check the sub-module's `entry_points_reached` equals its `entry_points`.

### Symptom: `validate_artifacts.py` Fails With `$.api_cases: one layout per dispatch case`
- **Cause (pipeline bug, fixed):** `api_harness.generate` drops the cases clang refuses, one probe round at a time, for at most `MAX_PROBE_ROUNDS` rounds. Clang stops after 20 errors by default, so a module with more refused cases than a few rounds can clear (nettle libhogweed: 88; `libnettle_a__sha256`: 5 more) ends with `api_cases` already filtered but `harness_<mod>.c` and `dispatch_cases` still holding a case that does not compile. The harness then fails to build, and the reach gate counted the broken case as reaching its function.
- **Fix:** `api_harness.probe_cases` lifts the error cap (`-ferror-limit=0` for clang, `-fmax-errors=0` for gcc), so one round finds every refused case, and the probe loop now runs until no case is refused (`MAX_PROBE_ROUNDS` is gone); the harness is rewritten after every drop, so the harness on disk and the sidecar always list the same cases (phase1-remediation `7b2a7ef`). If a run predates the fix, regenerate every sidecar the validator names. Expect the reach gate to report new gaps afterwards: the dropped cases never really reached their functions.

### Symptom: An `--api` Case Is Skipped With `redefinition of 'c0a0' with a different type: 'unsigned char[0]' vs 'struct AnomalyBase_T[1]'`
- **Seen on:** ptf-original run-2 (2026-11-10), `libPtfCom_a` entry `WriteAnomaly(const AnomalyDBEntry_T *AnomalyElement, char ChainId[])` (also `libXmlHandler_a__SwDownload` `FreeSwDownloadList`/`FreeSignalListType` and `ExternalInterfaces` `AddEventToList`/`FindEventInList`/`RemoveEventFromList`, which fail as `type 'X_T'` skips instead).

When the call sites give the struct argument a size, the object is an array and the path is `c0a0[0]`, so the generator wrote `static unsigned char c0a0[0]f2[N];`: a second `c0a0`. Reproduced at text level on a fixture of the `WriteAnomaly` record. `param_sizes` of 0 is not involved (the run's first explanation): a zero size gives one struct and a valid name.

Every declaration now goes through `_Case.declare()`: a name declared twice in a case, or one that is not an identifier, skips the function with `api_skipped` reason `generator defect: variable '<name>' would be declared twice in the case`, without waiting for the compile probe. Tests: `tests/test_api_harness.py`; the compile test of the fixed case is skipped without clang and passes in `framac-analysis:latest` (2026-11-11). Not run on ptf.
- **Hand-written cases with `--api` (fixed, same change):** `generate_harness.py --api --dispatch-case '<one line of C>'` appends the case after the generated ones in the same switch, with an `api_cases` layout of kind `custom` (`schemas/harness_sidecar.schema.json` `custom_case`; the seed writers make nothing for it). A later `--api` run without the flag keeps the cases, one with the flag replaces them, `--dispatch-case ''` drops them. A case that does not compile fails the generation. So a function in `api_skipped` no longer has to be exempted.
- **Open pipeline bug (the `type 'X_T'` skips, another cause):** `AddEventToList` / `FindEventInList` / `RemoveEventFromList` take a struct typedef by value, and `classify_type` (`scripts/seed_harvest.py`) rejects a typedef name passed by value; the model keeps the typedef name there. `FreeSwDownloadList` / `FreeSignalListType` were not reproduced (a pointer to a typedef plans fine; their real signatures are needed). Workaround: a hand-written `--api --dispatch-case`, else an exemption.
- **Open pipeline bug:** `scripts/benchmark.py` builds the `"generate": "api"` command without `--dispatch-case`, so a workspace regenerated from a manifest has no hand-written cases. A function covered by a hand-written case stays listed in `api_skipped` with its old reason (informational: nothing reads it as a gap).
- **Note:** a companion sub-module harness with `--scope-file` does not close the main module's gap (see the companion sub-module entry under Reach Gates below).

### Symptom: Harness Linking Fails With `undefined reference to '<internal_helper>'` (e.g. `syscall_iterate`)
- **Cause:** `scripts/api_harness.py` collected source files defining only the public entry points called by the harness case, omitting internal helper translation units (e.g. `src/syscalls.perf.c` generated by gperf or auxiliary module sources) required by those API functions.

### Symptom: A Dispatch Harness's Corpus Fills With Inputs That Run No Case (Empty Inputs, Selectors of Skipped Cases, Oversized Inputs)
- **Seen on:** H3 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), read from `templates/harness_dual.c.template` and `generate_harness._build_dispatch_invocation` (2026-11-10); not measured on a target run.
- **Cause:** `LLVMFuzzerTestOneInput` returned 0 for every input, also one longer than `MAX_INPUT_SIZE`, one without a selector byte, and one whose case a keep-going round skips (`-DFRAMAC_FUZZ_SKIP_CASES`). - **Fix (fixed, H3):** the template returns `-1` for those inputs, which libFuzzer never adds to the corpus. Checked in `framac-analysis:latest` (Debian clang 19.1.7): a harness that rejects all but one prefix keeps only inputs with it. In `eva_main` the macro is empty. ### Symptom: An `--api` Harness Never Finds a Use After Free, Double Free or Call After Error on an Opaque Handle
- **Seen on:** H2 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), from `scripts/api_harness.py` (2026-11-10).
- **Cause:** each single case builds a fresh handle, makes one call and releases it, so no input makes two calls on one handle. Sequence cases came only from recorded traces, and those pass a shared handle as a zeroed buffer (`sequence_case` shares buffers by address; the constructor's result is not recorded), or do not compile at all for a pointer to an incomplete struct (`sizeof(struct ctx)`).
- **Fix (fixed, H2):** `api_harness.lifecycle_case` adds one case per handle type with a constructor and a destructor: build the handle, then while the input lasts up to `LIFECYCLE_MAX_CALLS` (8) calls, each picked by one input byte among the functions taking exactly one handle of the type (`methods`, not its constructor or destructors), then release it. The sidecar layout is `kind: lifecycle`; its slots are the constructor's, so seeds start from the constructor's recorded arguments. Lifecycle cases share `MAX_SEQUENCE_CASES` (16) with the recorded chains, which come first. `tests/test_api_harness_lifecycle.py` fuzzes a library whose `reset` frees a buffer the other calls still use: ASan finds the use after free with the lifecycle case and not with the single cases, and Eva runs on the same harness.
- **Still open:** a recorded chain over a handle still passes a zeroed buffer (**open pipeline bug**, `sequence_case`): it needs the constructor's result threaded through the chain. A lifecycle case whose method changes the fuzzing process (`seccomp_load`, see the next entry) hangs the campaign like the single case; skip it by hand. If one method does not compile, the compile probe drops the whole lifecycle case, and no `api_skipped` entry says so. Eva cost on a target is not measured: on libseccomp the constructor never returns a handle in Eva (gap D of [`./eva.md`](./eva.md)), so the loop is dead there.

### Symptom: An `--api` Harness Campaign Hangs Without an Artifact, or Stops Early on `leak-*` / `bad-free` in `LLVMFuzzerTestOneInput`
- **Seen on:** libseccomp (`libseccomp_a`), the regenerated `--api` harness built with `-fsanitize=fuzzer,address` in `framac-analysis:latest`, 2026-11-10. Each run below stopped at its first artifact after 18 to 118 executions, so the handle cases were fuzzed only that briefly; none of the artifacts came from them.
- **Cause A (hang, new with constructed handles):** `seccomp_load` on a real handle installs a seccomp filter in the fuzzer process. With the default action 0 (`SCMP_ACT_KILL`), which is what a short input gives, the fuzzing thread is killed at its next system call and the process stays alive: the two-byte input `{13, 0}` was still running after 20 s with `-timeout=10`, and a 45 s campaign ran 46 minutes until it was stopped. LibFuzzer writes no artifact, so the crashed-case skip never sees the case. Before handles were constructed the zeroed buffer made `seccomp_load` return `-EINVAL`. **Open pipeline gap:** the generator cannot know that an API call changes the process it runs in. Skip such a case by hand (`-DFRAMAC_FUZZ_SKIP_CASES=<mask>`), or exempt the function and cover it with a `custom` case.
- **Cause B (false `leak-*`, older than the handle change):** the case discards an allocation the API hands to its caller: the string `seccomp_syscall_resolve_num_arch` returns (`strdup`), and the two objects `seccomp_notify_alloc` stores through its output parameters. The constructor's own case leaked the same way (`(void)seccomp_init(c0a0);`); that one is **fixed** with the handle change (`scripts/api_harness.py` releases a returned handle, commit 150b092). **Open pipeline bug** for the other two: the model does not say who owns a returned pointer.
- **Cause C (false `bad-free`, older than the handle change):** `seccomp_notify_free(&c0a0, &c0a1)` is called on two stack objects, since the harness gives every struct pointer one local object; Eva reports the same call as Invalid (`api.c:689 precondition of free`). **Open pipeline bug:** a function named like a destructor needs an object its allocator made.

### Symptom: Functions Named `Initialize`, `Freeze`, or `Destroyer` Falsely Selected as API Constructors/Destructors
- **Cause:** `_INIT_NAME_RE` and `_DTOR_NAME_RE` in `scripts/api_harness.py` matched bare `Init` and `Free|Destroy|Release` as unbounded substrings.
- **Fix (fixed, uncommitted, `scripts/api_harness.py`):** Bound CamelCase/PascalCase matches to C identifier word boundaries `(?:^|(?<=[a-z0-9_]))` and `(?=[A-Z0-9_]|$)`.

### Symptom: Multi-Dimensional and Array-Pointer Parameters Generate Broken Harness C Code
- **Cause:** `_PARAM_DECL_RE` in `scripts/generate_harness.py` allowed at most one array dimension bracket pair, corrupting parameter names and declarations for multi-dimensional arrays (`int matrix[3][4]`) and array pointers (`int (*ptr)[10]`).
- **Fix (fixed, uncommitted, `scripts/generate_harness.py`):** Allowed multiple bracket pairs in `_PARAM_DECL_RE`, added `_ARRAY_PTR_PARAM_RE`, decayed array parameters to pointers according to C99 rules, and added `_format_c_decl` helper for variable formatting.

### Symptom: String Literals Containing `main(...) {` Falsely Trigger `-Dmain` Redefinition
- **Cause:** `_source_defines_main` in `scripts/pipeline_make.py` and `scripts/generate_harness.py` scanned source files with a regex without masking string literals or checking build capture symbols.
- **Fix (fixed, uncommitted, `scripts/pipeline_make.py`, `scripts/generate_harness.py`):** Checked `defined_functions` from `build_capture.json` when available, and masked comments and string literals with `mask_comments_and_literals`.

### Symptom: Harness Dispatch Counting and Seed Binding Depend on Re-Parsing C Code

## Reach Gates, Coverage & `build-check`

### Symptom: The Reach Gate Fails (`harness_reach.py check` Exit 1, or `make` Stops at `reach-gate`)
- **Cause:** a harness does not reach one of its module's API entry points, a Tier 1A/1B/2 module has no harness (`no_harness`), or a harness changed after the check ran (its digest no longer matches `phase0_gates.json`).
- **Fix:** add a `--dispatch-case` per unreached entry point and rerun `check`, or record a reason with `harness_reach.py exempt` (`/framac-slice` Step 4b). A sub-module is checked only against the unit's entry points in its own scope; entry points no harness's scope holds are reported as the unit's gaps.

### Symptom: A Companion Sub-Module Harness (`--scope-file`) Does Not Close Another Harness Module's Reach Gap
- **Seen on:** ptf-original run-2 (2026-11-10): `ExternalInterfaces__Logger` (dispatch case for the by-value `EventEntry_T` helpers) left the main `ExternalInterfaces` module failing on the same three functions, and itself failed on every other `Logger.c` entry point.
- **Cause:** not a defect, but easy to misread: `harness_reach.py check` tests **each module against the entry points in its own scope**. The main module's scope also holds `Logger.c`, so it must reach those functions itself; the companion only adds obligations for its own scope. Coverage does not aggregate across a unit's harness modules for gate purposes.
- **Fix:** exempt the unreachable entry points on the module whose scope holds them, with a recorded reason; do not add companion harnesses to close another module's gaps.

### Symptom: The Static Reach Gate Passes for an Entry Point the Harness Never Calls
- **Seen:** 2026-11-11, regex audit (no target run). `harness_reach.harness_roots` returned `stat`, `hash` and `rec_next` for a harness holding `struct stat st;`, `int hash = 0;` and the string `"rec_next failed"`.
- **Cause:** every identifier of the harness text outside comments counted as a root: variable and member names, string contents, code under `#if 0`, and bare prototypes. The `dynamic` gate caught such an entry point later, the static gate did not.
- **Fix (fixed 2026-11-11, uncommitted, `scripts/harness_reach.py` `_used_identifiers`):** the harness is tokenized (`acsl_ast.tokenize_c_acsl`); literals, `#if 0` bodies, members, tags, declared names and file-scope prototypes are not roots. A function used as a value (`cb = on_msg;`, `register_cb(on_msg)`) and the body of a harness-local `#define` still count. Text the tokenizer rejects falls back to the old rule. **Behaviour change:** a harness that passed only through such a name now fails `reach-gate`; add the call or an exemption. Not run on a target. Tests: `tests/test_regex_hardening.py`.

### Symptom: Harness Root Extraction Dependent on Tokenizer Heuristics Instead of Clang AST
- **Cause:** `scripts/harness_reach.py` only used token heuristic filtering in `_used_identifiers`, which can misidentify non-callee identifier tokens or miss complex call contexts.
- **Fix (fixed, uncommitted, `scripts/harness_reach.py`):** Implemented `_callees_from_clang_ast` and `_callees_from_clang` to extract callees from Clang JSON AST when Clang is available, falling back to `_used_identifiers`.

### Symptom: `dynamic: entry points never executed by the corpus` in `phase0_gates.json`
- **Cause:** after `coverage-<mod>`, `reach-dynamic-<mod>` found an entry point the gate holds the module to that no input executed. Fuzz and Eva of that module stop at the gate until it is fixed.
- **Fix:** read `executions: 0` in `workspace/reports/coverage/<mod>.json`. If the harness never calls the function, add a case. If it does, the corpus is stuck behind an input check: try, in order, recorded seeds, a dictionary (`params set --fuzz-dict`), a larger budget (`params set --fuzz-budget`), and a dispatch case that calls the function directly. The gap stays while the harness is unchanged.
- **Exemptions:** exempt only an entry point that cannot be driven from bytes (a live socket, a real file descriptor, process-global state). "30 s of fuzzing did not get deep enough" is not a reason: try the steps above first, and exempt only what still cannot be driven.
- **After a repair:** rerun the reach gate (`pipeline_make.py run reach-gate`) before rerunning the module; after an exemption this is not needed (`harness_reach.py exempt` re-checks the gate, see the next entry). `build-<mod>` and `fuzz-<mod>` refuse a harness whose digest changed since the gate ran. A whole-run `reach-gate` exits 1 while another module still has a gap, but it still records this module's row.
- **No row for the module:** a module whose coverage could not be measured (coverage status `no_inputs`, `compile_error` or `coverage_error`, or no coverage report) gets no row. It is listed with its reason under `unmeasured` in `workspace/reports/harness_reach_dynamic.json`; `harness_reach.py dynamic` exits 2 and `reach-dynamic-<mod>` fails, but the gate is not reopened: fuzzing and Eva of the module continue. The usual cause is that every input crashes, so the corpus stays empty (qlz: a misaligned store at `quicklz.c:161`). Then the crash is the finding: verify it. There is nothing to repair in the harness, and the module's reach stays unmeasured; do not exempt entry points for it. Seen again on ptf-original run-2 (2026-11-10): `PtfHandler` (`no_inputs`, its one crash artifact is the finding) and `libXmlHandler_a__ClkInternComparData` / `__NetworkParam_3` (`coverage_error: no input replayed to completion`, every corpus input crashes or times out in the coverage replay).

### Symptom: After Exempting Dynamic-Reach Gaps, Every `coverage-<mod>` Still Fails With `reach gate failed ... dynamic: entry points never executed by the corpus`
- **Seen on:** ptf-original run-2 (2026-11-10): after exempting ~300 dynamic gaps, `pipeline_make.py run coverage reach-dynamic` still failed every affected `coverage-<mod>` at the `$(GATE) --module <mod> --need reach` check, and `harness_reach_dynamic.json` kept showing the same gaps although the sidecars held the exemptions.
- **Cause (two effects compounding):**
  1. `phase0_gates.py check --need reach` reads the **recorded** dynamic rows in `phase0_gates.json`, not a fresh computation. The rows were recorded when the gaps were found; exempting functions does not re-record them.
  2. The make target that re-records them, `reach-dynamic-%`, depends on `coverage-%`, which the stale gate now blocks — a circular block. `make -j` also leaves **stale rows** in `harness_reach_dynamic.json` for modules whose `reach-dynamic-%` never ran (the report merges per-module rows across invocations), so the file can show gaps that are already exempted.
  A second trap: the corpus evolves between coverage measures, so a later measure can list a **new** never-executed entry point that the exemption batch did not cover (run-2: `dateAndtime`, then `WriteOptionalNodes`, each appearing one measure later).
- **Workaround used on run-2:** `harness_reach.py dynamic --module <mod>` run directly (not through Make) for every affected module, then `pipeline_make.py run coverage reach-dynamic` again. The documented step, `pipeline_make.py run reach-gate` after the exemptions, was skipped; it re-records every row and would have unblocked the run in one command.
- **Fixed pipeline bug (2026-11-10, uncommitted; `scripts/harness_reach.py`, `scripts/phase0_gates.py`):**
  1. `harness_reach.py exempt` re-records the gate rows the exemption can change (`regate_after_exempt`: the module, its unit and sub-modules, and every row the gate holds as failed) and prints the result under `gate` (`rechecked`, `still_failing`). No `reach-gate` run is needed after an exemption, so the circular block cannot form. `--function` can be repeated. Before the gate's first run nothing is recorded (`note`).
  2. The gate's message ends with the next step: `reach gate failed for <mod>: ...; repair the harness and run python3 $S/harness_reach.py check again, or record why with python3 $S/harness_reach.py exempt --module <mod> --function <fn> --reason <why> (which re-checks the gate)`.
  3. Found while testing 1: the sidecar is part of the harness digest, so **one** exemption made the next reach check treat the harness as repaired and drop **every** dynamic gap of the module, also those not exempted (`apply_dynamic`). The gaps came back only with the next coverage measure, which may be part of run-2's "second trap". The dynamic rows now record a digest without `reach_exempt` and `warnings` (`phase0_gates.harness_digest(..., ignore_exempt=True)`); a row written before the change still matches while its sidecar is unchanged.
  Tests: `tests/test_harness_reach.py` (`test_exempting_a_dynamic_gap_reopens_the_gate_without_a_reach_gate_run` and the three after it).
- **Still open:** `exempt` does not refresh the module's row in `harness_reach_dynamic.json`, so the report keeps listing an exempted gap until the next `reach-dynamic-<mod>`; the gate ignores it. `benchmark.py` and `benchmark_seeded.py` call `record_exempt` directly and run the reach check afterwards themselves.

### Symptom: A variadic parser primitive's dangerous branch (`minmea_scan` `'s'` specifier, CVE-2026-29974) is never reached by any phase, though the function runs thousands of times

- **Seen on:** minmea run-1, 2026-11-14. CVE-2026-29974 (an unbounded copy by the `'s'` format specifier of `minmea_scan`, `minmea.c:236`) is public and unfixed on `master` (`c43c9e7`); no phase of run-1 raised it. Reproduced by hand under ASan on `framac-analysis:latest`: a 47-byte sentence with `minmea_scan(s, "ts", &type, buf)` and an 8-byte `buf` gives `AddressSanitizer: stack-buffer-overflow ... WRITE of size 1 ... minmea_scan /src/minmea.c:236`.
- **Cause (one root, three phases):** `minmea_scan` is variadic; the `'s'` handler copies a field into a caller buffer with no length check, and that branch is selected only by an `'s'` in the runtime format string. All 11 `minmea_scan` call sites inside `minmea.c` use formats built from `t T f d i c _ ;` and never `'s'`, so no `minmea_parse_*` wrapper reaches the `'s'` write. The target's own test suite does reach it: `tests.c` calls `minmea_scan` with `'s'` six times (`test_minmea_scan_s`, lines 270-285, and the `tTfdfdfcfcfcs` call at line 415), always into `char value[MINMEA_MAX_SENTENCE_LENGTH]` (80 bytes). Seed harvest recorded all six calls (`workspace/seed_records/calls.jsonl`, 63 `minmea_scan` records; decoded formats include `s` x2, `_;s` x3, `tTfdfdfcfcfcs` x1). The format, the vararg kinds and the buffer size the maintainers use were all in the run, and nothing used them.
  1. **Harness.** Phase 0 lists `minmea_scan` as a `candidate_entry_point` (correct). Run-1's harness is a hand-written `custom` `call_expr` (`workspace/harnesses/harness_minmea.json`); it calls the typed `minmea_parse_*` wrappers and never `minmea_scan` itself, so the primitive ran only with the parsers' own safe formats. The `--api` generator would not have done better: it has no case kind that calls a variadic function with a fixed format and call-site-sized vararg objects, and, worse, it does not even recognise `minmea_scan` as variadic (see the entry "Seed Recorder Segfaults in Tests That Call a Variadic API Function" below), so it would have built an unsound case that fuzzes the format string.
  2. **Open pipeline bug: the static reach gate counts a function it never calls directly as reached.** `workspace/reports/harness_reach.json` shows `entry_points: 17`, `entry_points_reached: 17`, `gaps: []`, `exempt: {}`, while `roots` lists 16 functions and not `minmea_scan`: [`../../scripts/harness_reach.py`](../../scripts/harness_reach.py) `check_module` counts every transitive callee of a root as reached, and never reads the sidecar's `api_skipped`. The `api_harness.py` module docstring says a skipped function goes to `api_skipped` and "the reach gate then reports them as gaps". That is false whenever another case reaches the skipped function transitively. So no gap was raised and no exemption was asked for. **Fixed** on branch `fix/reach-gate-direct-call` (`e235851`, `1bab71c`, `9443951`), merged into `phase1-remediation` on 2026-11-16 (`fd139c4`): an entry point counts only when the harness calls it itself (a root, a macro alias, or behind header `static inline` wrappers of a root); the others are gaps, and the row's `reached_only_through` names the roots that lead to each. A harness with `entry_style: argv` keeps the transitive reach, because the DAG lists a program's helpers as entry points while `main` is the real one (the first version raised 23 false gaps on nettle run-3 `sexp_conv`, `base16dec`, `nettle_hash`). The `argv` rule was broken inside the container until `ebb0629`: see "The Reach Gate Fails an `argv` Harness With `roots: []`" below. Measured on copies of 14 past runs (token scan, no clang on the host): 146 new gaps, four gates go from pass to fail (minmea run-1 with `minmea_scan` alone, nettle run-3 with 79, QCBOR run-4 and run-5 with one each). 129 of them are entry points in a generated harness's `api_skipped` and 17 are in hand-written harnesses. ## Seed Recording & Imported Corpora (`seed_harvest.py`, `fuzz_assets.py`)

### Symptom: No Seeds, or a Harness Case Without Seeds
- **Cause:** the recipe has no test command; the tests call the API through header `static inline` functions or nested library calls, which the `-Wl,--wrap` recorders do not see; or the harness's case layout (overlapping slots, structs deeper than one `{ptr, len}` level) cannot be filled.
- **Fix:** read `workspace/reports/seed_harvest.json` and `workspace/reports/seeds/<mod>.json`. Seeds are an improvement, never a requirement: the campaign runs from its own corpus without them.
- **Seen on ptf-original run-2 (2026-11-10):** with no test command, `seed_harvest.py record` ran the unit's non-test executables once each and got `no_calls_recorded` — the daemons exit immediately without their mounted configuration (`PtfHandler` logs `unable to open configuration file` and exits 0; `ExternalInterfaces` segfaults with no arguments, kept as a warning). Expected behaviour, not a defect; the run compensated with the target's own `SupportFiles/` imported as an external corpus (`inputs/corpora/`, `fuzz_assets.py map --function ...`).

### Symptom: `seed_harvest.py record` Returns `no_test_units` Although the Recipe Has a Test Command
- **Cause:** only executables the name rule calls tests were relinked with recorders. libpng's `ctest` runs `pngtest`, `pngvalid`, `pngstest`, ..., none of which the rule recognizes (libpng `a70313dbb`, run-3; `docs/progress/2026-11-09-libpng-harness-generation-bugs.md`, defect D).
- **Fix:** **fixed** in `scripts/seed_harvest.py` (`record`): with a test command every executable is relinked and the test command decides which ones run; `test_units` still lists the ones named as tests, and `executables` lists all of them.

### Symptom: Seed Recording Records 0 Calls With a `make check` Test Command
- **Cause:** `seed_harvest.py record` relinks only the units it classifies as test executables (nettle: just `testsuite/sha1-huge-test`); a suite of many separate test programs built by `make check` is not instrumented, and header `static inline` calls are never recorded.
- **Fix:** the relink part is **fixed** (phase1-remediation `7b2a7ef`, `seed_harvest.py record`): with a test command every executable is relinked and the test command decides which ones run. Programs that `make check` builds only during the test run are not units of the capture, so they are presumably still not relinked (not re-verified on nettle; O6 in [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md)); header `static inline` calls are never recorded. Seeds stay optional (see "No Seeds" above): fuzzing starts from its own corpus.

### Symptom: Seed Recording Records Only a Handful of Calls (mpack: 3 Calls) Although the Test Suite Runs Thousands of API Calls
- **Seen on:** mpack run-3 (2026-11-17). The test command `python3 test/unit/configure.py && ninja -f .build/unit/build.ninja more` ran the whole unit suite, but `seed_harvest.json` recorded 3 calls.
- **Cause:** the recorder's `fc_depth` counter was not longjmp-safe. mpack's unit tests longjmp out of a wrapped API call: the test framework's assert handler leaves through an expected `mpack_assert` failure. When a test longjmps out of a wrapped call, that wrapper's `fc_leave` never runs, so `fc_depth` stays above 0 for the rest of the process. From then on, every later call counts as nested and is not recorded.
- **Fix:** **fixed** in `84f76b6`, merged into `phase1-remediation` live during mpack run-3, in `scripts/seed_harvest.py` (`RECORDER_RUNTIME`, `wrapper_source`):
  - Each wrapper writes a unique token into its own frame.
  - The runtime keeps a per-thread stack of live wrappers (`FC_STACK` 256).
  - On entry, it drops every entry whose frame is not strictly above the current one, or whose token was overwritten.
  - A call is outermost when the stack is empty.
  - Test: `tests/test_seed_harvest_longjmp.py::test_recorder_records_outermost_calls_after_a_longjmp`, gcc and clang, Linux only, skipped on Windows.
  - On real mpack the recording went from 3 calls to 55,714 (9,641 unique), covering 189 of 342 functions. The rest are `MPACK_INLINE` header functions, which the recorder cannot wrap.
  - A run that recorded before the fix must rerun `seed_harvest.py record`, then regenerate its `--api` harnesses so the seeds bind to cases.

### Symptom: An `--api` Campaign Stops With `Too many open files: /framac-run/workspace/corpus/<mod>; exiting`
- **Seen on:** mpack run-3, Phase 1, 2026-11-17. `workspace/reports/fuzz/libmpack_a__mpack_writer_3.json` has status `fuzzer_error` and returncode 1 after about 64k executions. `libmpack_a__mpack_reader` shows the same message.
- **Cause:** pipeline defect in `scripts/api_harness.py`.
  - In `harness_libmpack_a__mpack_writer_3.c`, `case 7U` called `mpack_writer_init_filename(&c0a0, (char *)c0a1)` with the rest of the input as the path, and never called `mpack_writer_destroy`.
  - Every execution created or truncated a file the fuzzer named, and leaked its `FILE *`, until `RLIMIT_NOFILE` 1024 (`sandbox_exec.Limits.open_files`) was exhausted.
  - `mpack_reader_init_filename`, `mpack_tree_init_filename` and the `*_init_file` aliases had the same shape.
  - `sandbox_exec` has no filesystem isolation. The campaign's working directory is `/tmp/fuzz_scratch_*` in the container, but the coverage, replay, minimize and guardrail scratch directories sit under the run directory, and absolute or `../` names reach `/framac-run`. No stray file was found in run-3.
- **Fixed:** `7dc1be4` from `sup/mpack-harness-sources-and-fd-leak`, merged into `phase1-remediation` on 2026-11-17 (merge `7cb53a7`).
  - `api_harness.path_parameter` matches a byte-string parameter named like a path (`filename`, `file_name`, `fname`, `path`, `pathname`, `filePath`, `dirname`). Such a function goes to `api_skipped` with the reason "takes a file-system path ..." and is never chosen as an initializer or constructor. The match is on the name only, so a non-file `path` string is skipped too and stays a visible reach gap.
  - `struct_destructors` finds, per struct type, the unit's destructor, which may be outside the module's scope. An initializer's object is then released after the call; a destructor's own case and opaque handles are released only once.
  - On run-3's inputs, only the six `*_init_file*` functions become skipped, and `mpack_writer_destroy` and `mpack_tree_destroy` releases are added.
  - Fixture: 571 files and an exhausted fd table before the fix, 0 files and 3 fds after.
  - Tests are in `tests/test_api_harness_file_paths.py`.
- **Still open:**
  - The skipped functions are reach gaps: exempt them, or write a `custom` case on a fixed scratch file.
  - Struct objects shared in sequence cases are still not released, which matters under LeakSanitizer.
  - Regenerating the harness renumbers the selectors, so the module's existing corpus becomes stale.

### Symptom: A Module's Fuzz Campaign Starts From an Empty Corpus Although the Target Has Tests or Shipped Corpora, and No Log Says Why
- **Cause:** in `templates/pipeline.mk`, the `seeds` recipe and the two seed lines of `fuzz-%` (`seed_harvest.py write`, `fuzz_assets.py write`) start with `-`, and the `seeds` loop ends in `|| true`. Seeds are optional, so the recipes are non-blocking on purpose, but a failed write was invisible. Both writes stopped at the first exception with a traceback and exit 1, after deleting the module's old inputs, so `workspace/seeds/<mod>/` or `workspace/imported_corpus/<mod>/` could hold part of the new inputs while their per-module reports kept their old content. `fuzz_assets.py write` also raised on a malformed `workspace/reports/fuzz_assets.json`; `seed_harvest.py write` silently skipped a requested module with no sidecar. The fuzz report said nothing about seeds.
- **Fix (fixed, K1 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), commit 93446b9):** `scripts/seed_harvest.py` and `scripts/fuzz_assets.py` `write` record each module's outcome (`ok`, `skipped` with a reason, `failed` with the exception) in `workspace/reports/seed_status/<writer>/<mod>.json`. An exception fails only that module, and the write exits 1; the Make lines keep `-`, so a seed failure never fails the target. `scripts/run_eacsl_fuzz.py campaign` copies both statuses into `workspace/reports/fuzz/<mod>.json` as `seeds: {status, reason, writers}`; a writer that recorded no status while the campaign reads `--extra-corpus` counts as `failed`. Read `seeds.status` before tuning a module whose corpus is empty. A status file left over from an older run is shown as is, with its `generated_at`.

### Symptom: A Generated `--api` Case Passes an Arbitrary Input Byte as an Enumerated Argument (`QCBORDecode_Private_GetArrayOrMap(..., uType = 2, ...)`) and Produces a Harness-Shaped Witness
- **Seen on:** QCBOR, run-6, 2026-11-15, candidate `src/qcbor_main_decode.c#QCBORDecode_Private_GetArrayOrMap::initialization::b1b1b1fe2a`, dispatch case 30.
- **Cause:** `api_harness.py` treats a scalar or enum parameter as free input. Every legitimate caller of `QCBORDecode_Private_GetArrayOrMap` passes `QCBOR_TYPE_ARRAY` or `QCBOR_TYPE_MAP` (`inc/qcbor/qcbor_spiffy_decode.h` `QCBORDecode_GetArray`/`GetMap`, `src/qcbor_spiffy_decode.c` `PreSearchAndGetArrayOrMap`), but the recorded witness set the byte to `QCBOR_TYPE_INT64` on `0x00`, so the type check took a path no caller can take. The sink was a real defect (an empty definite-length aggregate leaves `End.uEndOffset` uninitialized), yet the verifier had to build contract-valid witnesses. A related gap: public `static inline` wrappers (`QCBORDecode_GetArray`, `QCBORDecode_GetMap`) get no case of their own, so the legitimate public path was reachable only by mutating the type byte.
- **Fix:** **Open pipeline gap.** Suggested: infer a constrained value set for a scalar/enum parameter from the model's call sites (all callers of the function pass one of two enum constants) and generate one case per value; emit a case per public inline wrapper so the documented path exists. Workaround in run-6: the verifier built its own witnesses with the documented constants and listed them in `record.reproducers`, which `ingest-verifier` replays.

### Symptom: A Crash Artifact No Longer Reproduces After the Harness Gains a Dispatch Case (`not_reproduced`, although the target defect is real)
- **Seen on:** QCBOR, run-6, 2026-11-15. Candidate `src/UsefulBuf.c#UsefulOutBuf_Compare::e_acsl_rte::0e34c586b3` (crash captured with a 181-case harness) replayed as `not_reproduced` after the harness was regenerated with one extra `--dispatch-case` (182 cases): the artifact's selector byte 191 met `191 % 181 = 10` at capture time and `191 % 182 = 9` afterwards, so it drove a different case and never called `UsefulOutBuf_Compare`. The same shift explains the earlier execution dropout of `case 74` after repair case `181` was appended during the `reach-dynamic` repair. Verifier `verify-usefuloutbuf_compare_b939358da2-4` also hit it. (Two entries recorded this bug, one by the run agent and one by the first supervisor. They were merged here.)
- **Cause:** `generate_harness.py` selects the dispatch case as `fuzz_buf[0] % <case count>` ([`../../templates/harness_dual.c.template`](../../templates/harness_dual.c.template)). Adding a case appends it at the end, but the count changes, so every artifact whose selector byte is at or above the old count (and every seed) silently addresses another case. The harness sidecar records the cases but not the count the corpus was captured under, and the campaign report does not record it either, so nothing detects the mismatch.
- **Fix:** **Open pipeline gap.** Suggested: decode a fixed-width selector (`uint8_t` up to 256 cases, `uint16_t` above) and reject out-of-range values (`if (sel >= N) return 0;`) instead of `sel % N`, so that appended cases never remap old inputs; or record the case count (and a harness digest) in `workspace/reports/fuzz/<mod>.json` and refuse or flag a replay whose digest differs; or map the selector to a stable case id (a per-case key written into the artifact at capture time); or require a re-run of `fuzz-<mod>` after any harness regeneration and say so in `wp_scheduler.py`'s repair actions. Workaround used in run-6: after the harness repair, the module's campaign was re-run on the repaired harness (`run build fuzz coverage reach-dynamic ingest`), so the corpus and the artifacts in `workspace/reports/fuzz/libqcbor_a.json` address the current 182-case harness; verifiers of the older artifacts rebuilt witnesses from the harness source and listed them in `record.reproducers`, which `ingest-verifier` replays.
- **Status (2026-11-17): fixed** in `45c7a5f` (2026-11-15), [`../../scripts/generate_harness.py`](../../scripts/generate_harness.py) `_build_dispatch_invocation`. The first byte is the case index (`dispatch selector: identity`), and a byte at or above the case count runs no case, so an appended case no longer remaps stored inputs. The sidecar records `dispatch_selector`; a harness without it is still decoded modulo its case count. Tests: `tests/test_dispatch_selector.py`.

### Symptom: `--api` Dispatch Cases Pass a NULL Callback or an Unterminated Input Array to Helpers That Require One, and Every Crash There Is Rejected as `harness_induced`
- **Seen on:**
  - QCBOR, run-5 (rejections #27, #28 in [`../runs/2026-11-09-qcbor-run5-assessment.md`](../runs/2026-11-09-qcbor-run5-assessment.md)).
  - QCBOR, run-6, 2026-11-15, external supervisor. Dispatch case `166` produced three crash candidates that the Crash Verifiers all rejected as harness-induced (03:49–03:51):
    - `QCBORDecode_Private_ProcessTagItem::mem_access::5b85e2af5a`: "passes a NULL `QCBORTagContentCallBack` and triggers the `(*pfCB)` call at `qcbor_tag_decode.c:485`".
    - `QCBORDecode_Private_CheckItemType::mem_access::c8bb6202f9` (stack-buffer-overflow) and `::5963747e94` (E-ACSL `\initialized`): the case "passes 6 raw fuzz bytes as the `QCBOR_TYPE_NONE`-terminated type table".
- **Cause:** **Open pipeline gap.** [`../../scripts/api_harness.py`](../../scripts/api_harness.py) passes NULL for every function-pointer parameter (module docstring, rule "a function pointer: NULL"). It builds a pointer to a scalar array from input bytes with no terminator, so a helper that walks to a sentinel runs off the end. These semi-private `*_Private_*` helpers are declared in public headers, so they count as API entry points. Each run then spends fuzz time, crash candidates, verifier subagents and harness-repair budget on crashes that can never be target bugs. In run-5 and run-6 this recurred on the same functions.
- **Fix:** none yet. Suggested:
  - For a function-pointer parameter, generate a no-op stub of the exact signature (return 0 or the zero value) instead of NULL. NULL only when the callee's own code checks it.

  - The module was later split into the freely named `libcares_a__dnsrec`, where 46 of 62 were skipped. The run's agent wrote grouped `--dispatch-case` cases instead.
- **Cause:** c-ares's public headers only declare its handle structs (`typedef struct ares_dns_record ares_dns_record_t;`).
  - Its constructors write the handle through an out-parameter and return a status: `ares_dns_record_create(ares_dns_record_t **, ...)`, `ares_init(ares_channel_t **)`, `ares_dns_parse(buf, len, flags, ares_dns_record_t **)`.
  - A child handle that the record owns is built the same way: `ares_dns_record_rr_add(ares_dns_rr_t **, ares_dns_record_t *, ...)`.
  - [`../../scripts/api_harness.py`](../../scripts/api_harness.py) `handle_functions` knew only constructors that return the handle, and `handle_prototypes` did not see `H **` parameters.
  - A handle parameter with no known constructor fell through to the generic pointer rule, which declares `struct ares_dns_record c0a0;`. That does not compile.
  - `initializers()` also took a `struct tag **` first parameter for an initializer of `struct tag *`, so a parser's case called the creator first and leaked the record.
- **Fix:** commit `2424b9b`, from branch `sup/c-ares-api-outparam-ctor`, fixed and merged into `phase1-remediation` (2026-11-16).
  - **Seeing out-parameters:** `handle_prototypes` records `outs`, the `H **` parameters.
  - **Choosing a constructor:** `outparam_constructors` picks one out-parameter constructor for each handle type that has no returning constructor. It looks at traces first, then prefers a constructor with no parent handle, then the plainest name, then the fewest parameters.
  - **Generated case:** the case declares `H *h = 0` and passes `&h`. It runs the call under test only when `h` is not NULL, then releases `h` with the destructor.
  - **Child handles:** a child handle with no destructor is added to a parent that is built first, and the parent is released.
  - **Other cases:** a constructor's own case releases what it wrote, and lifecycle cases use these constructors too.
  - **Skips instead of uncompilable code:** a pointer to a header-only struct is never declared as an object. When there is no constructor, no destructor, or two such handles in one call, the function goes to `api_skipped` with a reason such as `no constructor for opaque handle struct X *`. A call with two handles of the same struct was emitted before and failed the compile probe; it is now skipped.
  - On a copy of run-1's inputs, `libcares_a__dnsrec` went from 16 entry points with a case and 46 skipped to 59 with a case and 3 skipped, plus one lifecycle case. Those cases passed the compile probe; only the fixture was fuzzed (ASan/UBSan/LSan, 200k runs, clean).
  - Tests: `tests/test_api_harness_outparam.py` (10 tests). `tests/test_api_harness_lifecycle.py::test_plan_adds_one_lifecycle_case_per_uncovered_handle_type` was updated for the new same-struct skip.
- **Workaround on an older checkout without the fix:** hand-written `--dispatch-case` cases that build the handle through its constructor.
- **Still open:** a non-constructor that writes a buffer behind `**` (`ares_dns_write(rec, unsigned char **buf, size_t *len)`) is now called, and its output is never freed. That leak is made by the harness and matters only under LeakSanitizer.

### Symptom: `--api` Skips `ares_dns_class_fromstr` With `pointer to an anonymous struct`
- **Seen on:** c-ares run-1, 2026-11-16, `libcares_a__dnsrec`. After the out-parameter constructor fix, `ares_dns_class_fromstr`, `ares_dns_rec_type_fromstr` and `ares_dns_record_query_get` are still in `api_skipped`.
- **Cause:** the parameter is a pointer to an anonymous enum typedef: `ares_dns_class_t *`, which the model shows as `enum __anonenum_ares_dns_class_t_7 *` (a Frama-C tag that no header defines).
  - `_spell_params` in [`../../scripts/api_harness.py`](../../scripts/api_harness.py) rejected any pointer whose pointee contains `__anon`, and its reason said "anonymous struct" even for an enum.
- **Fix:** fixed and merged into `phase1-remediation` (2026-11-16), from branch `sup/c-ares-api-anon-enum` (`1a7799f`). Verified by the supervisor: `test_api_harness_anon_enum.py` and `test_api_harness_outparam.py` gave 15 passed, 2 skipped; the fixer also ran the Docker test, 7 of 7 passed.
  - The layout probe records each parameter that points to an enum through a typedef name, as the declaration writes it (`enum_pointer_spellings`, carried as `Declared.enum_pointers` into `ApiInfo.enum_ptrs`).
  - `_bind_call` declares the object and casts it through that typedef (`ares_dns_class_t c0a0[1]`, `(ares_dns_class_t *)c0a0`).
  - With no typedef name, the function stays skipped, with `pointer to an anonymous enum <tag>: ...`. There is no `int` stand-in, because an enum's size need not be `int`'s, and a write through it could become an overflow made by the harness.
  - Pointers to anonymous structs keep their reason. A pointer to an anonymous union now says union.
  - On a copy of run-1's inputs, dnsrec goes from 59 entry points with a case and 3 skipped to 62 with none skipped. `ares_dns_record_query_get` binds all five arguments and joins the record's lifecycle case.
  - Tests: `tests/test_api_harness_anon_enum.py`, including a Docker test that takes the AST from real clang, compiles and fuzzes 100k runs under ASan and UBSan.
- **Workaround on an older checkout without the fix:** the run's hand-written `--dispatch-case` (`record_case_1` in `run-1/gen_harnesses.py`). It can be dropped once the run's scripts have the fix.
- **Related pipeline bug (nested `const` dropped):** fixed and merged into `phase1-remediation` (2026-11-16), from branch `sup/c-ares-api-nested-const` (`95cab11`, `1265378`). Verified by the supervisor: the three `test_api_harness_*` files gave 22 passed, 3 skipped; the fixer ran the Docker tests, 105 passed.
  - **Symptom:** the model drops `const` inside nested pointers, so the cases cast to `char **` or `unsigned char **` where the header declares `const char **` or `const unsigned char **`.
  - **Affected:** `ares_dns_record_query_get` (its single case and the record's lifecycle case), `ares_dns_rr_get_opt` and `ares_dns_rr_get_opt_byid`. `ares_dns_write` takes `unsigned char **buf` and was not affected.
  - **Impact:** clang only warns (`-Wincompatible-pointer-types-discards-qualifiers`), and the compile probe's `-w` hid it. gcc 14 in the analysis image refuses all four calls even under `-w`, so a gcc build of the whole harness failed.
  - **Fix, spelling:** the layout probe records each parameter that points to a qualified pointer as the header writes it (`qualified_pointer_spellings` → `Declared.qualified_pointers` → `ApiInfo.qual_ptrs`). `_bind_call` casts to that type and declares the object with its element type (`const char * c0a2[1]`, `(const char **)c0a2`). The model's pointee still decides how the object is filled, so no input layout changes. Anonymous types are never spelled.
  - **Fix, compile probe (clang only):** `-w` is replaced with `-Wno-error -Werror=incompatible-pointer-types-discards-qualifiers`, and the target's own `-Werror*` and `-pedantic-errors` are dropped. That error counts only on case lines, so a target header's own inline code cannot fail the harness. Without a layout probe, the model's `(char **)` stays and the probe skips the case with its error. A hand-written `--dispatch-case` that drops a nested `const` is now refused too.
  - **On run-1's inputs:** still 64 dispatch cases for 62 entry points, none skipped, and identical `api_cases`. Before the fix the harness had 4 clang diagnostics and 4 gcc 14 errors; after it, none.
  - **Tests:** `tests/test_api_harness_nested_const.py` (8 tests, including a Docker test: real clang AST, a `-Werror=` compile, a gcc compile, `probe_cases` refusing the old casts, and 100k LibFuzzer runs under ASan and UBSan). `test_api_harness_anon_enum.py` now expects `(const char **)`.

### Symptom: `--api` Cases Pass an All-Zero Context Struct (`mpack_writer_t c0a0; memset(...)`, No Initializer Call), and Crash Verifiers Reject Their Crashes as `harness_induced`
- **Seen on:** mpack run-3 (2026-11-17), modules `libmpack_a__mpack_writer`, `_mpack_writer_2` and `_mpack_node`.   - Choice order: never an error (`*_init_error`) or `FILE *` initializer; then a (buffer, length) pair the call only reads; then any (buffer, length) pair; then the traces' first call; then the plainest name.
  - The object is released with the S7 destructor.
  - A new sidecar field, `api_helpers`, lists the out-of-scope initializers and destructors, and `harness_reach.check_module` removes them from the roots.
  - Selectors are unchanged, but the layouts of context-taking cases change, so those modules need re-seeding.
  - On run-3 inputs, cases that call an initializer: writer_2 0 → 48 of 59, writer 0 → 8 of 10, common 0 → 41 of 90, expect 0 → 44 of 67, node 0 → 6 of 55.
  - Tests: `tests/test_api_harness_unit_initializers.py` (7 tests). The supervisor reran them with the neighbouring api_harness suites on the branch: 157 passed, 2 skipped.
- **Still open:**
  - The other 49 `node` cases take `mpack_node_t` by value and still use shadow buffers.
  - Handle and out-parameter constructors are still searched only in the scope.
  - The dynamic reach gate still credits an entry point that only a helper executes.
  - Crash credit excludes only `inits`, so a crash under the destructor could be credited to the entry point.

### Symptom: WP and Eva Leave `\aligned(node.data, 8)` Unknown on an `--api` Harness Whose Pointer Is Backed by a `static unsigned char[]`
- **Seen on:** mpack run-3 (2026-11-17), Phase 3: `breaker-mpack_node_data_alloc` and one other breaker, both `clean`. The harness set `c0a0.data = (void *)c0a0f0` with `static unsigned char c0a0f0[4024]`. The breaker's misaligned control (`c0a0f0 + 1`) fails the same assertion, so the check is live.
- **Cause:** pipeline bug in [`../../scripts/api_harness.py`](../../scripts/api_harness.py): the byte buffers that back typed objects declare no alignment. Separately, WP in Frama-C 34.0~beta does not implement `\aligned` at all ("\aligned not yet implemented"), so the WP goals stay Unknown whatever the declaration. That part is an upstream limitation, not a pipeline defect.
- **Fix (supervisor S9, **fixed** for Eva: commit `6fefae3`, merged into `phase1-remediation` on 2026-11-17, merge `7cb53a7`):**
  - Every byte buffer a case declares is `_Alignas(16) unsigned char[]`. Eva then proves `\aligned`, while a plain array or a trailing `__attribute__((aligned(16)))` stays Unknown.
  - The value is 16 because Frama-C refuses `_Alignas` above `alignof(max_align_t)` (16), and `max_align_t` is undeclared under `-std=c99`.
  - E-ACSL reprints the declaration as `_Alignas(16)`, which gcc and clang accept under `-std=c99`.
  - Layouts and seeds are unchanged.
  - Tests: `tests/test_api_harness_buffer_alignment.py`.

### Symptom: An `--api` Case Passes One Object for a `(T *array, size_t count)` Pair, and a Crash Verifier Rejects the Crash as `harness_induced`
- **Seen on:** mpack run-3 (2026-11-17), module `libmpack_a__mpack_expect`, case 10, `mpack_expect_enum(mpack_reader_t *reader, const char *strings[], size_t count)`. The generated case declared `const char * c0a1; memset(&c0a1, 0, sizeof(c0a1));`, read `unsigned long c0a2` straight from the input and called `mpack_expect_enum(&c0a0, &c0a1, c0a2)`. Every count above 1 reads past the one-element "array" (ASan `stack-buffer-overflow ... 'c0a1'`). The same shape occurs in expect cases 11-13 (`mpack_expect_enum_optional`, `mpack_expect_key_cstr`, `mpack_expect_key_uint`) and in `libmpack_a__mpack_node_3` cases 0, 1 and 7. The run's model hand-patched the harness to a 2-element array and left the count unbounded; that is not a fix.
- **Cause:** pipeline bug in [`../../scripts/api_harness.py`](../../scripts/api_harness.py). (pointer, length) pairs were recognized only for byte pointers. A pointer to other elements followed by its count was built as one object, plus an unrelated scalar read from the input. Related: a lone `const` `T **` could have its pointer read from the input bytes.
- **Fix (supervisor S12, **fixed**: commits `15c5dda` and `d4256c3` from `sup/mpack-api-array`, merged into `phase1-remediation` on 2026-11-17, merge `7cb53a7`; the residuals listed below stay open):**
  - A run of pointers to non-byte elements followed by a count-named integer gets `ARRAY_ELEMENTS` = 4 valid elements per array: distinct NUL-terminated strings for string arrays, NULL for other pointers, and zeroed scalars or structs whose element 0 is read from the input as before.
  - The count keeps its input slot and is mapped into 1..4 with `1ULL + ((ull)c % 4 + 3) % 4`. It is never 0, because mpack asserts `count != 0`, which is `__builtin_unreachable` in a release build.
  - Layouts, selectors and seeds are unchanged: on run-3, 7 of 383 cases change their text and none changes its layout. Byte (buffer, length) pairs are unchanged.
  - Tests: `tests/test_api_harness_array_count.py`. The supervisor reran it with the neighbouring api_harness suites: 94 passed, 1 skipped.
- **Still open:**
  - Struct-field (pointer, count) pairs in `_fill_fields` are still clamped in bytes, not elements.
  - An array shared between the calls of a sequence case keeps an unclamped count.
  - A count named neither count, len nor size (`npts`, `max`) is not detected. Workaround: a `custom` case.
