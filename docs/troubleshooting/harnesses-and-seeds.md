# Harnesses, Reach Gates & Seeds

Issues encountered in dual harness generation (`generate_harness.py`, `api_harness.py`), static and dynamic reachability gates (`harness_reach.py`, `phase0_gates.py`), Phase 0 `build-check`, coverage builds (`llvm-cov`), and seed/corpus recording (`seed_harvest.py`, `fuzz_assets.py`). See [`./README.md`](./README.md) for the master index.

## Harness Generation (`generate_harness.py`, `api_harness.py`)

### Symptom: `lib/getopt.c:45: fatal error: gettext.h: No such file or directory` in a Harness Build (nettle getopt)
- **Fixed pipeline bug** (`scripts/build_callgraph_dag.py`, commit `d71b255`): 9 executable modules of nettle run-3 (`base16dec`, `base16enc`, `base64dec`, `base64enc` and the tools) failed `build-check` with this error.
- **Cause:** Frama-C parses with its own libc, which has no `__GLIBC__`; the build and every harness build use glibc. nettle's root `getopt.c` includes `lib/getopt.c` only when `ELIDE_CODE` is unset, and sets it under `__GLIBC__ >= 2`. The glibc build therefore compiled `getopt.c` to an empty object: in `build_capture.json` it has `headers: []` and `defined_functions: []`, and `lib/getopt.c` is no compiled source. The model took the other branch and put `_getopt_internal`, `getopt_long`, and the rest in `lib/getopt.c`. The DAG took `required_sources` from the model's defining files, so the argv harnesses compiled `lib/getopt.c` on its own.
- **Fix:** a module's `required_sources` now hold only compiled sources (`compiles[].source`). Any other file becomes the compiled source whose `cc -M` list (`compiles[].headers`) includes it, or is dropped when none does. A function the real build does not define carries `model_only` with the reason, and the DAG lists these per file under `model_only_functions` with a warning. A function is marked when no compile compiles or includes its file, or when it is non-static and no object of its units defines it (statics are never marked: the compiler may inline them). Marked functions are never harness sources or reach-gate entry points (`harness_reach.built_entries`). Eva and WP may still analyse them; the ledger shows `bookkeeping.model_only` and REPORT.md lists them. `build_capture.py` now records `compiles[].probe_errors`, so an empty `headers` or `defined_functions` list is no longer confused with a failed probe. A capture that predates it trusts only non-empty symbol lists. `build_only_functions` no longer reports the functions of an included `.c` (nettle's `eccdata.c` including `mini-gmp.c`).
- **Check:** after `build_callgraph_dag.py`, no `required_sources` names a file outside `compiles[].source`. Each `model_only_functions` warning names code only Frama-C's configuration compiles. Report it to the user: Eva and WP results there describe code the shipped binary does not contain.

### Symptom: A Harness Misses a Build Flag (`-include config.h`, a Quoted `-D`, `-std=`)
- **Cause:** harnesses take the unit's flags from the DAG. The unit's `-include` files are kept apart (`force_includes`) and applied by `generate_harness.py`. Quoted `-D` values (`-DLOG_PATH="log.txt"`) and the build's `-std=` are not copied, because later stages split and re-join flag strings (and a C89 `-std` rejects the C99 harness).
- **Fix:** state such flags in the harness's `--cppflags` yourself.

### Symptom: A Harness Line Like `break int main(void);`, or `too many arguments to function call, expected 0, have 2` on `main`
- **Cause:** the `main` prototype synthesizer read a statement keyword from a preceding macro continuation (`png-fix-itxt.c`'s `GETBREAK`) as the return type; and the default `argv` entry style calls `main(2, argv)` on a `main(void)` (libpng `pngfix-itxt`, `pnggetset`; defects B and C of `docs/progress/2026-11-09-libpng-harness-generation-bugs.md`).
- **Fix:** B is **fixed** in `scripts/generate_harness.py`: preprocessor continuations are stripped and statement keywords cut from the head. C is handled by failing early (`_check_argv_entry`) with what to do: exempt the module with `harness_reach.py exempt`, or give `--entry-style` with `--call-expr`. **Open pipeline bug:** there is no stdin-fed entry style yet, so programs that read stdin cannot be harnessed (O10 in [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md)).

### Symptom: `--api` Says `no API entry point the generator can call: {}` for an Executable Module
- **Cause:** an executable's only API entry point is `main`, which `--api` does not drive (no signature it can fill from bytes).
- **Fix:** use the argv style: `generate_harness.py --module <m> --unit <unit> --sources <required_sources...> --header none --entry-fn main --entry-style argv --cppflags='<DAG cppflags>'`. Modules that take no attacker input (table generators such as nettle's `desdata`/`eccdata`, benchmarks) get `harness_reach.py exempt --module <m> --reason '<why>'`.

### Symptom: `--api` Harness Fails With `unresolved identifiers after automatic prelude resolution: jmp_buf, FILE`, or Leaves Partial `harness_<mod>.{c,json}` After Exit 1
- **Cause:** the auto-prelude knew no header for standard-library names the target's headers use without including them; a failed generation left its half-written files, which `gen` and the reach gate can pick up; the case probe stopped at clang's 20-error cap, so more failing cases needed several rounds (libpng `pngwutil`, `pngset`, `pngget*`; defect E and "partial files" of `docs/progress/2026-11-09-libpng-harness-generation-bugs.md`).
- **Fix:** **fixed** in `scripts/generate_harness.py` and `scripts/api_harness.py`: the prelude includes the standard header of such names (`_STD_HEADER_OF`); generation restores the previous harness files on any failure (`harness_files_kept_on_failure`) and fails on a harness that still does not compile after the prelude (`fail_on_compile_error`); the probe lifts the error cap and fails on errors outside the cases instead of dropping cases for them. **Open pipeline bug:** `--api` still does not default `--header` to the unit's `public_headers` from the build capture; give `--header` by hand (O4 in [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md)).

### Symptom: Auto-Prelude Reports Identifiers Unresolved That a Manually Provided Prelude Header Already Defines
- **Seen on:** ptf-original run-2 (2026-11-10), `libXmlHandler_a__XmlUtil`: with `--extra-include xmlhandler_prelude.h` (which includes `<libxml/tree.h>`, `XmlParser.h`, ...) on the `-I` path, `resolve_prelude_headers` still reported `xmlNodePtr, xmlXPathParserContextPtr, xmlXPathContextPtr, XML_ERROR, xmlDocPtr` as unresolved, although a manual `clang -fsyntax-only` of a file including only that prelude compiles cleanly with the same flags.
- **Cause (from the code, reproduced with a modelled clang, not confirmed on ptf):** the harness includes the module header first and the `--extra-include` headers after it, so the module header is compiled before the header that defines its types; and the definition search reads only the `*.h` files directly in each `-I` directory, so a definition reached through `<libxml/tree.h>` is never found. The manual check compiled the prelude alone, which does not show the order.
- **Fix (fixed 2026-11-11, uncommitted, `scripts/generate_harness.py` `resolve_prelude_headers`):** before reporting `unresolved`, each `--extra-include` header is moved in turn before the module header and clang runs again; the move is kept only when identifiers are resolved, none is new and fewer errors remain. The moved headers are recorded as `extra_includes_first` in the sidecar, and their line carries `/* auto-prelude: moved before the header that needs it */`. Harnesses with nothing unresolved, and `--no-auto-prelude`, are unchanged. Tests: `tests/test_harness_prelude_extra_include.py` (clang modelled by a fake runner, plus a real-clang test that is skipped without clang and passes in `framac-analysis:latest`, 2026-11-11). Not run on ptf.
- **Workaround (still valid):** the documented manual form — `--no-auto-prelude` with an explicit prelude header that includes every definer in dependency order (`PtfUtil.h` before `ExtCommonDefs.h`, `XmlParser.h` before `XmlUtil.h`, `Logger.h` before `LogFiles.h`, ...). The skeleton compile still fails loudly if something is genuinely missing.

### Symptom: `--api` Skips Cases With `invalid application of 'sizeof' to an incomplete type` or `call to undeclared function`
- **Cause:** the harness was generated with `--header none`, so it includes no project header. The auto-prelude only searches for headers that define identifiers the module header uses, and there is none. Internal headers (`aes-internal.h`, `ghash-internal.h`...) are not found either. Found on nettle: 22 of 35 libnettle clusters failed outright and libhogweed skipped 109 cases.
- **Fix:** pass the headers explicitly, one `--extra-include <hdr>.h` each (the public headers of the unit and the internal ones its API uses), and regenerate. On nettle this took the gaps from 245 to 70.

### Symptom: Every `--api` Case of a Module Is Dropped (`no API case compiles`) on Opaque Handles (`png_const_structrp`)
- **Cause:** the generator declared an opaque struct, reached through a pointer typedef, as a by-value stack object (libpng `pngget*` clusters; defect A of `docs/progress/2026-11-09-libpng-harness-generation-bugs.md`).
- **Fix:** **open, not re-verified on libpng.** `18bc5e9` (initializer calls for struct pointers, layout probing) may cover it; re-run Phase 0 Step 4 on libpng to check before closing (O6 in [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md)).

### Symptom: `--api` Skips Cases With `pointer to an anonymous struct` (GMP `mpz_t`)
- **Cause:** `mpz_t` is `__mpz_struct[1]` with an anonymous struct, which the layout probe cannot fill. Every bignum API (RSA, DSA, ECC, PKCS#1, PSS, key parsers) is skipped and shows up as a reach gap (nettle libhogweed: 62 gaps after the header fix).
- **Fix:** write a dispatch sub-module by hand, which is the documented route for contracts the model does not know: a freely named sub-module (`libhogweed_a__mpz`) with `--scope-file` for the defining sources, `--entry-style dispatch` and one `--dispatch-case` per API family. Build the `mpz_t` values from `fuzz_buf` (`mpz_import`, `nettle_mpz_set_str_256_u`), initialise and clear everything, never `return`, and give sign/decrypt cases a fixed valid private key plus a deterministic random callback (a harness that violates the contract is rejected as harness-induced). A sub-module is checked only for its own scope, so the **unit's** harness still lists those entry points as gaps: record `harness_reach.py exempt --module <unit harness> --function <fn> --reason 'covered by sub-module <name>'` for exactly the functions the sub-module reaches, and check the sub-module's `entry_points_reached` equals its `entry_points`.

### Symptom: `validate_artifacts.py` Fails With `$.api_cases: one layout per dispatch case`
- **Cause (pipeline bug, fixed):** `api_harness.generate` drops the cases clang refuses, one probe round at a time, for at most `MAX_PROBE_ROUNDS` rounds. Clang stops after 20 errors by default, so a module with more refused cases than a few rounds can clear (nettle libhogweed: 88; `libnettle_a__sha256`: 5 more) ends with `api_cases` already filtered but `harness_<mod>.c` and `dispatch_cases` still holding a case that does not compile. The harness then fails to build, and the reach gate counted the broken case as reaching its function.
- **Fix:** `api_harness.probe_cases` lifts the error cap (`-ferror-limit=0` for clang, `-fmax-errors=0` for gcc), so one round finds every refused case, and the probe loop now runs until no case is refused (`MAX_PROBE_ROUNDS` is gone); the harness is rewritten after every drop, so the harness on disk and the sidecar always list the same cases (phase1-remediation `7b2a7ef`). If a run predates the fix, regenerate every sidecar the validator names. Expect the reach gate to report new gaps afterwards: the dropped cases never really reached their functions.

### Symptom: An `--api` Case Is Skipped With `redefinition of 'c0a0' with a different type: 'unsigned char[0]' vs 'struct AnomalyBase_T[1]'`
- **Seen on:** ptf-original run-2 (2026-11-10), `libPtfCom_a` entry `WriteAnomaly(const AnomalyDBEntry_T *AnomalyElement, char ChainId[])` (also `libXmlHandler_a__SwDownload` `FreeSwDownloadList`/`FreeSignalListType` and `ExternalInterfaces` `AddEventToList`/`FindEventInList`/`RemoveEventFromList`, which fail as `type 'X_T'` skips instead).
- **Cause (pipeline bug, fixed):** `scripts/api_harness.py` `_fill_fields` named the storage of a pointer field after the field's path. When the call sites give the struct argument a size, the object is an array and the path is `c0a0[0]`, so the generator wrote `static unsigned char c0a0[0]f2[N];`: a second `c0a0`. Reproduced at text level on a fixture of the `WriteAnomaly` record. `param_sizes` of 0 is not involved (the run's first explanation): a zero size gives one struct and a valid name.
- **Fix (fixed 2026-11-11, uncommitted, `scripts/api_harness.py`):** every character an identifier cannot hold becomes `_` (`c0a0_0_f2`). Every declaration now goes through `_Case.declare()`: a name declared twice in a case, or one that is not an identifier, skips the function with `api_skipped` reason `generator defect: variable '<name>' would be declared twice in the case`, without waiting for the compile probe. Tests: `tests/test_api_harness.py`; the compile test of the fixed case is skipped without clang and passes in `framac-analysis:latest` (2026-11-11). Not run on ptf.
- **Hand-written cases with `--api` (fixed, same change):** `generate_harness.py --api --dispatch-case '<one line of C>'` appends the case after the generated ones in the same switch, with an `api_cases` layout of kind `custom` (`schemas/harness_sidecar.schema.json` `custom_case`; the seed writers make nothing for it). A later `--api` run without the flag keeps the cases, one with the flag replaces them, `--dispatch-case ''` drops them. A case that does not compile fails the generation. So a function in `api_skipped` no longer has to be exempted.
- **Open pipeline bug (the `type 'X_T'` skips, another cause):** `AddEventToList` / `FindEventInList` / `RemoveEventFromList` take a struct typedef by value, and `classify_type` (`scripts/seed_harvest.py`) rejects a typedef name passed by value; the model keeps the typedef name there. `FreeSwDownloadList` / `FreeSignalListType` were not reproduced (a pointer to a typedef plans fine; their real signatures are needed). Workaround: a hand-written `--api --dispatch-case`, else an exemption.
- **Open pipeline bug:** `scripts/benchmark.py` builds the `"generate": "api"` command without `--dispatch-case`, so a workspace regenerated from a manifest has no hand-written cases. A function covered by a hand-written case stays listed in `api_skipped` with its old reason (informational: nothing reads it as a gap).
- **Note:** a companion sub-module harness with `--scope-file` does not close the main module's gap (see the companion sub-module entry under Reach Gates below).

### Symptom: Harness Linking Fails With `undefined reference to '<internal_helper>'` (e.g. `syscall_iterate`)
- **Cause:** `scripts/api_harness.py` collected source files defining only the public entry points called by the harness case, omitting internal helper translation units (e.g. `src/syscalls.perf.c` generated by gperf or auxiliary module sources) required by those API functions.
- **Fix:** **fixed** in `scripts/api_harness.py`. When building `--api` harness sources, the generator unions `dag.get("modules", {}).get(module, {}).get("required_sources")` into the harness compilation units so all internal helper sources of the module are linked into the harness binary.

### Symptom: A Dispatch Harness's Corpus Fills With Inputs That Run No Case (Empty Inputs, Selectors of Skipped Cases, Oversized Inputs)
- **Seen on:** H3 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), read from `templates/harness_dual.c.template` and `generate_harness._build_dispatch_invocation` (2026-11-10); not measured on a target run.
- **Cause:** `LLVMFuzzerTestOneInput` returned 0 for every input, also one longer than `MAX_INPUT_SIZE`, one without a selector byte, and one whose case a keep-going round skips (`-DFRAMAC_FUZZ_SKIP_CASES`). LibFuzzer counts such an input as executed and may keep it, so later rounds mutate inputs of a case that is no longer compiled in.
- **Fix (fixed, H3):** the template returns `-1` for those inputs, which libFuzzer never adds to the corpus. Checked in `framac-analysis:latest` (Debian clang 19.1.7): a harness that rejects all but one prefix keeps only inputs with it. The dispatch code calls `FRAMAC_FUZZ_REJECT()` on an empty input and on a skipped case; a hand-written case whose own length guard turns the input away before any call can call it too. In `eva_main` the macro is empty. The generated `--api` cases call with zeroed arguments when the input is short, so they never reject. `tests/test_harness_reject.py` builds a dispatch harness with case 0 skipped and checks that no kept input selects it, is empty or is oversized.

### Symptom: An `--api` Harness Never Finds a Use After Free, Double Free or Call After Error on an Opaque Handle
- **Seen on:** H2 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), from `scripts/api_harness.py` (2026-11-10).
- **Cause:** each single case builds a fresh handle, makes one call and releases it, so no input makes two calls on one handle. Sequence cases came only from recorded traces, and those pass a shared handle as a zeroed buffer (`sequence_case` shares buffers by address; the constructor's result is not recorded), or do not compile at all for a pointer to an incomplete struct (`sizeof(struct ctx)`).
- **Fix (fixed, H2):** `api_harness.lifecycle_case` adds one case per handle type with a constructor and a destructor: build the handle, then while the input lasts up to `LIFECYCLE_MAX_CALLS` (8) calls, each picked by one input byte among the functions taking exactly one handle of the type (`methods`, not its constructor or destructors), then release it. The sidecar layout is `kind: lifecycle`; its slots are the constructor's, so seeds start from the constructor's recorded arguments. Lifecycle cases share `MAX_SEQUENCE_CASES` (16) with the recorded chains, which come first. `tests/test_api_harness_lifecycle.py` fuzzes a library whose `reset` frees a buffer the other calls still use: ASan finds the use after free with the lifecycle case and not with the single cases, and Eva runs on the same harness.
- **Still open:** a recorded chain over a handle still passes a zeroed buffer (**open pipeline bug**, `sequence_case`): it needs the constructor's result threaded through the chain. A lifecycle case whose method changes the fuzzing process (`seccomp_load`, see the next entry) hangs the campaign like the single case; skip it by hand. If one method does not compile, the compile probe drops the whole lifecycle case, and no `api_skipped` entry says so. Eva cost on a target is not measured: on libseccomp the constructor never returns a handle in Eva (gap D of [`./eva.md`](./eva.md)), so the loop is dead there.

### Symptom: An `--api` Harness Campaign Hangs Without an Artifact, or Stops Early on `leak-*` / `bad-free` in `LLVMFuzzerTestOneInput`
- **Seen on:** libseccomp (`libseccomp_a`), the regenerated `--api` harness built with `-fsanitize=fuzzer,address` in `framac-analysis:latest`, 2026-11-10. Each run below stopped at its first artifact after 18 to 118 executions, so the handle cases were fuzzed only that briefly; none of the artifacts came from them.
- **Cause A (hang, new with constructed handles):** `seccomp_load` on a real handle installs a seccomp filter in the fuzzer process. With the default action 0 (`SCMP_ACT_KILL`), which is what a short input gives, the fuzzing thread is killed at its next system call and the process stays alive: the two-byte input `{13, 0}` was still running after 20 s with `-timeout=10`, and a 45 s campaign ran 46 minutes until it was stopped. LibFuzzer writes no artifact, so the crashed-case skip never sees the case. Before handles were constructed the zeroed buffer made `seccomp_load` return `-EINVAL`. **Open pipeline gap:** the generator cannot know that an API call changes the process it runs in. Skip such a case by hand (`-DFRAMAC_FUZZ_SKIP_CASES=<mask>`), or exempt the function and cover it with a `custom` case.
- **Cause B (false `leak-*`, older than the handle change):** the case discards an allocation the API hands to its caller: the string `seccomp_syscall_resolve_num_arch` returns (`strdup`), and the two objects `seccomp_notify_alloc` stores through its output parameters. The constructor's own case leaked the same way (`(void)seccomp_init(c0a0);`); that one is **fixed** with the handle change (`scripts/api_harness.py` releases a returned handle, commit 150b092). **Open pipeline bug** for the other two: the model does not say who owns a returned pointer.
- **Cause C (false `bad-free`, older than the handle change):** `seccomp_notify_free(&c0a0, &c0a1)` is called on two stack objects, since the harness gives every struct pointer one local object; Eva reports the same call as Invalid (`api.c:689 precondition of free`). **Open pipeline bug:** a function named like a destructor needs an object its allocator made.

### Symptom: Functions Named `Initialize`, `Freeze`, or `Destroyer` Falsely Selected as API Constructors/Destructors
- **Cause:** `_INIT_NAME_RE` and `_DTOR_NAME_RE` in `scripts/api_harness.py` matched bare `Init` and `Free|Destroy|Release` as unbounded substrings.
- **Fix (fixed, uncommitted, `scripts/api_harness.py`):** Bound CamelCase/PascalCase matches to C identifier word boundaries `(?:^|(?<=[a-z0-9_]))` and `(?=[A-Z0-9_]|$)`.

### Symptom: Multi-Dimensional and Array-Pointer Parameters Generate Broken Harness C Code
- **Cause:** `_PARAM_DECL_RE` in `scripts/generate_harness.py` allowed at most one array dimension bracket pair, corrupting parameter names and declarations for multi-dimensional arrays (`int matrix[3][4]`) and array pointers (`int (*ptr)[10]`).
- **Fix (fixed, uncommitted, `scripts/generate_harness.py`):** Allowed multiple bracket pairs in `_PARAM_DECL_RE`, added `_ARRAY_PTR_PARAM_RE`, decayed array parameters to pointers according to C99 rules, and added `_format_c_decl` helper for variable formatting.

### Symptom: String Literals Containing `main(...) {` Falsely Trigger `-Dmain` Redefinition
- **Cause:** `_source_defines_main` in `scripts/pipeline_make.py` and `scripts/generate_harness.py` scanned source files with a regex without masking string literals or checking build capture symbols.
- **Fix (fixed, uncommitted, `scripts/pipeline_make.py`, `scripts/generate_harness.py`):** Checked `defined_functions` from `build_capture.json` when available, and masked comments and string literals with `mask_comments_and_literals`.

### Symptom: Harness Dispatch Counting and Seed Binding Depend on Re-Parsing C Code
- **Cause:** `scripts/run_eacsl_fuzz.py` and `scripts/seed_harvest.py` parsed C switch statements with regex rather than consuming structured sidecar metadata.
- **Fix (fixed, uncommitted, `schemas/harness_sidecar.schema.json`, `scripts/generate_harness.py`, `scripts/api_harness.py`, `scripts/run_eacsl_fuzz.py`, `scripts/seed_harvest.py`):** Added `dispatch_case_count` to sidecar schema and generator outputs, and updated consumers to read sidecar metadata first.

## Reach Gates, Coverage & `build-check`

### Symptom: The Reach Gate Fails (`harness_reach.py check` Exit 1, or `make` Stops at `reach-gate`)
- **Cause:** a harness does not reach one of its module's API entry points, a Tier 1A/1B/2 module has no harness (`no_harness`), or a harness changed after the check ran (its digest no longer matches `phase0_gates.json`).
- **Fix:** add a `--dispatch-case` per unreached entry point and rerun `check`, or record a reason with `harness_reach.py exempt` (`/framac-slice` Step 4b). A sub-module is checked only against the unit's entry points in its own scope; entry points no harness's scope holds are reported as the unit's gaps.

### Symptom: A Companion Sub-Module Harness (`--scope-file`) Does Not Close Another Harness Module's Reach Gap
- **Seen on:** ptf-original run-2 (2026-11-10): `ExternalInterfaces__Logger` (dispatch case for the by-value `EventEntry_T` helpers) left the main `ExternalInterfaces` module failing on the same three functions, and itself failed on every other `Logger.c` entry point.
- **Cause:** not a defect, but easy to misread: `harness_reach.py check` tests **each module against the entry points in its own scope**. The main module's scope also holds `Logger.c`, so it must reach those functions itself; the companion only adds obligations for its own scope. Coverage does not aggregate across a unit's harness modules for gate purposes.
- **Fix:** exempt the unreachable entry points on the module whose scope holds them, with a recorded reason; do not add companion harnesses to close another module's gaps.

### Symptom: The Static Reach Gate Passes for an Entry Point the Harness Never Calls
- **Seen:** 2026-11-11, regex audit (no target run). `harness_reach.harness_roots` returned `stat`, `hash` and `rec_next` for a harness holding `struct stat st;`, `int hash = 0;` and the string `"rec_next failed"`.
- **Cause:** every identifier of the harness text outside comments counted as a root: variable and member names, string contents, code under `#if 0`, and bare prototypes. The `dynamic` gate caught such an entry point later, the static gate did not.
- **Fix (fixed 2026-11-11, uncommitted, `scripts/harness_reach.py` `_used_identifiers`):** the harness is tokenized (`acsl_ast.tokenize_c_acsl`); literals, `#if 0` bodies, members, tags, declared names and file-scope prototypes are not roots. A function used as a value (`cb = on_msg;`, `register_cb(on_msg)`) and the body of a harness-local `#define` still count. Text the tokenizer rejects falls back to the old rule. **Behaviour change:** a harness that passed only through such a name now fails `reach-gate`; add the call or an exemption. Not run on a target. Tests: `tests/test_regex_hardening.py`.

### Symptom: Harness Root Extraction Dependent on Tokenizer Heuristics Instead of Clang AST
- **Cause:** `scripts/harness_reach.py` only used token heuristic filtering in `_used_identifiers`, which can misidentify non-callee identifier tokens or miss complex call contexts.
- **Fix (fixed, uncommitted, `scripts/harness_reach.py`):** Implemented `_callees_from_clang_ast` and `_callees_from_clang` to extract callees from Clang JSON AST when Clang is available, falling back to `_used_identifiers`.

### Symptom: `dynamic: entry points never executed by the corpus` in `phase0_gates.json`
- **Cause:** after `coverage-<mod>`, `reach-dynamic-<mod>` found an entry point the gate holds the module to that no input executed. Fuzz and Eva of that module stop at the gate until it is fixed.
- **Fix:** read `executions: 0` in `workspace/reports/coverage/<mod>.json`. If the harness never calls the function, add a case. If it does, the corpus is stuck behind an input check: try, in order, recorded seeds, a dictionary (`params set --fuzz-dict`), a larger budget (`params set --fuzz-budget`), and a dispatch case that calls the function directly. The gap stays while the harness is unchanged.
- **Exemptions:** exempt only an entry point that cannot be driven from bytes (a live socket, a real file descriptor, process-global state). "30 s of fuzzing did not get deep enough" is not a reason: try the steps above first, and exempt only what still cannot be driven.
- **After a repair:** rerun the reach gate (`pipeline_make.py run reach-gate`) before rerunning the module; after an exemption this is not needed (`harness_reach.py exempt` re-checks the gate, see the next entry). `build-<mod>` and `fuzz-<mod>` refuse a harness whose digest changed since the gate ran. A whole-run `reach-gate` exits 1 while another module still has a gap, but it still records this module's row.
- **No row for the module:** a module whose coverage could not be measured (coverage status `no_inputs`, `compile_error` or `coverage_error`, or no coverage report) gets no row. It is listed with its reason under `unmeasured` in `workspace/reports/harness_reach_dynamic.json`; `harness_reach.py dynamic` exits 2 and `reach-dynamic-<mod>` fails, but the gate is not reopened: fuzzing and Eva of the module continue. The usual cause is that every input crashes, so the corpus stays empty (qlz: a misaligned store at `quicklz.c:161`). Then the crash is the finding: verify it. There is nothing to repair in the harness, and the module's reach stays unmeasured; do not exempt entry points for it. Seen again on ptf-original run-2 (2026-11-10): `PtfHandler` (`no_inputs`, its one crash artifact is the finding) and `libXmlHandler_a__ClkInternComparData` / `__NetworkParam_3` (`coverage_error: no input replayed to completion`, every corpus input crashes or times out in the coverage replay).

### Symptom: After Exempting Dynamic-Reach Gaps, Every `coverage-<mod>` Still Fails With `reach gate failed ... dynamic: entry points never executed by the corpus`
- **Seen on:** ptf-original run-2 (2026-11-10): after exempting ~300 dynamic gaps, `pipeline_make.py run coverage reach-dynamic` still failed every affected `coverage-<mod>` at the `$(GATE) --module <mod> --need reach` check, and `harness_reach_dynamic.json` kept showing the same gaps although the sidecars held the exemptions.
- **Cause (two effects compounding):**
  1. `phase0_gates.py check --need reach` reads the **recorded** dynamic rows in `phase0_gates.json`, not a fresh computation. The rows were recorded when the gaps were found; exempting functions does not re-record them.
  2. The make target that re-records them, `reach-dynamic-%`, depends on `coverage-%`, which the stale gate now blocks — a circular block. `make -j` also leaves **stale rows** in `harness_reach_dynamic.json` for modules whose `reach-dynamic-%` never ran (the report merges per-module rows across invocations), so the file can show gaps that are already exempted.
  A second trap: the corpus evolves between coverage measures, so a later measure can list a **new** never-executed entry point that the exemption batch did not cover (run-2: `dateAndtime`, then `WriteOptionalNodes`, each appearing one measure later).
- **Workaround used on run-2:** `harness_reach.py dynamic --module <mod>` run directly (not through Make) for every affected module, then `pipeline_make.py run coverage reach-dynamic` again. The documented step, `pipeline_make.py run reach-gate` after the exemptions, was skipped; it re-records every row and would have unblocked the run in one command.
- **Fixed pipeline bug (2026-11-10, uncommitted; `scripts/harness_reach.py`, `scripts/phase0_gates.py`):**
  1. `harness_reach.py exempt` re-records the gate rows the exemption can change (`regate_after_exempt`: the module, its unit and sub-modules, and every row the gate holds as failed) and prints the result under `gate` (`rechecked`, `still_failing`). No `reach-gate` run is needed after an exemption, so the circular block cannot form. `--function` can be repeated. Before the gate's first run nothing is recorded (`note`).
  2. The gate's message ends with the next step: `reach gate failed for <mod>: ...; repair the harness and run python3 $S/harness_reach.py check again, or record why with python3 $S/harness_reach.py exempt --module <mod> --function <fn> --reason <why> (which re-checks the gate)`.
  3. Found while testing 1: the sidecar is part of the harness digest, so **one** exemption made the next reach check treat the harness as repaired and drop **every** dynamic gap of the module, also those not exempted (`apply_dynamic`). The gaps came back only with the next coverage measure, which may be part of run-2's "second trap". The dynamic rows now record a digest without `reach_exempt` and `warnings` (`phase0_gates.harness_digest(..., ignore_exempt=True)`); a row written before the change still matches while its sidecar is unchanged.
  Tests: `tests/test_harness_reach.py` (`test_exempting_a_dynamic_gap_reopens_the_gate_without_a_reach_gate_run` and the three after it).
- **Still open:** `exempt` does not refresh the module's row in `harness_reach_dynamic.json`, so the report keeps listing an exempted gap until the next `reach-dynamic-<mod>`; the gate ignores it. `benchmark.py` and `benchmark_seeded.py` call `record_exempt` directly and run the reach check afterwards themselves.

### Symptom: A variadic parser primitive's dangerous branch (`minmea_scan` `'s'` specifier, CVE-2026-29974) is never reached by any phase, though the function runs thousands of times

- **Seen on:** minmea run-1, 2026-11-14. CVE-2026-29974 (an unbounded copy by the `'s'` format specifier of `minmea_scan`, `minmea.c:236`) is public and unfixed on `master` (`c43c9e7`); no phase of run-1 raised it. Reproduced by hand under ASan on `framac-analysis:latest`: a 47-byte sentence with `minmea_scan(s, "ts", &type, buf)` and an 8-byte `buf` gives `AddressSanitizer: stack-buffer-overflow ... WRITE of size 1 ... minmea_scan /src/minmea.c:236`.
- **Cause (one root, three phases):** `minmea_scan` is variadic; the `'s'` handler copies a field into a caller buffer with no length check, and that branch is selected only by an `'s'` in the runtime format string. All 11 `minmea_scan` call sites inside `minmea.c` use formats built from `t T f d i c _ ;` and never `'s'`, so the `'s'` write is dead from the library's own parse surface and reachable only when an integrating application calls the public `minmea_scan` with `'s'`.
  1. **Harness generation.** Phase 0 lists `minmea_scan` as a `candidate_entry_point` (correct), but [`../../scripts/generate_harness.py`](../../scripts/generate_harness.py) drove the module only through the typed `minmea_parse_*` wrappers; the harness `call_expr` never calls `minmea_scan` directly (0 occurrences in `workspace/harnesses/harness_minmea.c`). A variadic entry point has no synthesizable `call_expr` (the generator cannot invent a format string with matching varargs), so the primitive was exercised only with the parsers' own safe formats.
  2. **Reach-gate granularity.** `workspace/coverage/minmea/export.json` shows `minmea_scan` executed 2957 times with 139/332 regions covered. Function-level dynamic reach was satisfied (`executions > 0`), so [`../../scripts/harness_reach.py`](../../scripts/harness_reach.py) never reopened it, although ~58% of its regions — including the `'s'` branch — were never executed. The gate's unit is the function, not the branch, so a dead dangerous branch inside a heavily executed function is invisible.
  3. **WP bow-out.** Phase 0 records `verifiability: shell_unverifiable_wp`, `wp_blockers: ['internal_variadic']` (Frama-C WP does not model variadic functions). WP — the one analysis that is format-agnostic and could have raised an out-of-bounds-write (RTE) obligation on the `'s'` copy regardless of the call-site format — never got a contract for `minmea_scan`, although the function is Tier 1A (untrusted network parser, cyclomatic 67, `uses_format_or_write: True`).
  Compounding signal loss: `phase0_model` set `writes_bounded_buffer: False` and `takes_bounded_buffer: False` for `minmea_scan`, because the buffer write is hidden behind the variadic ABI (params recorded as `['char *', 'char *']`). The static heuristic that might have prompted a bespoke adversarial harness for an unbounded writer was blind to the one function that most needed it.
- **Scope / honest severity:** a real miss of a real memory-safety CVE, but out of the library's own attacker-reachable surface — an NMEA byte stream through `minmea_parse_*` cannot reach the `'s'` write; it needs the application to call `minmea_scan` with `'s'` and an undersized buffer. The pipeline scoped the untrusted surface to the typed parsers (`reachability: untrusted_surface` from the threat model) and never built an adversarial harness for the variadic primitive itself. Not reproduced through any built-in public function.
- **Open pipeline gap (nothing fixed):** the pipeline cannot (a) generate an adversarial harness for a variadic entry point that enumerates format specifiers — above all buffer-writing ones like `'s'` — against undersized buffers; (b) reopen the reach gate at branch/region granularity for a Tier 1A function whose dangerous regions stay uncovered; or (c) hand WP a non-variadic framing stub for a variadic callee so the write obligation is modeled. Until one of these exists, any variadic parser primitive whose dangerous behavior is format-selected is invisible to fuzz, Eva and WP alike. (a) and (b) are pipeline gaps, not Frama-C defects; (c) is blocked by the upstream WP variadic limitation. Related: the WP-side entry "Every `minmea_parse_*` Prover Stalls on the Variadic `minmea_scan`" in [`./wp-and-guardrail.md`](./wp-and-guardrail.md).

### Symptom: No Seeds, or a Harness Case Without Seeds
- **Cause:** the recipe has no test command; the tests call the API through header `static inline` functions or nested library calls, which the `-Wl,--wrap` recorders do not see; or the harness's case layout (overlapping slots, structs deeper than one `{ptr, len}` level) cannot be filled.
- **Fix:** read `workspace/reports/seed_harvest.json` and `workspace/reports/seeds/<mod>.json`. Seeds are an improvement, never a requirement: the campaign runs from its own corpus without them.
- **Seen on ptf-original run-2 (2026-11-10):** with no test command, `seed_harvest.py record` ran the unit's non-test executables once each and got `no_calls_recorded` — the daemons exit immediately without their mounted configuration (`PtfHandler` logs `unable to open configuration file` and exits 0; `ExternalInterfaces` segfaults with no arguments, kept as a warning). Expected behaviour, not a defect; the run compensated with the target's own `SupportFiles/` imported as an external corpus (`inputs/corpora/`, `fuzz_assets.py map --function ...`).

### Symptom: `seed_harvest.py record` Returns `no_test_units` Although the Recipe Has a Test Command
- **Cause:** only executables the name rule calls tests were relinked with recorders. libpng's `ctest` runs `pngtest`, `pngvalid`, `pngstest`, ..., none of which the rule recognizes (libpng `a70313dbb`, run-3; `docs/progress/2026-11-09-libpng-harness-generation-bugs.md`, defect D).
- **Fix:** **fixed** in `scripts/seed_harvest.py` (`record`): with a test command every executable is relinked and the test command decides which ones run; `test_units` still lists the ones named as tests, and `executables` lists all of them.

### Symptom: Seed Recording Records 0 Calls With a `make check` Test Command
- **Cause:** `seed_harvest.py record` relinks only the units it classifies as test executables (nettle: just `testsuite/sha1-huge-test`); a suite of many separate test programs built by `make check` is not instrumented, and header `static inline` calls are never recorded.
- **Fix:** the relink part is **fixed** (phase1-remediation `7b2a7ef`, `seed_harvest.py record`): with a test command every executable is relinked and the test command decides which ones run. Programs that `make check` builds only during the test run are not units of the capture, so they are presumably still not relinked (not re-verified on nettle; O6 in [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md)); header `static inline` calls are never recorded. Seeds stay optional (see "No Seeds" above): fuzzing starts from its own corpus.

### Symptom: A Module's Fuzz Campaign Starts From an Empty Corpus Although the Target Has Tests or Shipped Corpora, and No Log Says Why
- **Cause:** in `templates/pipeline.mk`, the `seeds` recipe and the two seed lines of `fuzz-%` (`seed_harvest.py write`, `fuzz_assets.py write`) start with `-`, and the `seeds` loop ends in `|| true`. Seeds are optional, so the recipes are non-blocking on purpose, but a failed write was invisible. Both writes stopped at the first exception with a traceback and exit 1, after deleting the module's old inputs, so `workspace/seeds/<mod>/` or `workspace/imported_corpus/<mod>/` could hold part of the new inputs while their per-module reports kept their old content. `fuzz_assets.py write` also raised on a malformed `workspace/reports/fuzz_assets.json`; `seed_harvest.py write` silently skipped a requested module with no sidecar. The fuzz report said nothing about seeds.
- **Fix (fixed, K1 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), commit 93446b9):** `scripts/seed_harvest.py` and `scripts/fuzz_assets.py` `write` record each module's outcome (`ok`, `skipped` with a reason, `failed` with the exception) in `workspace/reports/seed_status/<writer>/<mod>.json`. An exception fails only that module, and the write exits 1; the Make lines keep `-`, so a seed failure never fails the target. `scripts/run_eacsl_fuzz.py campaign` copies both statuses into `workspace/reports/fuzz/<mod>.json` as `seeds: {status, reason, writers}`; a writer that recorded no status while the campaign reads `--extra-corpus` counts as `failed`. Read `seeds.status` before tuning a module whose corpus is empty. A status file left over from an older run is shown as is, with its `generated_at`.
