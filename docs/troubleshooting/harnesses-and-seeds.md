## Harness Generation (`generate_harness.py`, `api_harness.py`)

### Symptom: `lib/getopt.c:45: fatal error: gettext.h: No such file or directory` in a Harness Build (nettle getopt)
- **Fixed pipeline bug** (`scripts/build_callgraph_dag.py`, commit `d71b255`): 9 executable modules of nettle run-3 (`base16dec`, `base16enc`, `base64dec`, `base64enc` and the tools) failed `build-check` with this error.
- **Cause:** Frama-C parses with its own libc, which has no `__GLIBC__`; the build and every harness build use glibc. nettle's root `getopt.c` includes `lib/getopt.c` only when `ELIDE_CODE` is unset, and sets it under `__GLIBC__ >= 2`. The glibc build therefore compiled `getopt.c` to an empty object: in `build_capture.json` it has `headers: []` and `defined_functions: []`, and `lib/getopt.c` is no compiled source. The model took the other branch and put `_getopt_internal`, `getopt_long`, and the rest in `lib/getopt.c`. The DAG took `required_sources` from the model's defining files, so the argv harnesses compiled `lib/getopt.c` on its own.
- **Fix:** a module's `required_sources` now hold only compiled sources (`compiles[].source`). Any other file becomes the compiled source whose `cc -M` list (`compiles[].headers`) includes it, or is dropped when none does. A function the real build does not define carries `model_only` with the reason, and the DAG lists these per file under `model_only_functions` with a warning. A function is marked when no compile compiles or includes its file, or when it is non-static and no object of its units defines it (statics are never marked: the compiler may inline them). Marked functions are never harness sources or reach-gate entry points (`harness_reach.built_entries`). Eva and WP may still analyse them; the ledger shows `bookkeeping.model_only` and REPORT.md lists them. `build_capture.py` now records `compiles[].probe_errors`, so an empty `headers` or `defined_functions` list is no longer confused with a failed probe. A capture that predates it trusts only non-empty symbol lists. `build_only_functions` no longer reports the functions of an included `.c` (nettle's `eccdata.c` including `mini-gmp.c`).
- **Check:** after `build_callgraph_dag.py`, no `required_sources` names a file outside `compiles[].source`. Each `model_only_functions` warning names code only Frama-C's configuration compiles. Report it to the user: Eva and WP results there describe code the shipped binary does not contain.

### Symptom: A Harness Misses a Build Flag (`-include config.h`, a Quoted `-D`, `-std=`)
- **Cause:** harnesses take the unit's flags from the DAG. The unit's `-include` files are kept apart (`force_includes`) and applied by `generate_harness.py`. Quoted `-D` values (`-DLOG_PATH="log.txt"`) and the build's `-std=` are not copied. Later stages split and re-join flag strings, and a pre-C99 `-std` rejects both the C99 harness and E-ACSL's printed code.
- **Fix:** since `784401d` (sudo run-1, 2026-11-21), the build's string-valued `-D` macros are copied with their quotes; see the `LOCALEDIR` entry below. State only a `-D` value with whitespace yourself, and only through a force-included header.
  - A `-std=` of C99 or later given there is kept.
  - A pre-C99 one got through until the fix described in the next entry, which drops it.

### Symptom: `generate_harness.py --api` Fails With `fatal error: 'workspace/work/config.h' file not found` When the Build Force-Includes a Generated `config.h`
- **Seen on:** libmodbus run-1 (2026-11-18, `standard` profile), module `libmodbus_so_5_1_0`. The command
  `generate_harness.py --module libmodbus_so_5_1_0 --api --header workspace/work/src/modbus.h --extra-include workspace/work/src/modbus-rtu.h --extra-include workspace/work/src/modbus-tcp.h --max-size 1500 --out-dir workspace/harnesses`
  exited 1 with `{"ok": false, "error": "module 'libmodbus_so_5_1_0': the harness does not compile outside its cases: <built-in>:1:10: fatal error: 'workspace/work/config.h' file not found"}`.
- **Cause:** pipeline bug. The build runs with `-include config.h`, and `config.h` is generated by `./configure`, so it exists only in the build tree and in `workspace/snapshot/generated/config.h`; it is not part of the shadow overlay (`workspace/work/` holds only the target's sources). `build_callgraph_dag.py` reads the unit's `-include`/`-imacros` tokens and roots every one at the work tree (`unit_cppflags` -> `_rooted(nxt, root)`), so the unit's `force_includes` is `workspace/work/config.h`. `generate_harness.py` applies that path with `-include` before its clang probe, ahead of the snapshot `-idirafter` that supplies generated headers. The earlier generated-header fix (`47d7c89`, [`./phase0-build-and-model.md`](./phase0-build-and-model.md), "A Generated Header (`config.h`) Is Missing in Eva, WP or the E-ACSL Build") covers the `-idirafter` path but not this explicit force include.
- **Fix:** **fixed** in [`../../scripts/build_callgraph_dag.py`](../../scripts/build_callgraph_dag.py), commit `9f7b123` on branch `sup/libmodbus-generated-force-include`, merged live into `phase1-remediation` as `222d1d3` (2026-11-18, while the run was paused). A force-include listed in the capture's `snapshot.generated.headers` now resolves to `workspace/snapshot/generated/<rel>` (new `generated_root`, and a `generated=` parameter on `unit_cppflags` filled by `unit_view`); in-tree force-includes keep `workspace/work/<rel>`. The `-idirafter workspace/snapshot/generated` alone could not rescue it, because a relative `-include` is looked up from the cwd before the include chain. Regression test: `tests/test_unit_view.py::test_generated_force_include_resolves_to_its_snapshot_copy`. A run that built its DAG before the fix reruns `build_callgraph_dag.py`, then `generate_harness.py`. No workaround was applied before the fix: copying `config.h` into `workspace/work/` would fail `workspace_overlay.py check-acsl-only` (`new source file created outside baseline`), and `generate_harness.py` has no flag to skip the DAG's force includes.

### Symptom: `seed_harvest.py record` Reports `status: "not_relinked"` and 0 Calls Because Every Test Unit Is `no_api_function`
- **Seen on:** libmodbus run-1 (2026-11-18, `standard` profile). `workspace/reports/seed_harvest.json` had `status: "not_relinked"`, `calls.recorded: 0`, and `relink.<exe>.status: "no_api_function"` for all 9 test executables (`unit-test-server`, `unit-test-client`, `proxy-test-server`, ...), although the test command succeeded and the library exports the 71 API functions.
- **Cause:** pipeline gap. `seed_harvest.plan_recorder` builds one wrapper plan per model API function, but the relink loop keeps only `mine = [p for p in plans if p["name"] in defined_functions(exe)]`, where `defined_functions` is `nm --defined-only` on the test executable. libmodbus builds its tests against the shared library (`src/.libs/libmodbus.so.5.1.0`), so the tests reference the API as undefined symbols and define none of it; every executable is skipped. The check works for a target whose tests link the library statically into the executable, where the API functions are defined there.
- **Fix:** **fixed** in [`../../scripts/seed_harvest.py`](../../scripts/seed_harvest.py), commit `6212e3b` on branch `sup/libmodbus-seed-shared-lib`, merged live into `phase1-remediation` as `5ef9ea4` (2026-11-18). New `undefined_functions()` (`nm -D --undefined-only`, version suffix cut); the relink wraps the API an executable defines or references undefined, since `ld --wrap` redirects undefined references too and `__real_<fn>` resolves to the `.so` at run time. libmodbus's libtool wrappers run `.libs/<exe>` directly (`relink_command=""`, `LD_LIBRARY_PATH` set to `src/.libs`), so the relinked binary is the one the tests run. On libmodbus in the build image: before `not_relinked`, 0 calls; after `ok`, 9 of 10 executables relinked, 321 calls (189 unique) over 46 API functions. The test command exits 255 on the unmodified build too (target-side, not diagnosed). Tests: `tests/test_seed_harvest.py::test_record_wraps_api_functions_the_executable_calls_from_a_shared_library`, `::test_undefined_functions_reads_the_dynamic_symbol_table`, and the Linux-only compiled `tests/test_seed_harvest_shared_lib.py::test_recorder_wraps_calls_into_a_shared_library`. This is not a target defect.
- **Open pipeline gap:** without a test command, `_run_executables` runs `tree/<unit>` (`.libs/<exe>`) directly, without the libtool wrapper's `LD_LIBRARY_PATH`: such an executable is now relinked but cannot load the project's `.so`, so it records nothing.
- **Open pipeline gap:** a libtool build whose wrapper runs `.libs/lt-<exe>` (fast-install relink) rebuilds that binary from its own `relink_command` without the wraps, and the report says `relinked` with 0 calls. Checked only on libmodbus, which is not affected.
- **Open test gap:** no local image ships pytest, so the Linux-only compiled seed-recorder tests skip on the Windows host; they were run in `framac-analysis:latest` with pytest copied from the host.

### Symptom: `--api` Harness Skips Every Function That Takes an Opaque Handle Built by `<lib>_new_<kind>` (`no constructor for opaque handle struct _modbus *`)
- **Seen on:** libmodbus run-1 (2026-11-18, `standard` profile), module `libmodbus_so_5_1_0` after the generated `config.h` force-include fix. `generate_harness.py --api` produced 20 cases and put 51 of the unit's 71 entry points in `api_skipped`, each with `no constructor for opaque handle struct _modbus *`. The skipped set is the security-relevant surface: `modbus_reply`, `modbus_reply_exception`, `modbus_receive`, `modbus_receive_confirmation`, `modbus_proxy`, every `modbus_read_*`/`modbus_write_*`, and every context setter/getter. `harness_reach.py check` then listed the same 51 functions as `gaps` and exited 1.
- **Cause:** pipeline bug in [`../../scripts/api_harness.py`](../../scripts/api_harness.py). `handle_functions` takes a function returning the handle as its constructor only when `_INIT_NAME_RE` matches its name, and that regex accepted `new`/`create` only as a suffix (`_new$`, `_create$`). The `<lib>_new_<kind>` constructors `modbus_new_tcp`, `modbus_new_tcp_pi` and `modbus_new_rtu` were therefore never candidates. Parameters were never the problem: the rule already allowed them. The docstring's "returns the handle type and takes none" meant no handle parameter, and the run's model read it as "no parameters" (a first diagnosis that turned out wrong). The three internal entry points (`_modbus_receive_msg`, `_modbus_init_common`, `_error_print`) are skipped separately, because their `struct _modbus *` parameter needs `modbus-private.h`.
- **Fix:** **fixed**, commit `08bec6c` on branch `sup/libmodbus-new-ctor-name`, merged live into `phase1-remediation` as `c8484c6` (2026-11-18). `_INIT_NAME_RE` now matches `init`/`new`/`create` as a whole word anywhere (`(?:^|_)(?:init|new|create)(?:$|_)`; not `modbus_renew`, `newline_count`, `recreate_x`), so `modbus_new_tcp` is the constructor (fewest parameters, then the name) and `modbus_free` the destructor. The `handle_functions` docstring and the `/framac-slice` skill now say a constructor takes no handle and no path parameter, other parameters coming from the input. Regression test: `tests/test_api_harness_lifecycle.py::test_a_lib_new_kind_constructor_builds_the_handle`. A run already past step 4 regenerates its `--api` harness. Before the fix the run stopped at the reach gate rather than write about 51 `--dispatch-case` cases.
- **Open pipeline gap:** a `char *device` parameter is not a file-system path for `path_parameter` (`_PATH_WORDS`). On libmodbus `modbus_new_rtu` loses to `modbus_new_tcp` and its own case never calls `modbus_connect`, so no fuzzed device string reaches `open()`; a library whose only constructor takes a device string could, through a connect-style method in the lifecycle case. Likewise a TCP handle built from fuzzed address and port can `bind`/`listen` on loopback (the containers run `--network none`), and `modbus_tcp_accept`/`modbus_receive` on such a handle may block: watch for libFuzzer timeouts in the `modbus_t` lifecycle case.

### Symptom: `validate_artifacts.py` Fails With `$.api_cases[<n>].rest: expected type null` After a Parameterized Constructor Creates a Lifecycle Case
- **Seen on:** libmodbus run-1 (2026-11-18, `standard` profile), module `libmodbus_so_5_1_0`, immediately after the constructor-name fix `08bec6c`. `pipeline_make.py run seed` ran `validate_artifacts.py run-dir .` and exited 1 with:
  ```text
  "workspace/harnesses/harness_libmodbus_so_5_1_0.json: $.api_cases[67].rest: expected type null",
  "workspace/harnesses/harness_libmodbus_so_5_1_0.json: $.warnings: the producer recorded a schema problem: schema: $.api_cases[67].rest: expected type null"
  ```
- **Cause:** pipeline bug. `modbus_new_tcp(const char *ip, int port)` is now the `modbus_t` constructor, so `api_harness.lifecycle_case` synthesizes a lifecycle case whose constructor takes a string. The generator records the port in `slots` but the string in `rest`, as `{"call": 0, "param": 0, "kind": "string"}`. [`../../schemas/harness_sidecar.schema.json`](../../schemas/harness_sidecar.schema.json)'s `lifecycle_case` requires `rest` to be `null` (a lifecycle case's constructor arguments are its `slots`; only `single_case` carries a `rest`, and `slot.kind` has no string member). `generate_harness.py` writes the schema problem into the sidecar's `warnings` but still exits 0, so the failure surfaces later, at the seed target's validation.
- **Fix:** fixed by `8e0472b` and `f40993b`, fast-forwarded into `phase1-remediation` during the run. In `scripts/api_harness.py`, `_lifecycle_case` now binds the constructor with the rest reserved (`_RESERVED_REST`), as `_construct` does.
  - Under a reserved rest, an unsized input string becomes a `STRING_SLOT_BYTES` (16-byte) `bytes` slot whose last byte is forced to 0. It is not a zeroed buffer, because `modbus_new_tcp` returns NULL on an empty IP and the case would never run a method.
  - An unsized input byte pair becomes a zeroed spare buffer with a clamped length.
  - Tests: `tests/test_api_harness_lifecycle.py::test_a_lifecycle_constructor_string_is_a_bounded_slot_never_the_rest`, `::test_an_out_parameter_lifecycle_constructor_string_is_a_bounded_slot_never_the_rest`, `::test_a_lifecycle_constructor_byte_pair_never_takes_the_rest`, `::test_an_out_parameter_constructor_string_in_a_single_case_is_a_slot_and_the_call_keeps_the_rest`.
  - A run that has already generated its harness must regenerate it, because rerunning the validation alone still fails.
  - The generator only records its own schema problems as a warning. That is deliberate (R5): the failure shows at `validate_artifacts.py run-dir`.
  - Still open, narrow:
    - a loop method's unsized string or byte pair reads at `fuzz_off` without advancing it;
    - a returning constructor inside a single case still takes the rest;
    - a lifecycle constructor's unsized byte pair is always zero data.

### Symptom: The Generated Harness Enables a Documented Infinite-Retry Mode (`MODBUS_ERROR_RECOVERY_LINK`), and the Crash Gate Confirms the Resulting libFuzzer Timeout
- **Seen on:** libmodbus run-1 (2026-11-18, `standard` profile). The generated `modbus_set_error_recovery` case, and the `modbus_t` lifecycle case's method for it, copy the fuzzed enum argument and can set `MODBUS_ERROR_RECOVERY_LINK`. A later send in the same lifecycle case then enters the documented infinite close/connect loop in `send_msg`, and libFuzzer's 10 s alarm records a timeout (`timeout-246633d0...`, 71 bytes). The independent crash verifier confirmed it as a medium-severity DoS.
- **Cause:** **Open pipeline gap.** The generator clamps a fuzzed enum argument to the declared constants, but it has no notion of a value the API documents to block. The target's own `docs/modbus_set_error_recovery.md` (in the libmodbus checkout, outside this repository) says of `MODBUS_ERROR_RECOVERY_LINK`: "This mode will try an infinite close/connect loop until success on send call ... The reconnection attempt can hang for several seconds if the network to the remote target unit is down." The crash-verifier brief's rejection classes have no "documented behaviour" basis for a hang, so a documented infinite retry can be confirmed as a target DoS. The harness call is otherwise legitimate (public API, declared enum value).
- **Fix:** none in the pipeline yet. Suggestions: let the sidecar mark blocking enum values or functions so the generator does not feed them to the target, and add a verifier rejection basis for behaviour the target documents. Workaround used in this run: after regenerating the harness for the A/B/C repair, the parent clears the LINK bit from the fuzzed argument (`value & ~MODBUS_ERROR_RECOVERY_LINK`) with a comment citing the doc, recorded in the repair reason. The confirmed record is left as the gate wrote it and is reported as a false positive, not a target bug. Not a target defect.

### Symptom: LeakSanitizer Direct Leaks From the Handle Constructor of Every API Case (`modbus_new_tcp`, `modbus_mapping_new_start_address`) and an Invalid `free` in `modbus_mapping_free`
- **Seen on:** libmodbus run-1, 2026-11-18, Phase 1 fuzz (`crash_found` after 165 s, 63 artifacts). Eva also reports `modbus_mapping_free` (modbus.c:2328, precondition of `free`) Invalid.
- **Cause:** pipeline bug.
  - `api_harness.handle_functions` took the alphabetically first destructor-named function. That was `modbus_close`, which only closes the socket, not `modbus_free`. So every single case and the lifecycle case released `modbus_t` with `modbus_close`, and each execution leaked the context.
  - A constructor returning a complete struct (`modbus_mapping_t *modbus_mapping_new_start_address(...)`) is not a handle, so its result was dropped as `(void)`.
  - The `modbus_mapping_free` single case passed a zeroed stack struct to a function that calls `free` on its members.
- **Fix:** fixed by `f59649e` and `8385bd1`, merged into `phase1-remediation` as `5a9ff81` during the run. The crash verification gate had rejected these crashes as harness-induced and opened a harness repair, which regenerates the harness with the fixed generator.
  - A destructor named for freeing wins (`_FREEING_DTOR_RE`).
  - A destructor-named `close` of the same handle runs before it (`handle_closers`).
    - The `close` is chosen by name only.
    - One that reaches `free` through direct call sites is excluded.
    - A `close` that frees through an indirect call (a vtable) would still be a double free; that remains open.
  - A constructor-named, allocating function returning `struct S *` has its result released by S's freeing destructor (`_made_struct`, `struct_freers`).
  - A freeing struct destructor of a struct with no initializer gets no single case.
  - Tests: `tests/test_api_harness_lifecycle.py::test_the_destructor_that_frees_wins_over_close_and_close_runs_first`, `::test_a_struct_made_by_a_constructor_is_released_by_its_freeing_destructor`, `::test_a_close_that_frees_the_handle_is_no_closer`.
  - The libmodbus harness drops from 69 to 68 cases, and selectors 39 and up shift down by one.

### Symptom: ASan stack-buffer-overflow in `modbus_get_float_*` / `modbus_set_float_*` (One `uint16_t` Passed, Two Read)
- **Seen on:** libmodbus run-1, 2026-11-18, Phase 1 fuzz. Eva reports the same eight functions Invalid (`mem_access`, modbus-data.c:89-238).
- **Cause:** pipeline bug. An unsized pointer to a non-byte scalar became a single object (`unsigned short c0a0; f(&c0a0)`), but `modbus_get_float_abcd(const uint16_t *src)` reads `src[0]` and `src[1]`. The overflow comes from the harness, not the library.
- **Fix:** fixed by `f59649e`, merged into `phase1-remediation` as `5a9ff81` during the run.
  - Such a pointer gets `ARRAY_ELEMENTS` zeroed elements (`_scalar_array`), with element 0 read from the input as before, so the layout does not move.
  - In a call that also takes a count or an index, it gets a spare buffer's worth of elements.
  - Test: `tests/test_api_harness_array_count.py::test_a_pointer_to_a_scalar_with_no_count_is_a_small_array`.

### Symptom: ASan SEGV / global-buffer-overflow in `modbus_get_byte_from_bits`, `modbus_set_bits_from_byte`, `modbus_set_bits_from_bytes` (Unbounded `idx`, `nb_bits`)
- **Seen on:** libmodbus run-1, 2026-11-18, Phase 1 fuzz.
- **Cause:** pipeline bug. The index (`idx`) and count (`nb_bits`, `nb`, `write_nb`, `read_nb`) that index a buffer with no length beside it were read from the input unbounded.
  - `_ARRAY_COUNT_RE` did not know `nb`.
  - The array/count logic only handled a count that follows its array, but libmodbus puts the count before the buffer.
- **Fix:** fixed by `f59649e`, merged into `phase1-remediation` as `5a9ff81` during the run.
  - `nb` as a word is now a count name.
  - In a call with no (buffer, length) pair, count- and index-named integers are clamped to half of the smallest buffer of no length (`_indexed_scalars`, `_index_rules`). Values within the bound pass as read.
  - Tests: `tests/test_api_harness_array_count.py::test_an_index_and_a_count_stay_within_a_buffer_of_no_length`, `::test_an_nb_count_before_its_buffer_is_bounded_by_it`, `::test_an_index_of_a_call_with_a_length_is_left_to_the_callee`.
  - Still open: a limit named otherwise (`modbus_report_slave_id`'s `max_dest`) stays unbounded.

### Symptom: ASan SEGV at modbus-tcp.c:684 in `modbus_tcp_pi_listen` (Single Case and Lifecycle Method)
- **Seen on:** libmodbus run-1, 2026-11-18, Phase 1 fuzz. It still occurs after the `sup/libmodbus-harness-contracts` fixes, in a replay of the run's crash inputs.
- **Cause:** pipeline bug (harness-induced type confusion).
  - The harness builds every `modbus_t` with `modbus_new_tcp`, the constructor with the fewest parameters.
  - `modbus_tcp_pi_listen` reads `backend_data` as a `modbus_tcp_pi_t`. Its `char *node` at offset 8 overlays `modbus_tcp_t.ip`, so the bytes of the IP string are dereferenced as a pointer.
  - The API's precondition (a context from `modbus_new_tcp_pi`) is broken by the harness. libmodbus cannot tell TCP from TCP-PI by `backend_type`, so this is at most a hardening note upstream, not a finding.
- **Fix:** **Open pipeline bug:** the generator picks one constructor per handle type, whatever backend the method expects. Suggested: prefer the constructor whose name shares the method's backend word (`tcp_pi` goes with `modbus_new_tcp_pi`, `rtu` with `modbus_new_rtu`). Until then, the crash verification gate must classify this crash as harness-induced.

### Symptom: `tf_<id>` (or Any Harness) Fails build-check With `instrumented.c:<N>: error: expected ')'` at `fd_set * restrict`
- **Seen on:** c-ares run-1, 2026-11-16 ([`../runs/2026-11-16-c-ares-run1-supervision.md`](../runs/2026-11-16-c-ares-run1-supervision.md)).
  - Modules: `tf_ares-test-fuzz` and `tf_ares-test-fuzz-name`, both `build_failed`.
  - First error: `workspace/harnesses/fuzz_tf_ares-test-fuzz-name.instrumented.c:2488:49: error: expected ')' 2488 | extern int select(int __nfds, fd_set * restrict __readfds,`.
  - The other 5 modules of the unit built.
- **Cause:** pipeline bug.
  - c-ares builds with `-std=gnu90`, and the `framac-slice` skill passes the unit's cppflags to `generate_harness.py --target-fuzzer`.
  - The generator dropped a link unit's `-std=` only on the DAG path, so the sidecar kept `-std=gnu90`.
  - `eacsl_toolchain.build_eacsl_flag_sets` then passed it to `e-acsl-gcc -e`. Its `CPPFLAGS` come after its own `-std=c99` on two compiles:
    - the printed program, where Frama-C prints glibc prototypes with C99 `restrict`;
    - E-ACSL's own runtime: `e_acsl_observation_model.c: error: redefinition of 'i'`, and `e_acsl_shadow_concurrency.c: error: expected ')'`.
  - An old sidecar with a strict `-std=c89` also breaks two more paths. `-std=gnu90` does not break them:
    - the sanitizer build: `unknown type name 'inline'` in the harness;
    - the Frama-C parse: `C++ style comments are not allowed in ISO C90` in `__fc_libc`.
- **Fix:** commit `2f22b2c`, from branch `sup/c-ares-tf-std-flag`, fixed and merged into `phase1-remediation` (2026-11-16).
  - `framac_common.is_pre_c99_std` recognises `-ansi` and `-std=c89/c90/gnu89/gnu90/iso9899:1990/iso9899:199409`.
  - `generate_harness.py` drops such a flag from every harness's cppflags and says so on stderr.
  - `build_eacsl_flag_sets` never passes one to E-ACSL, which also covers old sidecars.
  - `phase0_model.framac_file_flags` uses the same predicate.
  - The skill's target-fuzzer paragraph says the generator drops the flag.
  - In Docker, the fixture's E-ACSL build fails before the fix and builds after it, with either the new or the old sidecar flags.
  - Tests:
    - `tests/test_target_fuzzer_harness.py::test_target_fuzzer_drops_a_pre_c99_std_given_in_cppflags`
    - `tests/test_eacsl_toolchain.py::test_flag_sets_never_compile_instrumented_code_before_c99`
- **Run-side workaround on run-1:** the agent regenerated the `tf_` modules with `-std=` stripped from `--cppflags` (`run-1/gen_tf.py`).
- **Still open:**
  - The sanitizer and coverage builds still take an old sidecar's `-std` unchanged.

### Symptom: `generate_harness.py --api` Fails With `field has incomplete type 'struct in6_pktinfo'`

  - glibc's `features.h` reads the feature-test macros once, at the first system header. `struct in6_pktinfo` in `<netinet/in.h>` exists only under `__USE_GNU`, which `_GNU_SOURCE` turns on.

A `#define` written in the harness would come too late as well: only a command-line `-D` reaches the compiler before `-include`.

- **Run-side workaround on run-3:** the agent added `-D_GNU_SOURCE` to `--cppflags` by hand. It is hard-coded and omits `_FILE_OFFSET_BITS=64`, which nginx also sets (no layout change on x86_64, but a different `off_t` on a 32-bit target).

  - New shared module [`../../scripts/include_context.py`](../../scripts/include_context.py). It holds the `gcc -E -dD` scan that `stub_check.py` used for its include context, and adds the feature-macro scan.
  - **Which macros:** a macro the target defines (command line, its own files, or its generated headers) before the first system header that a target file enters, and that some system header the compile enters tests in an `#if`/`#ifdef`/`#ifndef`/`#elif`. Include guards of target files are never kept, nor are function-like macros or values with spaces or quotes. Nothing is hard-coded.
  - **Which compiles decide:** the build capture's compiles of the module's sources that include the harness's header (all of them when none does). A macro is carried when every scanned compile defines it with the same line. A source that defines it only after a system header (nginx's `ngx_event_quic_bpf_code.c`) agrees and is listed under `late`. A disagreement is not carried and is reported under `differing`.
  - **How it reaches the compiler:** `generate_harness.py` appends the macros to the harness cppflags as `-DNAME=value` before the first probe. The prelude probe, the `--api` layout and case probes, every automatic header attempt, and the Eva, E-ACSL and LibFuzzer builds all read those cppflags, and gcc applies every `-D` before any `-include`.
  - **Failures:** a compile that `gcc -E` cannot preprocess (no gcc, a missing include directory, a timeout) is said on stderr and listed under `failed`; the macros then come from the other compiles only, and with none left nothing is added.
  - **Given flags:** a macro already given in `--cppflags` with the same value is kept as is (listed under `given`); `-DX` agrees with an empty value or `1`. A different value, or a `-U`, is kept and reported on stderr and under `conflicts`. Nothing is added twice.
  - **Sidecar:** `harness_<mod>.json` gets `feature_macros` (`source`, `compiles`, `command`, `macros`, `flags`, and when non-empty `headers`, `late`, `given`, `conflicts`, `not_carried`, `differing`, `failed`); see [`../../schemas/harness_sidecar.schema.json`](../../schemas/harness_sidecar.schema.json). A target that sets no such macro, or a run without a build capture, gets a byte-identical harness and sidecar.
  - `stub_check.py` passes the same macros to its three probes as `-D` flags (`include_context.feature_flags`); see [`./kernel-and-stubs.md`](./kernel-and-stubs.md).
- **Tests:**

  - `::test_an_api_harness_of_a_target_without_feature_macros_gets_no_flag` (Docker).
  - Unit: `::test_the_harness_flags_get_the_targets_feature_macros`, `::test_a_compile_that_cannot_be_preprocessed_is_said_and_recorded`, `::test_a_given_flag_is_kept_and_a_conflicting_one_is_reported`, `::test_only_the_compiles_that_include_the_harness_headers_decide`, `::test_a_source_that_defines_them_after_a_system_header_agrees`, `::test_a_target_without_feature_macros_gets_the_same_harness_and_sidecar`, `::test_the_scan_keeps_what_the_target_defines_before_its_first_system_header`, `::test_a_macro_becomes_the_flag_that_defines_it_identically`.

### Symptom: `signed_downcast` RTE Alarms on a Byte Encoder's Deliberate `(char)0xC2` Narrowing, Every One Needing a Verifier Run
- **Seen on:** mpack run-3 (2026-11-17), modules `libmpack_a__mpack_writer_2` and `libmpack_a__mpack_writer`. - **Fix:** none yet; **open pipeline gap** (an overconstraint, not a target defect). ### Symptom: Auto-Prelude Reports Identifiers Unresolved That a Manually Provided Prelude Header Already Defines
- **Seen on:** ptf-original run-2 (2026-11-10), `libXmlHandler_a__XmlUtil`: with `--extra-include xmlhandler_prelude.h` (which includes `<libxml/tree.h>`, `XmlParser.h`, ...) on the `-I` path, `resolve_prelude_headers` still reported `xmlNodePtr, xmlXPathParserContextPtr, xmlXPathContextPtr, XML_ERROR, xmlDocPtr` as unresolved, although a manual `clang -fsyntax-only` of a file including only that prelude compiles cleanly with the same flags.

### Symptom: `validate_artifacts.py` Fails With `$.api_cases: one layout per dispatch case`
- **Cause (pipeline bug, fixed):** `api_harness.generate` drops the cases clang refuses, one probe round at a time, for at most `MAX_PROBE_ROUNDS` rounds. ### Symptom: An `--api` Harness Never Finds a Use After Free, Double Free or Call After Error on an Opaque Handle
- **Seen on:** H2 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), from `scripts/api_harness.py` (2026-11-10).
- **Cause:** each single case builds a fresh handle, makes one call and releases it, so no input makes two calls on one handle. Sequence cases came only from recorded traces, and those pass a shared handle as a zeroed buffer (`sequence_case` shares buffers by address; the constructor's result is not recorded), or do not compile at all for a pointer to an incomplete struct (`sizeof(struct ctx)`).
- **Fix (fixed, H2):** `api_harness.lifecycle_case` adds one case per handle type with a constructor and a destructor: build the handle, then while the input lasts up to `LIFECYCLE_MAX_CALLS` (8) calls, each picked by one input byte among the functions taking exactly one handle of the type (`methods`, not its constructor or destructors), then release it. The sidecar layout is `kind: lifecycle`; its slots are the constructor's, so seeds start from the constructor's recorded arguments. Lifecycle cases share `MAX_SEQUENCE_CASES` (16) with the recorded chains, which come first. `tests/test_api_harness_lifecycle.py` fuzzes a library whose `reset` frees a buffer the other calls still use: ASan finds the use after free with the lifecycle case and not with the single cases, and Eva runs on the same harness.

A lifecycle case whose method changes the fuzzing process (`seccomp_load`, see the next entry) hangs the campaign like the single case; skip it by hand. If one method does not compile, the compile probe drops the whole lifecycle case, and no `api_skipped` entry says so. Eva cost on a target is not measured: on libseccomp the constructor never returns a handle in Eva (gap D of [`./eva.md`](./eva.md)), so the loop is dead there.

### Symptom: An `--api` Harness Campaign Hangs Without an Artifact, or Stops Early on `leak-*` / `bad-free` in `LLVMFuzzerTestOneInput`
- **Seen on:** libseccomp (`libseccomp_a`), the regenerated `--api` harness built with `-fsanitize=fuzzer,address` in `framac-analysis:latest`, 2026-11-10. Each run below stopped at its first artifact after 18 to 118 executions, so the handle cases were fuzzed only that briefly; none of the artifacts came from them.
- **Cause A (hang, new with constructed handles):** `seccomp_load` on a real handle installs a seccomp filter in the fuzzer process. With the default action 0 (`SCMP_ACT_KILL`), which is what a short input gives, the fuzzing thread is killed at its next system call and the process stays alive: the two-byte input `{13, 0}` was still running after 20 s with `-timeout=10`, and a 45 s campaign ran 46 minutes until it was stopped. LibFuzzer writes no artifact, so the crashed-case skip never sees the case. Before handles were constructed the zeroed buffer made `seccomp_load` return `-EINVAL`. **Open pipeline gap:** the generator cannot know that an API call changes the process it runs in. Skip such a case by hand (`-DFRAMAC_FUZZ_SKIP_CASES=<mask>`), or exempt the function and cover it with a `custom` case.
- **Cause B (false `leak-*`, older than the handle change):** the case discards an allocation the API hands to its caller: the string `seccomp_syscall_resolve_num_arch` returns (`strdup`), and the two objects `seccomp_notify_alloc` stores through its output parameters. The constructor's own case leaked the same way (`(void)seccomp_init(c0a0);`); that one is **fixed** with the handle change (`scripts/api_harness.py` releases a returned handle, commit 150b092). **Open pipeline bug** for the other two: the model does not say who owns a returned pointer.
- **Cause C (false `bad-free`, older than the handle change):** `seccomp_notify_free(&c0a0, &c0a1)` is called on two stack objects, since the harness gives every struct pointer one local object; Eva reports the same call as Invalid (`api.c:689 precondition of free`). **Open pipeline bug:** a function named like a destructor needs an object its allocator made.

## Reach Gates, Coverage & `build-check`

### Symptom: The Reach Gate Fails (`harness_reach.py check` Exit 1, or `make` Stops at `reach-gate`)
- **Cause:** a harness does not reach one of its module's API entry points, a Tier 1A/1B/2 module has no harness (`no_harness`), or a harness changed after the check ran (its digest no longer matches `phase0_gates.json`).
- **Fix:** add a `--dispatch-case` per unreached entry point and rerun `check`, or record a reason with `harness_reach.py exempt` (`/framac-slice` Step 4b). A sub-module is checked only against the unit's entry points in its own scope; entry points no harness's scope holds are reported as the unit's gaps.

### Symptom: A Companion Sub-Module Harness (`--scope-file`) Does Not Close Another Harness Module's Reach Gap
- **Seen on:** ptf-original run-2 (2026-11-10): `ExternalInterfaces__Logger` (dispatch case for the by-value `EventEntry_T` helpers) left the main `ExternalInterfaces` module failing on the same three functions, and itself failed on every other `Logger.c` entry point.
- **Cause:** not a defect, but easy to misread: `harness_reach.py check` tests **each module against the entry points in its own scope**. The main module's scope also holds `Logger.c`, so it must reach those functions itself; the companion only adds obligations for its own scope. Coverage does not aggregate across a unit's harness modules for gate purposes.
- **Fix:** exempt the unreachable entry points on the module whose scope holds them, with a recorded reason; do not add companion harnesses to close another module's gaps.

### Symptom: The Static Reach Gate Passes for an Entry Point the Harness Never Calls
- **Seen:** 2026-11-11, regex audit (no target run). `harness_reach.harness_roots` returned `stat`, `hash` and `rec_next` for a harness holding `struct stat st;`, `int hash = 0;` and the string `"rec_next failed"`.
- **Cause:** every identifier of the harness text outside comments counted as a root: variable and member names, string contents, code under `#if 0`, and bare prototypes. The `dynamic` gate caught such an entry point later, the static gate did not.
- **Fix (fixed 2026-11-11, uncommitted, `scripts/harness_reach.py` `_used_identifiers`):** the harness is tokenized (`acsl_ast.tokenize_c_acsl`); literals, `#if 0` bodies, members, tags, declared names and file-scope prototypes are not roots. A function used as a value (`cb = on_msg;`, `register_cb(on_msg)`) and the body of a harness-local `#define` still count. Text the tokenizer rejects falls back to the old rule. **Behaviour change:** a harness that passed only through such a name now fails `reach-gate`; add the call or an exemption. Not run on a target. Tests: `tests/test_regex_hardening.py`.

### Symptom: Harness Root Extraction Dependent on Tokenizer Heuristics Instead of Clang AST
- **Cause:** `scripts/harness_reach.py` only used token heuristic filtering in `_used_identifiers`, which can misidentify non-callee identifier tokens or miss complex call contexts.
- **Fix (fixed, uncommitted, `scripts/harness_reach.py`):** Implemented `_callees_from_clang_ast` and `_callees_from_clang` to extract callees from Clang JSON AST when Clang is available, falling back to `_used_identifiers`.

### Symptom: `dynamic: entry points never executed by the corpus` in `phase0_gates.json`
- **Cause:** after `coverage-<mod>`, `reach-dynamic-<mod>` found an entry point the gate holds the module to that no input executed. Fuzz and Eva of that module stop at the gate until it is fixed.
- **Fix:** read `executions: 0` in `workspace/reports/coverage/<mod>.json`. If the harness never calls the function, add a case. If it does, the corpus is stuck behind an input check: try, in order, recorded seeds, a dictionary (`params set --fuzz-dict`), a larger budget (`params set --fuzz-budget`), and a dispatch case that calls the function directly. The gap stays while the harness is unchanged.
- **Exemptions:** exempt only an entry point that cannot be driven from bytes (a live socket, a real file descriptor, process-global state). "30 s of fuzzing did not get deep enough" is not a reason: try the steps above first, and exempt only what still cannot be driven.
- **After a repair:** rerun the reach gate (`pipeline_make.py run reach-gate`) before rerunning the module; after an exemption this is not needed (`harness_reach.py exempt` re-checks the gate, see the next entry). `build-<mod>` and `fuzz-<mod>` refuse a harness whose digest changed since the gate ran. A whole-run `reach-gate` exits 1 while another module still has a gap, but it still records this module's row.
- **No row for the module:** a module whose coverage could not be measured (coverage status `no_inputs`, `compile_error` or `coverage_error`, or no coverage report) gets no row. It is listed with its reason under `unmeasured` in `workspace/reports/harness_reach_dynamic.json`; `harness_reach.py dynamic` exits 2 and `reach-dynamic-<mod>` fails, but the gate is not reopened: fuzzing and Eva of the module continue. The usual cause is that every input crashes, so the corpus stays empty (qlz: a misaligned store at `quicklz.c:161`). Then the crash is the finding: verify it. There is nothing to repair in the harness, and the module's reach stays unmeasured; do not exempt entry points for it. Seen again on ptf-original run-2 (2026-11-10): `PtfHandler` (`no_inputs`, its one crash artifact is the finding) and `libXmlHandler_a__ClkInternComparData` / `__NetworkParam_3` (`coverage_error: no input replayed to completion`, every corpus input crashes or times out in the coverage replay).

### Symptom: After Exempting Dynamic-Reach Gaps, Every `coverage-<mod>` Still Fails With `reach gate failed ... dynamic: entry points never executed by the corpus`
- **Seen on:** ptf-original run-2 (2026-11-10): after exempting ~300 dynamic gaps, `pipeline_make.py run coverage reach-dynamic` still failed every affected `coverage-<mod>` at the `$(GATE) --module <mod> --need reach` check, and `harness_reach_dynamic.json` kept showing the same gaps although the sidecars held the exemptions.
- **Cause (two effects compounding):**
  1. `phase0_gates.py check --need reach` reads the **recorded** dynamic rows in `phase0_gates.json`, not a fresh computation. The rows were recorded when the gaps were found; exempting functions does not re-record them.
  2. The make target that re-records them, `reach-dynamic-%`, depends on `coverage-%`, which the stale gate now blocks — a circular block. `make -j` also leaves **stale rows** in `harness_reach_dynamic.json` for modules whose `reach-dynamic-%` never ran (the report merges per-module rows across invocations), so the file can show gaps that are already exempted.
  A second trap: the corpus evolves between coverage measures, so a later measure can list a **new** never-executed entry point that the exemption batch did not cover (run-2: `dateAndtime`, then `WriteOptionalNodes`, each appearing one measure later).
- **Workaround used on run-2:** `harness_reach.py dynamic --module <mod>` run directly (not through Make) for every affected module, then `pipeline_make.py run coverage reach-dynamic` again. The documented step, `pipeline_make.py run reach-gate` after the exemptions, was skipped; it re-records every row and would have unblocked the run in one command.
- **Fixed pipeline bug (2026-11-10, uncommitted; `scripts/harness_reach.py`, `scripts/phase0_gates.py`):**
  1. `harness_reach.py exempt` re-records the gate rows the exemption can change (`regate_after_exempt`: the module, its unit and sub-modules, and every row the gate holds as failed) and prints the result under `gate` (`rechecked`, `still_failing`). No `reach-gate` run is needed after an exemption, so the circular block cannot form. `--function` can be repeated. Before the gate's first run nothing is recorded (`note`).
  2. The gate's message ends with the next step: `reach gate failed for <mod>: ...; repair the harness and run python3 $S/harness_reach.py check again, or record why with python3 $S/harness_reach.py exempt --module <mod> --function <fn> --reason <why> (which re-checks the gate)`.
  3. Found while testing 1: the sidecar is part of the harness digest, so **one** exemption made the next reach check treat the harness as repaired and drop **every** dynamic gap of the module, also those not exempted (`apply_dynamic`). The gaps came back only with the next coverage measure, which may be part of run-2's "second trap". The dynamic rows now record a digest without `reach_exempt` and `warnings` (`phase0_gates.harness_digest(..., ignore_exempt=True)`); a row written before the change still matches while its sidecar is unchanged.
  Tests: `tests/test_harness_reach.py` (`test_exempting_a_dynamic_gap_reopens_the_gate_without_a_reach_gate_run` and the three after it).

### Symptom: The Reach Gate Passes After Hundreds of Exemptions Whose Reason Names a Pipeline Bug

- **Fix:** none. **Open pipeline gap.** Proposed:
  - `exempt` refuses a reason that cites an open pipeline bug or an `api_skipped` generator reason, and points to the troubleshooting entry instead.
  - Or it records such exemptions under a separate status that the report counts as pipeline-caused uncovered entry points.
- **For run-3's directory:** the fix on `sup/nginx-api-anon-struct-typedef` gives 221 of the 284 skipped functions a case. Remove the exemptions made for that reason when the harness is regenerated.

### Symptom: A variadic parser primitive's dangerous branch (`minmea_scan` `'s'` specifier, CVE-2026-29974) is never reached by any phase, though the function runs thousands of times

- **Seen on:** minmea run-1, 2026-11-14. CVE-2026-29974 (an unbounded copy by the `'s'` format specifier of `minmea_scan`, `minmea.c:236`) is public and unfixed on `master` (`c43c9e7`); no phase of run-1 raised it. Reproduced by hand under ASan on `framac-analysis:latest`: a 47-byte sentence with `minmea_scan(s, "ts", &type, buf)` and an 8-byte `buf` gives `AddressSanitizer: stack-buffer-overflow ... WRITE of size 1 ... minmea_scan /src/minmea.c:236`.
- **Cause (one root, three phases):** `minmea_scan` is variadic; the `'s'` handler copies a field into a caller buffer with no length check, and that branch is selected only by an `'s'` in the runtime format string. The target's own test suite does reach it: `tests.c` calls `minmea_scan` with `'s'` six times (`test_minmea_scan_s`, lines 270-285, and the `tTfdfdfcfcfcs` call at line 415), always into `char value[MINMEA_MAX_SENTENCE_LENGTH]` (80 bytes). Seed harvest recorded all six calls (`workspace/seed_records/calls.jsonl`, 63 `minmea_scan` records; decoded formats include `s` x2, `_;s` x3, `tTfdfdfcfcfcs` x1). The format, the vararg kinds and the buffer size the maintainers use were all in the run, and nothing used them.

Run-1's harness is a hand-written `custom` `call_expr` (`workspace/harnesses/harness_minmea.json`); it calls the typed `minmea_parse_*` wrappers and never `minmea_scan` itself, so the primitive ran only with the parsers' own safe formats. The `--api` generator would not have done better: it has no case kind that calls a variadic function with a fixed format and call-site-sized vararg objects, and, worse, it does not even recognise `minmea_scan` as variadic (see the entry "Seed Recorder Segfaults in Tests That Call a Variadic API Function" below), so it would have built an unsound case that fuzzes the format string.
  2. **Pipeline bug, fixed (merge `fd139c4`, see "Fixed on branch" further down this item): the static reach gate counted a function it never calls directly as reached.** `workspace/reports/harness_reach.json` shows `entry_points: 17`, `entry_points_reached: 17`, `gaps: []`, `exempt: {}`, while `roots` lists 16 functions and not `minmea_scan`: [`../../scripts/harness_reach.py`](../../scripts/harness_reach.py) `check_module` counts every transitive callee of a root as reached, and never reads the sidecar's `api_skipped`. The `api_harness.py` module docstring says a skipped function goes to `api_skipped` and "the reach gate then reports them as gaps". That is false whenever another case reaches the skipped function transitively. So no gap was raised and no exemption was asked for. **Fixed** on branch `fix/reach-gate-direct-call` (`e235851`, `1bab71c`, `9443951`), merged into `phase1-remediation` on 2026-11-16 (`fd139c4`): an entry point counts only when the harness calls it itself (a root, a macro alias, or behind header `static inline` wrappers of a root); the others are gaps, and the row's `reached_only_through` names the roots that lead to each. A harness with `entry_style: argv` keeps the transitive reach, because the DAG lists a program's helpers as entry points while `main` is the real one (the first version raised 23 false gaps on nettle run-3 `sexp_conv`, `base16dec`, `nettle_hash`). The `argv` rule was broken inside the container until `ebb0629`: see "The Reach Gate Fails an `argv` Harness With `roots: []`" below. Measured on copies of 14 past runs (token scan, no clang on the host): 146 new gaps, four gates go from pass to fail (minmea run-1 with `minmea_scan` alone, nettle run-3 with 79, QCBOR run-4 and run-5 with one each). 129 of them are entry points in a generated harness's `api_skipped` and 17 are in hand-written harnesses. **Open pipeline gap:** with clang on the PATH the roots are every function the harness's translation unit references, so a callee named in an included header body or in an `include_source` harness still counts as a root.
  3. **Dynamic reach granularity.** `workspace/coverage/minmea/export.json` shows `minmea_scan` executed 2957 times with 139/332 regions covered. Function-level dynamic reach was satisfied (`executions > 0`), so [`../../scripts/harness_reach.py`](../../scripts/harness_reach.py) never reopened it, although ~58% of its regions — including the `'s'` branch — were never executed. The gate's unit is the function, not the branch, so a dead dangerous branch inside a heavily executed function is invisible.
  4. **WP bow-out.** Phase 0 records `verifiability: shell_unverifiable_wp`, `wp_blockers: ['internal_variadic']` (Frama-C WP does not model variadic functions). WP — the one analysis that is format-agnostic and could have raised an out-of-bounds-write (RTE) obligation on the `'s'` copy regardless of the call-site format — never got a contract for `minmea_scan`, although the function is Tier 1A (untrusted network parser, cyclomatic 67, `uses_format_or_write: True`).
  Compounding signal loss: `phase0_model` set `writes_bounded_buffer: False` and `takes_bounded_buffer: False` for `minmea_scan`, because the buffer write is hidden behind the variadic ABI (params recorded as `['char *', 'char *']`). The static heuristic that might have prompted a bespoke adversarial harness for an unbounded writer was blind to the one function that most needed it.
- **Scope / honest severity:** a real miss of a real memory-safety CVE. No `minmea_parse_*` wrapper reaches the `'s'` write, but `minmea_scan` is public API and the project's own tests show the intended use: `'s'` into an 80-byte buffer.
