# Ledger, Crash Verifier & Artifact Validation Issues

Issues encountered in coverage ledger ingestion (`ledger.py`), Crash Verifier scaffolding and verdict validation (`scaffold-verifier`, `ingest-verifier`), candidate reopening, and JSON Schema checks (`validate_artifacts.py`, `schemas/`). See [`./README.md`](./README.md) for the master index.

---

### Symptom: `wp_scheduler.py` Rejects Verifier Results with `$.record.linked_units: fewer than 1 items`
- **Fixed pipeline bug** (commit `8936217`, 2026-11-10; the commit names no target or run).
- **Cause:** `schemas/findings.schema.json` enforced `minItems: 1` on `linked_units` for every record. A crash or leak candidate located in a libc stub (`FRAMAC_SHARE/libc/stdlib.h#free`) or in generated harness code (`harness_<module>.c#unknown_function`) has no target unit in `coverage-ledger.json`, so `scripts/ledger.py scaffold-verifier` wrote `linked_units: []`, the schema check failed, and the scheduler discarded the verifier's result as invalid.
- **Fix:** [`../../schemas/findings.schema.json`](../../schemas/findings.schema.json) keeps `minItems: 1` (definition `linked_units_nonempty`) on `confirmed` records only; a `rejected` record may have empty `linked_units` (`8936217`), and so may a `needs_validation` record (2026-11-10).
- **Regression of `8936217`, fixed 2026-11-10** (found by the O1 regression tests, [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md)): `8936217` made a non-`confirmed` scaffold take only the candidate's own `linked_units`. A `needs_validation` result for a candidate with none (an Eva Invalid in a libc stub, an unparsed crash in `harness_<mod>.c`) then had `linked_units: []`, which the schema still refused for `needs_validation`: `wp_scheduler` requeued it as `invalid_result`, then blocked the task, and the candidate stayed unverified. That held even when the verifier resolved the location to a target function with `--file/--function`, which linked that function's units before `8936217`. Now a non-`confirmed` scaffold falls back to the resolved function's units that may carry evidence (not `deferred`, `out_of_scope` or `not_applicable`), and `needs_validation` may link nothing. Tests: `tests/test_ledger_p1.py` (`test_rejected_record_without_target_unit_validates_and_ingests`, `test_scaffold_needs_validation_for_unlinked_candidate_is_ingestible`, `test_scaffold_rejected_links_only_the_candidate_units`).

### Symptom: `ingest-verifier refused the result: deferred unit must not hide evidence (use 'blocked' for partial work)`
- **Fixed pipeline bug** (commit `8936217`, 2026-11-10; the commit names no target or run).
- **Cause:** when `cmd_scaffold_verifier` scaffolded a `rejected` result for a function with `deferred` units (for example functions kept out of WP dispatch by `shell_unverifiable_wp` or a bounded profile), it linked every unit of the function that was not out of scope. `cmd_ingest_verifier` then added the rejection's non-discharging evidence to each of them, and `validate_artifacts.py` refused the ledger: a `deferred` unit cannot carry evidence.
- **Fix:** [`../../scripts/ledger.py`](../../scripts/ledger.py) `cmd_scaffold_verifier` links every unit of the function only for a `confirmed` result; `rejected` and `needs_validation` results keep the candidate's own `linked_units`. As a safety net, `cmd_ingest_verifier` turns a unit in `NO_EVIDENCE_STATES` (`deferred`, `out_of_scope`, `not_applicable`) that still receives rejection evidence into `blocked`. As committed in `8936217` it set the rejection as `unresolved` only when that list was empty, which a valid ledger never has for such a unit, so the blocked unit kept its deferral reason (`tier3_not_scheduled: ...`). Since 2026-11-10 the rejection comes first in `unresolved`, followed by the old reason. Test: `test_rejection_evidence_on_a_deferred_unit_blocks_it` ([`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md), O1).

### Symptom: `refusing to write invalid ledger: $[index].unresolved[N]: duplicate item`
- **Fixed pipeline bug** (commit `8936217`, 2026-11-10; the commit names no target or run).
- **Cause:** when several unproven goals of a function render to the same text (same kind, line and annotation, for example two pointer accesses on one source line), `cmd_ingest_wp` in `scripts/ledger.py` wrote each of them to `u["unresolved"]`, which `coverage-ledger.schema.json` declares `uniqueItems: true`.
- **Fix:** [`../../scripts/ledger.py`](../../scripts/ledger.py) `cmd_ingest_wp` deduplicates `unresolved` in order (`dict.fromkeys`), on both the unproven-goal and the error path. Test: `tests/test_ledger.py::test_ingest_wp_deduplicates_identical_unresolved_entries`.

### Symptom: A Rejected Candidate's Units Are `candidate` Again After a Re-Fuzz, But No Verifier Is Dispatched
- **Fixed pipeline bug** (branch `papers-generalization`, uncommitted, 2026-11-10). Found by reading the code while building the reopening of weak rejections; reproduced in `tests/test_rejection_reopen.py::test_flag_off_restores_the_earlier_behaviour`, not observed on a target run.
- **Cause:** `cmd_ingest_fuzz` in `scripts/ledger.py` called `mark_candidate` on the linked units of every fuzz failure, also when the candidate was already `verified` with a `rejected` record. After a `harness_induced` rejection and a harness repair, a recurring crash left the units `candidate` while `candidates.json` stayed `verified`, so nothing asked for a second verdict.
- **Fix:** [`../../scripts/ledger.py`](../../scripts/ledger.py) `tool_evidence_on_verified_candidate`: a replayed reproducer on a rejected candidate now reopens it or is recorded as contradicting evidence, and the units are not marked `candidate` otherwise. `FRAMAC_REJECTION_REOPEN=off` keeps the earlier behaviour, on purpose.

### Symptom: A Reopened Candidate (`status: unverified`, With a `reopened` Entry) Gets No New Verifier Task
- **Fixed pipeline bug** (branch `papers-generalization`, uncommitted, 2026-11-10). Read from the code, covered by `tests/test_wp_scheduler.py::test_a_candidate_the_ledger_reopened_gets_its_verify_task_back_once`; not exercised on a target run.
- **Cause:** `_sync` in `scripts/wp_scheduler.py` created `verify:<fingerprint>` only when no task with that id existed. A candidate reopened by `ledger.py` already has a terminal `verify:` task from its first verdict, so the scheduler left it.
- **Fix:** [`../../scripts/wp_scheduler.py`](../../scripts/wp_scheduler.py) `_sync` reopens a terminal verify task once per ledger reopening (`candidate_reopens` on the task against the candidate's `reopened` entries), so a verify task that ended blocked for another reason is not dispatched again.

### Symptom: Malformed `function_id` With Spaces Accepted by Schemas (`see a.c#f`)
- **Seen:** 2026-11-11, regex audit (Milestone M2). Schemas for build capture, Phase 0 model, and security properties accepted function IDs with space-separated file paths.
- **Cause:** `definitions.function_id.pattern` in `schemas/build_capture.schema.json`, `schemas/phase0_model.schema.json`, and `schemas/security_props.schema.json` was `^[^#\s][^#]*#[A-Za-z_$][A-Za-z0-9_$.@]*$`. The unanchored `[^#]*` permitted whitespace characters in filenames without slash directory separators.
- **Fix (fixed 2026-11-11, uncommitted, schemas):** pattern updated to `^(?:[^#\s]+|[^#\s][^#]*\/[^#/\\s]+)#[A-Za-z_$][A-Za-z0-9_$.@]*$`, which rejects unanchored whitespace in bare filenames while allowing legitimate spaces in directory paths containing slashes. Tests: [`../../tests/test_regex_hardening_infra.py`](../../tests/test_regex_hardening_infra.py).

### Symptom: `ingest-verifier` Refuses `confirmed` With `requires a parent-verified reproducible crash report matching sha256 ...` When the Verifier Lists a Reproducer It Created Itself
- **Fixed (commit `8f25258`, merged into `phase1-remediation` as `e2ba684` on 2026-11-14, not pushed).** The crash-verifier brief promises "the parent replays your reproducers itself before ingesting the verdict", but the parent only ever replays the candidate's original reproducers, so a witness-less candidate can never be confirmed with a verifier-found crash.
- **Seen on:** minmea, run-1, 2026-11-14, agent `verify-minmea_getdatetime_5ab43d1511` (candidate `minmea.c#minmea_getdatetime::signed_overflow::5ab43d1511`): `step --complete` returned `"error": "confirmed finding minmea.c#minmea_getdatetime::signed_overflow::5ab43d1511 requires a parent-verified reproducible crash report matching sha256 19de7e904c52c770751971280310988da016a8fa6c5fa3b008a94f9457ac818e"` and requeued the verifier (`verify-minmea_getdatetime_5ab43d1511-2`). The verifier had reproduced the candidate on the recorded crash and on a crafted, fully parsed ZDA sentence it wrote to `scratch/seeds/`, and listed both in `record.reproducers`.
- **Cause:** [`../../scripts/wp_scheduler.py`](../../scripts/wp_scheduler.py) `_parent_replay` (line 3219) replays only `cand["reproducers"]` from `candidates.json`; it never reads `record.reproducers` from the verifier result. `ledger.cmd_ingest_verifier` (line 3185) promotes a scratch reproducer and then requires its sha in `_collect_reproducible_shas`, which is built from `_parent_replay`'s reports plus the candidate's tool outputs. A reproducer that exists only in the verifier's scratch (a seed or a phase-3 campaign crash) is therefore never parent-verified, although [`../../skills/framac-wp/crash_verifier_brief.md`](../../skills/framac-wp/crash_verifier_brief.md) line 74 tells the agent it will be.
- **Workaround used in this run:** the second verifier was instructed to keep `record.reproducers` to the inputs in `workspace/reports/replay/minmea.c_minmea_getdatetime_signed_overflow_5ab43d1511-d69019b205.json` (the recorded `workspace/crashes/minmea/...` artifacts, whose shas the parent did replay) and to put the crafted seed in `record.evidence`. A candidate with no original reproducer at all (a pure Eva/prover hypothesis) would still be stuck.
- **Fix (`8f25258`, merged as `e2ba684`):** `_complete_verifier` calls the new `_parent_replay_verifier_inputs`: the reproducers of `confirmed` records that are files under `agents/<id>/scratch/` are replayed on the candidate's module binary, built by the parent, with the new `run_eacsl_fuzz.py replay-candidates --fingerprint <fp> --inputs <files> --out-json workspace/reports/replay/verifier/<agent id>.json`, and that report is passed to `ingest-verifier` with the candidate's own. `ledger.py` is unchanged, so an input the parent cannot reproduce is still refused. The step output carries `verifier_replay` (returncode, report, inputs, status, `fingerprint_matches`), and the brief now says what is replayed. Reproduced in Docker on a copy of the run (`minmea-repro/verifier-reproducers`): the unfixed scripts return the refusal above with `requeued_ingest_error`; the fixed scripts with the libc shim (then uncommitted, now commit `7be8bd1`) return `ingested`, `confirmed`, `fingerprint_matches: true`. Tests: `tests/test_wp_scheduler.py` (`test_parent_replays_the_scratch_reproducers_a_verifier_confirms_on`, `test_a_scratch_reproducer_the_parent_cannot_reproduce_is_still_refused`, `test_a_verdict_without_scratch_reproducers_needs_no_extra_replay`) and `tests/test_fuzz_subcommands.py::test_replay_candidates_fingerprint_replays_given_inputs_on_the_candidates_binary`.
- **Open pipeline bug:** `_collect_reproducible_shas` in [`../../scripts/ledger.py`](../../scripts/ledger.py) reads only `reproducible` and `sha256` of a replay report, so an input that makes the parent's replay fail on a different failure than the candidate's still confirms the finding. Seen in the Docker reproduction with the committed scripts of `7369244` alone: the verifier's seed failed on `\initialized(&endptr)` in `minmea_scan` (line 224, `minmea.c#minmea_scan::e_acsl_rte::f797a710af`), not on the candidate's signed overflow, and the verdict was ingested as `confirmed` with `fingerprint_matches: false`. The rule predates the branch and also applies to a candidate's own reproducers; the branch only reports `fingerprint_matches`. Why the committed scripts and the working tree build binaries that fail differently on this input was not investigated.

### Symptom: A Crash Verifier Replays a Sanitizer-Only Defect on the E-ACSL Binary, Gets `not_reproduced`, and Is One Step From Rejecting a Real Bug
- **Open pipeline gap:** [`../../skills/framac-wp/crash_verifier_brief.md`](../../skills/framac-wp/crash_verifier_brief.md) Case A tells the verifier to replay on `compile.binary` from `workspace/reports/fuzz/{module}.json` (usually the E-ACSL binary). A candidate whose alarm is a UBSan check inside libc (minmea's `abs(INT_MIN)` at `minmea.c:635`, where E-ACSL does not instrument the negation) then reports `not_reproduced` on the E-ACSL build.
- **Seen on:** minmea, run-1, 2026-11-14, agent `verify-minmea_parse_zda_ea5e61f9eb`: the same artifact failed on the sanitizer build (`agents/.../scratch/replay_minmea_san.json`, UBSan `negation of -2147483648 cannot be represented in type int`, fingerprint `minmea.c#minmea_parse_zda::signed_overflow::ea5e61f9eb`, rc 77) and exited 0 on `workspace/harnesses/fuzz_minmea.e-acsl` (`replay_minmea.json`, `not_reproduced`). The verifier recovered by reading the artifact's recorded `engine` and rebuilding with `run_eacsl_fuzz.py replay --engine sanitizers`; a less careful verifier would have returned `rejected`.
- **Cause:** the fuzz report records each artifact's `engine` (`eacsl` or `sanitizers`), and a `fw`/`asn`-only alarm (or one inside a libc function) is invisible to the E-ACSL build; the brief does not say to replay with the engine that produced the candidate.
- **Fix (proposed):** amend the Case A replay step to select the build recorded on the candidate: read the candidate's artifact `engine`, use the E-ACSL binary for `eacsl`, and rebuild/`--engine sanitizers` for `sanitizers`; when the two disagree, the sanitizer result is the witness and the E-ACSL `not_reproduced` is expected and must be stated in the record. Add a regression test with an artifact whose engine is `sanitizers` and whose E-ACSL replay is clean.

### Symptom: `ArtifactError: artifact exceeds 67108864 bytes: workspace/reports/eva/<module>.json` After Merging Sharded Eva Reports
- **Partially worked around live in-repo by the run agent; open pipeline bug across remaining readers** (seen on `QCBOR`, `run-6`, 2026-11-15).
- **Symptom:** After `eva_shards.py merge` combined the 9 shard reports of `libqcbor_a` into `workspace/reports/eva/libqcbor_a.json` (`217,053,269` bytes / `207.0 MiB`), Phase 2 -> 3 ingestion failed in two places:

### Symptom: `ledger.py scaffold-verifier` Pre-Populates `record.reproducers` With Artifacts That Do Not Reproduce, and Copies a Misleading `harness.entry_function`
- **Seen on:** QCBOR, run-6, 2026-11-15, Crash Verifier `verify-ieee754_singletohalf_ceaaa12428` (candidate `src/ieee754.c#IEEE754_SingleToHalf::shift::ceaaa12428`). The scaffold listed `workspace/crashes/libqcbor_a/crash-00ed842c...`, whose parent replay is `not_reproduced` under the regenerated (182-case) harness; the verifier had to prune it by hand because the brief says to list only inputs that reproduced. The scaffold also set `record.harness.entry_function` to the sidecar's `entry_fn` (`UsefulBuf_Compare`) although the crashing path is dispatch case 68's `QCBORDecode_GetInt64ConvertAll`, so the field named a function that is not on the path.
- **Cause:** `scaffold-verifier` copies the candidate's `reproducers` list (every artifact sharing the fingerprint) without consulting `workspace/reports/replay/`, and copies `entry_fn` from `harness_<mod>.json` even for `entry_style: "dispatch"` harnesses, where `entry_fn` is only the nominal parser and every dispatch case calls a different function.
- **Fix:** **Open pipeline gap.** Suggested: have `scaffold-verifier` keep only reproducers whose replay report says `reproducible: true` (and put the rest in a `stale_reproducers` field), and for a dispatch harness either leave `entry_function` unset or name the case's function from the artifact (`dispatch_case` + its call). Workaround in run-6: verifiers pruned stale inputs and named the real entry function in `record.verifier.notes`.

### Symptom: Two Crash Verifiers Give Opposite Verdicts on the Same Decision Point, and the Parent Has No Command to Reconcile Them (`ledger.py: error: argument cmd: invalid choice: 'reopen'`)
- **Seen on:** QCBOR, run-6, 2026-11-15 (external supervisor; run transcript from 03:20). `src/qcbor_main_encode.c#QCBOREncode_EncodeHead::index_bound` has two fingerprints at the same line, both about `uMinLen` > 8 reading past `aIterate[4]`.
  - `ce76fb1dc0` was ingested `confirmed` (medium): the function is public and takes any `uint8_t`.
  - `02209a353f` was ingested `rejected` (`harness_induced`): only the harness passes `uMinLen` > 8.
  - The scheduler raised no flag. The parent noticed by itself, tried `ledger.py reopen` (`invalid choice`), then dispatched an off-schedule subagent `reverify-encodehead-ce76` with a parent-written brief citing the sibling's rejection evidence. It planned to ingest that result with `ledger.py ingest-verifier` directly, outside `wp_scheduler.py`. The re-verifier returned `rejected` at 03:33.
  - `ledger.py ingest-verifier agents/reverify-encodehead-ce76/scratch/result.json` refused it: `"cannot merge conflicting verdicts for src/qcbor_main_encode.c#QCBOREncode_EncodeHead::index_bound::ce76fb1dc0: confirmed vs rejected"`.
  - The parent then backed up `findings.json` to `state/findings.json.bak` and deleted the finding by hand.
  - `validate_artifacts.py run-dir .` caught it: `candidates.json: ...ce76fb1dc0 marked verified but resolved fingerprint(s) [...] have no findings.json record`. The parent restored the backup (validation `ok`, 20 findings), so the run's state is as the pipeline wrote it. The validator worked as intended.
  - The run therefore keeps `EncodeHead` as a confirmed medium finding, while the parent's own assessment is "rejected". The parent says it will mention this in its final summary.
- **Cause:** **Open pipeline gap.** Verifiers are dispatched per fingerprint. Nothing in `wp_scheduler.py` `complete` or `ledger.py ingest-verifier` compares a new verdict with earlier verdicts that share its `decision_point` (or root cause), and there is no command for a deliberate second opinion.
  - Reopening exists only when new tool evidence reproduces a rejected candidate (`tool_evidence_on_verified_candidate`, entry above).
  - The parent's workaround breaks two properties the gate relies on. The re-verifier was not independent: its brief argued the sibling's case. And its verdict bypassed the scheduler's bookkeeping.
  - For context, the run-5 review judged this same defect a real public-API hardening bug (upstream draft 07).
  - The run-6 findings assessment ([`../runs/2026-11-15-qcbor-run6-findings-assessment.md`](../runs/2026-11-15-qcbor-run6-findings-assessment.md) §3.5) reproduced it again on `dev` `9bd0845` and `19c3367`.
    - The `harness_induced` rejection of `02209a353f` is wrong. It repeats run-5 #26: the verifier read the in-tree callers' `uMinLen` values as the contract of a function the public header exports.
    - Two verdicts on one decision point therefore disagree, and the gap is also in the verifier's reasoning, not only in reconciliation. `crash_verifier_brief.md` should say that an exported function's contract is its header documentation, not its callers' usage.
- **Fix:** none yet. `ledger.py` and `wp_scheduler.py` hold uncommitted hot patches from this run, so no fixer was dispatched. Suggested:
  - `complete`/`ingest-verifier` should flag a verdict that contradicts an ingested verdict with the same `decision_point`, and open a `reconcile:<decision_point>` task.
  - That task gets a fresh verifier whose brief carries both records, without the parent's framing.
  - `ledger.py` should keep both verdicts and record the reconciled one, instead of letting the last ingest win.
- **Status (2026-11-15, run-6 remediation):** **fixed** (`87bb1b6`, `5073fa8`, `f790d15`, `d4db9a5`), without a new command.
  - `ledger.py` (`_sink_key`, `sink_conflicts`, `_reconcile_sink_conflicts`, run at the end of `cmd_ingest_verifier`): a positive verdict (`confirmed`, `needs_validation`) and a rejection of any class but `duplicate` at one sink (file, function, baseline line, kind; not the decision point, which the rejected run-6 record did not have) are recorded on both records as `conflicts_with` and returned as `sink_conflicts`. A verifier cannot supply `conflicts_with` itself.

- **Seen on:** c-ares run-1, 2026-11-16 ([`../runs/2026-11-16-c-ares-run1-supervision.md`](../runs/2026-11-16-c-ares-run1-supervision.md)). Two Phase 1 candidates come from the checking tool, not from the target ([`./eacsl-and-fuzzing.md`](./eacsl-and-fuzzing.md)):

  - **Reject it as `harness_induced`:** this creates a harness repair that cannot help (`scripts/wp_scheduler.py` `_ensure_repair`, up to 2 per module), then `harness_unchanged` marks.

  - **Brief, Case A:** a new step, "Check That the Tool Is Right". The class follows what makes the property hold: a line of the target means `disproved_by_source`; a compiler, linker or tool behaviour means `toolchain_artifact`. Never use `harness_induced` for a tool's false alarm.
  - **Brief, "Rejection Classes":** a new section covering all 7 classes.
  - **Brief, "Toolchain Artifacts":** a new section. Basis `checked` needs all three of: a source that is correct at the sink, a named toolchain fact, and a tool output.
    - The tool output can be a replay on an independent checker that covers the alarm kind, a standalone minimal program, or the instrumented source.
    - A rebuild without the check is not evidence.
  - **Skills:** `framac-wp/SKILL.md` and `framac-verify/SKILL.md` say the class creates no task and is recorded as a pipeline or upstream defect.
  - **Tests:**
    - `tests/test_brief_result_contract.py::test_verifier_brief_names_every_rejection_class` (fails on `aab6b8f`)
    - `tests/test_rejection_reopen.py::test_a_checked_toolchain_artifact_is_not_repaired_or_reopened`
    - `tests/test_rejection_reopen.py::test_a_located_toolchain_artifact_is_reopened_by_a_new_reproducer`
    - `tests/test_wp_scheduler.py::test_toolchain_artifact_rejection_creates_no_repair`
- **Still open:**
  - `docs/references/e-acsl-quickref.md`, the only list of known issues verifiers see in the image, does not list the two c-ares families yet. Their fixes (`sup/c-ares-eacsl-literal-charset` and `sup/c-ares-eacsl-format-promotion`) are now merged into `phase1-remediation` (2026-11-16), so the families can be added.

### Symptom: A Candidate Merged by Site Replays Its Reproducers on One Engine, and `fingerprint_matches` / the Minimize Interest Test Read a Detection of the Other Engine as Not Reproduced
