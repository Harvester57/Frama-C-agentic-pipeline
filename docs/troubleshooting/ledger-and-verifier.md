# Ledger, Crash Verifier & Artifact Validation Issues

Issues encountered in coverage ledger ingestion (`ledger.py`), Crash Verifier scaffolding and verdict validation (`scaffold-verifier`, `ingest-verifier`), candidate reopening, and JSON Schema checks (`validate_artifacts.py`, `schemas/`). See [`./README.md`](./README.md) for the master index.

### Symptom: `ingest-verifier` Refuses `confirmed` With `requires a parent-verified reproducible crash report matching sha256 ...` When the Verifier Lists a Reproducer It Created Itself
- **Fixed (commit `8f25258`, merged into `phase1-remediation` as `e2ba684` on 2026-11-14, not pushed).** The crash-verifier brief promises "the parent replays your reproducers itself before ingesting the verdict", but the parent only ever replays the candidate's original reproducers, so a witness-less candidate can never be confirmed with a verifier-found crash.
- **Seen on:** minmea, run-1, 2026-11-14, agent `verify-minmea_getdatetime_5ab43d1511` (candidate `minmea.c#minmea_getdatetime::signed_overflow::5ab43d1511`): `step --complete` returned `"error": "confirmed finding minmea.c#minmea_getdatetime::signed_overflow::5ab43d1511 requires a parent-verified reproducible crash report matching sha256 19de7e904c52c770751971280310988da016a8fa6c5fa3b008a94f9457ac818e"` and requeued the verifier (`verify-minmea_getdatetime_5ab43d1511-2`). The verifier had reproduced the candidate on the recorded crash and on a crafted, fully parsed ZDA sentence it wrote to `scratch/seeds/`, and listed both in `record.reproducers`.
- **Cause:** [`../../scripts/wp_scheduler.py`](../../scripts/wp_scheduler.py) `_parent_replay` (line 3219) replays only `cand["reproducers"]` from `candidates.json`; it never reads `record.reproducers` from the verifier result. `ledger.cmd_ingest_verifier` (line 3185) promotes a scratch reproducer and then requires its sha in `_collect_reproducible_shas`, which is built from `_parent_replay`'s reports plus the candidate's tool outputs. A reproducer that exists only in the verifier's scratch (a seed or a phase-3 campaign crash) is therefore never parent-verified, although [`../../skills/framac-wp/crash_verifier_brief.md`](../../skills/framac-wp/crash_verifier_brief.md) line 74 tells the agent it will be.
- **Workaround used in this run:** the second verifier was instructed to keep `record.reproducers` to the inputs in `workspace/reports/replay/minmea.c_minmea_getdatetime_signed_overflow_5ab43d1511-d69019b205.json` (the recorded `workspace/crashes/minmea/...` artifacts, whose shas the parent did replay) and to put the crafted seed in `record.evidence`. A candidate with no original reproducer at all (a pure Eva/prover hypothesis) would still be stuck.
- **Fix (`8f25258`, merged as `e2ba684`):** `_complete_verifier` calls the new `_parent_replay_verifier_inputs`: the reproducers of `confirmed` records that are files under `agents/<id>/scratch/` are replayed on the candidate's module binary, built by the parent, with the new `run_eacsl_fuzz.py replay-candidates --fingerprint <fp> --inputs <files> --out-json workspace/reports/replay/verifier/<agent id>.json`, and that report is passed to `ingest-verifier` with the candidate's own. `ledger.py` is unchanged, so an input the parent cannot reproduce is still refused. The step output carries `verifier_replay` (returncode, report, inputs, status, `fingerprint_matches`), and the brief now says what is replayed. Reproduced in Docker on a copy of the run (`minmea-repro/verifier-reproducers`): the unfixed scripts return the refusal above with `requeued_ingest_error`; the fixed scripts with the libc shim (then uncommitted, now commit `7be8bd1`) return `ingested`, `confirmed`, `fingerprint_matches: true`. Tests: `tests/test_wp_scheduler.py` (`test_parent_replays_the_scratch_reproducers_a_verifier_confirms_on`, `test_a_scratch_reproducer_the_parent_cannot_reproduce_is_still_refused`, `test_a_verdict_without_scratch_reproducers_needs_no_extra_replay`) and `tests/test_fuzz_subcommands.py::test_replay_candidates_fingerprint_replays_given_inputs_on_the_candidates_binary`.
- **Status (2026-11-18):** the bug in the next bullet (`ingest-verifier` confirms on any reproducible replay) is **fixed** in `73dd079`, `0b3be3e` (a control test), `2ae1751`, `6166906` and `90d11ff`, now merged into `main`.
  - `scripts/ledger.py` (`_collect_reproducible_artifacts`, which replaces `_collect_reproducible_shas`; `_accepted_failures`, `_judge_reproducer`, `_other_failure_refusal`, `73dd079`): the parent's replay of each reproducer is compared with the record's defect: the candidate's key, an observation's fingerprint, the candidate's statement site, or the same of a related candidate. Where one side has no statement, function and kind decide. A replay that failed at another statement is refused, and the message names both failures and the candidate that owns the other one. A replay that names no statement (unparsed failure, timeout, resource abort) counts only for the candidate's own record and an input recorded on the candidate before verification; the finding then gets an evidence entry "Failure identity not compared" and the command returns `reproducers_not_compared` (copied into the step output by `wp_scheduler._complete_verifier`, `a5e8d57`). Tests: `tests/test_verifier_replay_identity.py` (fixtures `tests/fixtures/replay_identity/`, the recorded candidates and replay reports of libmodbus run-1 and mpack run-4).
  - `scripts/crash_replay.py` (`replay_identity`, `2ae1751`): each replay report says per input what the ledger would make of it (`identity`: `match`, `mismatch` or `uncompared`), by calling the ledger's own functions. `fingerprint_matches` is unchanged and compares fingerprints only; the two disagree both ways. Test: `tests/test_replay_identity_field.py`.
  - `scripts/generate_report.py` (`identity_not_compared`, `6166906`, `90d11ff`): REPORT.md section 3 counts and names the findings that count a reproducer whose failure was not compared, FINDINGS-DETAIL.md has a paragraph, and `report.sarif` marks them with `properties.failureIdentityNotCompared`. Test: `tests/test_report_identity_and_merge_notes.py`.
  - The crash verifier brief states the rule (`5d28f08` on the same branch).
- **Open pipeline bug:** [`../../scripts/wp_scheduler.py`](../../scripts/wp_scheduler.py) still copies `fingerprint_matches` of the verifier-input replay into its step output (`verifier_replay`), not `identity`.
- **Open pipeline bug:** a reproducer that fails elsewhere is refused for this candidate but not recorded as a candidate of its own; the verifier has to return it.
- **Open pipeline bug:** a verifier can still refingerprint the primary record to whatever its seed hit. Only the required `refingerprint_reason` guards it.
- **Open pipeline bug:** the callers of `_candidate_site` outside the replay path still mix work-tree and baseline line numbers.
- **Pipeline bug as recorded with the fix of `8f25258` (fixed on 2026-11-18, see the Status above):** `_collect_reproducible_shas` in [`../../scripts/ledger.py`](../../scripts/ledger.py) reads only `reproducible` and `sha256` of a replay report, so an input that makes the parent's replay fail on a different failure than the candidate's still confirms the finding. Seen in the Docker reproduction with the committed scripts of `7369244` alone: the verifier's seed failed on `\initialized(&endptr)` in `minmea_scan` (line 224, `minmea.c#minmea_scan::e_acsl_rte::f797a710af`), not on the candidate's signed overflow, and the verdict was ingested as `confirmed` with `fingerprint_matches: false`. ### Symptom: A Crash Verifier Replays a Sanitizer-Only Defect on the E-ACSL Binary, Gets `not_reproduced`, and Is One Step From Rejecting a Real Bug
- **Open pipeline gap:** [`../../skills/framac-wp/crash_verifier_brief.md`](../../skills/framac-wp/crash_verifier_brief.md) Case A tells the verifier to replay on `compile.binary` from `workspace/reports/fuzz/{module}.json` (usually the E-ACSL binary). A candidate whose alarm is a UBSan check inside libc (minmea's `abs(INT_MIN)` at `minmea.c:635`, where E-ACSL does not instrument the negation) then reports `not_reproduced` on the E-ACSL build.
- **Seen on:** minmea, run-1, 2026-11-14, agent `verify-minmea_parse_zda_ea5e61f9eb`: the same artifact failed on the sanitizer build (`agents/.../scratch/replay_minmea_san.json`, UBSan `negation of -2147483648 cannot be represented in type int`, fingerprint `minmea.c#minmea_parse_zda::signed_overflow::ea5e61f9eb`, rc 77) and exited 0 on `workspace/harnesses/fuzz_minmea.e-acsl` (`replay_minmea.json`, `not_reproduced`). The verifier recovered by reading the artifact's recorded `engine` and rebuilding with `run_eacsl_fuzz.py replay --engine sanitizers`; a less careful verifier would have returned `rejected`.
- **Cause:** the fuzz report records each artifact's `engine` (`eacsl` or `sanitizers`), and a `fw`/`asn`-only alarm (or one inside a libc function) is invisible to the E-ACSL build; the brief does not say to replay with the engine that produced the candidate.
- **Fix (proposed):** amend the Case A replay step to select the build recorded on the candidate: read the candidate's artifact `engine`, use the E-ACSL binary for `eacsl`, and rebuild/`--engine sanitizers` for `sanitizers`; when the two disagree, the sanitizer result is the witness and the E-ACSL `not_reproduced` is expected and must be stated in the record. Add a regression test with an artifact whose engine is `sanitizers` and whose E-ACSL replay is clean.
- **Status (2026-11-19):** fixed in the brief (`761e839`, `247d350`, now on `main`), not tried on a live run. Case A replays each reproducer on the engine the parent's replay uses (the report's `engine_used` or the artifact's `engine`, `observations[].engine`; `compile.binary` or `sanitizer_compile.binary`). A sanitizer failure with a clean E-ACSL replay is the witness, and the E-ACSL `not_reproduced` goes in `record.verifier.notes`. `ingest-verifier` accepts it when the parent's replay ran on the sanitizer build. Test: `test_ingest_verifier_confirms_a_sanitizer_only_witness_with_a_clean_eacsl_replay` in `tests/test_verifier_brief_gaps.py`.
  - **Open pipeline bug:** a breaker crash (its observation has no engine) and every input a verifier wrote itself (`wp_scheduler._parent_replay_verifier_inputs`) are replayed by the parent on `auto`, which is E-ACSL when it builds. A sanitizer-only witness there is refused with `requires a parent-verified reproducible crash report`; the brief tells the verifier to return `needs_validation`. `scaffold-verifier` still writes the E-ACSL binary in every reproducer command.

### Symptom: `ledger.py scaffold-verifier` Pre-Populates `record.reproducers` With Artifacts That Do Not Reproduce, and Copies a Misleading `harness.entry_function`
- **Seen on:** QCBOR, run-6, 2026-11-15, Crash Verifier `verify-ieee754_singletohalf_ceaaa12428` (candidate `src/ieee754.c#IEEE754_SingleToHalf::shift::ceaaa12428`). The scaffold listed `workspace/crashes/libqcbor_a/crash-00ed842c...`, whose parent replay is `not_reproduced` under the regenerated (182-case) harness; the verifier had to prune it by hand because the brief says to list only inputs that reproduced. The scaffold also set `record.harness.entry_function` to the sidecar's `entry_fn` (`UsefulBuf_Compare`) although the crashing path is dispatch case 68's `QCBORDecode_GetInt64ConvertAll`, so the field named a function that is not on the path.
- **Cause:** `scaffold-verifier` copies the candidate's `reproducers` list (every artifact sharing the fingerprint) without consulting `workspace/reports/replay/`, and copies `entry_fn` from `harness_<mod>.json` even for `entry_style: "dispatch"` harnesses, where `entry_fn` is only the nominal parser and every dispatch case calls a different function.
- **Fix:** **Open pipeline gap.** Suggested: have `scaffold-verifier` keep only reproducers whose replay report says `reproducible: true` (and put the rest in a `stale_reproducers` field), and for a dispatch harness either leave `entry_function` unset or name the case's function from the artifact (`dispatch_case` + its call). Workaround in run-6: verifiers pruned stale inputs and named the real entry function in `record.verifier.notes`.

### Symptom: Crash Verifiers Rate Application-Argument Bugs as `attacker_input` / `medium`, Under-Rate a Corrupt Returned Length, and Call Address-Taken Indeterminate Reads "Undefined Behaviour"
- **Seen on:** QCBOR, run-6, 2026-11-15, in the findings assessment ([`../runs/2026-11-15-qcbor-run6-findings-assessment.md`](../runs/2026-11-15-qcbor-run6-findings-assessment.md)). The defects are real; the labels are wrong.
  - `UsefulOutBuf_Compare` (`0e34c586b3`, `b939358da2`, `22aa038aa3`) and `QCBOREncode_EncodeHead` (`ce76fb1dc0`) are recorded `controlled_by: attacker_input`, `severity: medium`.
    - The only trigger is an argument the application chooses: offsets and lengths for `Compare`, and the `uMinLen` constant for `EncodeHead`.
    - QCBOR's own callers cannot produce these values. The run-5 review rated both low (drafts 05, 07).
  - One finding (`b1b1b1fe2a`, a private upstream draft; details in the assessment) is recorded `medium`, as a library-side initialization read. Its real impact is an out-of-bounds read in the caller's use of a value the library returns, which the assessment rates high.
  - `ConsumeItem` (`b5ec324eae`) and `GetItemInMap` (`c132f24cbe`) say that reading the indeterminate local is undefined behaviour. Both objects have their address taken, so C11 6.3.2.1p2 does not apply: the value is indeterminate, not UB.
- **Cause:** `skills/framac-wp/crash_verifier_brief.md`:
  - It defines `attacker_input` as "bytes of the fuzz input". In an `--api` dispatch harness those bytes also pick API arguments, so the label cannot tell decoded data from a caller's parameter. `reachability` is per harness (`untrusted_surface`), not per argument.
  - Its severity anchors only describe effects inside the target, not a corrupt value returned to the caller and used there.
  - It gives no rule for uninitialized reads.
- **Fix:** **Open pipeline gap** (brief). The verdicts were right, so no run state is wrong; only severities and wording in `findings.json` and `REPORT.md` are. Suggested:
  - Add a `caller_argument` value to `controlled_by`, for an exported function's parameter that the application normally supplies as a constant or as derived state, and cap it at `low` unless the header documents the parameter as untrusted.
  - Add a severity anchor for a corrupt value the library returns, when the caller's use of it goes out of bounds. Rate it like the out-of-bounds access it causes.
  - State that reading an indeterminate object whose address is taken is not UB, and that MSan's eager parameter check reports a value that is only passed, never used.

### Symptom: A Reproducible E-ACSL False Positive Has No Rejection Class in the Crash Verifier Brief
- **Seen on:** c-ares run-1, 2026-11-16 ([`../runs/2026-11-16-c-ares-run1-supervision.md`](../runs/2026-11-16-c-ares-run1-supervision.md)). Two Phase 1 candidates come from the checking tool, not from the target ([`./eacsl-and-fuzzing.md`](./eacsl-and-fuzzing.md)):
  - `src/lib/str/ares_buf.c#ares_buf_consume_until_charset::mem_access::32e8ca0441`: string literals merged at link time.
  - `unknown#inet_ntop4::eacsl_format_error::1f30ebf225`: `%u` given a promoted `unsigned char`.
- **Cause:** the schemas allow `toolchain_artifact`, and QCBOR run-5 used it. But [`../../skills/framac-wp/crash_verifier_brief.md`](../../skills/framac-wp/crash_verifier_brief.md) named only `harness_induced` and the source-based classes. A verifier facing a reproducing E-ACSL false alarm had three options, all wrong:
  - **Confirm it under Rule 2:** a false finding.
  - **Reject it as `harness_induced`:** this creates a harness repair that cannot help (`scripts/wp_scheduler.py` `_ensure_repair`, up to 2 per module), then `harness_unchanged` marks.
  - **Reject it under another class with basis `model` or `located`:** every new reproducer reopens it, up to `max_reopenings`.

  The ledger and the scheduler already handle `toolchain_artifact` correctly:
  - it creates no repair;
  - with `refutation_basis: checked`, later tool reproducers are recorded as `checked_rejection` and do not reopen it (`scripts/ledger.py` around 474-479).
- **Fix:** commits `fca3aa6` and `66166bd`, from branch `sup/c-ares-verifier-toolchain-artifact`, fixed and merged into `phase1-remediation` (2026-11-16).
  - **Brief, Case A:** a new step, "Check That the Tool Is Right". The class follows what makes the property hold: a line of the target means `disproved_by_source`; a compiler, linker or tool behaviour means `toolchain_artifact`. Never use `harness_induced` for a tool's false alarm.
  - **Brief, "Rejection Classes":** a new section covering all 7 classes.
  - **Brief, "Toolchain Artifacts":** a new section. Basis `checked` needs all three of: a source that is correct at the sink, a named toolchain fact, and a tool output.
    - The tool output can be a replay on an independent checker that covers the alarm kind, a standalone minimal program, or the instrumented source.
    - A rebuild without the check is not evidence.
  - **Skills:** `framac-wp/SKILL.md` and `framac-verify/SKILL.md` say the class creates no task and is recorded as a pipeline or upstream defect.
  - **Tests:**
    - `tests/test_brief_result_contract.py::test_verifier_brief_names_every_rejection_class` (fails on `aab6b8f`)
    - `tests/test_rejection_reopen.py::test_a_checked_toolchain_artifact_is_not_repaired_or_reopened`
    - `tests/test_rejection_reopen.py::test_a_located_toolchain_artifact_is_reopened_by_a_new_reproducer`
    - `tests/test_wp_scheduler.py::test_toolchain_artifact_rejection_creates_no_repair`
- **Still open:**
  - `docs/references/e-acsl-quickref.md`, the only list of known issues verifiers see in the image, does not list the two c-ares families yet. Their fixes (`sup/c-ares-eacsl-literal-charset` and `sup/c-ares-eacsl-format-promotion`) are now merged into `phase1-remediation` (2026-11-16), so the families can be added.
  - A `located` or `model` `toolchain_artifact` still reopens, up to `max_reopenings`.
  - Ingest does not check a stated `checked` basis against `record.evidence`.
  - A run on a checkout older than the merge (such as c-ares run-1) reads the old brief: its verifiers may still confirm these two families, or reject them as `harness_induced`.

### Symptom: A Verifier Result Is Requeued (`requeued_ingest_error`) Because One Cited Evidence File Exceeds the 1 MiB Promotion Limit, or Is a Path Outside the Run Directory
- **Seen on:** mpack run-3 (2026-11-17). `wp_scheduler.py step --complete verify-mpack_builder_complete_0f273bdef1` answered `action: requeued_ingest_error` with no decision; the same task was handed out again as `verify-mpack_builder_complete_0f273bdef1-2`.
- **Cause:** the record cited the module's instrumented source (`workspace/harnesses/fuzz_libmpack_a__mpack_writer_2.instrumented.c`, about 17 MB) as an evidence file. `ledger.py ingest-verifier` promotes cited evidence into the run's artifact store and refuses a file above 1 MiB, which fails the whole ingest instead of dropping or truncating that citation; the verdict is lost and the task is re-queued, costing a full verifier run. Second attempt (`-2`) succeeded because its record cites no file that large.
