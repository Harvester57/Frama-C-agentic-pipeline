### Symptom: `Exceeded heap allocation limit of 128MB -- heap memory space moved` Recorded as a Target Crash, and the Crash Parsed as `unparsed_crash`
- **Seen on:** mpack run-3 (2026-11-17), modules `libmpack_a__mpack_expect`, `_mpack_expect_2`, `_mpack_node_4`, `_mpack_writer`, `_mpack_writer_2`. Example artifact `workspace/crashes/libmpack_a__mpack_expect/crash-c82085c082a2d0df92180788ea3953381b1106d4` (11 bytes) replays with returncode 77 and stderr `e_acsl_segment_tracking.c:532: Exceeded heap allocation limit of 128MB -- heap memory space moved`, stack `raise -> raise_abort -> private_assert_fail -> set_heap_segment -> unsafe_malloc -> malloc -> mpack_read_bytes_alloc_impl`. All six unparsed-crash candidates of `_mpack_expect` come from one dispatch case with an 8-byte wire count between 2^32 and about 2^47. A further instance in `_mpack_writer_2` does not go through `malloc` at all: the 17-byte reproducer `02 f6ffffffffffffff 0000003b00000000` selects dispatch case 2, whose `mpack_realloc` call is the MPACK_REALLOC wrapper (`src/mpack/mpack-platform.h:1844-1847`), so the request is `realloc(4024 -> 253671833600)` and the abort is `set_heap_segment` (`e_acsl_segment_tracking.c:528`) <- `unsafe_realloc` (`:715`) <- `mpack_realloc__fc_inline_7`. Harness repair attempt 1 of that module had replaced the case's former static 4024-byte buffer with a `malloc`'d block (the earlier `harness_induced` defect, record `9d8a4c7c02`), which is what exposes the tool limit here. A target-free probe of `malloc(4024)` + `realloc(4024 -> 253671833600)` aborts with the identical line and message, while `realloc(4024 -> 8192)` succeeds and the uninstrumented build serves the 253 GB request (verifier `verify-unknown_function_fc5c85a81e`).
- **Cause:** two independent gaps in the E-ACSL path.
  1. **Tool limit:** with `--libc-replacements`, `malloc` is E-ACSL's `unsafe_malloc` and `realloc` its `unsafe_realloc`, which serve requests from a fixed `E_ACSL_HEAP_SIZE` of 128 MB and call `private_assert_fail` in `set_heap_segment` when the request makes dlmalloc move that space. A target that correctly checks `malloc`'s result and raises `mpack_error_memory` (target `src/mpack/mpack-reader.c:527-531`) therefore produces a *reproducible false crash*: a target-free probe that only calls `malloc(237065284864)` aborts identically under `e-acsl-gcc` and runs clean without instrumentation. `docs/references/e-acsl-quickref.md` ("Limitations that change verdicts") does not list this limit, so verifiers must recognise it themselves.
  2. **Parsing:** `run_eacsl_fuzz.py` keeps only the last 2000 bytes of a crash's stderr, and the runtime assertion line precedes the (long) backtrace, so the failure parses as `failure: null` and the candidate is recorded as `harness_...c#unknown_function::unparsed_crash::<fp>`. The fingerprint then names a placeholder function, one candidate per artifact instead of per site, and every one needs manual triage.
- **Correction (run supervisor):** in run-3, 17 of the 24 `unparsed_crash` candidates are this heap abort, all in `_mpack_expect` and `_mpack_expect_2` (caller `mpack_read_bytes_alloc_impl`). Not all of the other 7 are something else: at least two of the `_mpack_writer_2` candidates (`harness_libmpack_a__mpack_writer_2.c#unknown_function::unparsed_crash::fc5c85a81e` and `::d97cd040c9`) are this abort through `unsafe_realloc` from the `mpack_realloc` dispatch case, both rejected as duplicates of `src/mpack/mpack-reader.c#mpack_read_bytes_alloc_impl::crash::846ff215a0`; `_mpack_node_4` is a "Not a start of block in realloc" in `mpack_realloc__fc_inline_7`; the other `_mpack_writer` / `_mpack_writer_2` candidates are a UBSan SEGV in `mpack_tag_cmp`. ### Symptom: E-ACSL Reports `rte: initialization` on Benign Inputs
- **Cause:** E-ACSL builds pass `-rte-initialized @all`, so every read must be of initialized memory, and memory written outside instrumented code is never marked initialized. The usual culprits:
  1. target code reads libFuzzer's `data` directly instead of the harness copy `fuzz_buf`, for example in a hand-written or `custom` harness;
  2. an external library behind `fc_stubs` fills a buffer;
  3. a libc call outside `EACSL_LIBC_EFFECTS` writes through a pointer. Since S9 the libc shim marks what `read`, `recv`, `recvmsg`, `getsockname`, `strtol`'s `endptr` and the other functions of that table wrote (see "E-ACSL Reports `\initialized` Right After a libc Call" below).
- **Fix:**
  - Pass `fuzz_buf` (generated harnesses do), or copy the input into the harness's own buffer with `memcpy`, which E-ACSL marks initialized.
  - If a library-filled buffer is the cause, initialize it before the call (`= {0}` / `memset`) or rerun with `--no-rte-initialized`. That opt-out is recorded in `reduced_checks`, and Eva still reports uninitialized reads statically.
  - Per-function exclusion (`-rte-initialized=@all,-f`) works for `static` functions too since Frama-C 34 (option-hook bug fixed; in Frama-C 33 it only worked for non-`static` functions).
  - The crash verifier classifies such reports as `harness_induced`.

### Symptom: Why Not `-L` / Frama-C's libc for E-ACSL?
- E-ACSL aborts on Frama-C libc specifications (`unbounded ranges are not part of E-ACSL`, `share/libc/string.h`). Host-header mode is the only supported E-ACSL mode.

### Symptom: `call to undeclared function 'X'` or `invalid application of 'alignof' to an incomplete type`
- **Cause:** a [`../../templates/fc_stubs/`](../../templates/fc_stubs/) header lacks a prototype the target calls, or declares an opaque handle (`struct json_object`) as incomplete. E-ACSL emits `alignof` on pointed-to types.
- **Fix:** add the prototype and complete the handle with a single dummy member (see [`../../templates/fc_stubs/README.md`](../../templates/fc_stubs/README.md)). Tool JSONs list missing prototypes under `undeclared_functions`. For Eva/WP this is a soundness issue: Frama-C invents `int X()`.
- **Target-specific compat headers** (e.g. completing OpenSSL 3 opaque handles `EVP_PKEY`, `BIGNUM`, ... for the fuzz build) must be delivered **source-side**: pass them to `generate_harness.py --compat-include <header>` so the harness `#include`s them after the module header. Never add them to cppflags as `-include`: force-including a header that pulls in system headers re-registers libc properties per merged translation unit and the Frama-C kernel aborts with `trying to register twice property 'assumes nonnull_p'`.

### Symptom: Instrumentation Aborts With `no function 'X'`
- **Cause:** `-rte-select` / `-e-acsl-functions` named a function that is absent from the parsed AST (disabled by `#if`, or in a file that failed to parse).
- **Fix:** function discovery runs on preprocessed sources. Names Frama-C still rejects are dropped once and listed in `rte_select_dropped`.
- **Open pipeline gap:** the Frama-C kernel renames a function defined with plain `inline` (C99 semantics, no external declaration) to `<fn>__fc_inline`.
  - `-e-acsl-functions <fn>` then aborts: `[e-acsl] User Error: incorrect argument for option -e-acsl-functions (no function 'fix_scale')`.
  - The drop-and-retry leaves the function uninstrumented, whatever the `-std`.
- **Open pipeline bug (the retry gives up after 8 names):** seen on QCBOR v2.0-beta-1 run-2 (`run-2-d574bb040623`), 2026-11-24, Phase 3 header architect `arch-libqcbor_a` for `inc/qcbor/UsefulBuf.h`. The architect's guardrail (`agents/arch-libqcbor_a/scratch/header_guard_libqcbor_a.json`) ended `status: compile_error`, `reason: eacsl_instrumentation_failed`, with `[rte] User Error: incorrect argument for option -rte-select (no function 'UsefulOutBuf_SubString')` and `e-acsl-gcc: fatal error: aborted by Frama-C`; `rte_select_dropped` lists 8 names (`UsefulOutBuf_SubString`, `UsefulOutBuf_SetStream`, `UsefulOutBuf_RetrieveOutputStorage`, `UsefulOutBuf_InsertUint64`, `...InsertUint32`, `...InsertUint16`, `...InsertString`, `...InsertFloat`). The architect `failed`, so Phase 3 starts without baseline header contracts for `libqcbor_a`.
  - **Cause:** [`../../scripts/fuzz_build.py`](../../scripts/fuzz_build.py) (lines 1304-1323) retries the frontend at most 8 times (`for _ in range(8)`), and Frama-C names one unknown function per run, so a list with 9 or more unknown names always fails. The guardrail's `-rte-select` list holds every function the header declares; the `static inline` helpers of `UsefulBuf.h` that nothing in the translation unit calls are not in Frama-C's AST. Each retry is a full E-ACSL frontend run.
  - **Fix:** none yet. Directions: retry while each run drops a new name (bounded by the list length, not 8), or filter the list before the first run to the functions the parsed AST holds (the Phase 0 model, or a cheap `frama-c -print`/function listing), so one run suffices.
  - Seen on a supervisor fixer's fixture (branch `sup/c-ares-tf-std-flag`, 2026-11-16), not on c-ares.
  - Proposed: map `<fn>` to `<fn>__fc_inline` in the selection, which would keep its checks.

### Symptom: Linker or Shadow Memory Conflict When Combining E-ACSL with AddressSanitizer (`-fsanitize=address`)
- **Cause:** E-ACSL embeds its own shadow-memory runtime (`rtl`) to track byte-level pointer validity (`\valid`), initialization (`\initialized`), and sub-object bounds. AddressSanitizer (`ASan`) also maps shadow memory and intercepts `malloc`/`free`. Running both in the same binary causes immediate `mmap` collisions or false aborts.
- **Fix:**
  - Compile E-ACSL fuzz binaries with `-fsanitize=fuzzer` **without** `-fsanitize=address` (as configured in `run_eacsl_fuzz.py`). E-ACSL's own runtime already detects out-of-bounds accesses, use-after-free, bad free, uninitialized reads, and sub-object overflows.

### Symptom: E-ACSL Reports `\initialized` Right After a libc Call (`\initialized(&endptr)` After `strtol`, a Socket Address After `getsockname`)
- **Seen on:** libmnl's socket module (`getsockname` in `mnl_socket_bind`, runs 5 and 6, rejected by the Crash Verification Gate) and minmea (`\initialized(&endptr)` at `minmea.c:224` in `minmea_scan`, on both MINMEA-01 and MINMEA-02); finding F17 of [`../plans/phase1-review.md`](../plans/phase1-review.md).
- **Cause:** E-ACSL runs on host headers without Frama-C's libc specifications, so it does not see a libc call write through a pointer. With `-rte-initialized`, the next read of that value fails. The stop is the same on every input that reaches the call, so keep-going masks that dispatch case for the whole campaign.
- **Fix (fixed, commit `7be8bd1`, S9 of [`../plans/phase1-remediation-plan.md`](../plans/phase1-remediation-plan.md)):** the link-only libc shim (`build_errno_shim_object` in `scripts/eacsl_toolchain.py`) also wraps the functions of `EACSL_LIBC_EFFECTS` the slice calls, whether or not it reads errno. After the real call, each wrapper marks the bytes the call wrote initialized, with `__e_acsl_initialize`, and only in memory the runtime tracks (`__e_acsl_valid`). The ranges are those libc writes: `r` bytes of a `read` buffer, at most `len` of a `recv`/`recvfrom` buffer (with `MSG_TRUNC` they return the datagram's full length), the iovec of `recvmsg`/`readv` up to `r`, at most the caller's length of a socket address, and nothing on failure. The effects start once `templates/eacsl_runtime/fuzz_init.c` sets `__fc_eacsl_runtime_ready`: libFuzzer, and the runtime itself (it `read()`s `/proc/self/maps` during initialization), make wrapped calls before the shadow memory is mapped. The build records `errno_shim.eacsl_effects`. If the effects fail to compile against the host libc, the errno wrappers are linked alone and `effects_error` says why. Checked on a probe through `run_eacsl_fuzz.py replay`:
  - These now run clean: `strtol` then a read of `*endptr`; `socketpair` + `getsockname` then a read of the address; `recvmsg` then a read of the bytes received; `gettimeofday`, `gmtime`, and the two `strerror` cases.
  - These real defects still stop: a byte past what `read` returned, an address field past a short `getsockname` length, the address after a failed `getsockname`, a byte past what `recvmsg` returned, a byte past the 2 bytes `recv(..., 2, MSG_TRUNC)` wrote although it returned 8, a plain uninitialized local, and a printf type mismatch.
- **Checked on the targets (2026-11-14):** each target was replayed with HEAD's scripts and with the working tree, both as no-cache builds with `-rte-initialized`.
  - libmnl: run 1's `workspace/work/src/socket.c`, with a harness that binds a real `NETLINK_ROUTE` socket, receives a link dump and calls `mnl_socket_fdopen`. Before, it stopped at `socket.c:183` in `mnl_socket_fdopen`, `\initialized(&addr.nl_family)`. After, it runs clean. `mnl_socket_bind` never raised it, because it fills `nl->addr` itself before the call.
  - minmea: revision `c43c9e7`, the manifest's MINMEA-01 and MINMEA-02 inputs. Before, both stopped at the `endptr` alarm. After this fix, both stopped at the `va_list` alarm, a second pipeline false alarm (fixed, see "Every `va_arg` Fails" above). With both fixes, MINMEA-01 stops at its real bug, `minmea.c:656` in `minmea_getdatetime` (`-2147483648 ≤ date->month - 1`), the line the manifest expects. MINMEA-02 runs clean, as expected: E-ACSL does not check `abs(INT_MIN)`.
- **Seen again on libmodbus run-1 (2026-11-18), `strlcpy` (fixed, commit `af0b259` and its follow-up, merged to `main`):** Phase 1 stopped at `src/modbus-tcp.c:632` in `modbus_tcp_listen` on `\initialized(&ctx_tcp->ip[0])`, and the Crash Verification Gate rejected it `disproved_by_source`. `modbus_new_tcp` fills `ctx_tcp->ip` with `strlcpy(ctx_tcp->ip, ip, dest_size)` (`modbus-tcp.c:1023`). The run's `config.h` has `HAVE_STRLCPY 1` (glibc 2.38 and later provide it), so libmodbus's own fallback in `modbus.c` is not compiled and the call goes to uninstrumented glibc. `strlcpy` and `strlcat` were not in the table.
  - **Fix:** both are now in `EACSL_LIBC_EFFECTS`, with their exact writes. `strlcpy` marks `min(r, size - 1) + 1` bytes and nothing when `size` is 0 (`r` is `strlen(src)`). `strlcat` reads `strnlen(dst, size)` before the call and marks from there the copied bytes plus the NUL, and nothing when `dst` holds no NUL within `size`.
  - glibc declares these two functions from 2.38 only. The analysis image has glibc 2.41 (Debian trixie); bookworm has 2.36. The shim therefore declares them itself (`EACSL_SHIM_OWN_PROTOTYPES`). Without that prototype, an older libc would fail the `-Werror` shim and drop every other effect with it. Their `__real_` is weak, so the link does not fail when libc lacks the symbol and the target's fallback is `static` (its calls are then not wrapped). This was checked by compiling with the declarations hidden (`_POSIX_C_SOURCE`) and with `nm`. It was not linked against a real glibc older than 2.38.
  - Checked by the image probe `test_libc_shim_clears_libc_false_alarms_and_keeps_real_ones_in_the_analysis_image` (cases 9-12). Before the fix, a truncating `strlcpy` and an appending `strlcat` both stopped on `\initialized`. After it, they run clean, and a read one byte past either NUL still stops.
- **Remaining gaps:**
  - A libc function outside the table still raises the alarm; add it to the table. If a supported libc may not declare it, also add it to `EACSL_SHIM_OWN_PROTOTYPES`.
  - The copy entries keep one buffer per function.
  - `nanosleep` marks `rem` initialized on any failure, not only `EINTR`.
  - `poll` marks the whole `pollfd` array initialized, not only `revents`.
  - `gmtime` and `localtime` no longer share one buffer, as they do in glibc.
  - `test_every_shim_wrapper_compiles_against_the_host_libc` runs only where clang and glibc headers exist. The image has no pytest, so the full-table compile was checked by hand in the container (54 errno and 47 effect functions, `-Werror`). Recompile after any table edit. The probe is `test_libc_shim_clears_libc_false_alarms_and_keeps_real_ones_in_the_analysis_image` (`FRAMAC_DOCKER_TESTS=1`).

### Symptom: E-ACSL Ignores an Unbounded Quantifier (`invalid E-ACSL construct ... Missing upper bound for i. '. Ignoring annotation.`)
- **Cause:** E-ACSL can only compile **bounded** quantifiers where the lower and upper bounds of the quantified integer variable `k` are syntactic integer expressions (e.g., `\forall integer k; 0 <= k < len ==> ...`). It does not fail the build on an unbounded one: it warns, keeps the clause as a comment in the instrumented file, and checks nothing.
- **Seen on:** step M4 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md) (2026-11-10), a repro in `framac-analysis:latest` (Frama-C 35.0~~dev). It ran the real `run_eacsl_fuzz.py guardrail --functions session_status` on the `tests/fixtures/security_props` session library, with the `L5_sanitized_log_line` assertion MetAcsl generates (`L5_no_crlf(tmp)`) pasted into the source: `[e-acsl] ...:57: Warning: invalid E-ACSL construct ... in quantification ∀ ℤ i; 0 ≤ i ⇒ ... Missing upper bound for i. '. Ignoring annotation.`, and the guardrail returned `passed_dynamic_oracle`.
- **Generated security properties: not a pipeline defect.** Guardrail builds never see the MetAcsl properties or what MetAcsl generates from them. `run_wp_function.py` writes `security_meta_<fn>.c` into WP's out-dir and passes it to the WP run only (`-meta ... -then-last`); the generated clauses live in that Frama-C project and are never printed back to a source file. The prover guardrail (`prover_brief.md`, `--sources {scratch_module_sources}`) and the parent re-check (`workspace_overlay.py`) compile the sidecar sources and the harness only, and the prover brief forbids copying meta-properties into the source. So the L4–L6 meta properties are checked by WP only, never dynamically. Of the generated predicates only `L5_no_crlf` is unbounded; the wipe predicate (`templates/metacsl/l6_wiped.acsl`, `0 <= i < count`) is translated and checked by E-ACSL. A meta file passed by mistake to `--sources` is parsed and ignored without a warning (no `-meta`).
- **Status (2026-11-18):** the bug in the next bullet (clauses in the source) is **fixed** in `f45fe8b`, `ab2053f`, `9209f13`, `6e56cc7` and `a851aba`, merged to `main`. By design the status stays `passed_dynamic_oracle`: each clause E-ACSL did not execute is reported, becomes an assumption of the unit and is listed in the report.
  - `scripts/eacsl_toolchain.py` (`parse_ignored_annotations`, `attribute_ignored_annotations`, `f45fe8b`) parses the last instrumentation run's output and ties each ignored annotation to a function: the one whose declaration holds the reported line, or, for a `predicate` or `logic` reported at its definition, the functions whose clauses use it. What cannot be tied to a function says why. The list is part of the build result (`ignored_annotations`), so a cached build carries it.
  - `scripts/run_eacsl_fuzz.py` (`dynamic_oracle_fields`, `unchecked_clause_hints`): the guardrail report adds, on every status, `ignored_annotations`, `unchecked_clauses`, `dynamic_oracle_incomplete`, `dynamic_oracle_incomplete_functions` and `unattributed_ignored_annotations`, plus hints that name each unchecked clause. `assigns` clauses, which E-ACSL never checks, are counted and not listed; `decreases`, `terminates` and `exits` clauses are listed and do not set the flag. With `--functions` and `--reach-functions` together the checked set is their union (`ab2053f`). Test: `tests/test_eacsl_ignored_annotations.py` (fixtures `tests/fixtures/eacsl_ignored/`, real output of Frama-C 34.0~beta).
  - Readers (`9209f13`): `workspace_overlay._apply_guard_limits` copies the function's items into the parent WP report (`limits.dynamic_oracle.unchecked_clauses`, `unattributed`); `loop_seeds.py` gives a seed E-ACSL ignored the corpus verdict `not_executed` ("not checked on the corpus") where it used to read `held`; `wp_scheduler.py` merges a stalled negotiation's contract partially only when its guardrail report has no unchecked clause of the function. Test: `tests/test_unchecked_clauses_wiring.py`.
  - `scripts/ledger.py` (`add_wp_limit_assumptions`, `unchecked_clause_notes`, `6e56cc7`, `a851aba`) records one assumption per unchecked clause (at most 20 by name, then a count), one for the unattributed annotations, and "not known" when the guardrail had no build report to read. `generate_report.py` (`verdict_limits_section`) lists them per function. Test: `tests/test_unchecked_clause_assumptions.py`.
- **Open pipeline bug:** [`../../scripts/prover_candidates.py`](../../scripts/prover_candidates.py) ignores `dynamic_oracle_incomplete`: a candidate whose guardrail passed with unchecked clauses ranks like one whose clauses were all executed.

- **Pipeline bug as first recorded here (clauses in the source; fixed on 2026-11-18, see the Status above):** `run_eacsl_fuzz.py` does not scan the compile log for `Ignoring annotation` / `invalid E-ACSL construct`, so the guardrail reports `passed_dynamic_oracle` for a clause it never executed. ### Symptom: E-ACSL Rejects a Pointer the Program Got From an Uninstrumented Library (`\valid_read` False on a `strdup`, `getenv` or json-c String)
- **Seen on:** S4 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md) (2026-11-10), `framac-analysis:latest` and `framac-build:latest` (json-c 0.18). A string `json_object_get_string` returned, passed back to `json_object_new_string`, failed a `valid_read_string`-style precondition; so did `strdup`'s result passed to `strlcpy`.
- **Cause:** E-ACSL tracks only memory the instrumented code allocates (its own `malloc`, stack, globals). Blocks a library allocates internally (json-c's objects and strings, `getenv`'s environment, libc's static result buffers) are not in the shadow memory, so `\valid_read` and `\block_length` are false or zero on them.
- **Wider since 2026-11-14 (`--libc-replacements`, `--validate-format-strings`):** these checks run inside libc calls, so the target no longer has to read through the pointer for the check to fail. Seen with a control harness on Frama-C 34.0~beta, through `run_eacsl_fuzz.py replay`:
  - `fprintf(stderr, "%s", strerror(ENOENT))` stops with `fprintf: attempt to access unallocated memory via directive 1 ('%s')`.
  - `strncpy(d, strerror(EINVAL), n)` stops with `strncpy: source string string unallocated`.
  - `strlen(getenv("PATH"))`, `printf("%s", getenv("HOME"))`, `snprintf` into a stack buffer, `strcpy` from a literal, and `memcpy`/`memmove`/`memset` on the target's own buffers run clean.
  - Workaround (implemented, commit `7be8bd1`): `pipeline_make.py params set --module <mod> --no-fuzz-libc-checks` builds that module's E-ACSL binary without both options. It is recorded as `-no-libc-checks` in `reduced_checks`, and the Phase 3 guardrail re-check follows it.
  - **Fixed for libc's static results (S9, commit `7be8bd1`, `EACSL_LIBC_EFFECTS` in `scripts/eacsl_toolchain.py`):** the libc shim wraps `strerror`, `strsignal`, `gai_strerror`, `inet_ntoa`, `ctime`, `asctime`, `gmtime` and `localtime`, and returns a copy in a buffer of the shim, registered with the runtime and marked initialized. libc's own block cannot be registered in place: `__e_acsl_store_block` on it writes a shadow the runtime never mapped (no segment check in release builds). Both stops above and a read of `gmtime`'s fields now run clean. One buffer per function, as libc's contract allows, and a string is cut at 1023 bytes. In the S9 probe, `strdup` called from instrumented code ran clean even without the shim, presumably because the runtime defines `malloc` and glibc's `strdup` calls it; the shim also marks its bytes initialized. The S4 `strdup` stop above was not rechecked. `getenv`, json-c and other libraries are still untracked.
- **Fix in the S4 stubs (fixed):** the E-ACSL branches of `fc_strlcpy.h`, `bsd/string.h` and `json-c/json.h` check a pointer argument only when it lies in tracked memory (`\valid_read(s) ==> ...`), and require library handles only to be non-NULL where the library asserts on NULL. **Open pipeline bug (general):** any E-ACSL contract or RTE check on such a pointer (a prover's `requires valid_read_string(s)` in a guardrail build, an RTE on a read through it) is a false alarm, and the pipeline does not tell a fuzz crash of this kind from a real one. To make: `run_eacsl_fuzz.py` / `eacsl_toolchain.py` register the blocks the known allocating library calls return (`__e_acsl_store_block` after the call), or classify crashes whose pointer comes from such a call.

## Sanitizer Campaigns, Crash Parsing & Minimization

### Symptom: LeakSanitizer Reports `LeakSanitizer has encountered a fatal error` or `LeakSanitizer does not work under ptrace`
- **Cause:** LeakSanitizer (enabled by default with `-fsanitize=address` in the native LibFuzzer fallback) uses `ptrace` to stop threads while scanning. Docker's default seccomp profile allows `ptrace` on kernels >= 4.8; older hosts block it.
- **Fix:** Do not relax seccomp. Set `ASAN_OPTIONS=detect_leaks=0` (or pass LibFuzzer `-detect_leaks=0`) for the campaign and record in the run notes / agent result that leak detection was disabled, so missing leak coverage is visible.

### Symptom: A Crash Blamed on a Function Named `fuzzer`, or a Bare `memcpy: ...` / `printf: directive ...` Line Read as No Failure
- **Seen on:** libmnl `nlmsg`, Frama-C 34.0~beta, while adopting `--libc-replacements` (2026-11-14). The stop line was `memcpy: overlapping memory areas`, followed by `ERROR: libFuzzer: deadly signal` and a stack.
- **Cause 1:** `_STACK_FRAME_RE` cut C++ frame names at `::`, so libFuzzer's `fuzzer::PrintStackTrace()` frame read as a function `fuzzer`. That name does not match the runtime prefix `fuzzer::`. In a deadly-signal stack, `_parse_segment_failure` took the first frame that was not a runtime frame, so it could name `fuzzer` as the crashing function.
- **Cause 2:** the reports of E-ACSL's libc replacements and format-string checks carry no `file:line: Error:` header, so `parse_eacsl_failure` returned nothing for them.
- **Fix (commit `7be8bd1`):** in `scripts/run_eacsl_fuzz.py`:
  - The frame regex keeps `::`-scoped names.
  - `_parse_libc_failure` matches the runtime's closed list of message templates.
  - It names the caller from the first frame after the innermost E-ACSL runtime frame.
  - It leaves `file` `unknown` and `line` 0, so the sanitizer replay looks for a location.
  - Tests: `tests/test_eacsl_toolchain.py`.
- **Open pipeline gap:** format-string failures stay without a source location, because ASan does not stop on them. `instrumented_location` gives the line in the instrumented file (backlog). The Phase 3 guardrail has no sanitizer replay either, so a libc stop there gets a fingerprint `unknown#<fn>::...`. That fingerprint does not merge with the campaign's attributed `src/<file>#<fn>::...` for the same defect.
- **False alarms:** a stop on a string libc allocated (`strerror`) is a false alarm; see "E-ACSL Rejects a Pointer the Program Got From an Uninstrumented Library" above, and `--no-fuzz-libc-checks`.

### Symptom: A Crash Reproducer Is Large or Hard to Read
- **Fix:** `python3 /opt/framac-pipeline/scripts/pipeline_make.py run minimize` runs cvise (installed in the container image) on every unverified candidate's reproducer, under the sandbox, accepting only variants that still crash with the same fingerprint. Each crash artifact gets a `<artifact>.min` sibling; `workspace/reports/minimize/index.json` maps fingerprints to the reports. Crash verifiers should replay the `.min` first (`skills/framac-wp/crash_verifier_brief.md`).

### Symptom: The E-ACSL Guardrail Cannot Instrument `valid_read_string`/`strlen` Annotations (`[e-acsl] Failure: typing was not performed on construct strlen(sentence)`), So the Dual Oracle Rejects a Contract WP Would Prove
- **Seen on:** minmea, run-1, 2026-11-14, agents `prove-minmea_check` and `prove-minmea_checksum`. `prove-minmea_checksum`'s candidate with `loop variant strlen(sentence)` is `all_proven` under WP (11/11) but the guardrail returns `compile_error: eacsl_instrumentation_failed` with `[e-acsl] Failure: typing was not performed on construct strlen(sentence)` and `no assigns clause generated for function strlen`. `prove-minmea_check` then could not get any guardrail-evaluated candidate at all, because its contract and both loop invariants use `valid_read_string`/`strlen`; its WP run was still waiting when the 900 s budget expired.
- **Cause (corrected 2026-11-14 by the supervisor's diagnosis):** upstream E-ACSL bug, see the `terminates \true` / `strlen` loop variant entry of [`./wp-and-guardrail.md`](./wp-and-guardrail.md) and [`../upstream/frama-c/frama-c-eacsl-loop-variant-logic-function-application.md`](../upstream/frama-c/frama-c-eacsl-loop-variant-logic-function-application.md). Only a `loop variant` that is exactly `strlen(...)` aborts; `valid_read_string`/`strlen` in `requires`, `ensures`, `assert` and `loop invariant` are instrumented with the prelude's definitions, and the host C `strlen` plays no part. The workaround is `loop variant strlen(s) + 0;`. The text below is the run agent's earlier diagnosis and proposal, kept for the `assigns errno;` remark, which was not re-tested.
- **Earlier diagnosis (refuted for `strlen`):** `templates/fc_stubs/fc_compat_types.h` defines a concrete logic `strlen` for E-ACSL builds, but the E-ACSL parse also sees the host C `strlen`; no type is recorded for the variant term, and the plugin aborts. The same dual-oracle conflict makes `assigns errno;` unusable (the kernel accepts it, the E-ACSL frontend rejects `errno` as an unbound logic variable).
- **Fix (proposed; the `strlen` loop variant is fixed by image patch 16, the `assigns errno;` part was not retested):** give E-ACSL a typed logic alias for `strlen` (and `errno`) on the annotation path, or let the prover state the variant through a ghost integer that E-ACSL can instrument, with the brief showing the supported form. Until then a string-walking function cannot be both guardrail-clean and `terminates \true`-proved, and its units stay `blocked` with `proof_gap` set. A regression test should cover a `while (*s && *s != '*')` walk with a memory-shape-only contract.

### Symptom: One Defect Gets Different Fingerprints on the E-ACSL and the Sanitizer Builds, and Replaying on `compile.binary` Reports `not_reproduced`
- **Seen on:** QCBOR, run-6, 2026-11-15. `IEEE754_SingleToHalf` / `IEEE754_DoubleToSingle` shift candidates: the same input and the same sink line produce `...::shift::ceaaa12428` on the E-ACSL build (RTE assertion `0 <= nShiftAmount < 32`) and `...::shift::5614f2d044` / `...::31f1bd25a5` on the ASan+UBSan build (`shift exponent -21 is negative`). The brief tells verifiers to replay `compile.binary` from `workspace/reports/fuzz/<mod>.json`, which is the E-ACSL binary, so a sanitizer artifact replays as a different fingerprint or not at all. The sanitizer binary `workspace/harnesses/fuzz_<mod>` can also be newer than the recorded replay report (run-6: rebuilt at 02:26, replay report at 02:06), so its result disagrees with the report.
- **Cause:** `fingerprint.py` hashes the normalized predicate text, and the two engines phrase one RTE property differently (assertion form vs runtime message), so `candidates.json` tracks one defect as two or three entries. The campaign report records `engine` per artifact and per `engines` block, but neither the brief nor the replay command reads it.
- **Fix:** **Open pipeline gap (partly fixed).** Fixed on `phase1-remediation`: Phase 1 step S4 (merge `4de97ca`) records every engine's detection of one statement site on one candidate (`ledger.upsert_candidate`, `tests/test_candidate_sites.py`), and the skip rebuilds of the third cause below no longer overwrite `fuzz_<mod>` (`aeac81d`, `.skip_<bin>/`). Still open: the two engines keep different fingerprints, `crash_verifier_brief.md` still names `compile.binary` for a manual replay without the artifact's engine, and the replay report records no binary digest. Workarounds used in run-6: verifiers replayed sanitizer artifacts on `workspace/harnesses/fuzz_<mod>.sanreplay` or on a fresh `--engine sanitizers` build, and one defect is reported once by grouping on the decision point (the report already lists confirmed findings that share a decision point as possibly one defect). Suggested: normalize the two spellings to one fingerprint, or make `crash_verifier_brief.md` name the artifact's engine and the matching binary, and record the harness/binary digest in the replay report so a stale binary is detectable.

  A third cause of `not_reproduced`, found by the same batch of verifiers: `workspace/harnesses/fuzz_<mod>`, which `workspace/reports/fuzz/<mod>.json` names as the sanitizer `compile.binary`, is the **last keep-going round's rebuild**, compiled with the accumulated `-DFRAMAC_FUZZ_SKIP_CASES*` masks of every case that crashed in an earlier round. It therefore returns 0 for the very artifacts recorded on those cases (run-6: it reproduced none of the recorded artifacts, not even a NULL-deref SEGV one, while `.sanreplay` reproduced them 3/3-4/4). Replay on `<out>.sanreplay` (same `sanitizer_compile.log` command line) or rebuild with `--engine sanitizers`; do not read a clean run on `fuzz_<mod>` as a refutation. Suggested pipeline fix: keep the first-round (unmasked) sanitizer binary under its own name and record that path as `compile.binary`, or record the mask alongside the binary path.

### Symptom: Every Input That Formats a Byte With `%u`/`%x` Stops the Campaign With `snprintf: directive 1 ('%u') expects argument of type 'unsigned int' but the corresponding argument has type 'int'`
- **Seen on:** c-ares run-1, 2026-11-16, Phase 1 ([`../runs/2026-11-16-c-ares-run1-supervision.md`](../runs/2026-11-16-c-ares-run1-supervision.md)).
  - `libcares_a__parsers` produced 6 artifacts and `tf_ares-test-fuzz` 20, all with fingerprint `unknown#inet_ntop4::eacsl_format_error::1f30ebf225` (`file` `unknown`, line 0).
  - The caller is `inet_ntop4`: `snprintf(tmp, sizeof(tmp), fmt, src[0], ...)`, with `static const char fmt[] = "%u.%u.%u.%u"` and `const unsigned char *src`.
- **Cause:** E-ACSL's runtime is stricter than C; this is an upstream bug.
  - **Exact type match:** with `--validate-format-strings` (`EACSL_GCC_CHECK_OPTIONS`, adopted 2026-11-14), `validate_format_type` in `share/e-acsl/libc_replacements/e_acsl_stdio.c` requires the directive's type to equal the argument's static type after promotion.
  - **What aborts:** a promoted `unsigned char` or `unsigned short` is an `int`, so `%u`, `%x` and `%o` abort on every call. `%d` with a small `unsigned int` aborts too. The runtime sees only static types, so the message is identical for `-1` and for `7`.
  - **What C allows:** C11 7.16.1.1p2 lets `va_arg` read the type of the other signedness when the value fits both types; 7.21.6.1p9 alone reads stricter. gcc and clang `-Wformat` do not warn, and glibc prints the right value.
  - **Effect:** a tool false positive that also blinds the fuzzer. In fork mode, every input reaching the call aborts there, so the code after it is never reached.
  - **Second defect in the same function:** arguments are collected with `va_arg(ap, void *)`, so a `%s`, `%p` or `%n` after a `double` or `long double` reads the wrong slot. This gives `attempt to access unallocated memory via directive 2 ('%s')` or `unterminated string in directive 2 ('%s')`.
  - **Upstream draft:** [`../upstream/frama-c/frama-c-eacsl-format-promoted-argument-signedness.md`](../upstream/frama-c/frama-c-eacsl-format-promoted-argument-signedness.md), committed on `main`.
- **Fix:** commits `e66a68c` and `99a6871`, from branch `sup/c-ares-eacsl-format-promotion`, fixed and merged into `phase1-remediation` (2026-11-16). It ships a patched copy of an upstream runtime.
  - **Patched runtime:** stage 2 compiles the runtime from a run-local patched copy of the E-ACSL share directory, passed with `e-acsl-gcc --e-acsl-share` (`eacsl_toolchain.prepare_patched_eacsl_share`, patch `format-runtime-1`). The image is never written.
  - **What the copy accepts:** an `int`/`unsigned int`, `long`/`unsigned long` or `long long`/`unsigned long long` pair whose value fits both types. It also reads `double` and `long double` arguments with their own types.
  - **What still aborts:** negative or out-of-range values. They now carry `format_mismatch: "signedness"`, and nothing is dismissed automatically.
  - **Recorded outcome:** in `compile.runtime_patches.format_runtime`. On `not_applied` (share not found, anchor moved, patched file does not compile), the build uses the image's runtime and the false positive remains.
  - **Tests:** `tests/test_eacsl_format_signedness.py`, including a Docker probe of 15 cases built with and without the patch.
- **Run-1 consequence:** its binaries keep the unpatched runtime. Its 26 `inet_ntop4` artifacts are this false positive and should not be verified as findings.
- **Workaround on an unfixed checkout:** `pipeline_make.py params set --module <mod> --no-fuzz-libc-checks`, recorded as `-no-libc-checks`. This also drops the libc buffer checks.
- **Not a pipeline defect:** without `-e-acsl-full-mtracking`, a literal format string aborts as `invalid format string (unallocated or unterminated)`. This is upstream; the pipeline always uses full tracking. Analysed on 2026-11-17 as upstream package 33 ([`../upstream/frama-c/frama-c-eacsl-format-literal-without-full-mtracking.md`](../upstream/frama-c/frama-c-eacsl-format-literal-without-full-mtracking.md), validated patch, not filed): the memory-tracking analysis does not mark the arguments of the format functions as monitored, so the literal has no block.
- **Phase 3 guardrail consequence (c-ares run-1, 2026-11-16, prover `negotiate-config_defaults` on `src/tools/adig.c#config_defaults`):** the same false positive makes the Dual-Oracle guardrail unusable for module `adig`, not only the Phase 1 campaigns.
  - The brief's guardrail command for the module ends with `status: "guardrail_error"`, `reason: "A check failed outside the checked functions (E-ACSL eacsl_format_error: printf: directive expects argument of type 'unsigned int' but the corresponding argument has type 'int' at unknown:0 in print_header) on an input that cannot be dropped (not a replayed corpus file)"`, `crash_input: agents/<agent>/scratch/guard/crash-da39a3ee...`, and `reach.functions.config_defaults: 0`.
  - `print_header` in `adig.c` formats a `uint16_t` with `%u`, so the libc replacement aborts on every input the harness replays (the 33-file corpus and every mutation); the checked function is never reached, and the crash comes from a fresh mutation, so it is not an excludable corpus input.
  - **Workaround measured on the unfixed checkout:** add `--no-libc-checks` to the same `run_eacsl_fuzz.py guardrail` command (out-bin, scratch-dir and out-json pointed at separate names). With it the guardrail returns `passed_dynamic_oracle`, `reduced_checks: ["-no-libc-checks"]`, 100 executed inputs, `reach.functions.config_defaults: 39`, no excluded input. `config_defaults` calls no libc formatting function, so dropping the libc replacement checks does not weaken the check of that contract.

## MetAcsl Properties in the E-ACSL Build

Entries from package C of [`../plans/metacsl-exploitation-plan.md`](../plans/metacsl-exploitation-plan.md), 2026-11-18, on the fixture `tests/fixtures/metacsl_eacsl/` in `framac-analysis:latest` (Frama-C 34.0~beta, MetAcsl 0.12~beta). ### Symptom: An E-ACSL Build With `-meta` Returns 0 but the Instrumented File Has No `__e_acsl_assert` Call for the Properties
- **Cause:** MetAcsl ran in the same Frama-C stage as RTE and E-ACSL, which then see the untranslated project. `-then` inside `-F` gives `no input file`. The build is silently blind.
- **Fix (fixed, commit `fd13c04`):** MetAcsl runs in a stage of its own: `-F "<non-RTE flags> -meta -meta-warn-key unknown-func=inactive"` plus `--then-last --e-acsl-extra "<RTE flags>"` (`meta_stage_flags`). On the fixture: 100 assertion calls without the properties, 112 with them, none lost.

### Symptom: An Out-of-Bounds Write Is Reported as `<unknown>:0: Error: E-ACSL RTE failed` and Its Fingerprint Changes Once the Properties Are On
- **Cause:** every Frama-C flag had been moved after `--then-last`, the non-RTE ones included.
- **Fix (fixed, commit `fd13c04`):** only the RTE flags go to `--e-acsl-extra`. The fixture's ordinary bug keeps the fingerprint `src/prog.c#mix::mem_access::60975404fe` with and without the properties.

### Symptom: A Failure Located in `<out>.security_meta.c` With the Label `memory access` or `uninitialized` and No Property Name
- **Cause:** E-ACSL guards the evaluation of a property's predicate (for example `\valid_read(dst + i)` before `\separated(dst + i, &auth_ok)`), and such a guard failed.
- **Fix (fixed, commit `54098ac`, [`../../scripts/failure_identity.py`](../../scripts/failure_identity.py)):** the guard is mapped to its property through the line map of the sidecar `<out>.security_meta.json`; its predicate reads `<name>: meta: guard <label>: <pred>` and it carries `meta_guard`, so its fingerprint differs from a violation's. Unit-tested on a synthetic report only; no guard failure was provoked in the image.
- **Open pipeline bug:** a guard reported at `<unknown>:0` or inside `templates/acsl/acsl_vocabulary.h` (an unterminated string reaching `no_crlf_string`) is not mapped and keeps an ordinary identity.

### Symptom: A Write Through `memcpy` Into a `\writing`-Protected Global Runs Clean in the E-ACSL Build
- **Seen on:** measurement of `-meta-fold` / `-meta-quantify-range`, 2026-11-19, on a scratch copy of `tests/fixtures/metacsl_eacsl/` with the case `memcpy(&auth_ok, work, sizeof auth_ok);` in `process` (input `Xabcd`), built by `fuzz_build.build_module_binary` from a clean export of `b9bc780` in `framac-analysis:latest`. The binary exited 0 under the current flags, and also with `-meta-fold`, `-meta-quantify-range` or both. The planted `backdoor(&auth_ok)` write in the same build was reported (`L4_auth_state_login`, exit 77).
- **Cause:** pipeline gap, and a missing MetAcsl warning (upstream draft 49 in [`../upstream/frama-c/README.md`](../upstream/frama-c/README.md), for `pub/meta`, not filed): MetAcsl warns about a behavior without `assigns` but says nothing about a callee with no specification at all. A `\writing` property takes a call's written locations from the callee's `assigns`, and a callee without a contract is assumed to respect every property (MetAcsl `README.md`). `e-acsl-gcc` parses with the host headers (`-no-frama-c-stdlib`), so `memcpy`, `memset`, `strcpy` and the rest of libc had no contract in this build: the instrumented file had `__e_acsl_builtin_memcpy((void *)(& auth_ok), ...)` with no meta check before it. WP and Eva parse with the Frama-C libc, whose contracts give these calls an instance, so the generator's `declared_callees.no_assigns` warning (see [`./security-properties.md`](./security-properties.md)) does not list them, and the fuzz report said nothing either: the property read as `translated` when the module had another write it checked.
- **Fix (fixed for `memcpy`, `memmove`, `memset`, `strncpy`; commit `db357a0`, merged to `main` in `fe8cb33` on 2026-11-20):** the E-ACSL meta file now ends with `assigns` contracts for those four writers ([`../../templates/metacsl/eacsl_libc_writers.h`](../../templates/metacsl/eacsl_libc_writers.h), appended by `fuzz_build.eacsl_security_meta_text`). MetAcsl instantiates a callee's `assigns` with the formals of the first declaration it meets, which is glibc's, so the contracts use glibc's names (`__dest`, `__src`, `__n`, `__s`, `__c`); with other names clang fails on `use of undeclared identifier '__dest'`. The contracts are part of the cache key. A build they make fail, for a reason other than a property MetAcsl rejects or the build time limit (`eacsl_build_timeout`, since `0c10521`), is redone once without them, and `security_props.libc_contracts` says `dropped` with the failed log as `<out>.security_meta_libc.log`. In the image: `memcpy(&auth_ok, ...)` now fails as `L4_auth_state_login` in `process` (fingerprint `src/prog.c#process::meta_l4_auth_state_login::...`), the correct `memcpy` into a local runs clean, and build time is unchanged (~31 s). Tests: `tests/test_metacsl_eacsl.py` (`test_in_the_image_a_libc_write_into_the_state_is_reported_and_an_overflow_keeps_its_identity` and the unit tests around `libc_contracts`).
- **Open pipeline bug:** (reported, not checked) the other libc functions that write or read through a pointer (`strcpy`, `strcat`, `sprintf`, `read`, `recv`, `fgets`, ... : `EACSL_META_LIBC_UNCHECKED` in [`../../scripts/eacsl_toolchain.py`](../../scripts/eacsl_toolchain.py)) still have no contract in this build. `security_props.libc_unchecked` maps each one the module's functions call to its callers, and the build prints `security props: libc unchecked: ...`, so the gap is visible. `strcpy` cannot take its contract: see the next entry.

### Symptom: E-ACSL Aborts With `invalid label 'Old' within statement annotation 'Assertion' in '__src'` When the Meta File Gives `strcpy` an `assigns`
- **Seen on:** the libc contracts above, 2026-11-19, `framac-analysis:latest` (Frama-C 34.0~beta, MetAcsl 0.12~beta), with `assigns __dest[0 .. strlen(__src)] \from __src[0 .. strlen(__src)];` on `strcpy`.
- **Cause:** upstream, MetAcsl (corrected on 2026-11-20; this entry first blamed E-ACSL). At a call to a function known by its contract, MetAcsl's `inspect_contract` (`meta_annotate.ml`) replaces the formals by the actual arguments but keeps the contract's labels: `strlen(__src)` in the callee's `assigns` is `strlen{Old}(__src)`, and `Old` is not allowed in the statement assertion MetAcsl places before the call. The kernel, WP (`LabelError`) and E-ACSL all refuse it, so E-ACSL is right to abort. A `Pre` label is accepted but means the caller's pre-state, and `Here` in `assumes` or `assigns` means the post-state under an `After` property, so WP can prove a false property in both cases. Drafted with a patch as upstream package 47 in [`../upstream/frama-c/README.md`](../upstream/frama-c/README.md) (for `pub/meta`), not filed. With that patch alone `strcpy` is still not checked: E-ACSL then ignores the `strlen(...)` instance ("logic functions or predicates performing read accesses is not yet supported").
- **Workaround:** `strcpy` (and every writer whose bound is a logic function of its arguments: `strcat`, `stpcpy`, `sprintf`) gets no contract and stays in `EACSL_META_LIBC_UNCHECKED`, reported through `libc_unchecked`.

### Symptom: An Out-of-Bounds `memcpy` Changes Its Fingerprint to `<unknown>:0: E-ACSL RTE failed` Once `memcpy` Has a `\writing` Instance
- **Seen on:** the libc contracts above, input `O` + 40 bytes on `memcpy(out, work, m)` (`RTE_MEMCPY` in `tests/fixtures/metacsl_eacsl/prog.c`).
- **Cause:** the meta assertion MetAcsl places before the call (`\separated(\written, &auth_ok)` over `out[0 .. m-1]`) runs before E-ACSL's own `memcpy` check. E-ACSL guards `\separated` with the validity of its operands, so on an overflow the run stopped in the meta assertion's guard (`<unknown>:0: E-ACSL RTE failed`) instead of at `memcpy: insufficient space in destination space`, and the overflow lost its identity. The `<unknown>:0` itself is upstream and not specific to `memcpy` or callee `assigns`: MetAcsl's `addr_of_tlval` and `Logic_const.term` calls in `meta_annotate.ml` omit `~loc` (defaulting to `Kernel.gen_loc`), so every `\written`, `\read` and `\called` term carries `<unknown>:0` — an ordinary out-of-bounds `*p = 1` write fails its E-ACSL RTE guard at `<unknown>:0` too (same root cause as the open pipeline bug in the guard-mapping symptom above; see upstream draft 49 in [`../upstream/frama-c/README.md`](../upstream/frama-c/README.md), not filed). Under `-meta-fold` every folded instance's assertion loses its own location the same way (draft 48).
- **Fix (fixed, commit `db357a0`, merged to `main` in `fe8cb33` on 2026-11-20):** in the E-ACSL meta file only, each `\writing` predicate is guarded as `\valid(\written) ==> (P)` and each `\reading` predicate as `\valid_read(\read) ==> (P)` (`eacsl_toolchain.eacsl_meta_guarded_text`), on the property's own lines so the line map does not move. An invalid access is left to the RTE and libc checks, which name it as before; WP and Eva keep the unguarded text. The overflow's fingerprint is now the same with and without the properties (checked in the image test above).
- **Side effects:** every meta fingerprint changes once, because the predicate text is hashed (for example the fixture's `backdoor` violation went from `...::dd581c3f76` to `...::49ba3ab8d0`); no real run has meta fingerprints yet. E-ACSL now prints the guarded predicate over two lines and `failure_identity.parse_runtime_failure` keeps the first one (`\valid(...) ⇒`); the fingerprint is still stable per property and location.

### Symptom: `test_in_the_image_the_planted_violations_become_candidates_on_their_units` Fails Once With the First Campaign a Cache Miss
- **Seen on:** branch `meta-libc-contracts`, 2026-11-19, `pytest tests/test_metacsl_eacsl.py tests/test_metacsl_eacsl_wiring.py -m integration -n 2`: the `backdoor` campaign got `{'hit': False, 'key': '4e67a2b2...'}` while the builds before it (`first`, `again`, `by_default`, `back`) shared `613809bc...`; the five later campaigns all hit `4e67a2b2...`. ### Symptom: `[acsl-missing-backslash] 'separated(' should be '\separated('` on a Python f-string That Builds an Annotation With the Backslash in a Hole
- **Seen on:** package F of the MetAcsl plan, 2026-11-18, writing `tests/test_metacsl_followups.py`: an f-string holding a whole MetAcsl annotation (comment opener and closer included) in which each backslash is the hole `{b}`, `b` being a one-backslash string, as in `{b}separated({b}written, &auth_ok)`.
