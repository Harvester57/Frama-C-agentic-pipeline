# E-ACSL + LibFuzzer Build & Runtime Issues

Issues encountered in E-ACSL instrumentation (`e-acsl-gcc`, `eacsl_toolchain.py`), runtime shadow memory, LibFuzzer / sanitizer campaigns (`run_eacsl_fuzz.py`), crash parsing/fingerprinting (`fingerprint.py`), and reproducer minimization. For `--api` harness layout and `build-check` module triage, see [`./harnesses-and-seeds.md`](./harnesses-and-seeds.md). For Dual-Oracle Guardrail checks in Phase 3, see [`./wp-and-guardrail.md`](./wp-and-guardrail.md).

### Symptom: `Exceeded heap allocation limit of 128MB -- heap memory space moved` Recorded as a Target Crash, and the Crash Parsed as `unparsed_crash`
- **Seen on:** mpack run-3 (2026-11-17), modules `libmpack_a__mpack_expect`, `_mpack_expect_2`, `_mpack_node_4`, `_mpack_writer`, `_mpack_writer_2`. Example artifact `workspace/crashes/libmpack_a__mpack_expect/crash-c82085c082a2d0df92180788ea3953381b1106d4` (11 bytes) replays with returncode 77 and stderr `e_acsl_segment_tracking.c:532: Exceeded heap allocation limit of 128MB -- heap memory space moved`, stack `raise -> raise_abort -> private_assert_fail -> set_heap_segment -> unsafe_malloc -> malloc -> mpack_read_bytes_alloc_impl`. All six unparsed-crash candidates of `_mpack_expect` come from one dispatch case with an 8-byte wire count between 2^32 and about 2^47. A further instance in `_mpack_writer_2` does not go through `malloc` at all: the 17-byte reproducer `02 f6ffffffffffffff 0000003b00000000` selects dispatch case 2, whose `mpack_realloc` call is the MPACK_REALLOC wrapper (`src/mpack/mpack-platform.h:1844-1847`), so the request is `realloc(4024 -> 253671833600)` and the abort is `set_heap_segment` (`e_acsl_segment_tracking.c:528`) <- `unsafe_realloc` (`:715`) <- `mpack_realloc__fc_inline_7`. Harness repair attempt 1 of that module had replaced the case's former static 4024-byte buffer with a `malloc`'d block (the earlier `harness_induced` defect, record `9d8a4c7c02`), which is what exposes the tool limit here. A target-free probe of `malloc(4024)` + `realloc(4024 -> 253671833600)` aborts with the identical line and message, while `realloc(4024 -> 8192)` succeeds and the uninstrumented build serves the 253 GB request (verifier `verify-unknown_function_fc5c85a81e`).
- **Cause:** two independent gaps in the E-ACSL path.
  1. **Tool limit:** with `--libc-replacements`, `malloc` is E-ACSL's `unsafe_malloc` and `realloc` its `unsafe_realloc`, which serve requests from a fixed `E_ACSL_HEAP_SIZE` of 128 MB and call `private_assert_fail` in `set_heap_segment` when the request makes dlmalloc move that space. A target that correctly checks `malloc`'s result and raises `mpack_error_memory` (target `src/mpack/mpack-reader.c:527-531`) therefore produces a *reproducible false crash*: a target-free probe that only calls `malloc(237065284864)` aborts identically under `e-acsl-gcc` and runs clean without instrumentation. `docs/references/e-acsl-quickref.md` ("Limitations that change verdicts") does not list this limit, so verifiers must recognise it themselves.
  2. **Parsing:** `run_eacsl_fuzz.py` keeps only the last 2000 bytes of a crash's stderr, and the runtime assertion line precedes the (long) backtrace, so the failure parses as `failure: null` and the candidate is recorded as `harness_...c#unknown_function::unparsed_crash::<fp>`. The fingerprint then names a placeholder function, one candidate per artifact instead of per site, and every one needs manual triage.
- **Correction (run supervisor):** in run-3, 17 of the 24 `unparsed_crash` candidates are this heap abort, all in `_mpack_expect` and `_mpack_expect_2` (caller `mpack_read_bytes_alloc_impl`). Not all of the other 7 are something else: at least two of the `_mpack_writer_2` candidates (`harness_libmpack_a__mpack_writer_2.c#unknown_function::unparsed_crash::fc5c85a81e` and `::d97cd040c9`) are this abort through `unsafe_realloc` from the `mpack_realloc` dispatch case, both rejected as duplicates of `src/mpack/mpack-reader.c#mpack_read_bytes_alloc_impl::crash::846ff215a0`; `_mpack_node_4` is a "Not a start of block in realloc" in `mpack_realloc__fc_inline_7`; the other `_mpack_writer` / `_mpack_writer_2` candidates are a UBSan SEGV in `mpack_tag_cmp`. Counting by module therefore understates the family: it also appears wherever a harness case forwards an input-controlled size to `realloc`.
- **Fix (pipeline bug, **fixed**: commits `eeae815` and `a55e339` from `sup/mpack-eacsl-heap-limit`, merged into `phase1-remediation` on 2026-11-17, merge `0668dab`):**
  - `failure_identity.parse_eacsl_resource_abort` recognises the abort from its message, or from the `private_assert_fail` <- `set_heap_segment`/`shadow_copy` stack.
  - `crash_replay.replay_artifact` reads it from the whole output, not the tail.
  - The campaign marks the artifact `eacsl_resource_abort`. A failure that the sanitizer replay reports still wins and stays a candidate.
  - `ledger.cmd_ingest_fuzz` makes no candidate of it and records non-discharging `fuzz_eacsl_resource_limit` evidence on the module's units.
  - E-ACSL stage 2 builds pass `--zone-sizes heap:1024` (`eacsl_toolchain.EACSL_HEAP_ZONE_MB`). The value is fixed, recorded in `compile.eacsl_zone_sizes` and part of the build cache key.
  - Measured: about 1 MiB of RSS per tracked MiB. `heap:2048` makes every input segfault at startup (exit 139), most likely an `int` overflow of `E_ACSL_HEAP_SIZE * MB` (inferred; a possible upstream bug, not filed).
  - Tests: `tests/test_eacsl_resource_abort.py` (13 tests). The supervisor reran them on the branch: 13 passed.
  - Not measured: the calloc peak, and the per-input time of 500-1000 MiB blocks.

### Symptom: Fuzz Stage Fails With `ZeroDivisionError: integer modulo by zero` in `artifact_dispatch_case`; Campaigns `not_run`
- **Seen on:** benchmark runs `ab-fc35dev` and `ab-fc34` (2026-11-13), on both analysis images: `fuzz: rc=1` on cryptolib, minmea, oscs-qlz, oscs-semver, oscs-stmr, qcbor-dev and qcbor-master, and `benchmark.py compare` against `phase0-r1` reports `campaign no longer runs: not_run` for their modules. The fuzz log ends `File ".../run_eacsl_fuzz.py", line 1429, in artifact_dispatch_case: return first[0] % n_cases ... ZeroDivisionError: integer modulo by zero`, then `make: *** [.../pipeline.mk:148: fuzz-minmea] Error 1`. Recall stayed 7/7: the replays do not go through the campaign.
- **Cause:** a pipeline bug from `f23757c` (M4 hardening). `dispatch_case_count` started reading the harness sidecar first and returned its `dispatch_case_count` as is. Every sidecar records that field, 0 for a harness that is not a dispatch harness, so a plain `LLVMFuzzerTestOneInput` harness was taken for a dispatch harness with 0 cases: `run_campaign_rounds` ran dispatch rounds, and the first crash it recorded computed `first[0] % 0`. The sidecar shortcut also skipped the old check that the source holds `FRAMAC_FUZZ_SKIP_CASES`, without which a build cannot skip cases.
- **Fixed (uncommitted, written in a worktree while the benchmark ran, then applied to the checkout):** [`../../scripts/run_eacsl_fuzz.py`](../../scripts/run_eacsl_fuzz.py) `dispatch_case_count` reads the sidecar only for a source holding the skip macro and returns None for a count of 0 or an empty case list; `artifact_dispatch_case` returns None for `n_cases <= 0`; `run_campaign_rounds` runs fork mode when `n_cases` is 0. Test: `tests/test_run_eacsl_fuzz.py::test_a_harness_that_is_not_a_dispatch_harness_runs_in_fork_mode`. The two A/B runs both carry the bug, so their fuzz results compare like for like but are not campaign results.

### Symptom: `e-acsl-gcc` Fails on `__fc_builtin.h`, `__fc_libc/stdlib.h` (`\old(endptr)`), or Unknown Legacy Flag `--rte=`
- **Cause:**
  1. `e-acsl-gcc` runs `frama-c -no-frama-c-stdlib` so its second pass can compile `instrumented.c` with host `clang` against host glibc. If a harness guards `#include "__fc_builtin.h"` only with `#ifdef __FRAMAC__`, `e-acsl-gcc` enters that block and fails because `__fc_builtin.h` is not on the host include path, and host `<math.h>`/`<stdlib.h>` expose `_Float128` prototypes on glibc >= 2.26.
  2. Frama-C 33+ installs `e-acsl-gcc` (no `.sh`). Its `-h` lists only the short flags (`-F`, `-G`, `-E`, `-e`, `-l`, `-n`, `-C`, `-M`), though long options such as `--rte=all` are still accepted. Running `-rte` across all functions without `-rte-select` instruments unused inline helpers.
- **Fix:** `harness_dual.c.template` guards `#include "__fc_builtin.h"` and `eva_main()` with `#if defined(__FRAMAC__) && !defined(__FRAMAC_EACSL__)`, and `run_eacsl_fuzz.py` automatically passes `-D__FRAMAC_EACSL__ -D_Float128=double -U__SIZEOF_INT128__` (host `<linux/types.h>` declares `__int128` typedefs, which Frama-C rejects, only when that macro is defined) along with `-rte-select` and `-e-acsl-functions` scoped to the functions defined in the target slice `.c` files. Full compiler diagnostics are saved to `<out-bin>.compile.log`. If `e-acsl-gcc` still fails in `campaign` mode, `--engine auto` falls back to native `clang -fsanitize=fuzzer,address,undefined`.

### Symptom: Selftest `compiled: false` With `undefined reference to 'main'` / `fail to compile/link un-instrumented code`
- **Cause:** by default `e-acsl-gcc` instruments **and** links the original sources. A libFuzzer harness has no `main()`, so that link fails and `e-acsl-gcc` exits 1, even though the instrumented file was written.
- **Fix:** `run_eacsl_fuzz.py` passes `-n` (instrument only) in stage 1.

### Symptom: Every Input Crashes in `shadow_alloca` (`e_acsl_segment_tracking.c`), or Valid Stack Accesses Fail `\valid`
- **Cause:** E-ACSL initializes its runtime at the top of `main()`, and a harness has none. Without full memory tracking, its memory analysis leaves a caller's stack buffer untracked, so a callee's valid write fails `\valid`. With full tracking but no runtime initialization, the runtime segfaults on the first tracked stack block.
- **Fix:** automatic. Fuzz builds use `-e-acsl-full-mtracking` and link [`../../templates/eacsl_runtime/fuzz_init.c`](../../templates/eacsl_runtime/fuzz_init.c), whose `LLVMFuzzerInitialize` calls `__e_acsl_memory_init` and `__e_acsl_globals_init`. Do not define `LLVMFuzzerInitialize` in a harness (`reason: eacsl_init_hook_conflict`). The selftest's `benign_input_clean` check catches either regression.

### Symptom: E-ACSL Reports `rte: initialization` on Benign Inputs
- **Cause:** E-ACSL builds pass `-rte-initialized @all`, so every read must be of initialized memory, and memory written outside instrumented code is never marked initialized. The usual culprits:
  1. target code reads libFuzzer's `data` directly instead of the harness copy `fuzz_buf`, for example in a hand-written or `custom` harness;
  2. an external library behind `fc_stubs` fills a buffer;
  3. a libc call outside `EACSL_LIBC_EFFECTS` writes through a pointer. Since S9 the libc shim marks what `read`, `recv`, `recvmsg`, `getsockname`, `strtol`'s `endptr` and the other functions of that table wrote (see "E-ACSL Reports `\initialized` Right After a libc Call" below).
- **Fix:**
  - Pass `fuzz_buf` (generated harnesses do), or copy the input into the harness's own buffer with `memcpy`, which E-ACSL marks initialized.
  - If a library-filled buffer is the cause, initialize it before the call (`= {0}` / `memset`) or rerun with `--no-rte-initialized`. That opt-out is recorded in `reduced_checks`, and Eva still reports uninitialized reads statically.
  - Per-function exclusion (`-rte-initialized=@all,-f`) works for `static` functions too since Frama-C 34 (option-hook bug fixed; in Frama-C 33 it only worked for non-`static` functions).
  - The crash verifier classifies such reports as `harness_induced`.

### Symptom: Every `va_arg` Fails `\initialized(&ap)` (`rte: initialization` in a Variadic Function)
- **Seen on:** minmea (benchmark revision `c43c9e7`), the manifest's MINMEA-01 and MINMEA-02 reproducers replayed through `run_eacsl_fuzz.py replay` with `-rte-initialized` (2026-11-14). Both stopped at `minmea.c:253` in `minmea_scan` with `\initialized(&ap)`, on `va_arg(ap, union minmea_type *)`. Until S9 the `strtol` `endptr` false alarm at `minmea.c:224` stopped both earlier and hid this one. The benchmark manifest built minmea with `fuzz_rte_initialized: false` because of these alarms; that opt-out was dropped on 2026-11-14.
- **Cause:** only `va_start` and `va_copy` initialize a `va_list`, and both are compiler builtins (`__builtin_va_start(ap,format)`) that E-ACSL does not instrument. So the `\initialized(&ap)` check `-rte-initialized` puts before each `__builtin_va_arg` is false on every call. Marking `ap` initialized after `va_start` does not work: the instrumented code registers it with Frama-C's machdep size (`__e_acsl_store_block((void *)(& ap),8UL)` on `gcc_x86_64`), while the check uses clang's `sizeof(va_list)`, 24 bytes.
- **Fix (fixed, commit `7be8bd1`, `scripts/eacsl_toolchain.py` `skip_va_list_initialized_checks`, called from `scripts/run_eacsl_fuzz.py`):** with `-rte-initialized`, the build replaces each `__e_acsl_initialized(&<lv>, sizeof(va_list))` in the instrumented file by `1` and records the count as `va_list_init_checks_skipped`. A `va_list` read before `va_start` is no longer reported; compilers warn about that one.

### Symptom: Every Input Fails `\initialized(&__retres)` in a `__gen_e_acsl_<fn>` Wrapper
- **Cause:** an E-ACSL gap in Frama-C 33. The wrapper that checks a function contract registers its `__retres` with the runtime but never marks it initialized after `__retres = <fn>(...)`. Under `-rte-initialized`, any `ensures` that reads `\result` then fails on the first input.
- **Fix:** automatic. Between instrumentation and compilation, `run_eacsl_fuzz.py` inserts the missing `__e_acsl_initialize` after each such assignment; the build report counts them in `compile.wrapper_result_inits`. This is sound, because the callee's own return value is still checked for uninitialized reads. A report of this failure means the build ran without that step: rebuild it, and never weaken a contract to get past it.

### Symptom: The E-ACSL Selftest Passes Although the Result-Init Pass, the `isnan` Shim or the errno Shim Is Broken
- **Seen on:** C1 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), `framac-analysis:latest` (Frama-C 35.0~~dev), 2026-11-10.
- **Cause:** the canary called no function with a contract on its result, used no `<math.h>` classification macro and never wrote `errno`, so a regression of `mark_wrapper_results_initialized`, of `-D__SUPPORT_SNAN__` with the `fc_stubs/eacsl` `math.h` shim, or of the errno stub and shim (S5) still passed the selftest and showed only on a target. Frama-C 35 checks `\initialized` on a contract wrapper's `__retres` only where the `ensures` reads a field of a struct `\result` (`\initialized(&\result.n)`); a scalar `\result` (`ensures \result <= len`, `\result >= 0`, `\result == \old(x) + 1`) or a pointer `\result` gets no such check, so a canary with a scalar result would not catch the regression.
- **Fix (fixed, C1):** `templates/eacsl_canary/canary.c` runs three more calls on every input, before its input-dependent bugs: `canary_clamp` (`ensures \result.len <= span.len` on a struct result), `canary_classify` (`isnan`) and `canary_errno` (`errno = 0`, `strtol` of an out-of-range number, then `/*@ assert canary_errno_synced: synced != 0; */` on `errno == ERANGE`). `tests/test_eacsl_canary.py` (Docker) builds the canary four times: production passes, and without the result-init pass (`\initialized(&\result.len)`) or without the errno shim (`canary_errno_synced`) `benign_input_clean` fails; without `-D__SUPPORT_SNAN__` the build fails.

### Symptom: Every Call Fails `\initialized` on a Formal Parameter (`\initialized(&s.len)`, often at a Function's First Statement)
- **Cause:** an E-ACSL gap, reproduced on Frama-C 35. Each function registers its formals with `__e_acsl_store_block` but never marks them initialized, although the caller has just written them. Under `-rte-initialized`, the first read of a by-value struct field, or of a scalar formal through its address, fails whatever the caller passed. The assertion is blocking, so nothing after it in that function is ever checked. In QCBOR run-5, 13 of 29 crash candidates were this artifact, and it hid a real signed overflow a few lines below one of them.
- **Fix:** automatic. Between the two stages, `run_eacsl_fuzz.py` inserts `__e_acsl_full_init` after each formal's registration; the build report counts them in `compile.formal_inits`, and the selftest canary reads a by-value struct and an address-taken scalar formal on every input. Locals are untouched, so uninitialized locals are still reported. The cost: E-ACSL no longer reports a struct passed by value with uninitialized members. A report of this failure means the build ran without that step: rebuild it rather than using `--no-rte-initialized`. Upstream report (filed as [pub/frama-c#2797](https://git.frama-c.com/pub/frama-c/-/work_items/2797), merge request [!28](https://git.frama-c.com/pub/frama-c/-/merge_requests/28)): [`frama-c-eacsl-formal-params-initialized.md`](../upstream/frama-c/frama-c-eacsl-formal-params-initialized.md).

### Symptom: E-ACSL Formals Uninitialized or Scalar Const Global Aborts on Non-`UL` Integer Suffixes
- **Cause:** `_STORE_BLOCK_LINE_RE` and `_READONLY_SCALAR_RE` in `scripts/eacsl_toolchain.py` required `\d+UL`. Size constants emitted with `U`, `L`, `ULL`, or bare digits failed to match, leaving formals uninitialized or const scalars without address-of.
- **Fix (fixed, uncommitted, `scripts/eacsl_toolchain.py`):** Replaced `\d+UL` with `\d+[uUlL]*`. Added a warning when store_block lines exist in text but none match the regex.

### Symptom: `implicit cast: cannot cast from __e_acsl_mpz_t to size_t` (E-ACSL silently in GMP-only mode)
- **Cause:** `e-acsl-gcc` splits the values of `-e`/`-E`/`-F`/`-l` on spaces and re-parses the tokens. A standalone `-g` inside `-e` is read as its own `--gmp` option (`-e-acsl-gmp-only`).
- **Fix:** `run_eacsl_fuzz.py` normalizes every passthrough value: `-g` becomes `-gline-tables-only`, `-I dir` becomes `-Idir`, and other standalone single-letter tokens or paths with spaces are refused (`reason: eacsl_argv_unsafe`). `run_eacsl_fuzz.py selftest` checks that the compile log never contains `-e-acsl-gmp-only`.

### Symptom: Campaign Reports `engine_used: eacsl` but E-ACSL Never Fires, or the Guardrail Always Passes
- **Cause:** `e-acsl-gcc -O <out>` writes the instrumented executable to `<out>.e-acsl`; `<out>` is a plain build.
- **Fix:** the script selects `<out>.e-acsl` and refuses any binary without E-ACSL instrumentation (`reason: eacsl_binary_not_instrumented`). The guardrail refuses uninstrumented binaries (`guardrail_error`) instead of reporting `passed_dynamic_oracle`.

### Symptom: `redefinition of 'timeval'` / `'timespec'` or Conflicting `fd_set` Types When Compiling the Instrumented File
- **Cause:** the instrumented file printed by Frama-C is self-contained (it has no `#include` lines and already contains every typedef). Force-including headers that pull in host system headers into its compile duplicates those typedefs.
- **Fix:** `run_eacsl_fuzz.py` builds in two stages. All preprocessor flags (`-I`, `-D`, `-include`) go to instrumentation (`-E`) only; the instrumented file is compiled with codegen flags only (`e-acsl-gcc -C -e ...`). `fc_compat_types.h` is empty whenever `__FRAMAC__` is undefined. Boundary stub headers need no E-ACSL-specific branches.

### Symptom: `syntax error` on `__int32_t`, `u_short` (E-ACSL Host-Header Mode)
- **Cause:** E-ACSL runs Frama-C with `-no-frama-c-stdlib`, so the glibc-internal and BSD aliases must come from host headers.
- **Fix:** in host-header mode `fc_compat_types.h` includes glibc `<sys/types.h>`, so the aliases are identical to glibc's by construction. Do not hand-write `__intN_t` typedefs: `__int64_t` is `long` on LP64 and `long long` on ILP32.

### Symptom: Why Not `-L` / Frama-C's libc for E-ACSL?
- E-ACSL aborts on Frama-C libc specifications (`unbounded ranges are not part of E-ACSL`, `share/libc/string.h`). Host-header mode is the only supported E-ACSL mode.

### Symptom: `undefined reference to 'open_fallback_N'` at Link Time
- **Cause:** in host-header mode, the Variadic translation emits `<fn>_fallback_<N>` for variadic calls without a libc specification (`open`, `fcntl`, `ioctl`, ...), and the E-ACSL RTL does not define them.
- **Fix:** automatic. The script generates `<out-bin>_fallbacks/eacsl_fallbacks.c`, which forwards to the real function (or fails with `ENOSYS` when the signature or header is unknown, recorded as `mode: enosys`), compiles it to a link-only object, and retries the link once. Never add these definitions to the instrumented sources: each definition shifts the fallback numbering. `--no-variadic-translation` passes `-no-variadic-translation` to Frama-C instead (no fallbacks are emitted).

### Symptom: Link Repair and Fallback Function Generation Fail on LLVM lld `undefined symbol:` Diagnostics
- **Cause:** `_UNDEFINED_REF_RE` in `scripts/run_eacsl_fuzz.py` and `_FALLBACK_UNDEFINED_RE` in `scripts/eacsl_toolchain.py` only parsed GNU ld's `undefined reference to 'X'`, ignoring LLVM lld's `undefined symbol: X`.
- **Fix (fixed, uncommitted, `scripts/run_eacsl_fuzz.py`, `scripts/eacsl_toolchain.py`):** Expanded regexes to match both `undefined reference to` and `undefined symbol:`.

### Symptom: `call to undeclared function 'X'` or `invalid application of 'alignof' to an incomplete type`
- **Cause:** a [`../../templates/fc_stubs/`](../../templates/fc_stubs/) header lacks a prototype the target calls, or declares an opaque handle (`struct json_object`) as incomplete. E-ACSL emits `alignof` on pointed-to types.
- **Fix:** add the prototype and complete the handle with a single dummy member (see [`../../templates/fc_stubs/README.md`](../../templates/fc_stubs/README.md)). Tool JSONs list missing prototypes under `undeclared_functions`. For Eva/WP this is a soundness issue: Frama-C invents `int X()`.
- **Target-specific compat headers** (e.g. completing OpenSSL 3 opaque handles `EVP_PKEY`, `BIGNUM`, ... for the fuzz build) must be delivered **source-side**: pass them to `generate_harness.py --compat-include <header>` so the harness `#include`s them after the module header. Never add them to cppflags as `-include`: force-including a header that pulls in system headers re-registers libc properties per merged translation unit and the Frama-C kernel aborts with `trying to register twice property 'assumes nonnull_p'`.

### Symptom: Instrumentation Aborts With `no function 'X'`
- **Cause:** `-rte-select` / `-e-acsl-functions` named a function that is absent from the parsed AST (disabled by `#if`, or in a file that failed to parse).
- **Fix:** function discovery runs on preprocessed sources. Names Frama-C still rejects are dropped once and listed in `rte_select_dropped`.
- **Open pipeline gap:** the Frama-C kernel renames a function defined with plain `inline` (C99 semantics, no external declaration) to `<fn>__fc_inline`.
  - `-e-acsl-functions <fn>` then aborts: `[e-acsl] User Error: incorrect argument for option -e-acsl-functions (no function 'fix_scale')`.
  - The drop-and-retry leaves the function uninstrumented, whatever the `-std`.
  - Seen on a supervisor fixer's fixture (branch `sup/c-ares-tf-std-flag`, 2026-11-16), not on c-ares.
  - Proposed: map `<fn>` to `<fn>__fc_inline` in the selection, which would keep its checks.

### Symptom: Linker or Shadow Memory Conflict When Combining E-ACSL with AddressSanitizer (`-fsanitize=address`)
- **Cause:** E-ACSL embeds its own shadow-memory runtime (`rtl`) to track byte-level pointer validity (`\valid`), initialization (`\initialized`), and sub-object bounds. AddressSanitizer (`ASan`) also maps shadow memory and intercepts `malloc`/`free`. Running both in the same binary causes immediate `mmap` collisions or false aborts.
- **Fix:**
  - Compile E-ACSL fuzz binaries with `-fsanitize=fuzzer` **without** `-fsanitize=address` (as configured in `run_eacsl_fuzz.py`). E-ACSL's own runtime already detects out-of-bounds accesses, use-after-free, bad free, uninitialized reads, and sub-object overflows.

### Symptom: The E-ACSL Fuzz Binary Never Sees an `errno` Set by libc (`errno == ERANGE` After `strtol`, `EINTR`/`EBADF` After `read` Take the Wrong Branch)
- **Seen on:** S5 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), a minimal repro in `framac-analysis:latest` built with `run_eacsl_fuzz.compile_eacsl_binary` (2026-11-10).
- **Cause:** `templates/fc_stubs/errno.h` maps `errno` to the tracked global `__fc_eacsl_errno` in E-ACSL builds, and libc never writes it: `ERRNO_AFTER_STRTOL=0 ERANGE=34 v=9223372036854775807`. The mapping cannot simply go away. glibc's errno lives in libc.so's TLS block, outside the TLS segment the E-ACSL runtime shadows (only the executable's block; probe: `errno_location=0x7f6007f480c0 tls_segment=[0x7f6007f48140,0x7f6007f48440)`). Without the stub every input aborts with `e_acsl_segment_tracking.c:1018: Use of invalid address ... in unsafe_initialize`. Registering the address from `fuzz_init.c` (`__e_acsl_store_block(__errno_location(), sizeof(int))` and `__e_acsl_full_init`) crashes instead with `UndefinedBehaviorSanitizer: SEGV on unknown address 0x000000000000 ... e_acsl_segment_tracking.c:303:22 in shadow_alloca`.
- **Fix (fixed, commit 7a23e9e):** `run_eacsl_fuzz.py` links a generated, link-only errno shim (`<out>_errno_shim/eacsl_errno_shim.o`, `-Wl,--wrap=<fn>` for the functions of `ERRNO_SHIM_FUNCTIONS` in `scripts/eacsl_toolchain.py` that the slice calls). Each wrapper copies the global into libc's errno before the call and libc's errno back after it, and the variadic fallbacks sync errno the same way. The build result records `errno_shim` (the wrapped functions, or `status: failed` with `unsynced`) as a coverage caveat. Remaining gap, by design: after a libc call outside the table, or a call through a function pointer, the target still reads the last errno it wrote, and the global is shared across threads. Add a function to the table when a target branches on its errno.

### Symptom: Libc Calls in Complex Statements Lack Errno Shims
- **Cause:** `_CALL_SITE_RE` in `scripts/eacsl_toolchain.py` expected calls only at line starts or after `=;{}`. Calls in `if (f) fclose(f);`, `return close(fd);`, and ternary expressions were missed, leaving `__fc_eacsl_errno` unsynced after those calls.
- **Fix (fixed, uncommitted, `scripts/eacsl_toolchain.py`):** Extended `_CALL_SITE_RE` delimiters to include `(`, `)`, `:`, `!`, `?`, `&`, `|`, `,`, and keywords `return`, `else`, while excluding control keywords with lookahead. Added a warning when a libc call gets no errno shim.

### Symptom: E-ACSL Reports `\initialized` Right After a libc Call (`\initialized(&endptr)` After `strtol`, a Socket Address After `getsockname`)
- **Seen on:** libmnl's socket module (`getsockname` in `mnl_socket_bind`, runs 5 and 6, rejected by the Crash Verification Gate) and minmea (`\initialized(&endptr)` at `minmea.c:224` in `minmea_scan`, on both MINMEA-01 and MINMEA-02); finding F17 of [`../plans/phase1-review.md`](../plans/phase1-review.md).
- **Cause:** E-ACSL runs on host headers without Frama-C's libc specifications, so it does not see a libc call write through a pointer. With `-rte-initialized`, the next read of that value fails. The stop is the same on every input that reaches the call, so keep-going masks that dispatch case for the whole campaign.
- **Fix (fixed, commit `7be8bd1`, S9 of [`../plans/phase1-remediation-plan.md`](../plans/phase1-remediation-plan.md)):** the link-only libc shim (`build_errno_shim_object` in `scripts/eacsl_toolchain.py`) also wraps the functions of `EACSL_LIBC_EFFECTS` the slice calls, whether or not it reads errno. After the real call, each wrapper marks the bytes the call wrote initialized, with `__e_acsl_initialize`, and only in memory the runtime tracks (`__e_acsl_valid`). The ranges are those libc writes: `r` bytes of a `read` buffer, at most `len` of a `recv`/`recvfrom` buffer (with `MSG_TRUNC` they return the datagram's full length), the iovec of `recvmsg`/`readv` up to `r`, at most the caller's length of a socket address, and nothing on failure. The effects start once `templates/eacsl_runtime/fuzz_init.c` sets `__fc_eacsl_runtime_ready`: libFuzzer, and the runtime itself (it `read()`s `/proc/self/maps` during initialization), make wrapped calls before the shadow memory is mapped. The build records `errno_shim.eacsl_effects`. If the effects fail to compile against the host libc, the errno wrappers are linked alone and `effects_error` says why. Checked on a probe through `run_eacsl_fuzz.py replay`:
  - These now run clean: `strtol` then a read of `*endptr`; `socketpair` + `getsockname` then a read of the address; `recvmsg` then a read of the bytes received; `gettimeofday`, `gmtime`, and the two `strerror` cases.
  - These real defects still stop: a byte past what `read` returned, an address field past a short `getsockname` length, the address after a failed `getsockname`, a byte past what `recvmsg` returned, a byte past the 2 bytes `recv(..., 2, MSG_TRUNC)` wrote although it returned 8, a plain uninitialized local, and a printf type mismatch.
- **Checked on the targets (2026-11-14):** each target was replayed with HEAD's scripts and with the working tree, both as no-cache builds with `-rte-initialized`.
  - libmnl: run 1's `workspace/work/src/socket.c`, with a harness that binds a real `NETLINK_ROUTE` socket, receives a link dump and calls `mnl_socket_fdopen`. Before, it stopped at `socket.c:183` in `mnl_socket_fdopen`, `\initialized(&addr.nl_family)`. After, it runs clean. `mnl_socket_bind` never raised it, because it fills `nl->addr` itself before the call.
  - minmea: revision `c43c9e7`, the manifest's MINMEA-01 and MINMEA-02 inputs. Before, both stopped at the `endptr` alarm. After this fix, both stopped at the `va_list` alarm, a second pipeline false alarm (fixed, see "Every `va_arg` Fails" above). With both fixes, MINMEA-01 stops at its real bug, `minmea.c:656` in `minmea_getdatetime` (`-2147483648 ≤ date->month - 1`), the line the manifest expects. MINMEA-02 runs clean, as expected: E-ACSL does not check `abs(INT_MIN)`.
- **Seen again on libmodbus run-1 (2026-11-18), `strlcpy` (fixed, commit `af0b259` and its follow-up on branch `sup/libmodbus-strlcpy-effect`, not yet merged):** Phase 1 stopped at `src/modbus-tcp.c:632` in `modbus_tcp_listen` on `\initialized(&ctx_tcp->ip[0])`, and the Crash Verification Gate rejected it `disproved_by_source`. `modbus_new_tcp` fills `ctx_tcp->ip` with `strlcpy(ctx_tcp->ip, ip, dest_size)` (`modbus-tcp.c:1023`). The run's `config.h` has `HAVE_STRLCPY 1` (glibc 2.38 and later provide it), so libmodbus's own fallback in `modbus.c` is not compiled and the call goes to uninstrumented glibc. `strlcpy` and `strlcat` were not in the table.
  - **Fix:** both are now in `EACSL_LIBC_EFFECTS`, with their exact writes. `strlcpy` marks `min(r, size - 1) + 1` bytes and nothing when `size` is 0 (`r` is `strlen(src)`). `strlcat` reads `strnlen(dst, size)` before the call and marks from there the copied bytes plus the NUL, and nothing when `dst` holds no NUL within `size`.
  - glibc declares these two functions from 2.38 only. The analysis image has glibc 2.41 (Debian trixie); bookworm has 2.36. The shim therefore declares them itself (`EACSL_SHIM_OWN_PROTOTYPES`). Without that prototype, an older libc would fail the `-Werror` shim and drop every other effect with it. Their `__real_` is weak, so the link does not fail when libc lacks the symbol and the target's fallback is `static` (its calls are then not wrapped). This was checked by compiling with the declarations hidden (`_POSIX_C_SOURCE`) and with `nm`. It was not linked against a real glibc older than 2.38.
  - Checked by the image probe `test_libc_shim_clears_libc_false_alarms_and_keeps_real_ones_in_the_analysis_image` (cases 9-12). Before the fix, a truncating `strlcpy` and an appending `strlcat` both stopped on `\initialized`. After it, they run clean, and a read one byte past either NUL still stops.
- **Remaining gaps:**
  - A libc function outside the table still raises the alarm; add it to the table. If a supported libc may not declare it, also add it to `EACSL_SHIM_OWN_PROTOTYPES`.
  - The copy entries keep one buffer per function.
  - `nanosleep` marks `rem` initialized on any failure, not only `EINTR`.
  - `poll` marks the whole `pollfd` array initialized, not only `revents`.
  - `gmtime` and `localtime` no longer share one buffer, as they do in glibc.
  - `test_every_shim_wrapper_compiles_against_the_host_libc` runs only where clang and glibc headers exist. The image has no pytest, so the full-table compile was checked by hand in the container (54 errno and 47 effect functions, `-Werror`). Recompile after any table edit. The probe is `test_libc_shim_clears_libc_false_alarms_and_keeps_real_ones_in_the_analysis_image` (`FRAMAC_DOCKER_TESTS=1`).

### Symptom: E-ACSL Ignores an Unbounded Quantifier (`invalid E-ACSL construct ... Missing upper bound for i. '. Ignoring annotation.`)
- **Cause:** E-ACSL can only compile **bounded** quantifiers where the lower and upper bounds of the quantified integer variable `k` are syntactic integer expressions (e.g., `\forall integer k; 0 <= k < len ==> ...`). It does not fail the build on an unbounded one: it warns, keeps the clause as a comment in the instrumented file, and checks nothing.
- **Seen on:** step M4 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md) (2026-11-10), a repro in `framac-analysis:latest` (Frama-C 35.0~~dev). It ran the real `run_eacsl_fuzz.py guardrail --functions session_status` on the `tests/fixtures/security_props` session library, with the `L5_sanitized_log_line` assertion MetAcsl generates (`L5_no_crlf(tmp)`) pasted into the source: `[e-acsl] ...:57: Warning: invalid E-ACSL construct ... in quantification ∀ ℤ i; 0 ≤ i ⇒ ... Missing upper bound for i. '. Ignoring annotation.`, and the guardrail returned `passed_dynamic_oracle`.
- **Generated security properties: not a pipeline defect.** Guardrail builds never see the MetAcsl properties or what MetAcsl generates from them. `run_wp_function.py` writes `security_meta_<fn>.c` into WP's out-dir and passes it to the WP run only (`-meta ... -then-last`); the generated clauses live in that Frama-C project and are never printed back to a source file. The prover guardrail (`prover_brief.md`, `--sources {scratch_module_sources}`) and the parent re-check (`workspace_overlay.py`) compile the sidecar sources and the harness only, and the prover brief forbids copying meta-properties into the source. So the L4–L6 meta properties are checked by WP only, never dynamically. Of the generated predicates only `L5_no_crlf` is unbounded; the wipe predicate (`templates/metacsl/l6_wiped.acsl`, `0 <= i < count`) is translated and checked by E-ACSL. A meta file passed by mistake to `--sources` is parsed and ignored without a warning (no `-meta`).
- **Open pipeline bug (clauses in the source):** `run_eacsl_fuzz.py` does not scan the compile log for `Ignoring annotation` / `invalid E-ACSL construct`, so the guardrail reports `passed_dynamic_oracle` for a clause it never executed. The quantifier hint in `derive_eacsl_diagnostic_hints` runs only on `compile_error`, so it never fires here. To make: the guardrail and build report list the annotations E-ACSL ignored (file:line and reason), and a clause ignored in the checked function does not count as dynamically checked.
- **Fix:** Always write explicit integer lower and upper bounds in `\forall` and `\exists` predicates (`0 <= k < n`), and use the `integer` type (or `size_t` / `int`) explicitly.

### Symptom: An E-ACSL `\exists` Passes Although One of Its Conjuncts Is False (`\exists integer i; 0 <= i < n && P && Q` Checks Only `Q`)
- **Seen on:** S4 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md) (2026-11-10), `framac-analysis:latest` (Frama-C 35.0~~dev, E-ACSL). In a minimal repro (`requires` clauses, called with `size == 5`, `char buf[8] = "abc"`), `\exists integer n; 0 <= n < size && n == 1000 && n >= 0` passed, and so did `\exists integer n; 0 <= n < size && buf[n] == 'z' && \valid(buf + (0 .. n))`; with the two conjuncts swapped, both fail as they should. In the S4 stubs, the conjuncts moved into one predicate call (`0 <= i < n && P(s, i)`) are all checked: the E-ACSL cases of `tests/test_fc_stub_repairs.py` stop the overflowing and unterminated calls.
- **Cause:** an E-ACSL translation bug of guarded quantifiers: the conjunct right after the guard is dropped (`bound_variables.ml`, `Pand` case, loses the goal found in its left operand). Drafted with a validated patch as Issue 24, [`../upstream/frama-c/frama-c-eacsl-guarded-exists-drops-conjunct.md`](../upstream/frama-c/frama-c-eacsl-guarded-exists-drops-conjunct.md), and filed upstream as [pub/frama-c#2793](https://git.frama-c.com/pub/frama-c/-/work_items/2793) on 2026-11-15, with the fix in merge request [pub/frama-c!25](https://git.frama-c.com/pub/frama-c/-/merge_requests/25) (reproduces on `master` `3dff90fc70` and 34.0~beta).
- **Fix in the S4 stubs (fixed):** every E-ACSL quantifier in `fc_strlcpy.h`, `bsd/string.h` and `json-c/json.h` has exactly one predicate call after its guard (`__fc_bsd_cpy_fits(...)`, `__fc_json_nul(...)`); `tests/test_fc_stub_repairs.py::test_eacsl_quantifiers_have_one_conjunct_after_the_guard` enforces it.
- **Fixed for the vocabulary (integration of S4 and S8, branch `templates-stubs-integration`):** S8 replaced `valid_nstring` and gave `valid_read_nstring` libc's semantics without a quantifier; the E-ACSL `valid_read_string` and `valid_string` in `templates/fc_stubs/fc_compat_types.h` still had the dropped form (`\exists integer i; 0 <= i <= 65536 && \valid_read(s + (0 .. i)) && s[i] == '\0'`) and now call one predicate after the guard (`__fc_eacsl_read_nul_at`, `__fc_eacsl_nul_at`), checked by `tests/test_fc_stub_repairs.py::test_compat_eacsl_string_predicates_have_one_conjunct_after_the_guard`. **Open pipeline bug:** contracts written by provers and breakers can hit it too: a guardrail can pass a clause it did not check in full. Not yet done: a lint over guardrail sources, and an upstream report.

### Symptom: E-ACSL Rejects a Pointer the Program Got From an Uninstrumented Library (`\valid_read` False on a `strdup`, `getenv` or json-c String)
- **Seen on:** S4 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md) (2026-11-10), `framac-analysis:latest` and `framac-build:latest` (json-c 0.18). A string `json_object_get_string` returned, passed back to `json_object_new_string`, failed a `valid_read_string`-style precondition; so did `strdup`'s result passed to `strlcpy`.
- **Cause:** E-ACSL tracks only memory the instrumented code allocates (its own `malloc`, stack, globals). Blocks a library allocates internally (json-c's objects and strings, `getenv`'s environment, libc's static result buffers) are not in the shadow memory, so `\valid_read` and `\block_length` are false or zero on them.
- **Wider since 2026-11-14 (`--libc-replacements`, `--validate-format-strings`):** these checks run inside libc calls, so the target no longer has to read through the pointer for the check to fail. Seen with a control harness on Frama-C 34.0~beta, through `run_eacsl_fuzz.py replay`:
  - `fprintf(stderr, "%s", strerror(ENOENT))` stops with `fprintf: attempt to access unallocated memory via directive 1 ('%s')`.
  - `strncpy(d, strerror(EINVAL), n)` stops with `strncpy: source string string unallocated`.
  - `strlen(getenv("PATH"))`, `printf("%s", getenv("HOME"))`, `snprintf` into a stack buffer, `strcpy` from a literal, and `memcpy`/`memmove`/`memset` on the target's own buffers run clean.
  - Workaround (implemented, commit `7be8bd1`): `pipeline_make.py params set --module <mod> --no-fuzz-libc-checks` builds that module's E-ACSL binary without both options. It is recorded as `-no-libc-checks` in `reduced_checks`, and the Phase 3 guardrail re-check follows it.
  - **Fixed for libc's static results (S9, commit `7be8bd1`, `EACSL_LIBC_EFFECTS` in `scripts/eacsl_toolchain.py`):** the libc shim wraps `strerror`, `strsignal`, `gai_strerror`, `inet_ntoa`, `ctime`, `asctime`, `gmtime` and `localtime`, and returns a copy in a buffer of the shim, registered with the runtime and marked initialized. libc's own block cannot be registered in place: `__e_acsl_store_block` on it writes a shadow the runtime never mapped (no segment check in release builds). Both stops above and a read of `gmtime`'s fields now run clean. One buffer per function, as libc's contract allows, and a string is cut at 1023 bytes. In the S9 probe, `strdup` called from instrumented code ran clean even without the shim, presumably because the runtime defines `malloc` and glibc's `strdup` calls it; the shim also marks its bytes initialized. The S4 `strdup` stop above was not rechecked. `getenv`, json-c and other libraries are still untracked.
- **Fix in the S4 stubs (fixed):** the E-ACSL branches of `fc_strlcpy.h`, `bsd/string.h` and `json-c/json.h` check a pointer argument only when it lies in tracked memory (`\valid_read(s) ==> ...`), and require library handles only to be non-NULL where the library asserts on NULL. **Open pipeline bug (general):** any E-ACSL contract or RTE check on such a pointer (a prover's `requires valid_read_string(s)` in a guardrail build, an RTE on a read through it) is a false alarm, and the pipeline does not tell a fuzz crash of this kind from a real one. To make: `run_eacsl_fuzz.py` / `eacsl_toolchain.py` register the blocks the known allocating library calls return (`__e_acsl_store_block` after the call), or classify crashes whose pointer comes from such a call.

## Sanitizer Campaigns, Crash Parsing & Minimization

### Symptom: LeakSanitizer Reports `LeakSanitizer has encountered a fatal error` or `LeakSanitizer does not work under ptrace`
- **Cause:** LeakSanitizer (enabled by default with `-fsanitize=address` in the native LibFuzzer fallback) uses `ptrace` to stop threads while scanning. Docker's default seccomp profile allows `ptrace` on kernels >= 4.8; older hosts block it.
- **Fix:** Do not relax seccomp. Set `ASAN_OPTIONS=detect_leaks=0` (or pass LibFuzzer `-detect_leaks=0`) for the campaign and record in the run notes / agent result that leak detection was disabled, so missing leak coverage is visible.

### Symptom: E-ACSL Crash With `failure: null` or a Location Inside the E-ACSL Runtime (`unsafe_initialize`)
- **Cause:** heap corruption made the E-ACSL RTL crash before it printed the failing assertion.
- **Fix:** automatic. The crash input is replayed on a sanitizer build of the same slice; `attribution` and `failure_source: sanitizer_replay` give the precise file:line. The crash is still classified from the E-ACSL run.

### Symptom: A Crash Blamed on a Function Named `fuzzer`, or a Bare `memcpy: ...` / `printf: directive ...` Line Read as No Failure
- **Seen on:** libmnl `nlmsg`, Frama-C 34.0~beta, while adopting `--libc-replacements` (2026-11-14). The stop line was `memcpy: overlapping memory areas`, followed by `ERROR: libFuzzer: deadly signal` and a stack.
- **Cause 1:** `_STACK_FRAME_RE` cut C++ frame names at `::`, so libFuzzer's `fuzzer::PrintStackTrace()` frame read as a function `fuzzer`. That name does not match the runtime prefix `fuzzer::`. In a deadly-signal stack, `_parse_segment_failure` took the first frame that was not a runtime frame, so it could name `fuzzer` as the crashing function.
- **Cause 2:** the reports of E-ACSL's libc replacements and format-string checks carry no `file:line: Error:` header, so `parse_eacsl_failure` returned nothing for them.
- **Fix (commit `7be8bd1`):** in `scripts/run_eacsl_fuzz.py`:
  - The frame regex keeps `::`-scoped names.
  - `_parse_libc_failure` matches the runtime's closed list of message templates.
  - It names the caller from the first frame after the innermost E-ACSL runtime frame.
  - It leaves `file` `unknown` and `line` 0, so the sanitizer replay looks for a location.
  - Tests: `tests/test_eacsl_toolchain.py`.
- **Open pipeline gap:** format-string failures stay without a source location, because ASan does not stop on them. `instrumented_location` gives the line in the instrumented file (backlog). The Phase 3 guardrail has no sanitizer replay either, so a libc stop there gets a fingerprint `unknown#<fn>::...`. That fingerprint does not merge with the campaign's attributed `src/<file>#<fn>::...` for the same defect.
- **False alarms:** a stop on a string libc allocated (`strerror`) is a false alarm; see "E-ACSL Rejects a Pointer the Program Got From an Uninstrumented Library" above, and `--no-fuzz-libc-checks`.

### Symptom: `memcmp` With Identical or Overlapping Buffers Aborts Under `--libc-replacements` With `memcpy: overlapping memory areas` (`libc_contract` False Positive)
- **Seen on:** QCBOR run-6, 2026-11-14, module `libqcbor_a`, dispatch case `5` (`UsefulInputBuf_Compare` in `src/UsefulBuf.c:236`), Frama-C `34.0~beta (Selenium)`, engine `eacsl` (`--libc-replacements`). - **Fix / workaround:** Crash Verifier subagents replay the artifact on a plain ASan+UBSan build (where `memcmp` succeeds) and inspect `e_acsl_string.c:240` to reject the false positive. When a module hits repeated false stops in `--libc-replacements`, `--no-fuzz-libc-checks` disables E-ACSL's libc replacement wrappers for that module. **Open pipeline gap:** [`../../scripts/eacsl_toolchain.py`](../../scripts/eacsl_toolchain.py) does not yet wrap or rewrite `__e_acsl_builtin_memcmp` to check only `\valid_read` without `validate_overlapping_spaces`.

### Symptom: E-ACSL Instrumentation Succeeds but the Generated C Is Rejected With `error: cannot redeclare builtin function '__builtin_add_overflow'`
- **Seen on:** mpack run-3 (2026-11-17), `build-check` of all 13 harness modules. The instrumented file fails to compile (`workspace/harnesses/fuzz_<mod>.instrumented.c:<line>:34: error: cannot redeclare builtin function '__builtin_add_overflow'`), and the same run logs `[kernel:typing:implicit-function-declaration] .../mpack-expect.c:480: Warning: Calling undeclared function __builtin_mul_overflow. Old style K&R code?` plus the matching `__builtin_add_overflow` warnings in `mpack-reader.c`.
- **Cause:** MPack's checked arithmetic expands to `__builtin_add_overflow`/`__builtin_mul_overflow` under GCC (`MPACK_HAS_OVERFLOW_BUILTINS=1`, target mpack `src/mpack/mpack-platform.h:1889-1927`). Frama-C's kernel has no prototype for those builtins, so E-ACSL's printer emits `extern int ( /* missing proto */ __builtin_add_overflow)(...)` into the instrumented C, and clang refuses to redeclare a compiler builtin. The instrumentation step itself finishes; only the compile of the generated file fails. The E-ACSL toolchain did not stub or normalize the GCC overflow builtins (fixed, see below).
- **Run workaround (before the fix):** `-DMPACK_HAS_OVERFLOW_BUILTINS=0` in the module cppflags (`generate_harness.py --cppflags`), which selects the target's portable checked-arithmetic fallback (`result < a`, division-based multiply check: same semantics, no builtins). A report for such a run must state that the analysed configuration uses that fallback.
- **Eva and WP:** with Frama-C's own libc on the pipeline's `gcc_x86_64` machdep, the generated `__fc_machdep.h` includes `FRAMAC_SHARE/libc/__fc_gcc_builtins.h`. It declares the typed forms (`__builtin_sadd_overflow` ... `__builtin_umulll_overflow`) with contracts and defines `__builtin_{add,sub,mul}_overflow` as `_Generic` macros over them, so only the `_p` forms were undeclared (`missing-spec`, any value). Frama-C's `_Generic` picks the typed form from the first operand's type alone, so mixed operand types call the wrong one (`[kernel:typing:incompatible-types-call]`); that is Frama-C's model and the pipeline leaves it alone.
- **Upstream (2026-11-17):** drafted as package 34, issue only, [`../upstream/frama-c/frama-c-kernel-gcc-overflow-builtins.md`](../upstream/frama-c/frama-c-kernel-gcc-overflow-builtins.md). Not filed. It reports the wrong Eva result for mixed operand types, the parse error for `char` operands, the missing `_p` forms and the uncompilable implicit declaration.
- **Fix (fixed 2026-11-17, `a3ec02c` from `sup/mpack-overflow-builtins`, merged into `phase1-remediation` as `f32ba49`; analysis image rebuilt):**
  - `templates/fc_stubs/fc_compat_types.h` defines the three `_p` forms for every Frama-C parse, and the generic and typed forms only under `__FRAMAC_EACSL__` (the E-ACSL frontend on host headers, where none is known). They are GNU statement-expression macros with GCC's semantics: each operand is evaluated once, and the computation uses 32-bit halves, so no step raises a downcast or overflow alarm.
  - Tests: `tests/test_fc_compat_contracts.py::test_overflow_builtins_are_defined_only_where_frama_c_lacks_them`, `::test_overflow_builtins_parse_with_frama_c_libc_on_the_pipeline_machdep` (Docker: Eva on `gcc_x86_64` with the compat flags, no syntax error, no undeclared builtin, 0 alarms) and `::test_overflow_builtins_match_gcc_under_eacsl` (Docker: E-ACSL output equal to gcc's builtins case by case, no `missing proto`). mpack's `mpack-{expect,reader,writer,node}.c` typecheck with both flag sets.
  - Not covered: a `_p` form whose third argument is a bit-field or const-qualified.
- **History (pipeline bug in the first fix):** the first version (`4127a28`, merged as `87841fb`) defined all 24 forms for every Frama-C parse. Because `fc_compat_types.h` is force-included before `__fc_gcc_builtins.h`, the typed-form macros expanded inside that header's declarations and every kernel-libc parse failed: the analysis image build stopped at `phase0_model.py selftest` with `parse_failed`, `[kernel] FRAMAC_SHARE/libc/__fc_gcc_builtins.h:37: User Error: syntax error:`. It was reverted the same day (`6632b74`). Its Docker test ran Eva on Frama-C's default machdep (`x86_64`), which never includes that header, so it did not catch this.

### Symptom: Every Sanitizer and Coverage Build of a Module Fails With `clang: error: cannot specify -o when generating multiple output files`
- **Seen on:** mpack run-3, Phase 1, 2026-11-17.
  - `workspace/harnesses/fuzz_libmpack_a__mpack_writer_3.sanitizer_compile.log` holds `clang ... workspace/work/src/mpack/mpack-writer.c workspace/work/src/mpack/mpack-writer.h ... -o ...` and `Returncode: 1`.
  - Every `libmpack_a__*` fuzz report says `"dual_engine_skipped": "sanitizer build failed"`, so Phase 1 ran E-ACSL only.
  - Every `reports/coverage/<mod>.json` had `compile.returncode` 1 and `the coverage build failed`, until the driving session dropped the `.h` files from `--sources` by hand with a run-local script.
  - `sax_example`, which has no header in its sources, built both engines.
- **Cause:** pipeline defect.
  - mpack defines functions in its headers (`MPACK_INLINE`), so the Phase 0 model gives those functions the header as their file.
  - `api_harness.generate` builds a harness's `sources` from its entries' files plus `dag["modules"][module]["required_sources"]`. For a split cluster, which lives in `dag["submodules"]`, that list is empty, so the header becomes a harness source.
  - Frama-C (E-ACSL stage 1, Eva, WP) parses a header as a file of its own. clang treats it as a precompiled-header output and refuses `-o` when there are several outputs.
  - The mix of `src/...` and `workspace/work/...` paths in the sidecar comes from the overlay resolution, which every consumer normalises; it is not a defect.
- **Fixed:** `6cae079` from `sup/mpack-harness-sources-and-fd-leak`, merged into `phase1-remediation` on 2026-11-17 (merge `7cb53a7`).
  - `framac_common.compile_inputs` keeps the translation units of a source list.
  - `fuzz_build._compile_clang_binary` compiles only those. That covers the sanitizer build (fuzz, attribution, crash replay, decision-point replays) and the coverage build.
  - The header stays in the sidecar's `sources`, where E-ACSL's function list (`_discover_slice_functions`) and the module scope read it.
  - Tests are in `tests/test_clang_build_inputs.py`; the supervisor reran them (24 passed together with the S7 tests).
- **Workaround on an older checkout:** pass `--sources` without the `.h` files to the coverage and sanitizer steps. This does not lose header functions from the coverage report, because llvm-cov lists the inline functions the translation units instantiate under the header's name. Run-3's report lists 140 of them.

## MetAcsl Properties in the E-ACSL Build

Entries from package C of [`../plans/metacsl-exploitation-plan.md`](../plans/metacsl-exploitation-plan.md), 2026-11-18, on the fixture `tests/fixtures/metacsl_eacsl/` in `framac-analysis:latest` (Frama-C 34.0~beta, MetAcsl 0.12~beta). They apply only when `security_props.json` lists `eacsl` in `meta_engines`.

### Symptom: `fatal error: __fc_string_axiomatic.h: No such file or directory` in Stage 1 of an E-ACSL Build With the Meta File
- **Cause:** the generated meta file includes a Frama-C libc header, which is not on the include path of an `e-acsl-gcc` build (`-no-frama-c-stdlib`).
- **Fix (fixed, commit `fd13c04`, [`../../scripts/eacsl_toolchain.py`](../../scripts/eacsl_toolchain.py)):** `eacsl_meta_file_text` replaces that line with a comment, so the line numbers of the properties are kept.

### Symptom: An E-ACSL Build With `-meta` Returns 0 but the Instrumented File Has No `__e_acsl_assert` Call for the Properties
- **Cause:** MetAcsl ran in the same Frama-C stage as RTE and E-ACSL, which then see the untranslated project. `-then` inside `-F` gives `no input file`. The build is silently blind.
- **Fix (fixed, commit `fd13c04`):** MetAcsl runs in a stage of its own: `-F "<non-RTE flags> -meta -meta-warn-key unknown-func=inactive"` plus `--then-last --e-acsl-extra "<RTE flags>"` (`meta_stage_flags`). On the fixture: 100 assertion calls without the properties, 112 with them, none lost.

### Symptom: An Out-of-Bounds Write Is Reported as `<unknown>:0: Error: E-ACSL RTE failed` and Its Fingerprint Changes Once the Properties Are On
- **Cause:** every Frama-C flag had been moved after `--then-last`, the non-RTE ones included.
- **Fix (fixed, commit `fd13c04`):** only the RTE flags go to `--e-acsl-extra`. The fixture's ordinary bug keeps the fingerprint `src/prog.c#mix::mem_access::60975404fe` with and without the properties.

### Symptom: `[meta] User Error: Error during the typing of a HILARE!` With `What: the HILARE named '<property>'` During a Fuzz Build
- **Cause:** a property names a global or a term unknown in this module's sources.
- **Fix (fixed, commit `fd13c04`, [`../../scripts/fuzz_build.py`](../../scripts/fuzz_build.py)):** the named property is dropped and stage 1 retried, three times at most; after that the build is redone without any property, with `security_props.status = "dropped"` and the log kept as `<out>.security_meta.log`.
- **Open pipeline bug:** nothing shows `rejected` or `dropped` to the user yet, so the engine can be lost for a module without a visible message. Assigned to package C2.

### Symptom: A `requires` Property Fails on Every Input That Makes the Harness Call the Protected Function
- **Cause:** the harness calls the function without the state its callers establish. Not a target defect.
- **Fix (fixed for the case the build can see, commit `fd13c04`):** a `\precond` property whose target a harness source names is left out of the build and listed under `security_props.left_out`. Any other precondition failure carries `caller` and `harness_induced`.
- **Open pipeline bug:** `ledger.py ingest-fuzz` does not read `caller` or `harness_induced`, and a precondition failure is located at the callee. Assigned to package C2.

### Symptom: A Failure Located in `<out>.security_meta.c` With the Label `memory access` or `uninitialized` and No Property Name
- **Cause:** E-ACSL guards the evaluation of a property's predicate (for example `\valid_read(dst + i)` before `\separated(dst + i, &auth_ok)`), and such a guard failed.
- **Fix (fixed, commit `54098ac`, [`../../scripts/failure_identity.py`](../../scripts/failure_identity.py)):** the guard is mapped to its property through the line map of the sidecar `<out>.security_meta.json`; its predicate reads `<name>: meta: guard <label>: <pred>` and it carries `meta_guard`, so its fingerprint differs from a violation's. Unit-tested on a synthetic report only; no guard failure was provoked in the image.
- **Open pipeline bug:** a guard reported at `<unknown>:0` or inside `templates/acsl/acsl_vocabulary.h` (an unterminated string reaching `no_crlf_string`) is not mapped and keeps an ordinary identity.

### Symptom: Builds With the Properties Are Never Served From the Build Cache
- **Cause:** `fuzz_build.py` bypasses the E-ACSL build cache when properties are loaded, because the cache key does not cover the meta file yet.
- **Open pipeline gap:** add the meta text and the meta flags to `_eacsl_cache_material` and the meta file and sidecar to the cached outputs, then remove the bypass. Assigned to package C2. Until then every such build, link-repair rounds and replays included, is a full build.

### Symptom: `tools/check_generated_text.py` Reports a Literal `\n` in a `.sh` File That Contains `\name(`
- **Cause:** the hook's pattern for a literal backslash-n in shell files also matches the start of the ACSL keyword `\name`.
- **Open pipeline bug:** in [`../../tools/check_generated_text.py`](../../tools/check_generated_text.py). Not fixed; package C avoided the form in its files.
