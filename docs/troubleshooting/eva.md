# Eva Abstract Interpretation Precision & Runtime Issues

Issues encountered in module-level abstract interpretation (`run_eva_slice.py`), precision tuning (`eva_tuning.py`, `eva_loops.py`), flamegraphs (`eva_flamegraph.py`), and global initializer evaluation. See [`./README.md`](./README.md) for the master index.

---

### Symptom: Eva Reports High `Unknown` (Orange) Alarm Counts (> 30%) on a Module Slice
- **Cause:** Loop widening or path merging occurred before precision could stabilize, or an external helper function had no ACSL contract (`builtins:missing-spec`).
- **Fix:**
  1. Check `workspace/eva/<mod>/eva.log` for `missing-spec` warnings. Add a contract stub to `external_stubs.h` for any unmodeled external function so Eva does not widen its return value to `[-inf, +inf]`.
  2. Run `pipeline_make.py run eva-tune`, then read `tuning` in `workspace/reports/eva/<mod>.json`. It tries slevel, unrolling and the other precision options as a fixed ladder, and says what helped and why any run was rejected ([`../guides/resources-and-caching.md`](../guides/resources-and-caching.md), Section 6). If nothing helped, look at the harness: a symbolic input length, for one, leaves every option with the same Unknowns.
  3. For a small fixed-bound parsing loop the ladder did not settle, add `//@ loop unroll 32;` above it in `workspace/work/`. Do not write `loop pragma UNROLL`: the kernel rejects it and the run fails.

### Symptom: Many Eva Unknowns of One Kind: `function strcmp: precondition 'valid_string_s1' got status unknown`, `unaligned pointer creation. assert \aligned(ctx,alignof(struct db_filter_col))`, or `\initialized(&c0a0_8)` in the Harness
- **Seen on:** libseccomp run-4, modules `libseccomp_a`, `scmp_bpf_sim`, `scmp_bpf_disasm`, `scmp_sys_resolver` (`workspace/eva/<mod>/eva.log`). 97 `strcmp` preconditions and 44 `pointer_alignment` obligations out of 245 Unknowns in the target sources. No precision option changes them, so `eva-tune` cannot help. Diagnosed 2026-11-10 from the logs and a repro in `framac-analysis:latest`.
- **Cause A (56 `strcmp` preconditions in `src/`, and the harness's own `\initialized(&c0aN)` Unknowns):** the Eva entry of the generated harness initializes only a prefix of its input (`if (input_len > 0) Frama_C_make_unknown((char *)input_buf, input_len);`, with the comment "Initialize only [0 .. input_len - 1] so reads past input_len trigger Eva alarms"). Eva does not relate `fuzz_len` to that prefix, so every `memcpy` from `fuzz_buf` copies bytes that may be uninitialized, even behind the `fuzz_len >= fuzz_off + sizeof(x)` guard. A string argument built as `memset(c0a0, 0, ...); memcpy(c0a0, fuzz_buf + fuzz_off, rest_n); c0a0[rest_n] = 0;` is then not a provable `valid_read_string`, and each `strcmp(name, "...")` of the callee is one Unknown (`abi_syscall_resolve_name_munge`: 32, `arch_def_lookup_name`: 23, `in_word_set`: 1). In the repro, initializing the whole buffer (`Frama_C_make_unknown((char *)input_buf, MAX)`) turns the precondition Valid.
- **Cause B (38 `pointer_alignment` obligations in `src/api.c` and `src/db.c`):** `api_harness.py` passes an opaque handle parameter (`scmp_filter_ctx`, a `void *`) as `static unsigned char c0a0[4024]`, zeroed. A `char` array has alignment 1, so the callee's cast `(struct db_filter_col *)ctx` is never provably aligned. In the repro, passing the address of a zeroed object of the struct type removes the alarm. The zeroed buffer has a second effect, not measured here: the handle fails the target's own validity check (`_ctx_valid`), so the code after that check is Dead in every such case.
- **Cause C (41 `strcmp` preconditions and 6 alignment obligations in `tools/`):** not the harness. `eva.log` says `The specification of function getopt has generated a garbled mix of addresses`, so `optarg` and `argv + optind` are imprecise after `getopt`. This is a limit of the Frama-C libc model of `getopt`, not a pipeline defect.
- **Fix:** A and B are **fixed** (H1 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), commit 150b092 and the variadic follow-up after it); run-4 itself was not touched. **A:** `templates/harness_dual.c.template` gives `eva_main` a fully initialized shadow of the input (`framac_input_init`), and the copies a case makes itself go through `FRAMAC_FUZZ_COPY(fuzz_buf, fuzz_off)` (`scripts/api_harness.py`; `scripts/seed_harvest.py` reads the new spelling). `input_buf` keeps its uninitialized tail, so a pointer the target receives into the input still raises an alarm on a read past `input_len`. Hand-written `custom` and `dispatch` cases that copy from `fuzz_buf` themselves must use the macro to get the same effect. **B:** `scripts/api_harness.py` reads the declared types from the layout probe (`handle_prototypes`), builds an opaque handle with the API's constructor and releases it with the API's destructor (`seccomp_init` / `seccomp_release`), and releases a handle the call under test returns. A variadic function whose header declaration names one parameter fewer than the model lists gets its handle too. **Still open (B):** a call that takes two handles of one type (`seccomp_merge`) and a handle type with no destructor keep zeroed buffers (`notes` in the sidecar), because who owns the handles afterwards is not known.
- **Measured** on a copy of run-4's `libseccomp_a` inputs in `framac-analysis:latest`, same Eva options, old harness against the regenerated one: Unknown 184 -> 18, Valid 1198 -> 1347, functions with an Unknown 44 -> 10; the `strcmp` preconditions (56), the harness's own `\initialized` Unknowns (34) and 34 of the 38 alignment Unknowns are gone (the other 4 are `seccomp_merge` and `db_col_valid`, which it calls). 21 of the 38 cases build a handle, the variadic `seccomp_rule_add` and `seccomp_rule_add_exact` among them.
- **Read that number with this in mind. Open pipeline gap (D):** in Eva the constructor never returns a handle on libseccomp. `db.c:1078` (`col->state = _DB_STA_VALID;`, `0xA1B2C3D4` into an `int`) is an Invalid `signed_downcast` alarm, and Eva stops propagation there (`nonterm`: `db.c:1078 non-terminating statement`, in the old run too). Every handle case therefore runs with a NULL handle, and part of the drop is code that is not reached rather than proven. With the magic replaced by a value that fits an `int` (in the container's copy only, as a diagnostic) the handles are valid: the old harness is unchanged (189 Unknown of 1413 obligations), the new one (measured before the two variadic cases got their handles) reaches about twice the code (2658 obligations, 2411 Valid, 242 Unknown, Dead 4508 -> 3439) and Eva takes 1094 s instead of 24 s. The pipeline has no way to look past an Invalid alarm in a constructor; one would be a second, diagnostic run without that one check, never credited.
- **Confirmation pending:** the libseccomp confirming run (O6 of [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md)) compares the Unknown counts with the 97 `strcmp` and 44 alignment obligations of run-4 (H1 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md)).
- **Cause C, open (not the harness):** stub `getopt` with a contract that keeps `optarg` inside `argv` (S4 of the same plan).

### Symptom: Eva Does Not Relate `input_len` to the Initialized Prefix of `input_buf` (`\initialized(fuzz_buf + 0)` on the Dispatch Selector, Target Reads of the Input)
- **Seen on:** H4 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), measured 2026-11-10 in `framac-analysis:latest`. Also on the H2 test harness: `harness.c: accessing uninitialized left-value. assert \initialized(fuzz_buf + 0);` on `harness_selector = fuzz_buf[0]`.
- **Cause:** `eva_main` initializes `input_buf[0 .. input_len - 1]` with `input_len` an interval, and Eva joins all lengths, so a read below `input_len` is not provably initialized. The copies a case makes itself go through `FRAMAC_FUZZ_COPY` (H1); the selector byte and the target's own reads of the input do not.
- **Tried, not adopted:** `//@ split input_len;` after the declaration, with a small `MAX_INPUT_SIZE`. Measured on QCBOR run-3 `qcbor_main_decode` (custom harness, `QCBORDecode_Init` and `GetNext` over the input, `-DMAX_INPUT_SIZE=16`, `run_eva_slice.py --slevel 100`, current scripts): without split 50 s, 347 obligations, 325 Valid, 22 Unknown, 0 Invalid, 1385 Dead; with split 690 s and 797 s (two runs), 640 obligations, 325 Valid, 310 Unknown, 5 Invalid, 1219 Dead. Split is 14 to 16 times slower and reaches more code (Dead 1385 -> 1219: most new obligations, such as the `IEEE754_*` conversions, are in code the joined run never reached); none of the new obligations became Valid. The 5 Invalid are `Invalid or unreachable` calls through `pMe->pfAllocator` (`StringAllocator_Reallocate`, `_Allocate`, `_Destruct`, `qcbor_main_decode.c:182-196`), on a harness that installs no allocator; not diagnosed further. Unknowns per shared obligation were not compared, so it is open whether split makes any obligation of the joined run Valid.
- **Status: open, no generator option.** It does not pay on the one module measured. A further trial needs a per-obligation comparison and a module whose input reads are the Unknowns (a parser behind `fuzz_buf + fuzz_off`).

### Symptom: An Eva Run Is Slow (or Hangs) on a Module Slice
- **Fix:** first read `cost_profile` and `timeout_fallback` in `workspace/reports/eva/<mod>.json`. `cost_profile` lists the five functions with the largest share of the run's time on their own (`self`) and with their callees (`inclusive`), read from `flamegraph.txt`; `timeout_fallback` names the cheaper settings a timed-out run was retried with (less precise: more Unknowns). Tune (Step 2a of `/framac-eva`) or stub the functions it names. To see more, the module's base and plain Eva runs write `workspace/eva/<mod>/flamegraph.txt` (`-eva-flamegraph`; tuning rungs and loop trials skip it, and a tuned module publishes its base run's profile when the report rests on a rung). Render it to `flamegraph.svg`/`flamegraph.html` with `python3 /opt/framac-pipeline/scripts/pipeline_make.py run flamegraph-<mod>` (it renders the existing file and never re-runs Eva; or `scripts/eva_flamegraph.py --dir workspace/eva/<mod>`), then read the widest bars: they name the functions where Eva spends its time. Cross-check `workspace/eva/<mod>/nonterm.log` and the report's `nonterm` field (`workspace/reports/eva/<mod>.json`): a non-terminating loop is the usual cause of a hang, and `-eva-slevel`/`-eva-auto-loop-unroll` tuning (Step 2a of `/framac-eva`) is the usual fix.

### Symptom: `repair_hints` in the Eva Report (recursive call, or function with neither code nor specification)
- **Cause:** ported from upstream `frama-c-script make-wrapper` (see [`../upstream/sources/make_wrapper_tips.md`](../upstream/sources/make_wrapper_tips.md)). `run_eva_slice.py` matches `detected recursive call` and `Neither code nor (specification|... assigns clause) for function X,` in `eva.log` and lists the matching pipeline action in `repair_hints`.
- **Fix:** follow the hint's `action`: add the defining file to the module sources (locate it via `build_callgraph_dag.py`'s function index), add a stub/contract in `templates/acsl/external_stubs.h`, or enable the recursion fallback with `pipeline_make.py params set --module <mod> --eva-recursion-fallback` (recorded in `reduced_checks`).

### Symptom: Eva Reports `undeclared_functions: ["syscall"]` and Aborts with `invalid user input`
- **Cause:** `system.c` invokes the Linux `syscall(...)` glibc wrapper. Frama-C's internal libc headers (`__fc_libc/unistd.h`) omit the `syscall` function prototype when `-nostdinc` is used for Eva and WP.
- **Fix:** Add `/*@ assigns \result \from number; */ long syscall(long number, ...);` to `templates/fc_stubs/fc_compat_types.h` under the `__fc_libc` block. Fixed in the pipeline (commit `7e15154`); listed in `templates/fc_stubs/README.md`.
- **Caveat (open, by design):** a variadic contract cannot say what the call writes through its arguments, so Eva and WP assume `syscall` writes no memory: a buffer it fills (`getrandom`, `read` through `syscall`) keeps the caller's value. Results that depend on such a buffer are optimistic.

### Symptom: Eva Aborts on Global Initializers with `invalid pointer creation ... evaluation of initializer failed: Eva not started because globals initialization is not computable`
- **Cause:** Code generated by `gperf` (such as `syscalls.perf.c`) or traditional C code uses `(size_t)&((struct stringpool_t *)0)->member` for static offset tables. When Frama-C's `-warn-invalid-pointer` is active, Eva treats pointer arithmetic on `NULL` during static const global table initialization as an invalid pointer alarm, aborting before analysis starts.
- **Workaround used by the libseccomp run (replaced):** `--no-warn-invalid-pointer` in `eva_args` of `templates/pipeline.mk`. It was global, so every module of every target lost the invalid-pointer alarms (`p + n` past an object), not only gperf tables; it is removed again.
- **Fix (pipeline, commit `7e15154`):** `scripts/fc_cpp_wrapper.py` (the preprocessor `-wrapper`, see the `offsetof` entry in [`./kernel-and-stubs.md`](./kernel-and-stubs.md)) rewrites the idiom behind an integer cast, `(int)(size_t)&((struct stringpool_t *)0)->str5` into `(int)(size_t)__builtin_offsetof(struct stringpool_t, str5)`, which the kernel folds to the same constant gcc computes; a non-constant index goes through the same arithmetic as `offsetof(T, m[i])`. Each rewrite is logged as `[fc-cpp] <file>:<line>: null-pointer offset idiom rewritten: ...`. `-warn-invalid-pointer` stays on. Verified on the analysis image with a gperf-style table: the rewrite off reproduces `Eva not started because globals initialization is not computable`, on gives `0 alarms` (`test_frama_c_and_eacsl_accept_a_non_constant_offsetof_without_losing_precision`, `FRAMAC_DOCKER_TESTS=1`).
- **Limits:** only `(I)&((T *)0)->D` with an identifier-only cast and a null pointer written `0`, `(0)` or `((void *)0)` is rewritten. Without an integer cast (a pointer result), behind a pointer cast, or with any other null-based arithmetic (`(char *)0 + n`, `container_of` variants), Eva still reports the invalid pointer: triage those, or stub the code. libseccomp needs a re-run to confirm the whole module now starts (O6 in [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md)).

### Symptom: A timed-out Eva rung reports preprocessor lines in `error_summary` (`note: this is the location of the previous definition`, `2 | #define _POSIX_C_SOURCE 199309L`)
- **Seen on:** minmea run-1, 2026-11-14, `workspace/reports/eva-tuning/minmea/precision.json` and `loop-minmea_scan-0.json`, both `analysis_timeout` after `Frama-C Eva exceeded the 600 s wall-clock limit`.
- **Cause:** pipeline bug. On a timeout, `run_eva_on_slice` in [`../../scripts/run_eva_slice.py`](../../scripts/run_eva_slice.py) appends `extract_error_summary(combined_log)[-5:]` to the limit line. When the log holds no error line, `extract_error_summary` falls back to the last non-empty lines of the log, which here are the compiler's `_POSIX_C_SOURCE` redefinition warning from the `-pp-annot` pass. The report then reads as if preprocessing had failed. Why the macro is defined twice was not diagnosed; the analysis itself is not affected (the same warning is in the logs of the rungs that finished).

### Symptom: An eva-tune rung ends `analysis_timeout` with `Frama-C Eva exceeded the 137 s wall-clock limit` although the rung limit is 1030 s
- **Seen on:** nanopb run-1, 2026-11-20, module `libprotobuf_nanopb_a`, second eva-tune ladder after harness repair 1. `EVA_TUNE_TIMEOUT_libprotobuf_nanopb_a := 1030` in `workspace/build/modules.mk` (8 x the 128.8 s base run). `workspace/reports/eva-tuning/libprotobuf_nanopb_a/returns.json`: `status: analysis_timeout`, `elapsed_s: 137.1`, `auto_recursion_fallback: true`, `eva_options: {"slevel": 500, "split-return": "auto"}`. Its `red_alarms.csv` is from 22:19:18 and its `eva.log` ends at 22:21:36.
- **Cause:** pipeline gap (supervisor diagnosis from the run's files and the code).
  - Every Eva run of this module first aborts on direct recursion in `pb_read` (`pb_decode.c:100`: `Recursive call to pb_read without assigns clause`). `run_eva_slice.py` `_attempt()` then retries once with `-eva-warn-key assigns:missing=warning`, as documented. The base run, the module report and the `history`, `values`, `relational` and `returns` rungs all carry `auto_recursion_fallback: true`.
  - The retry runs under `_remaining()`, the trial budget minus the first attempt. In `returns`, the first attempt ran 893 s at `slevel` 500 before reaching the recursion, so the retry got 1030 - 893 = 137 s and timed out.
  - The rungs do not learn from the base run that the retry is needed: `EVA_RECURSION_FALLBACK_<mod>` stays empty (it is set only by `params set --eva-recursion-fallback`, which the Eva skill presents for mutual recursion), so every rung, loop trial and module rerun repeats the first attempt that is bound to abort.
  - `elapsed_s` is the retry's time only. The base run's 128.8 s excludes its first attempt, so the 8x rung limit is computed from part of the base cost, and a rung's `elapsed_s` hides the time it lost.
  - `slevel` and `unroll` timed out at 1030 s in their first attempt, before reaching the recursion (no recursion line in `tune/slevel/eva.log`); they would have aborted and retried with no time left anyway.
- **Workaround:** `params set --module <mod> --eva-recursion-fallback` before `eva-tune` when the base report has `auto_recursion_fallback: true`. Not applied in this run (the supervisor does not steer the run).
- **Fix (fixed: branch `sup/nanopb-eva-tune-recursion`, commits `7c2b480` and `2ff5040`, merged to main in `794b367` on 2026-11-21):**
  - `pipeline_make._plan_tuning` reads `auto_recursion_fallback` from `eva-tuning/<mod>/base.json` and writes `EVA_TUNE_RECURSION_FALLBACK_<mod> := 1` (only then; other `modules.mk` files are unchanged). `templates/pipeline.mk` (`EVA_RUNG_RULE`, `eva_finish_cmd`) starts every rung and loop trial with `--allow-incomplete-recursion-specs`: the command and `reduced_checks` of the auto-retry, under the full rung limit.
  - The base run (it stays the detector), the plain `eva-<mod>` run (it shares the base run's cache entry) and shards are unchanged. `settings_digest` is unchanged, so recorded decisions stay current; each rung misses the Eva cache once because its command changed. A stale flag (a later base run without the retry) makes the guards refuse the rungs as `different_analysis`, which fails closed.
  - `run_eva_slice.py` adds the report field `auto_recursion_fallback_first_attempt_s` (the aborted first attempt's wall time) at both retry sites, and keeps the marker through a timeout-fallback tier; `eva_shards.py merge` sums it over the retried shards. `elapsed_s` and `trial_timeout` are unchanged.
  - Tests: `tests/test_eva_tune_recursion.py` (13 tests, 7 fail on the old code; the `make -n` one checked by hand in `framac-analysis:latest`). `skills/framac-eva/SKILL.md` (mirrors synced) and `docs/guides/eva-sharding.md` updated.
  - Still repeating the aborting attempt: the plain `eva-<mod>` run with tuned options that cannot be replayed, and sharded modules.

- **Cause:** (diagnosed from `workspace/reports/eva/libqcbor_a.json` and `workspace/eva/libqcbor_a/eva.timed_out.log`)
  - The base run (`run eva`, slevel 100) hit the 7200 s Eva limit at 12:15 local (`error_summary`: `Frama-C Eva exceeded the 7200 s wall-clock limit`). Its two retries both timed out at 900 s (`timeout_fallback_tried`: `cvalue_fast`, `cvalue_imprecise_alloc`). The report is `status: analysis_timeout` with `total_properties: 0`: nothing was salvaged from a run that was killed. Run-1 analysed the 126-case harness of the same target in 3362 s (4315 properties). The harness doubled its cases and added stateful sequences, and the decoder is now analysed through long call chains: `cost_profile.inclusive` puts 97% of the time under `QCBORDecode_Private_GetNextMapOrArray`, 93% under `QCBORDecode_Private_ConsumeItem` and 85% under `QCBORDecode_Private_NestLevelAscender`; `self` is led by `QCBOR_Private_DecodeHead` (25%).
