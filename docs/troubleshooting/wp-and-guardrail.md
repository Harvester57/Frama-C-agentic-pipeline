Issues encountered in Phase 3 deductive verification (`run_wp_function.py`), Dual-Oracle E-ACSL Guardrail (`run_eacsl_fuzz.py guardrail`), prover/negotiation scheduling (`wp_scheduler.py`), pure-ACSL splicing (`acsl_ast.py`), function facts and frame skeletons (`function_facts.py`, `frame_skeleton.py`), mutation checks (`mutation_check.py`), and proof carry-forward (`proof_carry.py`). For Layer 4–6 MetAcsl security properties, see [`./security-properties.md`](./security-properties.md). For ledger and verifier ingestion, see [`./ledger-and-verifier.md`](./ledger-and-verifier.md).

## Quick Symptom-to-Fix Reference

| Symptom in `wp.log` / `run_wp_function.py` | Root Cause | Exact Fix |
| :--- | :--- | :--- |
| Every goal after a loop fails, even for untouched variables | Missing `loop assigns` (WP havocs all memory on every iteration) | Write `loop assigns` (**Step A**) before any `loop invariant` (**Step B**). |
| `loop invariant` is `Valid` for `established`, `Unknown` for `preserved` | Invariant is not inductive across `i -> i + 1` or omits modified variables | Conjoin loop counter bounds (`0 <= i <= n`) with accumulator/pointer relationship (`offset == i * sizeof(elem_t)`), constrain all variables modified in the loop body, or drill down with `--prop <clause_name> --dump-goal` (`vc_goal_dumps`). |
| `loop invariant` fails `established` on `0 <= i <= n` | `n` can be negative on entry | Add `requires n >= 0;` (or use unsigned `size_t`). |
| `[wp] warning: Missing assigns clause` | Loop or callee lacks `assigns` (`run_wp_function.py` flags this as `unsound_proof`) | Add explicit `loop assigns ...;` and callee `assigns ...;`. |
| `[wp] warning: Memory model hypotheses for function ...` | `-wp-check-memory-model` detected raw `\separated` missing on pointer arguments | Add `requires \separated(p + (0 .. n-1), q + (0 .. m-1));` to the function contract. |
| `[rte:annot] warning: ... Through function pointer ... cannot generate ...` | Indirect call `fp(...)` without `calls` specification | Add `//@ calls f1, f2;` above the call or `//@ assert fp \in {&f1, &f2};`. |
| `Instance of 'Pre-condition ...' status: Unknown` at call site | Caller has not proven callee's `requires` | Add an intermediate `//@ assert ...;` before the call or strengthen the caller's loop invariant / `requires`. |
| `while (count--) { ... }` fails `rte:unsigned_overflow` | Post-decrement wraps `0U -> UINT_MAX` on loop exit | Use `--no-warn-unsigned --wrap-lines <lines>` (the declared lines are recorded in `reduced_checks` as an assumption; any other unsigned overflow goal not fully proved leaves the function unproven) or bound a non-wrapping counter. |
| Pointer cast `(uint32_t *)byte_buf` or `(void *)attr + 4` stays unproven under `Typed` | Type reinterpretation across pointer types, which the `Typed` memory model does not support | Do not switch to `Typed+cast`: the WP manual calls that model unsound, and `run_wp_function.py` records any proof under it as `unsound_proof`. When such goals stay unproven, `run_wp_function.py` re-runs the function once under `Typed+cast` as a diagnostic (`cast_model_probe`, never credited). If that probe proves every goal, the report sets `wp_cast_limitation` and `next_synthesis_focus: wp_typed_cast_limitation_stop_now`: stop, since a stronger contract will not help (on libmnl, `Typed+nocast`, `Bytes` and cast-free contracts left the same goals unproven). The unit stays unproven by WP: report it as a WP memory-model limit. |
| Address taken `&local_var` passed to helper | Stack variable address taken | Pass `--wp-model Typed+ref` (the default in `run_wp_function.py`). |
| `syntax error` on `terminates` or `exits` | Wrong ACSL clause order in function contract | Order clauses strictly: `requires` -> `terminates` / `decreases` -> `exits` -> `assigns` -> `ensures` -> `behavior`. |

## WP Soundness, Verdict Gates & Log Parsing (`run_wp_function.py`)

### Symptom: `unsound_proof` With `Neither code nor specification for function X`
- `X` is called but has neither a body nor a contract. Frama-C generates a default contract and WP would trust it, so the proof does not hold.
- Add a contract to the prototype through `strengthening_requests`, or use a stub from `templates/acsl/external_stubs.h` for an external function.
- `Neither code nor explicit exits and terminates for function X` is a different message: `X` has a specification, and this one is harmless.

### Symptom: Missing Assigns Clauses Silently Considered Sound by WP Log Scanner
- **Seen:** 2026-11-11, regex audit. Frama-C warnings of the form `Neither code nor explicit assigns for function ...` or `Neither code nor explicit exits, assigns and terminates...` were not caught by `scan_wp_log_soundness`, allowing ungrounded proofs relying on invented empty assigns clauses to pass as sound.
- **Cause:** `_TIER_B_PATTERNS` only matched the exact string `Neither code nor specification for function`.
- **Fix (fixed 2026-11-11, uncommitted, `scripts/run_wp_function.py`):** Wired [`../../scripts/framac_common.py`](../../scripts/framac_common.py) `parse_missing_spec` and `fold_messages` into `scan_wp_log_soundness`, `apply_verdict_limits`, and `derive_wp_diagnostic_hints`. Any missing-spec message whose clauses are not exclusively benign (`exits`/`terminates`) is flagged as Tier B silent unsoundness and its callee is recorded in limits. Tests: `tests/test_run_wp_function.py`.

### Symptom: Two-Line `Missing assigns clause` Warning Defeated Macro-Loop Unsoundness Filter
- **Seen:** 2026-11-11, regex audit. Realistic two-line Frama-C warning outputs (`[wp] macro_test.c:3: Warning:\n  Missing assigns clause ...`) split the file/line location from the warning text, causing `_MISSING_ASSIGNS_LINE_RE` to fail matching and resulting in `unsound_proof` for macro loops.
- **Cause:** `_TIER_B_RE` matched single lines without message folding, capturing only line 2 without line 1's source location.
- **Fix (fixed 2026-11-11, uncommitted, `scripts/run_wp_function.py`, `tests/test_workspace_overlay.py`):** `scan_wp_log_soundness` folds multi-line Frama-C log messages into single-line messages via [`../../scripts/framac_common.py`](../../scripts/framac_common.py) `fold_messages` prior to pattern matching. Updated fixture in `tests/test_workspace_overlay.py:305` to realistic two-line format. Tests: `tests/test_run_wp_function.py`, `tests/test_workspace_overlay.py`.

### Symptom: Substring Overlap in File Names Matched Unrelated Diagnostics
- **Seen:** 2026-11-11, regex audit. `_kernel_error_line` in [`../../scripts/loop_seeds.py`](../../scripts/loop_seeds.py) and `_MISSING_ASSIGNS_LINE_RE` in [`../../scripts/run_wp_function.py`](../../scripts/run_wp_function.py) matched file names that were substrings of other files (e.g. `sum.c` within `not_sum.c:9`). In addition, `_kernel_error_line` previously used `(?<![\w./-])`, which incorrectly rejected valid error lines on path-qualified file names (e.g. `dir/sum.c:9`, `./sum.c:9`).
- **Cause:** Unanchored file name regex patterns in `run_wp_function.py`, and overly restrictive negative lookbehind including `'/'` against basename queries in `loop_seeds.py`.
- **Fix (fixed 2026-11-11, uncommitted, [`../../scripts/loop_seeds.py`](../../scripts/loop_seeds.py), [`../../scripts/run_wp_function.py`](../../scripts/run_wp_function.py)):** Used negative lookbehind `(?<![\w./-])` before full file path matches in `run_wp_function.py`, and `(?<![\w.-])` in `loop_seeds.py` (omitting `/` so directory-prefixed paths are accepted while continuing to reject prefix/suffix word overlaps such as `not_sum.c` or `prefix_sum.c`). Tests: [`../../tests/test_loop_seeds.py`](../../tests/test_loop_seeds.py), [`../../tests/test_run_wp_function.py`](../../tests/test_run_wp_function.py), [`../../tests/test_challenger_m3_stress.py`](../../tests/test_challenger_m3_stress.py).

### Symptom: A Unit Stays Uncovered With `wp_trivial_clause_only` or `wp_limits_unmet`
- `wp_trivial_clause_only`: every `L4_*`, `L5_*` or `L6_*` clause of that class holds whatever the function does. Write a clause that constrains the output or state.
- `wp_limits_unmet`: the report has no `limits`, or its contract check did not pass. Re-run with the current `run_wp_function.py`; reports written before verdict limits existed are not credited.

### Symptom: Truncated WP Log With CSV Report Produces False `all_proven` Verdict
- **Seen:** 2026-11-11, regex audit. If WP crashed, hit OOM or was truncated after generating `report.csv` but before printing `[wp] Proved goals:`, `run_wp_on_function` reported `status: "all_proven"`.
- **Cause:** `all_valid` evaluated `(vc_total == 0 or vc_proved == vc_total)`, where `vc_total` defaulted to 0 when the summary line was absent. This also undermined the degenerated-goal waiver backstop.
- **Fix (fixed 2026-11-11, uncommitted, `scripts/run_wp_function.py`):** When `csv_path.exists()` is true, `all_valid` strictly requires `vc_proved_valid = (proved_m is not None and vc_total > 0 and vc_proved == vc_total)`. A missing `Proved goals:` line or a count of 0 proved goals falls through to `unproven_goals_remain`. Tests: `tests/test_run_wp_function.py`.

### Symptom: Mock WP Test Runners Failing With `AssertionError: assert 'unproven_goals_remain' == 'all_proven'`
- **Seen:** 2026-11-11, regex audit (Milestone M3 & M5). Tests using simulated Frama-C runners in `tests/test_tool_sizing.py` and `tests/test_promote_and_verifier.py` failed with `status: unproven_goals_remain` instead of `all_proven`.
- **Cause:** Feature A3 ([`../../scripts/run_wp_function.py`](../../scripts/run_wp_function.py)) instituted a strict fail-closed verdict gate requiring explicit `[wp] Proved goals:    k / n` in stdout logs when a report CSV is present. Mock runners (`FakeFramaC`, `fake_run`) generated valid CSV reports but emitted empty or incomplete stdout logs missing the `Proved goals` line, correctly triggering the fail-closed guard.
- **Fix (fixed 2026-11-11, uncommitted, [`../../tests/test_tool_sizing.py`](../../tests/test_tool_sizing.py), [`../../tests/test_promote_and_verifier.py`](../../tests/test_promote_and_verifier.py)):** updated `FakeFramaC` default log output to include `[wp] Proved goals:    1 / 1\n` and added the line to retry branch mocks in `test_bitwise_retry_reuses_the_cache_dir_and_sizing` and `test_wp_unsigned_downcast_and_bitwise_retry`, aligning test mocks with real Frama-C log behavior. Tests: [`../../tests/test_tool_sizing.py`](../../tests/test_tool_sizing.py), [`../../tests/test_promote_and_verifier.py`](../../tests/test_promote_and_verifier.py).

### Symptom: Contradictory WP Proofs Misclassified as Consistent Under Non-Typed Prover Memory Models
- **Seen:** 2026-11-11, regex audit. Vacuity smoke test logs under `-wp-model Bytes`, `-wp-model Hoare`, or `-wp-model Caveat` proving `\false` were declared `consistent` by `run_wp_function.classify_vacuity_log`.
- **Cause:** `_DOOMED_REQUIRES_RE` and `_DOOMED_DEAD_RE` in [`../../scripts/run_wp_function.py`](../../scripts/run_wp_function.py) hardcoded the literal prefix `typed_`. When running under other memory models, goal names carry prefixes such as `bytes_` or `hoare_`, resulting in 0 regex matches and silently declaring contradictory contracts consistent. In addition, `classify_vacuity_log` did not validate smoke test ratio bounds (`k > n`, `n <= 0`, `k < 0`) and returned `consistent` whenever unexplained smoke test failures remained (`(n - k) > len(dead)`).
- **Fix (fixed 2026-11-11, uncommitted, [`../../scripts/run_wp_function.py`](../../scripts/run_wp_function.py)):** Dropped the `typed_` prefix requirement from `_DOOMED_REQUIRES_RE` and `_DOOMED_DEAD_RE`, expanded dead goal matching to include `_dead_local_init_`, added `_SMOKE_COUNT_RE` parsing `k / n`, added ratio bounds validation (`n <= 0` or `k > n` or `k < 0`), checked for unexplained smoke test failures (`(n - k) > len(dead)`), and failed closed to `status: "inconclusive"`. Tests: [`../../tests/test_run_wp_function.py`](../../tests/test_run_wp_function.py), [`../../tests/test_challenger_m3_stress.py`](../../tests/test_challenger_m3_stress.py), [`../../tests/test_verdict_limits.py`](../../tests/test_verdict_limits.py).

### Symptom: Unproved `pointer_value` Goals Are Counted `proven_under_hyp` After One `(Degenerated)` Line in the WP Log
- **Seen:** 2026-11-11, regex audit, by reading `run_wp_on_function` (no target run, no test: the loop is inside the function that runs Frama-C).
- **Cause:** `_FPV_DEGEN_RE` captures the degenerated goal names, but only their count was used: with one or more, every Unknown or Invalid row whose property contained `pointer_value` or `\valid_function` moved to `proven_under_hyp`, a data-pointer `\object_pointer` alarm included.
- **Fix (fixed 2026-11-11, uncommitted, `scripts/run_wp_function.py`):** a row is moved only when its property contains `\valid_function` and not `\object_pointer`, and at most one row per degenerated goal. The report CSV has no goal name, so rows cannot be matched to the log by name.

## Dual-Oracle E-ACSL Guardrail

### Symptom: E-ACSL Fails With `labels pre-analysis was not performed on construct \old(b)` on a Guardrail Build
- **Toolchain bug (Frama-C 35.0~dev regression), worked around in the pipeline since 2026-11-10** (see Fix), diagnosed 2026-11-09. Seen in the Tier 6 A/B: the parent guardrail of `mnl_nlmsg_batch_is_empty` returned `compile_error`, so its merge was refused (`parent guardrail returned status='compile_error'`). The same contract passed under run 1's Frama-C 34 image.
- **Cause:** E-ACSL in 35 aborts on any `p1 <==> p2` whose operands contain a labelled term: `\old(...)`, `\at(..., L)`, or a formal parameter in an `ensures` (the kernel reads it as `\old(formal)`). The contract here was `ensures empty_iff_zero: (\result != 0) <==> (b->buflen == 0);`. The `Piff` translation now deep-copies its operands and skips the labels pre-analysis on the copies. A 6-line reproducer fails on `framac-analysis:latest` (35) and builds and runs on `framac-pipeline:fc34-20261105`. Upstream draft with the failing shapes and the 34/35 source diff: [`../upstream/frama-c/frama-c-eacsl-iff-labelled-term.md`](../upstream/frama-c/frama-c-eacsl-iff-labelled-term.md) (Issue 14, not filed).
- **Impact:** a WP-proven contract of this shape can never pass the parent guardrail on 35, so the prover's merge is refused, or a carry-forward replay rejected. In libmnl run 1, 4 merged contracts have it: `mnl_nlmsg_batch_is_empty`, plus three header `ensures` of the form `... ==> (\result <==> ...)` (`ok_iff`, `seq_track`, `pid_track`).
- **Fix:** **Toolchain bug open upstream; worked around in the pipeline (fixed, 2026-11-10).** Writing the equivalence as `(p1 ==> p2) && (p2 ==> p1)` avoids it, and the pipeline now does this in two places:
  - **Every E-ACSL build** (guardrails, fuzz harnesses, the Phase 0 E-ACSL gate): the frontend runs gcc's preprocessor under [`../../scripts/fc_cpp_wrapper_eacsl.py`](../../scripts/fc_cpp_wrapper_eacsl.py) instead of `fc_cpp_wrapper.py` (`eacsl_toolchain.EACSL_CPP_WRAPPER`). It rewrites every `<==>` inside an ACSL annotation of the preprocessed text as two implications (`fc_cpp_wrapper.rewrite_iff_text`), so this covers contracts already proved with `<==>`: carried-forward proofs, contracts already merged into `workspace/work/`, and `<==>` written in the target's own headers. The source files, WP and Eva are unchanged and read `<==>` as written. Line numbers are kept (the reversed copy of each operand is written on one line), so E-ACSL failures still point at the original file and line. Each rewrite is logged in the compile log as `[fc-cpp] <file>:<line>: N `<==>` in an annotation (E-ACSL: two implications) rewritten`. `FRAMAC_CPP_REWRITE=off` turns it off together with the `offsetof` repair. Checked in `framac-analysis:latest` (35) by `tests/test_fc_cpp_wrapper.py::test_eacsl_builds_and_checks_equivalences_over_labelled_terms`: the unrewritten file still fails with this message, the rewritten one builds and runs, and a broken `<==>` postcondition is still reported at its own line.
  - **Prover brief:** [`../../skills/framac-wp/prover_brief.md`](../../skills/framac-wp/prover_brief.md) Strict Rule 4 tells provers to write equivalences as two implications, so new contracts do not depend on the rewrite.
- **Remove when** the image's E-ACSL translates `Piff` without copying its operands (Issue 14). The rewrite is harmless on 34, whose E-ACSL did the same rewrite internally.

### Symptom: A Guardrail Returns `guardrail_error` (`Binary failed without a recognizable E-ACSL failure report`, Exit Code 1) for a Contract That Cannot Be Wrong
- **Fixed pipeline bug** (diagnosed 2026-11-10 on the Tier 6 A/B replay of libmnl run 1, Frama-C 35.0~dev image; the A/B copy is kept in `targets/libmnl/ab-2026-11-09-tier6/`). Not a Frama-C 35 issue. The replayed contract of `mnl_attr_get_len` was `requires \valid_read(attr); assigns \nothing; ensures \result == attr->nla_len;`, and its parent guardrail was refused.
- **Cause:** a guardrail replays the module corpus and libFuzzer stops at the first crash. `select_replay_inputs` always replays the targeted inputs (`seed-*`, `crash-*`, ...), and run 1 had put `seed-ext-parse-offset-2pow31` into the `attr` corpus on purpose: it reproduces a verified bug in `mnl_attr_parse` and ends in a SEGV in `mnl_attr_ok`. The guardrail build instruments only the checked function (`-e-acsl-functions mnl_attr_get_len`), so the crash came out as `UndefinedBehaviorSanitizer: SEGV ... in mnl_attr_ok`, not as an E-ACSL report, and `classify_guardrail` returned `guardrail_error`. Every guardrail of module `attr` would have failed the same way, whatever its contract, and the replay had stopped after 18 of 64 inputs without ever running `mnl_attr_get_len`. The report hid the cause: `parse_guardrail_reach` stripped the `COVERED_FUNC` lines of `-print_coverage` but not the 307 indented `UNCOVERED_PC:` lines, which filled the 4,000-character `runtime_trace` (its first line, a truncated `UNCOVERED_PC` at `e_acsl_segment_tracking.c:336`, looked like a crash in the E-ACSL runtime).
- **Fix:** [`../../scripts/run_eacsl_fuzz.py`](../../scripts/run_eacsl_fuzz.py): `crash_outside_checked_functions` recognises a replay that stopped on a sanitizer or libFuzzer crash (not a timeout or out-of-memory) with no E-ACSL report and no checked function (or `__gen_e_acsl_<fn>`) in its stack. `run_guardrail_check` then drops that input (matched to the replayed file by content), replays the rest from a scratch copy, and lists it in `excluded_inputs` with its crash line; after `GUARDRAIL_MAX_EXCLUDED_INPUTS` (8) it gives up with `guardrail_error` and says so. A crash through a checked function, or without a stack, is still `guardrail_error`. `UNCOVERED_PC` lines are stripped too, so the crash report stays in `runtime_trace`. Checked on the kept guardrail binary in `framac-analysis:latest`: the seed is excluded, all 64 inputs run, `mnl_attr_get_len` is reached twice and the verdict is `passed_dynamic_oracle`. Tests in `tests/test_guardrail_p1.py`, built from the real output.
- **Still open:** an excluded input is only listed in the guardrail report; it does not become a fuzz candidate, so a crash that is not already known is visible only there. The same UBSan `SEGV` output is not recognised by `parse_sanitizer_failure` either (see [`./eacsl-and-fuzzing.md`](./eacsl-and-fuzzing.md), `UndefinedBehaviorSanitizer: SEGV`).

### Symptom: A Guardrail Replay Excuses a Crash Inside a Checked Function (`crash outside the checked functions`) When the Function Lives in a `.y`, `.l` or `.inc` File
- **Seen:** 2026-11-11, regex audit (no target run). `crash_outside_checked_functions` returned an excuse for a stack whose frame #0 was `parse_attr /w/src/attr_tables.inc:41:9` with `functions=["parse_attr"]`.
- **Cause:** it read the stack with `_STACK_FRAME_RE`, which wants a `.c` or `.h` file and a line. A frame in another file, with a space in its path or with no line information was skipped, and a skipped frame counted as "not a checked function".
- **Fix (fixed 2026-11-11, uncommitted, `scripts/run_eacsl_fuzz.py`):** the excuse reads the function of every frame with `_STACK_FRAME_FN_RE`, whatever follows the name. Tests: `tests/test_regex_hardening.py`. `_STACK_FRAME_RE` was decoupled to extract functions with or without `.c`/`.h` file and line, and `_FN_RE`, `_ERR_RE`, `_OLD_RE`, and `_UBSAN_RE` accept non-whitespace path locations with any extension.

## Pure-ACSL Checks, Splicing, Facts & Skeletons

### Symptom: A Prover's Merge Is Refused With `agent modified content outside assigned function '<fn>'` After It Added a Ghost Lemma Function
- **Fixed pipeline bug** (found 2026-11-09 while reviewing [`../plans/formal-discovery-plan.md`](../plans/formal-discovery-plan.md); reproduced on `acsl_ast.splice_prover_changes` with a `/*@ ghost /@ requires ...; decreases n; ... @/ void lem(int n) {...} */` block placed directly above the prover's function; fixed by Tier 3 in `be4a909`, [`../plans/formal-discovery/tier-3-rule3-ghost-lemma.md`](../plans/formal-discovery/tier-3-rule3-ghost-lemma.md)). Runs made before the fix still show the old message.
- **Cause:** [`../../skills/framac-wp/prover_brief.md`](../../skills/framac-wp/prover_brief.md) Step B item 3 ("Inductive Lemmas Without Coq") told the prover to replace a global `lemma` with a recursive `/*@ ghost ... */` C function carrying `decreases` and `ensures`. Such a function can only live at file scope, and `acsl_ast._compute_span_start` deliberately leaves top-level ACSL declarations (`ghost` included, via `_TOP_DECL_KWS`) outside the function span, so `splice_prover_changes` raised `ScopeViolationError` for exactly the construct the brief asked for. `verify_acsl_only` passes (the block is pure ACSL), so the prover saw no warning until `merge-agent`. A prover could reach `all_proven` in its scratch (WP under `-wp-fct` takes the ghost function's contract as a hypothesis and never proves the ghost function itself), then lose the whole attempt at merge. A second defect hid the declaration's name: `_parse_acsl_inner_segments` cut a ghost function at the first `;` of its `/@ ... @/` contract and `_extract_decl_name` returned the first parameter (`n`) instead of `lem`.
- **Fix:** (1) the brief's rule now forbids file-scope ghost functions as well as global `lemma`s and tells the prover to stop with `stalled_after_k_retries` and `proof_gap: {"predicate": ..., "reason": "inductive lemma required: ..."}`; (2) [`../../scripts/prover_candidates.py`](../../scripts/prover_candidates.py) `note_oracle` diffs the top-level declarations of `scratch/work` against `scratch/base` after every oracle run and reports `scope_violation_pending: ["ghost lem", ...]` in the first `candidate` block, with `next_synthesis_focus: "remove_top_level_acsl_declarations"`, `next_action: "continue"` even when `all_proven`, and the candidate never kept as best; (3) [`../../scripts/acsl_ast.py`](../../scripts/acsl_ast.py) `splice_prover_changes` names the added declarations (`agent added top-level ACSL declaration(s) outside '<fn>': ghost lem; ...`), and the segmenter treats a ghost function's `/@ ... @/` contract as part of the declaration; (4) [`../../scripts/ledger.py`](../../scripts/ledger.py) tags such a `proof_gap` with `details.gap_kind: "inductive_lemma_required"` and [`../../scripts/generate_report.py`](../../scripts/generate_report.py) counts those functions under "Open units: prover-limited vs spec-limited". Provers still cannot contribute lemmas: that is Tier 7 of the plan.

### Symptom: A Candidate With `admit`, `axiom` or `requires \false` Passes the Unsound-Construct Check
- **Seen:** 2026-11-11, regex audit (no target run). `find_unsound_acsl_keywords` returned no error for `/*@ requires c != '"'; admit requires \false; ensures d != '"'; */`, and none for `requires (\false);`, `requires 1 == 0;`, `requires \false && x > 0;` or `requires x != x;`.
- **Cause (two defects in `scripts/acsl_ast.py`):** `_STRING_IN_ACSL_RE` did not know character literals and crossed lines, so two `'"'` literals hid the text between them from every check. `_VACUOUS_FALSE_CLAUSE_RE` matched only a bare `\false` or `0` as the whole predicate.
- **Fix (fixed 2026-11-11, uncommitted, `scripts/acsl_ast.py`):** `_scrub_acsl_literals` empties string and character literals in one pass, bounded by the line. `_first_vacuous_clause` cuts each `requires` / `assumes` / `loop invariant` clause with `_scan_clause_end` and asks the new `is_trivially_false_predicate`, the twin of `is_trivial_predicate`. Tests: `tests/test_regex_hardening.py`. The check stays syntactic: a predicate false for a reason it cannot see (`x < 0 && x > 0`) is left to the WP smoke test.

### Symptom: User Variables Named `tmp` or `__retres` Dropped From Loop Guards and Prover Facts
- **Seen:** 2026-11-11, regex audit (Milestone M1).
- **Cause:** [`../../scripts/function_facts.py`](../../scripts/function_facts.py) matched compiler temporaries using a static regex `_TEMP_RE = re.compile(r"\b(?:tmp(?:_\d+)?|__retres)\b")`. When user C code legitimately declared variables named `tmp`, `tmp_1`, or `__retres`, their expressions were stripped from write values, loop guards, loop scalars, return-path conditions, Eva flow locations, and caller conditions, producing incomplete or unprovable prover briefs.
- **Fix (fixed 2026-11-11, uncommitted, [`../../scripts/function_facts.py`](../../scripts/function_facts.py), [`../../scripts/kernel_ast.py`](../../scripts/kernel_ast.py), [`../../scripts/kernel_ast_dump.ml`](../../scripts/kernel_ast_dump.ml)):** [`../../scripts/kernel_ast_dump.ml`](../../scripts/kernel_ast_dump.ml) records exact compiler temporaries using the Cil `v.vtemp` flag in the dumped JSON as `temps`.
