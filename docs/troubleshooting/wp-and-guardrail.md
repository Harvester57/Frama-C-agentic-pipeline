Issues encountered in Phase 3 deductive verification (`run_wp_function.py`), Dual-Oracle E-ACSL Guardrail (`run_eacsl_fuzz.py guardrail`), prover/negotiation scheduling (`wp_scheduler.py`), pure-ACSL splicing (`acsl_ast.py`), function facts and frame skeletons (`function_facts.py`, `frame_skeleton.py`), mutation checks (`mutation_check.py`), and proof carry-forward (`proof_carry.py`). ## Quick Symptom-to-Fix Reference

| Symptom in `wp.log` / `run_wp_function.py` | Root Cause | Exact Fix |
| :--- | :--- | :--- |
| Every goal after a loop fails, even for untouched variables | Missing `loop assigns` (WP havocs all memory on every iteration) | Write `loop assigns` (**Step A**) before any `loop invariant` (**Step B**). |
| `loop invariant` is `Valid` for `established`, `Unknown` for `preserved` | Invariant is not inductive across `i -> i + 1` or omits modified variables | Conjoin loop counter bounds (`0 <= i <= n`) with accumulator/pointer relationship (`offset == i * sizeof(elem_t)`), constrain all variables modified in the loop body, or drill down with `--prop <clause_name> --dump-goal` (`vc_goal_dumps`). |
| `loop invariant` fails `established` on `0 <= i <= n` | `n` can be negative on entry | Add `requires n >= 0;` (or use unsigned `size_t`). |
| `[wp] warning: Missing assigns clause` | Loop or callee lacks `assigns` (`run_wp_function.py` flags this as `unsound_proof`) | Add explicit `loop assigns ...;` and callee `assigns ...;`. |
| `[wp] warning: Memory model hypotheses for function ...` | `-wp-check-memory-model` detected raw `\separated` missing on pointer arguments | Add `requires \separated(p + (0 .. n-1), q + (0 .. m-1));` to the function contract. |
| `[rte:annot] warning: ... Through function pointer ... cannot generate ...` | Indirect call `fp(...)` without `calls` specification | Add `//@ calls f1, f2;` above the call or `//@ assert fp \in {&f1, &f2};`. |
| `Instance of 'Pre-condition ...' status: Unknown` at call site | Caller has not proven callee's `requires` | Add an intermediate `//@ assert ...;` before the call or strengthen the caller's loop invariant / `requires`. |
| `while (count--) { ... }` fails `rte:unsigned_overflow` | Post-decrement wraps `0U -> UINT_MAX` on loop exit | Use `--no-warn-unsigned --wrap-lines <lines>` (the declared lines are recorded in `reduced_checks` as an assumption; any other unsigned overflow goal not fully proved leaves the function unproven) or bound a non-wrapping counter. |
| Pointer cast `(uint32_t *)byte_buf` or `(void *)attr + 4` stays unproven under `Typed` | Type reinterpretation across pointer types, which the `Typed` memory model does not support | Do not switch to `Typed+cast`: the WP manual calls that model unsound, and `run_wp_function.py` records any proof under it as `unsound_proof`. When such goals stay unproven, `run_wp_function.py` re-runs the function once under `Typed+cast` as a diagnostic (`cast_model_probe`, never credited). If that probe proves every goal, the report sets `wp_cast_limitation` and `next_synthesis_focus: wp_typed_cast_limitation_stop_now`: stop, since a stronger contract will not help (on libmnl, `Typed+nocast`, `Bytes` and cast-free contracts left the same goals unproven). The unit stays unproven by WP: report it as a WP memory-model limit. |
| Address taken `&local_var` passed to helper | Stack variable address taken | Pass `--wp-model Typed+ref` (the default in `run_wp_function.py`). |
| `syntax error` on `terminates` or `exits` | Wrong ACSL clause order in function contract | Order clauses strictly: `requires` -> `terminates` / `decreases` -> `exits` -> `assigns` -> `ensures` -> `behavior`. |

## WP Soundness, Verdict Gates & Log Parsing (`run_wp_function.py`)

### Symptom: Every Guardrail of a Module Stops With `guardrail_error` on a printf "%u" Outside the Checked Function
- **Seen on:** c-ares run-1, Phase 3, 2026-11-16, every prover of an `adig` function. For example, `agents/prove-print_opt_none/scratch/guard_print_opt_none.json`: `A check failed outside the checked functions (E-ACSL eacsl_format_error: printf: directive expects argument of type 'unsigned int' but the corresponding argument has type 'int' at unknown:0 in print_header) on an input that cannot be dropped (not a replayed corpus file)`, on crash input `crash-da39a3ee5e6b4b0d3255bfef95601890afd80709` (the empty input). WP had proven all goals (6/6 for `print_opt_none`), yet `prover_candidates.py restore-best` found no eligible candidate.
- **Cause:** E-ACSL false positive, not a target defect.
  - `print_header` (`src/tools/adig.c`) passes `ares_dns_record_get_id()` to `%u`. It returns an `unsigned short`, which C promotes to `int`, and C allows that for `%u`.
  - The image's E-ACSL format runtime compares static types exactly and aborts. See [`../upstream/frama-c/frama-c-eacsl-format-promoted-argument-signedness.md`](../upstream/frama-c/frama-c-eacsl-format-promoted-argument-signedness.md).
  - The run's scripts predate the patched runtime, so the guardrail build (`run_eacsl_fuzz.py guardrail`, which goes through `compile_eacsl_binary`, stage 2) had no `--e-acsl-share`.
  - The out-of-scope policy in [`../../scripts/run_eacsl_fuzz.py`](../../scripts/run_eacsl_fuzz.py) drops a corpus input that fails outside the checked functions. But libFuzzer always runs its own empty unit first, and that unit cannot be dropped. The verdict is therefore `guardrail_error` for every function of the module.
- **Fix:** fixed and merged into `phase1-remediation` (2026-11-16), from branches `sup/c-ares-eacsl-format-promotion` (`e66a68c`, `99a6871`) and `sup/c-ares-guardrail-format-runtime` (`342e2c5`).
  - The guardrail shares the fuzz build's stage 2, so the patched share applies to it: `eacsl_toolchain.prepare_patched_eacsl_share`, which falls back to the image runtime when the patch does not compile.
  - `342e2c5` adds guardrail regression tests in [`../../tests/test_guardrail_format_runtime.py`](../../tests/test_guardrail_format_runtime.py). Its Docker test reproduces the run's verdict with the image runtime and passes with the patch. The commit also makes the digest of the patched share copy cover the patch text.
  - A run on an older checkout must update its scripts, then re-dispatch the blocked provers.
- **Open policy question** (not a defect): a check that fails outside the checked functions, on a path every input reaches (such as the empty unit), blocks every function of the module. Whether it should is for the maintainers to decide.

### Symptom: Provers End `stalled_after_k_retries` After One WP Call; the Next Call Is Refused With "Prover budget exhausted ... elapsed=...s/900s"
- **Seen on:** c-ares run-1, Phase 3, 2026-11-16.
  - `prove-print_help_info_ahost`: its first WP call at 19:57:35Z took about 30 s. The second call was refused at 20:12:55Z, before Frama-C started.
  - `prove-ares_getopt` (19:57:00 to 20:13:21) and `negotiate-ares_malloc` show the same pattern.
  - The scheduler's `auto` slots dispatched 15 agents on a 32-CPU pool (`resources.recommend()`, `duty = 4.0`), and `wp` grants are elastic.
  - `state/resource-history/wp/` has no WP completion from 20:03:00 to 20:12:51. Then five refused calls end together, each using about 0.4 CPU-s and 35 MiB.
  - The run's parent then capped the scheduler with `--slots 6`.
- **Cause:** pipeline bug.
  - [`../../scripts/run_wp_function.py`](../../scripts/run_wp_function.py) checked `max_wall_clock_s` (in `.prover_budget.json`, 900 s for `standard`) as `now - first_wp_at`.
  - The script runs inside a container that `resources.py exec` starts only after the host broker grants the `wp` lease. So the time later calls spent queued for that lease counted as prover time.
  - The call that finally got its lease was refused before Frama-C started, and the lease it waited for was wasted.
  - The broker recorded only a `waited` bool, never a duration.
- **Fix:** fixed and merged into `phase1-remediation` (2026-11-16), from branch `sup/c-ares-prover-budget-lease-wait` (`db0a0f4`, `698f2d3`), verified by the supervisor.
  - [`../../scripts/resources.py`](../../scripts/resources.py): the broker measures `Lease.wait_s`, and `exec` passes `FRAMAC_LEASE_ID` and `FRAMAC_LEASE_WAITED_S` into the container.
  - `run_wp_function.py` accumulates `lease_wait_s` in `.prover_budget.json` and subtracts it from the elapsed time and from the WP wall timeout for the remaining time. It credits each lease once, never the first call's (which came before `first_wp_at`), and never more than the time since `first_wp_at`.
  - Without the two variables, it behaves as before.
  - [`../../scripts/workspace_overlay.py`](../../scripts/workspace_overlay.py): the brief's budget line says what the wall budget counts.
  - Tests: [`../../tests/test_prover_budget_lease_wait.py`](../../tests/test_prover_budget_lease_wait.py) (12 tests, all failing before the fix), and `tests/test_resources.py::test_exec_dry_run_builds_the_full_engine_command`.
- **Status (2026-11-20, fixed):** all three remaining gaps are closed across [`../../scripts/workspace_overlay.py`](../../scripts/workspace_overlay.py) and [`../../scripts/resources.py`](../../scripts/resources.py):
  - `prepare_agent` now renders the "WP Verifiability & Iteration Budget" section for every `role == "prover"` brief (including `core_provable` on `standard`), omitting empty blocker/note bullets.
  - `cmd_exec` and `cmd_run` in [`../../scripts/resources.py`](../../scripts/resources.py) now idempotently credit non-`wp` broker lease waits (for example `guardrail` and `replay`) and in-container `resources.py run` sub-lease waits into `.prover_budget.json` (`_credit_prover_budget_lease_wait`, keyed by `lease_wait_credited` so `run_wp_function.py` never double-counts, and never crediting waits before `first_wp_at`).
  - Before acquiring a `wp` lease in `cmd_exec` / `cmd_run`, `_prover_budget_already_exhausted` checks `.prover_budget.json` (unless `--ignore-prover-budget` is passed) and downgrades already-exhausted `run_wp_function.py` calls to ungated `light` so `run_wp_function.py` writes its normal `budget_exhausted: true` report immediately without waiting on or wasting a `wp` lease.
  - Tests: [`../../tests/test_prover_budget_lease_wait.py`](../../tests/test_prover_budget_lease_wait.py), [`../../tests/test_resources.py`](../../tests/test_resources.py), [`../../tests/test_workspace_overlay.py`](../../tests/test_workspace_overlay.py).

### Symptom: `unsound_proof` With `Neither code nor specification for function X`
- `X` is called but has neither a body nor a contract. Frama-C generates a default contract and WP would trust it, so the proof does not hold.
- Add a contract to the prototype through `strengthening_requests`, or use a stub from `templates/acsl/external_stubs.h` for an external function.
- `Neither code nor explicit exits and terminates for function X` is a different message: `X` has a specification, and this one is harmless.

### Symptom: Missing Assigns Clauses Silently Considered Sound by WP Log Scanner
- **Seen:** 2026-11-11, regex audit. Frama-C warnings of the form `Neither code nor explicit assigns for function ...` or `Neither code nor explicit exits, assigns and terminates...` were not caught by `scan_wp_log_soundness`, allowing ungrounded proofs relying on invented empty assigns clauses to pass as sound.

- **Fix (fixed 2026-11-11, uncommitted, `scripts/run_wp_function.py`):** Wired [`../../scripts/framac_common.py`](../../scripts/framac_common.py) `parse_missing_spec` and `fold_messages` into `scan_wp_log_soundness`, `apply_verdict_limits`, and `derive_wp_diagnostic_hints`. Any missing-spec message whose clauses are not exclusively benign (`exits`/`terminates`) is flagged as Tier B silent unsoundness and its callee is recorded in limits. Tests: `tests/test_run_wp_function.py`.

### Symptom: Two-Line `Missing assigns clause` Warning Defeated Macro-Loop Unsoundness Filter
- **Seen:** 2026-11-11, regex audit. Realistic two-line Frama-C warning outputs (`[wp] macro_test.c:3: Warning:\n  Missing assigns clause ...`) split the file/line location from the warning text, causing `_MISSING_ASSIGNS_LINE_RE` to fail matching and resulting in `unsound_proof` for macro loops.

- **Fix (fixed 2026-11-11, uncommitted, `scripts/run_wp_function.py`, `tests/test_workspace_overlay.py`):** `scan_wp_log_soundness` folds multi-line Frama-C log messages into single-line messages via [`../../scripts/framac_common.py`](../../scripts/framac_common.py) `fold_messages` prior to pattern matching. Updated fixture in `tests/test_workspace_overlay.py:305` to realistic two-line format. Tests: `tests/test_run_wp_function.py`, `tests/test_workspace_overlay.py`.

### Symptom: Substring Overlap in File Names Matched Unrelated Diagnostics
- **Seen:** 2026-11-11, regex audit. `_kernel_error_line` in [`../../scripts/loop_seeds.py`](../../scripts/loop_seeds.py) and `_MISSING_ASSIGNS_LINE_RE` in [`../../scripts/run_wp_function.py`](../../scripts/run_wp_function.py) matched file names that were substrings of other files (e.g. `sum.c` within `not_sum.c:9`). ### Symptom: A Unit Stays Uncovered With `wp_trivial_clause_only` or `wp_limits_unmet`
- `wp_trivial_clause_only`: every `L4_*`, `L5_*` or `L6_*` clause of that class holds whatever the function does. Write a clause that constrains the output or state.
- `wp_limits_unmet`: the report has no `limits`, or its contract check did not pass. Re-run with the current `run_wp_function.py`; reports written before verdict limits existed are not credited.

### Symptom: Truncated WP Log With CSV Report Produces False `all_proven` Verdict
- **Seen:** 2026-11-11, regex audit. If WP crashed, hit OOM or was truncated after generating `report.csv` but before printing `[wp] Proved goals:`, `run_wp_on_function` reported `status: "all_proven"`.
- **Cause:** `all_valid` evaluated `(vc_total == 0 or vc_proved == vc_total)`, where `vc_total` defaulted to 0 when the summary line was absent. This also undermined the degenerated-goal waiver backstop.
- **Fix (fixed 2026-11-11, uncommitted, `scripts/run_wp_function.py`):** When `csv_path.exists()` is true, `all_valid` strictly requires `vc_proved_valid = (proved_m is not None and vc_total > 0 and vc_proved == vc_total)`. A missing `Proved goals:` line or a count of 0 proved goals falls through to `unproven_goals_remain`. Tests: `tests/test_run_wp_function.py`.

### Symptom: Contradictory WP Proofs Misclassified as Consistent Under Non-Typed Prover Memory Models
- **Seen:** 2026-11-11, regex audit. Vacuity smoke test logs under `-wp-model Bytes`, `-wp-model Hoare`, or `-wp-model Caveat` proving `\false` were declared `consistent` by `run_wp_function.classify_vacuity_log`.
- **Cause:** `_DOOMED_REQUIRES_RE` and `_DOOMED_DEAD_RE` in [`../../scripts/run_wp_function.py`](../../scripts/run_wp_function.py) hardcoded the literal prefix `typed_`. When running under other memory models, goal names carry prefixes such as `bytes_` or `hoare_`, resulting in 0 regex matches and silently declaring contradictory contracts consistent. In addition, `classify_vacuity_log` did not validate smoke test ratio bounds (`k > n`, `n <= 0`, `k < 0`) and returned `consistent` whenever unexplained smoke test failures remained (`(n - k) > len(dead)`).
- **Fix (fixed 2026-11-11, uncommitted, [`../../scripts/run_wp_function.py`](../../scripts/run_wp_function.py)):** Dropped the `typed_` prefix requirement from `_DOOMED_REQUIRES_RE` and `_DOOMED_DEAD_RE`, expanded dead goal matching to include `_dead_local_init_`, added `_SMOKE_COUNT_RE` parsing `k / n`, added ratio bounds validation (`n <= 0` or `k > n` or `k < 0`), checked for unexplained smoke test failures (`(n - k) > len(dead)`), and failed closed to `status: "inconclusive"`. Tests: [`../../tests/test_run_wp_function.py`](../../tests/test_run_wp_function.py), [`../../tests/test_challenger_m3_stress.py`](../../tests/test_challenger_m3_stress.py), [`../../tests/test_verdict_limits.py`](../../tests/test_verdict_limits.py).

### Symptom: Unproved `pointer_value` Goals Are Counted `proven_under_hyp` After One `(Degenerated)` Line in the WP Log

### Symptom: A Loop Invariant Goal Is Counted Under `l2_termination`
- **Seen:** package D2 of [`../plans/metacsl-exploitation-plan.md`](../plans/metacsl-exploitation-plan.md), 2026-11-18, in a unit test: `goal_obligation_class({"kind": "precondition", "annotation": "L4_invariants: len <= cap"})` returned `l2_termination`. ## Dual-Oracle E-ACSL Guardrail

### Symptom: E-ACSL Fails With `labels pre-analysis was not performed on construct \old(b)` on a Guardrail Build
- **Toolchain bug (Frama-C 35.0~dev regression), worked around in the pipeline since 2026-11-10** (see Fix), diagnosed 2026-11-09. Seen in the Tier 6 A/B: the parent guardrail of `mnl_nlmsg_batch_is_empty` returned `compile_error`, so its merge was refused (`parent guardrail returned status='compile_error'`). The same contract passed under run 1's Frama-C 34 image.
- **Cause:** E-ACSL in 35 aborts on any `p1 <==> p2` whose operands contain a labelled term: `\old(...)`, `\at(..., L)`, or a formal parameter in an `ensures` (the kernel reads it as `\old(formal)`). The contract here was `ensures empty_iff_zero: (\result != 0) <==> (b->buflen == 0);`. The `Piff` translation now deep-copies its operands and skips the labels pre-analysis on the copies. A 6-line reproducer fails on `framac-analysis:latest` (35) and builds and runs on `framac-pipeline:fc34-20261105`. Upstream draft with the failing shapes and the 34/35 source diff: [`../upstream/frama-c/frama-c-eacsl-iff-labelled-term.md`](../upstream/frama-c/frama-c-eacsl-iff-labelled-term.md) (Issue 14, filed as [pub/frama-c#2800](https://git.frama-c.com/pub/frama-c/-/work_items/2800), merge request [!31](https://git.frama-c.com/pub/frama-c/-/merge_requests/31)).
- **Impact:** a WP-proven contract of this shape can never pass the parent guardrail on 35, so the prover's merge is refused, or a carry-forward replay rejected. In libmnl run 1, 4 merged contracts have it: `mnl_nlmsg_batch_is_empty`, plus three header `ensures` of the form `... ==> (\result <==> ...)` (`ok_iff`, `seq_track`, `pid_track`).
- **Fix:** **Toolchain bug open upstream; worked around in the pipeline (fixed, 2026-11-10).** Writing the equivalence as `(p1 ==> p2) && (p2 ==> p1)` avoids it, and the pipeline now does this in two places:
  - **Every E-ACSL build** (guardrails, fuzz harnesses, the Phase 0 E-ACSL gate): the frontend runs gcc's preprocessor under [`../../scripts/fc_cpp_wrapper_eacsl.py`](../../scripts/fc_cpp_wrapper_eacsl.py) instead of `fc_cpp_wrapper.py` (`eacsl_toolchain.EACSL_CPP_WRAPPER`). It rewrites every `<==>` inside an ACSL annotation of the preprocessed text as two implications (`fc_cpp_wrapper.rewrite_iff_text`), so this covers contracts already proved with `<==>`: carried-forward proofs, contracts already merged into `workspace/work/`, and `<==>` written in the target's own headers. The source files, WP and Eva are unchanged and read `<==>` as written. Line numbers are kept (the reversed copy of each operand is written on one line), so E-ACSL failures still point at the original file and line. Each rewrite is logged in the compile log as `[fc-cpp] <file>:<line>: N `<==>` in an annotation (E-ACSL: two implications) rewritten`. `FRAMAC_CPP_REWRITE=off` turns it off together with the `offsetof` repair. Checked in `framac-analysis:latest` (35) by `tests/test_fc_cpp_wrapper.py::test_eacsl_builds_and_checks_equivalences_over_labelled_terms`: the unrewritten file still fails with this message, the rewritten one builds and runs, and a broken `<==>` postcondition is still reported at its own line.
  - **Prover brief:** [`../../skills/framac-wp/prover_brief.md`](../../skills/framac-wp/prover_brief.md) Strict Rule 4 tells provers to write equivalences as two implications, so new contracts do not depend on the rewrite.
- **Remove when** the image's E-ACSL translates `Piff` without copying its operands (Issue 14). The rewrite is harmless on 34, whose E-ACSL did the same rewrite internally.

### Symptom: A Guardrail Returns `guardrail_error` (`Binary failed without a recognizable E-ACSL failure report`, Exit Code 1) for a Contract That Cannot Be Wrong
