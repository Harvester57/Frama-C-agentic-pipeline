# Security Properties (Layers 4–6) & MetAcsl Issues

Issues encountered in threat-model security property generation (`security_props.py`, `templates/metacsl/`), MetAcsl goal simplification, Layer 4 authentication gates, Layer 5 output sanitization and format strings, and Layer 6 secret wiping and Eva taint tracking. For threat-model Markdown fence parsing, see [`./phase0-build-and-model.md`](./phase0-build-and-model.md). See [`./README.md`](./README.md) for the master index.

---

### Symptom: `L5_sanitized_send_msg` Is False at the Call Although No Uninitialized Byte Is Ever Sent (`\initialized(&req[0 .. req_length - 1])`)
- **Seen on:** libmodbus run-1 (2026-11-18). `breaker-modbus_mask_write_register` reported the property false at the `send_msg` call with `req_length == 14`, and `verify-modbus_mask_write_register_2a7ed14cd2` closed the candidate `src/modbus.c#modbus_mask_write_register::l5_sanitized::2a7ed14cd2` as `rejected`. The same property raised candidates on `modbus_write_bits`, `modbus_write_registers` and `modbus_write_and_read_registers`, and their verifiers rejected them for the same reason. The three verifications held `modbus_write_bit` and `modbus_write_register` back: both were dispatched 11 s after the last verifier closed, 23 minutes after their callee's negotiation.
- **Cause:** the property is evaluated at the call of the wrapper `send_msg`, one step before the buffer is complete. On TCP, `_modbus_tcp_build_request_basis` leaves the MBAP length bytes `req[4]` and `req[5]` unset. `send_msg` first calls `ctx->backend->send_msg_pre(msg, msg_length)` (`src/modbus.c:174`), and `_modbus_tcp_send_msg_pre` writes both bytes (`src/modbus-tcp.c:170-171`) before anything is transmitted. The target is correct: the generated property demands more than the sink needs.
- **Open pipeline bug:** the goal cannot be proven on the TCP path, and each caller of `send_msg` can raise a false candidate that costs a verifier. Not yet measured: how many of the caller stalls this goal explains on its own. Suggested: let `security_props.py` place an initialization property on the function that actually transmits the buffer, or let the threat model name the bytes a pre-send hook completes. No workaround was applied in run-1.

### Symptom: A Security Unit Whose Instance MetAcsl Decides Statically Is Never Credited (`wp_no_credited_goals`)
- **Seen on:** `tests/test_security_props.py::test_template_variant_acceptance_in_the_image[l6_no_leak_calling_static-satisfied]` (M1 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), 2026-11-10). The program calls `log_line(banner)` with `banner` a global distinct from the secret `key`. The WP report of `show` lists `L6_no_leak_key` in `security_props.properties`, but no goal name starts with `L6_no_leak_key:`; the only meta goal is `L5_sanitized_log_line`.
- **Cause:** MetAcsl runs with `-meta-simpl` by default, which discards instances that are obviously true. `-meta -then-last -print` shows `show` with the L5 assert only; with `-meta-no-simpl` the instance comes back as `assert L6_no_leak_key: meta: &log_line == &log_line ==> \separated(&(banner[0]), &key);`. `run_wp_function.py` (`meta_stage`: `-meta -meta-warn-key unknown-func=inactive -then-last`) then reports no goal of class `l6_no_leak`, and `ledger.py ingest-wp` credits the zero-goal case only for `rte`, `l2_termination` and `l3_frame`. The unit falls through to `wp_no_credited_goals` and stays uncovered although the function satisfies the property. Not unsound: it under-credits. Any `\calling`, `\writing` or `\reading` instance MetAcsl decides syntactically can hit it.
- **Open pipeline bug:** add `-meta-no-simpl` to `meta_stage` in `scripts/run_wp_function.py`, so every instance becomes a goal Qed discharges; or have `ledger.py ingest-wp` credit an L4–L6 unit whose function ran with the property in `security_props.properties`, ended `all_proven` and has no goal of that class. The test case is `xfail(strict=True)` until then.

### Symptom: A Gate That Sets the Auth State Before Its Check Passes Both L4 Properties (`auth_ok = 1; if (pw != 42) return -1;`)
- **Seen on:** `tests/fixtures/security_props/gate/l4_gate_failure.c` built with `-DVIOLATE` (M7 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), 2026-11-10).
- **Cause:** `L4_auth_state_<gate>` exempts the gate from the write check and `L4_auth_required_<gate>` only reads the state at the protected calls, so nothing constrains what the gate writes on its failure path. The natural fix, a MetAcsl `\postcond` on the gate (`\result != success ==> state == \old(state)`), is refused by MetAcsl: `Error during the typing of a HILARE! ... Why: \result meaningless` (checked in the image).
- **Fixed (M7, worktree commit of M7):** auth gates take an optional `success` ([`../../schemas/threat_model.schema.json`](../../schemas/threat_model.schema.json)). [`../../scripts/security_props.py`](../../scripts/security_props.py) generates `L4_auth_state_<gate>_on_failure` (template variant `on_failure` of [`../../templates/metacsl/l4_auth_state.acsl`](../../templates/metacsl/l4_auth_state.acsl)) as an in-code `check` before each `return` of the gate, with the returned expression in place of `\result` and `\at(state, Pre)` for the state on entry; the M6 code-check machinery writes it (`code_checks`). In the image WP proves it on the correct gate and not on the violating one, and E-ACSL reports the violation and goes on. A `return` whose expression the check cannot repeat (a call, an assignment) or a `return;` is skipped and reported in the warnings.

### Symptom: An `L5_sanitized_<sink>` Goal on a String Literal Never Proves (`log_line("admin command")`)
- **Seen on:** the `tests/fixtures/security_props` session library (`session_admin`), and the known limit in [`../guides/security-properties.md`](../guides/security-properties.md): `L5_no_crlf` on a literal argument stays unproven with Alt-Ergo, Z3 and CVC5 at 10 s.
- **Cause:** `L5_no_crlf` quantifies over every index before the terminating NUL; the provers do not unroll that quantifier over the literal's bytes. A correct caller stayed `blocked`.
- **Fixed (M2 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), worktree commit of M2):** the Phase 0 dump records the string literals each direct call passes (`scripts/phase0_dump.ml`, dump schema 4; since Frama-C 32 a literal is a global the argument points to, `Ast_info.is_string_literal`), the model keeps them as `call_sites` (`scripts/phase0_model.py`, feature `call_sites`). `scripts/security_props.py` decides a caller whose every call of a `log`/`terminal` sink passes literals to its text parameters: satisfied when no literal holds CR or LF before its first NUL, else violated. That caller is no instance (no meta goal), the property lists it under `decided`, and `ledger.py seed` records the verdict: `covered` by evidence of phase `static` (`decided_syntactically`) or `blocked` (`decided_violated`), which no WP result overrides. A caller that also passes other text keeps its goal, and the literal calls in it still do not prove (a note on the property says so). A model without call sites (dump before schema 4) decides nothing and `security_props.json` says so in a warning. Option 2 of the plan (restate the predicate over libc's `strlen`) was not needed.

### Symptom: Two Predicates for "No CR or LF in the String": `L5_no_crlf` in the MetAcsl Preamble and the Vocabulary's Names
- **Seen on:** plan step S8 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), MetAcsl half (2026-11-10). The MetAcsl preamble defined a private `L5_no_crlf{L}(char *s)` (an unbounded quantifier guarded by "no NUL before i"), while `templates/acsl/acsl_vocabulary.h` has `no_crlf_or_nul(buf, len)` for buffers and, on the libc track's S8 branch, `no_crlf_string(s)` bounded by `strlen`. A prover saw two names for one notion, and only the vocabulary's can be executed by E-ACSL.
- **Cause:** the meta file `run_wp_function.py` writes is its own translation unit and includes nothing, so the preamble defined what it needed itself.
- **Fixed (MetAcsl half, worktree commit of S8):** [`../../templates/metacsl/preamble.acsl`](../../templates/metacsl/preamble.acsl) defines no name of its own: the meta file includes `__fc_string_axiomatic.h` (for `strlen`; `security_props.meta_file_text` writes the directive, so the templates stay pure ACSL) and the preamble repeats the vocabulary's `no_crlf_string` text word for word, and [`../../templates/metacsl/l5_sanitized.acsl`](../../templates/metacsl/l5_sanitized.acsl) names `no_crlf_string(\called_arg(p))`. Checked in the image: the meta file and a target that includes the vocabulary parse together (Frama-C merges identical definitions), and the property proves on a caller that requires the predicate. `test_preamble_repeats_the_vocabulary_text` fails if the two texts drift apart (it compares with the vocabulary once the libc track's definition is there) or if a template defines a predicate. E-ACSL never runs the MetAcsl properties; it executes `no_crlf_string` through `strlen` where a contract names it. A string literal still does not prove under `no_crlf_string` (the M2 decision from the model stays). `L5_no_crlf` remains only as the name hand-written contract clauses use (`ensures L5_no_crlf: no_crlf_or_nul(out, \result)`), which is a clause name, not a predicate.

### Symptom: Every MetAcsl WP Run Stops on `predicate no_crlf_string is already declared with the same profile`
- **Seen on:** `tests/test_security_props.py::test_wipe_acceptance_in_the_image` and every `test_template_variant_acceptance_in_the_image` case (32 tests), on an analysis image rebuilt from the current templates (`framac-analysis:fc34`, 2026-11-13). The WP report of the function is `status: acsl_syntax_error`, with `[kernel:annot-error] workspace/wp/security_meta_<fn>.c:3: Failure: predicate no_crlf_string is already declared with the same profile. Ignoring global annotation`, and has no `security_props` key.
- **Cause:** a pipeline bug, not a Frama-C change. Since S8 (`733235c`), `templates/acsl/acsl_vocabulary.h` defines `no_crlf_string`, and `fc_compat_types.h`, which `augment_framac_cppflags` force-includes into every Frama-C unit, includes that vocabulary. The meta file also repeats the predicate through the preamble, so its own unit declared it twice. Frama-C merges identical definitions across files but refuses a second one in the same file, on 35.0~~dev and on 34.0~beta alike (a two-line file shows it on both). The tests passed on the old `framac-analysis:latest` only because that image was built before S8: its vocabulary had no `no_crlf_string`. The entry above ("checked in the image: ... Frama-C merges identical definitions") checked two separate files, never the force-included header.
- **Fixed (uncommitted):** [`../../scripts/security_props.py`](../../scripts/security_props.py) `meta_file_text` puts the preamble under `#ifndef ACSL_VOCABULARY_H` (`META_PREAMBLE_GUARD`), so it applies only to a run without the vocabulary; the comment in [`../../templates/metacsl/preamble.acsl`](../../templates/metacsl/preamble.acsl) says so. Test: `test_meta_file_lines_and_function_match` checks the guard; the 32 acceptance tests pass in the image again.

### Symptom: `syslog(LOG_INFO, user)` (a Non-Literal Format String, CWE-134) Passes Every Layer
- **Seen on:** `tests/fixtures/security_props/decided/l5_format.c` built with `-DVIOLATE` (M5 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), 2026-11-10).
- **Cause:** the threat model had no way to say which sink parameter is a format, and L5 only checked CR/LF and initialization.
- **Fixed (M5, worktree commit of M5):** sinks take an optional `format` ([`../../schemas/threat_model.schema.json`](../../schemas/threat_model.schema.json)). [`../../scripts/security_props.py`](../../scripts/security_props.py) generates `L5_sanitized_format_<sink>`, decided from the model's `call_sites` like the M2 literals, with no MetAcsl goal: a caller passing a non-literal format is `violated` (the seed blocks its `l5_sanitized` unit), one passing literals only is `satisfied`; a caller that is a format sink itself is skipped (its callers are checked). Tests: `test_a_format_argument_is_decided_from_the_model`, `test_format_strings_are_decided_from_the_real_model`.
- **Gotcha, not a pipeline defect:** Frama-C's libc declares `syslog(int, const char *, ...)` without parameter names, and the model names such formals `param0`, `param1`, ...: `"format": "format"` is then refused with a warning that lists the names to use (`"format": "param1"`). The same holds for `params` and `length` of such a sink.

### Symptom: An `L6_wiped_*` Goal Stays Unproven Although the Release Function Calls `explicit_bzero` or `memset_s`
- **Cause:** `__fc_libc` declares neither function, so before step M6 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md) the call had no contract (`unsound_proof`) and only a wipe loop with invariants proved. A second cause is WP's Typed model: it reads a `void *` parameter as `char *`, so passing an `unsigned char` or `uint8_t` array is a pointer cast it rejects (`Cast with incompatible pointers types (source: uint8*) (target: sint8*)`), whatever the callee's contract says.
- **Fix (pipeline, step M6):** `fc_compat_types.h` (`__fc_libc` branch) declares `explicit_bzero(void *, size_t)` and `memset_s(void *, size_t, int, size_t)` with postconditions that state each written element, through `char` and through `unsigned char`, plus `\subset` for Eva and `\initialized`. Verified in the analysis image (`tests/test_fc_compat_contracts.py`, `FRAMAC_DOCKER_TESTS=1`): a wipe of a `char` array through either function proves under Typed with `-wp-check-memory-model`; an `unsigned char` or `uint8_t` array proves under `Typed+cast` only; a partial wipe never proves; Eva reads zeros after the call.
- **Still open (WP model limit, not a contract defect):** under Typed, which is the only model whose proofs count, an `unsigned char` secret wiped through these functions stays unproven. Write the wipe as a loop with invariants (the prover brief says so), or use a `char` array. Define `FC_STUBS_NO_WIPE_DECLS` when a target defines its own `explicit_bzero` or `memset_s` and the contracts must not apply to that definition.

### Symptom: `L6_no_leak_<secret>` Is Proven Although a Copy of the Secret Reaches a Sink (`memcpy(line, key, ...); log_line(line);`)
- **Seen on:** `tests/fixtures/security_props/taint/l6_indirect.c` built with `-DVIOLATE` (M3 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), 2026-11-10), and the known limit in [`../guides/security-properties.md`](../guides/security-properties.md).
- **Cause:** the MetAcsl no-leak property is a `\calling` separation check: no sink argument points into the secret. A buffer holding a copy is separated from it, so the property holds and WP proves it. Only Eva's taint domain follows the copy, and the pipeline generated no taint annotation.
- **Fixed, opt-in (M3 of the same plan, worktree commit of M3):** [`../../scripts/security_props.py`](../../scripts/security_props.py) gives each no-leak property a `taint` plan and, with `run --eva-taint` (kept in `security_props.json` for later runs), writes `/*@ taint ...; */` at the secret's sources and `/*@ assert L6_no_leak_<secret>: eva_taint: !\tainted(...); */` before each sink call into the work tree, on the same lines, and sets `eva_taint` in `params.json` for the harness modules holding them. [`../../scripts/ledger.py`](../../scripts/ledger.py) `ingest-eva` files the check statuses under the `l6_no_leak` unit (bookkeeping `eva_taint`; the rows are taken out of the `rte` unit's), Unknown or Invalid blocks it, and `ingest-wp` does not credit it while one is open. In the image the copy leaves the check Unknown and a buffer that never held the key proves it Valid (`test_taint_annotations_in_the_image`). Two notes from the probes: Frama-C's `-report-csv` gives the assertion's predicate without its names, so the placed checks (file, line, property) are recorded under `eva_taint.checks`; and `strlen` in the annotation breaks E-ACSL builds, so a sink without `length` is checked on its first byte.
- **Fixed (branch `templates-stubs-integration`):** the taint assertions are hidden from WP: when a source holds an `eva_taint:` assertion, `run_wp_function.py` passes `-wp-prop=-eva_taint` (`WP_PROP_EXCLUDE`; with `--prop`, `-wp-prop=<prop>,-eva_taint`), and never otherwise. Checked in `framac-analysis:latest`: any `-wp-prop`, even a purely negative one, also drops the kernel-generated Exit- and Termination-conditions (the first version passed it on every run and the M1 acceptance variant `l6_no_leak_calling_static` lost its only two goals: `total_goals: 0`, `unproven_goals_remain`). So an `--eva-taint` WP run does not check those two conditions; `tests/test_tool_sizing.py::test_wp_leaves_out_eva_taint_checks_only_where_there_are_some`. `--eva-taint` stays opt-in until a full pipeline run on a real target has used it. **Open, not handled:** a parameter secret handed to a callee is not followed into it (the checks sit only in the property's calling instances), and a module whose harness is generated after the last `security-props` run gets `eva_taint` only when `seed` runs it again.

### Symptom: `secret <name>: ... has no lvalue a property can name` for a Key Held in a Local Buffer, or a Returned Secret With No Trace in the Report
- **Seen on:** a threat model naming a stack buffer of a key-derivation function (M6 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), 2026-11-10): the schema offered `global`, `parameter`, `field` and `return` only, and a postcondition cannot name a local. A secret of kind `return` gave a warning in `security_props.json` that no report showed.
- **Cause:** the wipe property is a MetAcsl postcondition (`\context(\postcond)`), which sees the function's formals and globals, never its locals.
- **Fixed (M6, worktree commit of M6):** the threat-model schema has secret kind `local` ([`../../schemas/threat_model.schema.json`](../../schemas/threat_model.schema.json)). [`../../scripts/security_props.py`](../../scripts/security_props.py) turns it into an `L6_wiped_<name>` property with a `code` field (template variant `local` in [`../../templates/metacsl/l6_wiped.acsl`](../../templates/metacsl/l6_wiped.acsl)) and writes `/*@ check L6_wiped_<name>: ...; */` into the work tree, on the same line, before each `return` in the local's scope and before its block's closing brace (`security_props.json` `code_checks`). WP proves it with the function; E-ACSL runs it as a non-blocking `check` (checked in the image: the failure is printed, the program goes on, exit 0); `ledger.py ingest-eva` files Eva's status of it as evidence on the `l6_wiped` unit instead of the `rte` one. [`../../scripts/generate_report.py`](../../scripts/generate_report.py) lists the threat-model items that became no property ("Threat-model items without a property"), returned secrets included; kind `return` stays a warning. Tests: `test_local_checks_go_before_each_return_in_scope`, `test_local_wipe_check_in_the_image`. Left as is: a local found by its first use in the body is assumed to be declared there (a global of the same name used earlier in the function would mislead it), and a local secret gets no no-leak property.
