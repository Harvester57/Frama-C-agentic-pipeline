# Security Properties (Layers 4–6) & MetAcsl Issues

Issues encountered in threat-model security property generation (`security_props.py`, `templates/metacsl/`), MetAcsl goal simplification, Layer 4 authentication gates, Layer 5 output sanitization and format strings, and Layer 6 secret wiping and Eva taint tracking. For threat-model Markdown fence parsing, see [`./phase0-build-and-model.md`](./phase0-build-and-model.md). See [`./README.md`](./README.md) for the master index.

### Symptom: `L5_sanitized_send_msg` Is False at the Call Although No Uninitialized Byte Is Ever Sent (`\initialized(&req[0 .. req_length - 1])`)
- **Seen on:** libmodbus run-1 (2026-11-18). `breaker-modbus_mask_write_register` reported the property false at the `send_msg` call with `req_length == 14`, and `verify-modbus_mask_write_register_2a7ed14cd2` closed the candidate `src/modbus.c#modbus_mask_write_register::l5_sanitized::2a7ed14cd2` as `rejected`. The same property raised candidates on `modbus_write_bits`, `modbus_write_registers` and `modbus_write_and_read_registers`, and their verifiers rejected them for the same reason. The three verifications held `modbus_write_bit` and `modbus_write_register` back: both were dispatched 11 s after the last verifier closed, 23 minutes after their callee's negotiation.
- **Cause:** the property is evaluated at the call of the wrapper `send_msg`, one step before the buffer is complete. On TCP, `_modbus_tcp_build_request_basis` leaves the MBAP length bytes `req[4]` and `req[5]` unset. `send_msg` first calls `ctx->backend->send_msg_pre(msg, msg_length)` (`src/modbus.c:174`), and `_modbus_tcp_send_msg_pre` writes both bytes (`src/modbus-tcp.c:170-171`) before anything is transmitted. The target is correct: the generated property demands more than the sink needs. Pipeline bug: [`../../scripts/security_props.py`](../../scripts/security_props.py) put the obligation of every declared sink on its callers, whether the sink transmits or only forwards. Rebuilt as [`../../tests/fixtures/security_props/forward/l5_forwarding.c`](../../tests/fixtures/security_props/forward/l5_forwarding.c): before the fix, WP on the wrapper's caller left `L5_sanitized_send_msg: meta: \initialized(&req[0 .. 12 - 1])` Unknown on the correct program. Not measured: how many of the run-1 caller stalls this goal explains on its own.
- **Fixed (package A of [`../plans/metacsl-exploitation-plan.md`](../plans/metacsl-exploitation-plan.md), commit `14f017e` on `metacsl/a-l5-placement`):** a bytes sink (every kind but `log`, `terminal` and `buffer`) that the target defines and that reaches another declared bytes sink in the Phase 0 model's call graph (direct and indirect edges) is a forwarding sink (`_Gen._forwarding`). Its property has no instance and no MetAcsl text, and names the innermost sinks under `forwarded_to` ([`../../schemas/security_props.schema.json`](../../schemas/security_props.schema.json)); the bytes are checked at the calls of those sinks, so the wrapper's callers get no `l5_sanitized` unit. Regression tests in [`../../tests/test_security_props.py`](../../tests/test_security_props.py): `test_a_forwarding_sink_is_checked_at_the_innermost_sink` and its neighbours, and in the image `test_forwarding_sink_acceptance_in_the_image` (the caller proves with no L5 goal; `L5_sanitized_tcp_send` proves in `send_msg` after the hook, and stays Unknown when `send_msg` skips the hook).
  - **Why it is sound:** bytes leave the target only through the declared sinks. On every path the model finds from the wrapper, the first declared sink is checked at its own call, after whatever the wrapper or its callees completed. An uninitialized byte handed to the wrapper is either written before that call or reported there.
  - **Limits:** (1) the threat model must list every function the bytes leave through: a wrapper that also transmits by itself through an undeclared function on a direct call (`write`) is not seen. (2) The reach is the model's: a pointer call resolved by type that never happens at run time still counts as a path to a sink. (3) Text sinks keep their placement (a wrapper does not sanitize, its callers must). (4) Two sinks that only reach each other keep one property between them.
  - **A backend that is not declared keeps the old placement.** See the next entry: with `_modbus_tcp_send` declared and the RTU backend's send undeclared, `L5_sanitized_send_msg` stays at the callers of `send_msg` and a warning names the function to declare. Not verified on libmodbus itself: the target is not in this repository and no target run was made for this fix.

### Symptom: `output sink send_msg: it forwards to tcp_send, but the call through ... reaches the declared sink(s) tcp_send and also rtu_send, which reach(es) none`
- **Seen on:** `tests/test_security_props.py::test_an_undeclared_backend_keeps_the_wrapper_property_with_a_warning` (package A of [`../plans/metacsl-exploitation-plan.md`](../plans/metacsl-exploitation-plan.md), 2026-11-18): the libmodbus shape with two backends, of which the threat model declares one `send`. The warning is in `security_props.json` (`warnings`), and `REPORT.md` lists it under "Threat-model items without a property" although the wrapper keeps its property.
- **Cause:** not a pipeline defect, a gap in the threat model. One indirect call site on the way from the wrapper has a candidate that reaches a declared sink and another, callable through the same pointer type, that reaches none. Forwarding would stop checking what the second one transmits, so `security_props.py` keeps the wrapper's property at its callers (the placement of the entry above, false when a callee of the wrapper completes the buffer). The Phase 0 type match ignores `const`, so a site typed like the backend's `send` (`const unsigned char *`) also lists its `recv` (`unsigned char *`): a candidate counts only when its parameters have the kinds (`value`, `pointer`, `const_pointer`) of a candidate that reaches a sink, or when the model does not know them (GCC fallback).
- **Fix:** declare the named function, or the function it transmits through, as an output sink (`{"function": "_modbus_rtu_send", "kind": "file", "params": ["req"], "length": "req_length", "description": "RTU backend: writes the frame to the serial line."}`). The wrapper then forwards to both and the warning goes. A candidate that is named but does not transmit (a type match with the same parameter kinds) has no remedy in the threat model today: the wrapper keeps its property. **Open pipeline gap:** the threat model cannot say that a sink forwards (`schemas/threat_model.schema.json` has no field for it).

### Symptom: An `L5_sanitized_<sink>` Goal at a Function-Pointer Call Reads `!((ctx->backend)->send == &tcp_send)` and Never Proves (`[meta] Warning: \called_arg cannot be used with indirect calls`)
- **Seen on:** Step 0 of package A of [`../plans/metacsl-exploitation-plan.md`](../plans/metacsl-exploitation-plan.md) (2026-11-18, `framac-analysis:latest`, Frama-C 34.0~beta), on `tests/fixtures/security_props/forward/l5_forwarding.c`: WP on `send_msg`, which calls the declared sink `tcp_send` through `ctx->backend->send`, left `L5_sanitized_tcp_send: meta: !((ctx->backend)->send == &tcp_send)` Unknown. libmodbus has this shape (`send_msg` calls `_modbus_tcp_send` through the backend table); the run-1 logs were not searched for this goal.
- **Cause:** at an indirect call MetAcsl has no callee to read the formals from, so `\called_arg(req)` does not type. The `\fguard` around the clause turns it into `\false`, and the `\calling` instance becomes `\called == tcp_send ==> \false`. That is never silently true, but it never proves where the pointer may hold the sink. An upstream MetAcsl limitation, met by a pipeline template that had no other form ([`../../templates/metacsl/l5_sanitized.acsl`](../../templates/metacsl/l5_sanitized.acsl), `emit`).
- **Fixed for L5 (package A, commit `14f017e` on `metacsl/a-l5-placement`):** a sink (bytes or text) that the target defines and that the model shows called through a pointer (an `indirect` edge) gets the obligation as its precondition: template variant `entry` (`\targets({sink}), \context(\precond)`) with the clauses `text_formal`, `bytes_formal` and `object_formal` over `\formal(...)`. WP proves the generated `requires` at each call; a pointer call needs `/*@ calls sink; */`. Without that annotation the run reports `indirect call present without '//@ calls'` (`soundness.ok` false), has no goal of the class, and `ledger.py ingest-wp` records `wp_no_credited_goals`: nothing is credited. Tests: `test_a_sink_called_through_a_pointer_is_checked_as_its_precondition`, the image variants `l5_sanitized_entry_text` and `l5_sanitized_entry_object`, and the `no_calls` case of `test_forwarding_sink_acceptance_in_the_image`. A sink the target only declares, or one called directly only, keeps the `\calling` assertion.
- **Open pipeline gap:** `L6_no_leak_<secret>` has the same clause form (`call_clause` of [`../../templates/metacsl/l6_no_leak.acsl`](../../templates/metacsl/l6_no_leak.acsl)). Checked in the image on the same fixture: `assert L6_no_leak_key: meta: !((ctx->backend)->send == &tcp_send);`. The unit of a function that calls a declared sink through a pointer stays unproven (not unsound). Suggested: the same `\precond` form, `\separated(\formal(p), region)`, for a sink the target defines and calls through a pointer.

### Symptom: A Security Unit Whose Instance MetAcsl Decides Statically Is Never Credited (`wp_no_credited_goals`)
- **Seen on:** `tests/test_security_props.py::test_template_variant_acceptance_in_the_image[l6_no_leak_calling_static-satisfied]` (M1 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), 2026-11-10). The program calls `log_line(banner)` with `banner` a global distinct from the secret `key`. The WP report of `show` lists `L6_no_leak_key` in `security_props.properties`, but no goal name starts with `L6_no_leak_key:`; the only meta goal is `L5_sanitized_log_line`.
- **Cause:** MetAcsl runs with `-meta-simpl` by default, which discards instances that are obviously true. `-meta -then-last -print` shows `show` with the L5 assert only; with `-meta-no-simpl` the instance comes back as `assert L6_no_leak_key: meta: &log_line == &log_line ==> \separated(&(banner[0]), &key);`. `run_wp_function.py` (`meta_stage`: `-meta -meta-warn-key unknown-func=inactive -then-last`) then reports no goal of class `l6_no_leak`, and `ledger.py ingest-wp` credits the zero-goal case only for `rte`, `l2_termination` and `l3_frame`. The unit falls through to `wp_no_credited_goals` and stays uncovered although the function satisfies the property. Not unsound: it under-credits. Any `\calling`, `\writing` or `\reading` instance MetAcsl decides syntactically can hit it.
- **Fixed (M2 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md), commit `1848426`):** the second option was taken. `ledger.py ingest-wp` (`_meta_decided_statically` in [`../../scripts/ledger.py`](../../scripts/ledger.py)) credits an L4–L6 unit, with evidence `wp_meta_simplified`, when the WP run ended `all_proven` with no goal of the unit's class and its report lists every property the unit names under `security_props.properties` without an error. `run_wp_function.py` still runs MetAcsl with the default `-meta-simpl`. Tests: `test_an_instance_metacsl_decides_statically_is_credited`, and the image case `test_template_variant_acceptance_in_the_image[l6_no_leak_calling_static-satisfied]`, which is no longer `xfail` (`OPEN_DEFECTS` in [`../../tests/test_security_props.py`](../../tests/test_security_props.py) is empty).

### Symptom: A Call Placed in an Initializer (`int n = send(fd, buf, 8);`) Gets No `\calling`, `\writing` or `\strong_invariant` Instance, and Its Unit Can Still Be Credited
- **Seen on:** package R of [`../plans/metacsl-exploitation-plan.md`](../plans/metacsl-exploitation-plan.md) (2026-11-18, `framac-analysis:latest`, MetAcsl 0.12~beta), on a probe file holding each call twice, as a statement (`n = send(fd, buf, 8);`) and as an initializer (`int n = send(fd, buf, 8);`), with the L4, L5 and L6 templates filled in. `frama-c local_init.c -meta -then-last -print` puts `L5_sanitized_send`, `L6_no_leak_key` and `L4_auth_state_login` assertions before the statement calls and none before the initializer calls. The `\reading` property does get its instance on `int x = key[0];`. The parent re-ran the probe and saw the same output.
- **Cause:** an upstream MetAcsl limitation. A call in an initializer is a `Local_init (_, ConsInit ...)` instruction in the AST, which the `\calling` visitor, the callee-assigns part of the `\writing` visitor and the `\strong_invariant` visitor do not visit. No warning is printed.
- **The unsound credit, shown end to end (Step 0 of package E, 2026-11-18, before any fix):** the probe is now [`../../tests/fixtures/security_props/initializer/local_init.c`](../../tests/fixtures/security_props/initializer/local_init.c) with the hand-written [`local_init_meta.c`](../../tests/fixtures/security_props/initializer/local_init_meta.c). On the `-DVIOLATE` build, `g_init` (`int n = net_send(fd, key, 16);`, the secret handed to the sink) went through the model, `security_props.py`, `run_wp_function.py` and `ledger.py ingest-wp`: WP status `all_proven`, properties `L5_sanitized_net_send` and `L6_no_leak_key` loaded, no goal named after either, unit `prog.c#g_init::l6_no_leak` `covered` with evidence `wp_meta_simplified`. The same call as a statement (`g_assign`) left `L6_no_leak_key: meta: \separated(&(key[0]), &key)` Unknown and the unit `blocked`. With `-meta-no-simpl` the `\strong_invariant` assertion does appear after the initializer, so for that context it is MetAcsl's default simplification that drops it.
- **Fixed in the generator (D1 half of package E, commit `d7405e8` on `metacsl/d1-kinds`):** [`../../scripts/phase0_dump.ml`](../../scripts/phase0_dump.ml) marks each direct call with `initializer` (dump schema 5). For every property whose context is skipped there (`\calling`: L5 emit, L6 no-leak, call rules; `\writing` from a declared callee's `assigns`: auth state, asset writers; `\strong_invariant`), [`../../scripts/security_props.py`](../../scripts/security_props.py) lists the site under the property's `init_checks`, and `run` writes `/*@ check <property>: ...; */` on the line of the declaration, with the call's arguments in place of the parameters (`code_checks`, each with an `index` among the checks of its line). A site no check can be written for (the call is not the whole initializer of a one-declarator declaration, an argument holds a call or an assignment, a macro hides the call, the callee's parameter types or `assigns` are unknown, a monotonic transition) moves to the property's `unchecked` with the reason. Tests in [`../../tests/test_security_props.py`](../../tests/test_security_props.py): `test_an_initializer_call_gets_an_in_code_check_per_skipped_context` and its neighbours; in the image, `test_metacsl_skips_calls_in_initializers_in_the_image` (a watch on MetAcsl itself) and `test_initializer_checks_acceptance_in_the_image` (`f_init`, `g_init` and `h_init` each carry the checks as WP goals, Valid on the correct program; on `-DVIOLATE` the check of the broken property is Unknown).
- **Fixed (the model dropped the flag; package G, commit `6f7f100` on `metacsl/g-wiring`):** `phase0_model.py::_call_sites` built each call site as `{callee, line, literals}`, so the dump's `initializer` never reached `phase0_model.json`, no in-code check was written in a real run, and the generator warned `the model's call sites do not say which calls are initializers`. [`../../scripts/phase0_model.py`](../../scripts/phase0_model.py) now carries `bool(c["initializer"])` when the dump's call has the key; the copy of `scripts/` the image tests used (`PASSTHROUGH_FROM`/`PASSTHROUGH_TO`) is gone and they mount `scripts/` itself. Tests: `test_the_model_carries_the_initializer_flag_of_a_call_site` in [`../../tests/test_metacsl_wiring.py`](../../tests/test_metacsl_wiring.py), and the image tests of `test_security_props.py` through the real model.
- **What a placed check changes for the credit:** the violating `g_init` now has an unproven `check` goal, its run is no longer `all_proven`, and `ledger.py ingest-wp` does not cover `prog.c#g_init::l6_no_leak`; on the correct program the check proves and the unit is covered (`test_a_leak_through_an_initializer_call_is_not_credited_in_the_image`).
- **Fixed (the ledger credited where no check was placed; package G, commit `6f7f100`):** `ledger.py` read none of `init_checks`, `unchecked` and `code_checks[].index`, so `ingest-wp` gave the `wp_meta_simplified` credit to a unit whose function was listed under a property's `unchecked`. [`../../scripts/ledger.py`](../../scripts/ledger.py) now reads them from `security_props.json` (`_meta_facts`): a unit whose property lists its function under `unchecked`, whose obligation entry carries `unchecked`, or whose `init_checks` site has no placed check is blocked by `ingest-wp` with evidence `wp_meta_unchecked`, whatever the run proved, and `ingest-eva` does not cover it (`_eva_meta_cover_barred`). A function with placed checks whose run reports none of them no longer gets the no-goal credit (`wp_meta_check_not_reported`). Tests in [`../../tests/test_metacsl_wiring.py`](../../tests/test_metacsl_wiring.py): `test_a_unit_with_an_unchecked_initializer_site_is_never_credited`, `test_a_function_left_out_of_the_targets_is_never_credited`, `test_an_initializer_check_that_was_not_written_bars_the_credit`, `test_a_written_check_the_run_did_not_report_bars_the_no_goal_credit`, `test_eva_does_not_cover_a_unit_with_an_unchecked_site`; end to end in the image, `test_initializer_calls_end_to_end_in_the_image[satisfied|violated]` (the real model, generator, `run_wp_function.py` and `ingest-wp`: every unit of `f_init`, `g_init` and `h_init` `covered` with `wp_proven` on the correct program, the broken property's unit `blocked` on `-DVIOLATE`).
- **Fixed (a model without flags; package H of [`../plans/metacsl-exploitation-plan.md`](../plans/metacsl-exploitation-plan.md), branch `metacsl/h-report-and-credit`):** a model built from a dump older than schema 5 has no `initializer` key; the generator warned and wrote no check, but `security_props.json` held nothing the ledger could read, and the `wp_meta_simplified` credit of a function that calls a sink in an initializer was still given. [`../../scripts/security_props.py`](../../scripts/security_props.py) now writes `initializer_flags` (`known`, and when false the `properties` whose context is `\calling`, `\writing` or `\strong_invariant`; a model with some sites unflagged, or with no `call_sites`, is unknown). `_meta_initializers_unknown` in [`../../scripts/ledger.py`](../../scripts/ledger.py) refuses those units the no-goal credit with evidence `wp_meta_initializers_unknown`. A document without the field is refused for every MetAcsl unit, and re-running `security_props.py run` settles it. `REPORT.md` says `MetAcsl initializer calls: NOT CHECKED` at the top. Tests in [`../../tests/test_metacsl_report_and_credit.py`](../../tests/test_metacsl_report_and_credit.py), red before the fix.
- **Limit (a proven goal or an Eva cover):** the refusal covers the no-goal credit only. A function with a proven statement-call goal of the class, or an Eva cover, is still credited under unknown flags although a call in one of its initializers may be unchecked. Rebuilding the model closes it: the in-code checks are then written.

### Symptom: MetAcsl Stops With `Unexpected error (File "meta_annotate.ml", line 675, characters 19-25: Assertion failed)`
- **Seen on:** package R, same date and image, with a `\writing` property over a function that calls a declared function whose contract reads `assigns \union(*a, *b);` or `assigns {*a, *b};`.
- **Cause:** an upstream MetAcsl defect: `writing_visitor#external_assigns` asserts that each `assigns` term of a callee is a single lvalue.
- **Fixed in the generator (package D1, commit `d7405e8` on `metacsl/d1-kinds`):** for every `\writing` property (`L4_auth_state_*`, `L3_writers_*`, monotonic `L4_invariant_*`), [`../../scripts/security_props.py`](../../scripts/security_props.py) reads the `assigns` of each declared function its targets call, textually, at the declaration the model records (`external_decls[].decl`; `contract_assigns`). The callers of a callee whose `assigns` holds `\union(...)` or braces are left out of the property's `\targets`, listed under its `unchecked` (and on their obligation entry), and a warning names the callees; the property lists them under `declared_callees.set_assigns`. Tests: `test_a_set_valued_assigns_takes_its_callers_out_of_a_writing_property`, and in the image `test_a_set_valued_assigns_does_not_stop_the_other_proofs_in_the_image` on [`../../tests/fixtures/security_props/callees/set_assigns.c`](../../tests/fixtures/security_props/callees/set_assigns.c): with the caller left out, the WP run of another instance (`store`) proves its `L4_auth_state_login` goal and ends `all_proven`; with the same properties generated without the tree (contract unknown, caller left in) the run fails with MetAcsl's assertion. Not filed upstream.
- **Limits:** (1) the callers left out are not checked by anything: rewrite the contract with one `assigns` term per location and re-run `security_props.py run`. (2) The contract is read where the model says the function is first declared. A contract on a later declaration, or one a Phase 3 prover writes after the properties were generated, is not seen: a set-valued `assigns` added then still stops the WP runs of the callers. **Fixed (package G, commit `6f7f100`):** `run_wp_function.py` recognises the failure (`metacsl_set_assigns_failure`) and ends the run `analysis_error` with reason `metacsl_set_assigns`, a `metacsl_failure` record (`message`, `cause`, `callees`) and a hint that says not to re-run. MetAcsl's log names no callee (`Current location was: <generated by Frama-C kernel>`), so the runner reads the contracts of the run's sources and their quoted includes, one level deep, and names the functions whose `assigns` holds `\union`, `\inter` or `{`; with none found, the cause is still stated. Before the fix the run landed as `analysis_error`, reason `crashed`, through the no-CSV branch. Tests: `test_the_set_valued_assigns_failure_is_recognised_with_the_callee`, `test_the_failure_without_a_readable_contract_still_names_the_cause` and, in the image, `test_the_set_valued_assigns_failure_is_named_in_the_image`. (3) A declaration the generator cannot open (outside the work tree, the model's tree and Frama-C's share directory) is `declared_callees.unknown`: nothing is excluded.

### Symptom: A Write Made by a Callee Without a Contract Gives No `\writing` Instance and No Warning
- **Seen on:** package R, same date and image.
- **Cause:** for a call, the `\writing` context takes the written locations from the callee's `assigns`. A declared callee with no contract contributes nothing, silently.
- **Reported by the generator (package D1, commit `d7405e8` on `metacsl/d1-kinds`):** each `\writing` property lists the declared functions without `assigns` that its targets call, with their callers, under `declared_callees.no_assigns`, and a warning names them (`... have no `assigns` at their declaration: MetAcsl generates nothing for what they write`). A caller of a declared callee that does assign something is now an instance of the property (it was not for `L4_auth_state_*`: only pointer writers and direct writers were). The gap itself stays: nothing checks what such a callee writes until it has a contract (a stub in `workspace/stubs/`, then re-run `security_props.py run`).

- **Fixed (the report; package H, branch `metacsl/h-report-and-credit`):** [`../../scripts/generate_report.py`](../../scripts/generate_report.py) lists each property's `unchecked` sites (`Where a property does not check its function`) and its `declared_callees` with their callers (`Declared functions the write-checking properties call`). A declared-callee warning no longer lands under `Threat-model items without a property`: the property exists. Tests: `test_a_declared_callee_warning_is_not_an_item_without_a_property` and its neighbours in [`../../tests/test_metacsl_report_and_credit.py`](../../tests/test_metacsl_report_and_credit.py).

### Symptom: `In ACSL, there is no implicit conversion between a C array and a pointer` on a Generated `check` at an Initializer Call, and the Function's WP Run Ends `acsl_syntax_error`
- **Seen on:** `test_initializer_checks_acceptance_in_the_image` during package E (2026-11-18, `framac-analysis:latest`), on `f_init` of the initializer fixture: `char buf[8]; ... int n = net_send(fd, buf, 8);` with the first form of the generated check, `/*@ check L5_sanitized_net_send: \initialized((buf) + (0 .. (8) - 1)); */`. `[kernel:annot-error] /target/prog.c:62: Failure: In ACSL, there is no implicit conversion between a C array and a pointer.` The run had no goal at all.
- **Cause:** a pipeline bug in the first draft of the generator, never committed. An in-code check repeats the text of the call's argument, and C converts an array argument to a pointer where ACSL does not. One annotation that does not type stops the whole WP run of the function, which is worse than the missing instance the check stands in for.
- **Fixed (commit `d7405e8`):** `_Model.arg_refs` writes a pointer parameter's argument as `((T)${argN})`, with `T` the parameter's type from the model's `signature` (`char const *`, `int *`; a `void *` parameter is cast to `char *`, a function-pointer parameter takes no cast). Frama-C normalises `(char const *)(buf)` to `&buf[0]`. When the model has no type for a pointer parameter, the site is `unchecked` instead. Test: the cast texts in `test_an_initializer_call_gets_an_in_code_check_per_skipped_context` and the image acceptance test.
- **Two more cases guarded the same way (third commit of package D1, not seen failing):** a check that names a global the function's file does not define (the secret of a no-leak property kept in another file, the auth state, a global of an invariant or call rule) is not written, because the generator cannot tell whether the file declares it; and no check is written for a text sink, because `no_crlf_string` is declared in the meta file's preamble and not known to be declared in the caller's file. Both sites go to `unchecked` with the reason (`test_an_initializer_check_that_might_not_type_is_not_written`). **Open pipeline gap:** a global declared `extern` in a header the file includes would type; the model does not record declarations, so such a site is left unchecked although a check could be written.

### Symptom: An `L6_wiped_*` Goal Stays Unproven Although the Release Function Calls `explicit_bzero` or `memset_s`
