# Frama-C Kernel Parsing, Preprocessing & Stubs

Issues encountered in Frama-C C/ACSL parsing, `__fc_libc` gaps, preprocessor wrappers (`fc_cpp_wrapper.py`), shipped and overlay header stubs (`templates/fc_stubs/`, `stub_check.py`), and ACSL string vocabulary (`templates/acsl/acsl_vocabulary.h`). See [`./README.md`](./README.md) for the master index.

---

### Symptom: `[kernel] user error: syntax error` on GCC/Clang Intrinsics or System Headers (`_Float128`, etc.)
- **Cause:** The target C file or its `-I` flags pulled in host `/usr/include` headers containing glibc/compiler-specific extensions (`_Float128`, `__builtin_va_arg_pack`, inline assembly `__asm__`, or SIMD intrinsics) instead of Frama-C's standard library (`__fc_libc`).
- **Fix:**
  1. Never pass `-I/usr/include` or `-I/usr/local/include` in harness flags. Frama-C must use its portable `__fc_libc` headers: the target's own system headers reach it from the snapshot through `-idirafter`, searched after Frama-C's libc.
  2. If the target requires third-party system headers (e.g., `<bsd/string.h>`, `<openssl/evp.h>`), add the `-dev` package to the build recipe and rerun the build capture (`--build-image --target-packages "<pkg>"`, `-BuildImage -TargetPackages` in PowerShell). The capture copies the headers and libraries to the run's snapshot (`workspace/snapshot/`), and the analysis image reads them from there (`-idirafter`, after Frama-C's libc). The analysis image itself never gets target packages. Check `snapshot.headers` in `workspace/reports/build_capture.json`.
  3. Ensure `-machdep gcc_x86_64` (already the default in `run_eva_slice.py`, `run_wp_function.py`, and `run_eacsl_fuzz.py`, which every Make recipe calls) is active so GNU C extensions supported by Frama-C are enabled.
  4. Guard hardware inline assembly or unsupported compiler intrinsics with `#ifndef __FRAMAC__ ... #else ... #endif` in the `workspace/work/` shadow tree.

### Symptom: `[kernel:annot-error] unbound logic variable alse` or `orall`
- **Cause:** An ACSL annotation containing `\false`, `\forall`, `\at`, or `\base_addr` was written through an unescaped Python or shell string, turning `\f` into ASCII `0x0c` (form-feed), `\a` into `0x07`, or `\b` into `0x08`.
- **Fix:** Always use raw Python strings (`r"..."`) or file-editing tools when writing ACSL annotations. `acsl_ast.py` (`check-acsl-only`) automatically flags control characters (`\x07`, `\x08`, `\x0c`) inside ACSL comments.

### Symptom: `static assertion failed: "fc_compat_types.h assumes an LP64 machdep (x86_64): run Frama-C with -machdep x86_64"`
- **Cause:** the run used a machdep that is not LP64 (`-machdep x86_32`, `x86_16`, `ppc_32`, a custom one). `templates/fc_stubs/fc_compat_types.h` hard-codes x86_64 facts: the generic ioctl encoding, the x86_64 numbers of the typed `syscall` rewrites (`scripts/fc_cpp_wrapper.py`) and the `long` literals of the `abs`/`labs` contracts. Before step S9 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md) such a run parsed and gave results computed on the wrong sizes.
- **Fix (pipeline, step S9):** the header starts with `_Static_assert(sizeof(long) == 8 && sizeof(void *) == 8, ...)`, so another machdep stops at parse time with the message above. Use the pipeline's default `-machdep gcc_x86_64` (or `x86_64`). Verified in the analysis image: `x86_64` parses, `x86_32` stops (`tests/test_fc_compat_contracts.py`, `FRAMAC_DOCKER_TESTS=1`).
- **Open:** a 32-bit target needs its own ioctl and syscall tables before the assertion can be relaxed.

### Symptom: `fatal error: elf.h: No such file or directory` or `linux/audit.h: No such file or directory` During Frama-C Model Parse
- **Cause (pipeline bug, fixed):** Frama-C parses with `-nostdinc`, so GCC does not search the system include directories (`/usr/include`, `/usr/include/x86_64-linux-gnu`). `build_capture.py` excludes libc and linux headers from the snapshot because they are present in the analysis container image. However, `augment_framac_cppflags` did not append the container's system include directories via `-idirafter`, making host system headers that `__fc_libc` does not define unreachable. Found on `libseccomp` run-2.
- **Fix:** `scripts/framac_common.py` (`augment_framac_cppflags`) appends `-idirafter /usr/include/x86_64-linux-gnu` and `-idirafter /usr/include` if they exist on the filesystem and are not already present (commit `7e15154`). Verified on the analysis image: `<elf.h>`, `<linux/audit.h>` and `<linux/seccomp.h>` parse after Frama-C's libc, and without the two options `elf.h` is not found. (Frama-C's cpp runs with `-undef`, so `<linux/types.h>` skips its `__int128` typedefs.)
- **Follow-up (pipeline bug, fixed by O7 of [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md), branch `ot/o7-system-headers`, commit `9da5f02`):** two defects remained after `7e15154`. First, the headers came from the **analysis** image, not from the build image the target was built in, so `linux-libc-dev` versions could differ. Second, the "already present" test was a substring test, so a flag such as `-idirafter /usr/include/foo` in a unit's flags suppressed `-idirafter /usr/include`. The fix has three parts:
  - **The export:** `build_capture.build_snapshot` copies the libc headers the dependency lists name that Frama-C's libc lacks (`framac_libc_gaps`: all of `linux-libc-dev`, plus `/usr/include/elf.h`) to `<snapshot>/libc/<path>`. The manifest gets a `libc` key, and the report gets `snapshot.framac_libc_gaps`.
  - **The include order:** `target_env.with_include_flags(..., nostdinc=True)` now owns it, and `augment_framac_cppflags` only calls it. The order is the snapshot's target headers, then `<snapshot>/libc/usr/include/x86_64-linux-gnu` and `<snapshot>/libc/usr/include`, then the image's own directories last.
  - **The match:** directories are matched as whole `-idirafter DIR` (or `-idirafterDIR`) tokens.
- **Symlinked `asm/` on Debian trixie:** found while verifying O7. The build image's `/usr/include/x86_64-linux-gnu/asm/*.h` are symlinks to `/usr/lib/linux/uapi/x86/asm/*.h`. The capture's `cc -M` names the real path, because gcc canonicalizes system header paths by default (`-fcanonical-system-headers`; with `-fno-canonical-system-headers` it prints `/usr/include/x86_64-linux-gnu/asm/types.h`). No `-idirafter` reaches the real path. `system_dir_links` maps each such header back to the path an `#include` finds; the report keeps the real path as `source`. Without this mapping, `asm/types.h` still came from the analysis image.
- **Verified:** `tests/test_o7_system_headers.py` (fixtures) and `tests/test_o7_images.py` (`FRAMAC_DOCKER_TESTS=1`). The Docker test captures `tests/fixtures/o7_libc_gaps` in `framac-build:latest`, then parses it with Frama-C in `framac-analysis:latest`. The parse's dependency file shows `elf.h`, `linux/*`, `asm-generic/*` and `asm/*` all read from `<snapshot>/libc`, and none from the image.
- **Fixed with the merge (2026-11-17):** [`../../scripts/stub_gen.py`](../../scripts/stub_gen.py) mapped only `snapshot/root/...` back to a system path (`_SNAPSHOT_ROOT_RE`), so a function declared in `snapshot/libc/...` kept its snapshot path as the header it is stubbed for. `system_path` now maps both subtrees; test `test_system_path_maps_both_snapshot_subtrees_back` in [`../../tests/test_stub_gen.py`](../../tests/test_stub_gen.py).
- **Still open (by design, not a pipeline defect):** the image's `/usr/include` directories stay last, after the export. A capture made before O7 has no `libc/`, so it keeps the old flags. A libc header a Frama-C parse reaches but the build's `cc -M` never named (Frama-C's libc and `-undef` can take other `#if` branches) still comes from the analysis image. Not checked on a real target run.
- **Caveat (by design):** functions declared only by these glibc headers have no ACSL contract: Eva lists them under `repair_hints`, WP marks them `unsound_proof`.

### Symptom: A String Contract Fails With an E-ACSL RTE `\valid_read(s + i)` Inside the Predicate, or `valid_read_nstring(s, n)` Rejects a Full n-Byte Buffer Without a NUL
- **Seen on:** a scratch test (`len(raw)` on `char raw[4] = {'a','b','c','d'}`, and `strnlen(raw, 4)` under `requires valid_read_nstring(raw, 4)`) in `framac-analysis:latest`, 2026-11-10, while unifying the string vocabulary (plan step S8). Before S8 three files spelled the same notions differently: `fc_compat_types.h` defined bounded E-ACSL versions of `valid_read_string`, `valid_string`, `valid_read_nstring` and a `valid_nstring` that `__fc_libc` does not have; `acsl_vocabulary.h` defined `valid_c_string` and `c_strlen`; the briefs and the knowledge base also named `\strlen`, which does not exist in Frama-C.
- **Cause A (wrong semantics, fixed):** the old E-ACSL `valid_read_nstring(s, n)` required a NUL within `n` bytes. `__fc_libc` (what Eva and WP read) accepts `n` readable, initialized bytes as well, which is what `strnlen` and `strncpy` need, so the guardrail rejected inputs the proof accepted.
- **Cause B (E-ACSL limit, not fixed):** E-ACSL checks the read `s[i]` inside a predicate body before the `\valid_read` guard on the left of `&&`, so `valid_read_string(s)` on a buffer that is not a string aborts with the RTE inside the predicate (`fc_compat_types.h`) instead of failing the precondition. The run still fails on the bad input; only the message names the predicate's line. A string longer than 65536 bytes also fails the executable `valid_read_string` / `valid_string`.
- **Fix (pipeline, step S8, fixed):** one name per notion, `__fc_libc`'s own: `valid_read_string`, `valid_string`, `valid_read_nstring`, `valid_string_or_null`, `strlen` (logic function) and the new `no_crlf_string`. `templates/acsl/acsl_vocabulary.h` lists them with whether E-ACSL executes each (all do), includes `__fc_string_axiomatic.h` outside E-ACSL builds, and keeps `valid_c_string` / `c_strlen` only as aliases. `templates/fc_stubs/fc_compat_types.h` gives E-ACSL builds executable definitions of the same names, with libc's `valid_read_nstring` semantics, and drops `valid_nstring`. The prover and header-architect briefs and the knowledge-base query (`scripts/spec_kb.py`) name only the canonical names; `scripts/acsl_ast.py` treats `valid_read_string` like `valid_c_string` in the trust-boundary check. Checked in the image: the E-ACSL build runs every name (including the recursive `strlen`) and fails the non-string and CR/LF calls, WP proves the scratch contracts (18/18), and Eva marks both bad calls Invalid.

### Symptom: Which libc or Linux Functions Do the Targets Call Without a Contract? (`repair_hints`, `unsound_proof` on External Functions)
- **Cause:** Eva and WP parse with Frama-C's libc (`__fc_libc`). A function it does not declare, or declares without a contract, gets a default frame: Eva lists it in `repair_hints`, WP reports `unsound_proof`, and a buffer the call fills keeps the caller's value. Until step S7 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md) nothing listed these functions across targets; the plan's list (`getrandom`, `explicit_bzero`, `reallocarray`, `memrchr`, `accept4`, `pipe2`) was a guess.
- **Fix (pipeline, step S7):** `scripts/libc_gap_report.py <runs-root or run dirs> [--json out.json]`, run in the analysis image. For every external name of the newest Phase 0 model of each target it prints one status: `stub` or `libc` (a contract with `assigns`), `variadic` (`printf` family: the Variadic plugin writes the contract per call), `no_contract`, `undeclared_host` (declared only by a header of the image, `declared_in` names it), `undeclared_other` (a library absent from the image, or code outside the model's units) or `internal`. Gaps (`no_contract`, `undeclared_host`) come first, most-called first. The header scan is textual and ignores `#if`, so a declaration in a branch the parse never takes still counts. Tested on fixtures (`tests/test_libc_gap_report.py`).

### Symptom: Frama-C Cannot Parse glibc `<sys/epoll.h>` / `<sys/inotify.h>`; the Library Goes to the GCC Fallback
- **Seen on:** c-ares `run-1` (2026-11-16, [`../runs/2026-11-16-c-ares-run1-supervision.md`](../runs/2026-11-16-c-ares-run1-supervision.md)). `phase0_model.py run` put `build/lib/libcares.a` and `libcares.so` on `gcc_fallback`, which blocks Eva and WP for the whole library: `[kernel] /usr/include/x86_64-linux-gnu/sys/inotify.h:34: User Error: syntax error` (`char name __flexarr;`). With that fixed, the parse stopped at `sys/epoll.h:139` (`__attr_access ((__write_only__, 2, 3)) __nonnull ((2));`), then at `sys/epoll.h:150` (`__sigset_t` undefined), then at `bits/types/struct_timespec.h:11: User Error: redefinition of 'timespec' in the same scope`.
- **Cause:** Frama-C 34.0~beta's libc has no `<sys/epoll.h>` or `<sys/inotify.h>`, so they resolve to glibc's through the `-idirafter /usr/include/x86_64-linux-gnu` that `augment_framac_cppflags` appends. glibc's headers expect glibc's `<sys/cdefs.h>`, which Frama-C's libc never includes. Frama-C's `features.h` defines `__THROW`, `__nonnull` and `__BEGIN_DECLS`, but not `__attr_access` or `__flexarr`. Frama-C's `__fc_define_sigset_t.h` sets `__sigset_t_defined`, the guard of glibc's `bits/types/sigset_t.h`, so `__sigset_t` is never defined. glibc guards its `struct timespec` with `_STRUCT_TIMESPEC`, Frama-C with `__FC_DEFINE_TIMESPEC_H`. Any Linux target with an epoll or inotify event loop is affected.
- **Run workaround (run-1 only, not in the pipeline):** the run's agent wrote `workspace/stubs/sys/epoll.h` and `sys/inotify.h`. They include glibc's `<sys/cdefs.h>` and `<bits/types/__sigset_t.h>`, set `_STRUCT_TIMESPEC`, then `#include_next`. They parse, with side effects:
  - glibc's cdefs redefines `__THROW` and others for every later libc header (cpp "redefined" warnings in Frama-C's `time.h`, `__attribute__((__nothrow__))` in the model's prototypes).
  - glibc's `__sigset_t` struct turns `epoll_pwait(..., &mask)` with a `<signal.h>` mask into an `incompatible-types-call` warning.
  - Because they contain `#include_next`, `stub_gen.py write_overlay` appends its draft blocks after their include guard.

  Delete them once the fix below is merged.

  - They never included glibc's `<sys/cdefs.h>`.
  - E-ACSL got glibc's header unchanged.
  - They declared nothing, so `stub_gen.py` classified `epoll_*` and `inotify_*` as `host_header`.

### Symptom: A Stub Contract the Real Library Breaks, or a Stub Type That Differs From the Real Header, Goes Unnoticed
- **Cause:** nothing checked a stub against what it stands for. An overlay contract (`workspace/stubs/<name>`) or a shipped stub (`templates/fc_stubs/`) is an assumption every caller's proof rests on: a prototype that no longer matches the library, a `requires` too weak to catch a short buffer, or an `ensures` the library does not keep was found only by luck. `netinet/ip_icmp.h` declared `icmp_ip` as `uint8_t[20]` where glibc has a `struct ip`. - **Pipeline bug (fixed, S3 of [`../plans/templates-and-stubs-improvement-plan.md`](../plans/templates-and-stubs-improvement-plan.md)):** new `scripts/stub_check.py` and Make target `stub-check` (after `stubs`, before `seed`, `--class replay` since it runs library code). Per overlay header it writes `workspace/reports/stub_check.json`: `abi` (the header compiled with its drafts after the real one), `eva` (a generated smoke caller per function, a valid call and a call one element short: `too_weak` or `valid_call_alarm`, warnings only), and `dynamic` (E-ACSL build of a generated driver linked with the libraries the calling modules link, one sandboxed process per function, `--trials` calls with varied lengths: a failed `ensures` is `violated`). A failed ABI check or a violated contract lists the calling modules, with their lexer and sub-modules, under `blocked_modules`, and `phase0_gates.check` refuses them (`stub-check failed for <header> (...)`) until a stub-check of the fixed header passes. `ledger.py record-stub-contracts` adds the status found for the same header digest to each `stub_contract` assumption. `stub_check.py shipped` runs the ABI check on `templates/fc_stubs` (prototypes, plus a layout probe of each struct: offset, size and GCC type class of every member and member macro, against the real header); it reports the `icmp_ip` divergence, which S4 repairs. Verified in `framac-analysis:latest` on a synthetic library (`tests/test_stub_check.py`, `tests/fixtures/stub_check/`): the right contracts pass all three checks, a wrong `ensures` comes out `violated` with the value the library returned, and the gate blocks the module and its lexer module. Not yet run on a benchmark target.
- **Gotcha met on the way (not a pipeline defect):** `e-acsl-gcc` re-splits every option value on spaces and matches each word against its own options (`for i in $@` in the script), so a link value `-l '-lfoo -L /dir'` makes the lone `-L` eat the input file and the build fails with `e-acsl-gcc: fatal error: no input files`. `eacsl_toolchain.normalize_passthrough` joins such pairs (`-L/dir`); `stub_check.build_driver` now uses it, as `run_eacsl_fuzz.py` does.
- **Open pipeline bug:** module fuzzing never checks stub contracts. `run_eacsl_fuzz.compile_eacsl_binary` restricts `-e-acsl-functions` and `-rte-select` to the functions defined in the slice, and E-ACSL then leaves out the contracts of declared-only functions at their call sites; both options also refuse a function without a body (`-rte-select: no function 'ml_hash'`), so the stubbed functions cannot simply be added to the list. Stub-check builds its own driver without a selection for that reason. A fuzz campaign therefore cannot find a caller that breaks a stub's `requires`, nor a library that breaks its `ensures`.
- **Limits:** generic arguments only: every pointer gets a 64-byte initialized buffer, every other value is zero. A function whose arguments must be a real object (an opened handle, a parsed context) gets an `inconclusive` or `driver_rejected` dynamic check, never a pass, and a variadic or function-pointer prototype is `not_callable`. The dynamic check needs the library in the snapshot (`no_library` otherwise). A header that changes after a failure stays blocking until stub-check runs again on it.

### Symptom: A Negative Index Passes `if (i < N)` With `enum { N = 4 }`, and No Phase Sees It: Frama-C Prints `if ((unsigned int)i < N)`
- **Seen on:** the upstream audit of 2026-11-18 (no pipeline run), by hand on `framac-analysis:latest` (34.0~beta) and on `master` `b80fcac74f`, with `-machdep gcc_x86_64`, the same results on both. An upstream Frama-C kernel behaviour, not a pipeline defect; the pipeline inherits it in all three phases. No past run was checked for it.
- **Cause:** Frama-C gives an enumeration constant the type of its enum, and an enum without a negative member is `unsigned int` under the default representation. So `i < N` is compiled as an unsigned comparison, where C11 6.7.2.2p3 and gcc give the constant the type `int`. For `enum { N = 4 }; int a[N]; int get(int i) { if (i < N) return a[i]; return -1; }`, the gcc binary reads `a[-1]` when `i` is -1. With Frama-C: `-print` shows `N = (unsigned int)4` and `if ((unsigned int)i < N)`; WP with `-wp-rte` proves `get` (`Proved goals: 4 / 4`); the E-ACSL build (`e-acsl-gcc --no-constfold -c -F "-rte -machdep gcc_x86_64"`) compiles the printed C, so the instrumented binary takes the other branch and never executes the faulty read; Eva raises both index alarms on this function only because it does not reduce `i` through the unsigned comparison, and gives wrong statuses when the values are known (`i = -1; return i < MAX;` is `{0}`). The change is deliberate upstream (Changelog 2026-04-10, "Fix enumeration typing by making sure all items are of type ekind", commit `2da90c219f`, in the tags from `33.0-beta` on). Candidate N1 of [`../upstream/frama-c/frama-c-hunt-2026-11-18-candidates.md`](../upstream/frama-c/frama-c-hunt-2026-11-18-candidates.md), with the full reproducer; not filed.
- **Fix:** none in the pipeline. **Open pipeline gap:** a signed comparison or subtraction with an enumeration constant is analysed and fuzzed with unsigned semantics, so a finding of that shape can be missed by Phase 1 (the fuzzed binary differs from the target), Phase 2 and Phase 3 together, and nothing in a report says so. `-enums int` is not a sound workaround: it gives the right answers for the constants (WP no longer proves the index; the E-ACSL binary aborts on `rte/index_bound: 0 <= i`) and makes enum-typed objects signed, which is wrong the other way (`enum E e = (enum E)-1; e < B` is 0 with gcc and 1 with `-enums int`). No pipeline code was changed. A cheap detection, not built: grep the kernel's printed code for `(unsigned int)<signed expression> <op> <enumerator>` and list the functions in the report.
