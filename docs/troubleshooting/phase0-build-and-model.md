### Symptom: `"status": "needs_build_recipe"` (Exit Code 3 From `build_capture.py run`)
- **Cause:** the target's build failed, built no C file, or has no recipe. Phase 0 has no inventory without a build, so it stops here. The checkpoint keeps the same status until a capture succeeds.
- **Fix:**
  1. Read `diagnostics` in `workspace/reports/build_capture.json`: `first_error` with its context, `missing_headers`, `candidate_packages` (a heuristic from headers, pkg-config modules, CMake packages and commands) and `packages_not_installed`.
  2. Ask the user for a corrected command, packages or flags. Never record a recipe the user has not given or confirmed.
  3. Record it with `run_metadata.py set-build ... --package <pkg>` and rerun the capture with `-BuildImage -Scratch -TargetPackages "<pkgs>"` (`--build-image --scratch --target-packages`). A success clears the status.
- **Without a recipe at all:** `build_capture.py propose` prints one guessed from the build files, as a starting point for the user.

### Symptom: `needs_build_recipe` With `the build compiled no C file` on a Recipe That Ends in `clean all` (PTF `make -C src/LibPtfCom clean all`)
- **Seen on:** ptf-original run-1, module scope `src/LibPtfCom`, 2026-11-10. `build.returncode` 0, `executions` recorded, but `compiles: []` and the log shows only `ar rcs libPtfCom.a *.o`.
- **Cause:** the capture runs the recipe with `MAKEFLAGS=-j15`. With a multi-goal invocation (`make clean all`), GNU make runs the goals **in parallel**: `all` sees the prebuilt `.o` files the target ships before `clean` removes them, so nothing recompiles (and `clean` then deletes the `.o` files afterwards). Not a pipeline defect: the recipe shape and the target's prebuilt tree trigger it.
- **Fix:** split the goals into sequential commands in the recipe: `make -C src/LibPtfCom clean && make -C src/LibPtfCom all`. The same applies to any target Makefile whose `clean` and `all` are given as one multi-goal invocation under the capture's parallel `MAKEFLAGS`.

### Symptom: A Target Built With `-fwrapv`, `-funsigned-char`, `-fshort-enums` or `-fpack-struct` Is Analysed as if the Flag Were Absent, and Nothing Reports It
- **Seen:** 2026-11-20, by reading and `git grep` (no hit for any of these flags under `scripts/`, `templates/`, `skills/` or `wrappers/`), while comparing the pipeline with the dropped-flag table of `sysprog21/frama-c-mcp` (`src/mcp/project.rs`, its `COMPILE_FLAGS_DROPPED` code). Step 0A (2026-11-20) scanned 35 build files across all 10 benchmark manifest targets, 6 local captures (`c-ares/run-2`, `nginx-1.31.9/run-1..5`), and 8 benchmark Phase 0 captures: 0 hits across all 7 semantic-flag families. Step 0B scanned 10 distinct projects (16 `status == "ok"` `-no-annot` parse jobs): 0 `asm:clobber`, 0 `attrs:unknown`, and project-code unclassified `[kernel:...]` categories in `nginx-1.31.9` (`typing:implicit-function-declaration`, `typing:incompatible-types-call`, `typing:int-conversion`, `typing:merge-conversion`, `parser:decimal-float`) and `x509-parser` (71 `typing:incompatible-types-call`).
- **Cause:** pipeline gap (Parts A and B fixed 2026-11-20; Part C behavior mitigation deferred until a target hits one). Some compiler flags change what the C program means, and Frama-C does not read them: every analysis runs under the fixed `-machdep gcc_x86_64`, which decides `char` signedness, enum size and struct layout, and RTE reports signed overflow as undefined whatever the build said. The effect differs by flag: under `-fwrapv` or `-fno-strict-overflow` every `signed_overflow` alarm, E-ACSL stop and Phase 1 UBSan abort is on behaviour the build defines (and in GCC 8+, `-fno-strict-overflow` also implies `-fwrapv-pointer`, interacting with `-warn-invalid-pointer`); under `-funsigned-char`, `-fshort-enums`, `-fpack-struct=<n>`, `-fshort-wchar` or `-funsigned-bitfields` the analysed layouts and value ranges are not the compiled ones. Likewise, Frama-C's `-no-annot` parse warnings (`kernel:asm:clobber`, semantically impactful `kernel:attrs:unknown`, and unclassified `[kernel:...]` categories) were previously ignored on `status == "ok"` parses.
- **Fix (Parts A & B fixed 2026-11-20; Tier 2 of [`../plans/external-projects-improvement-plan.md`](../plans/external-projects-improvement-plan.md)):**
  1. **Report-only `semantic_flags` (Part A):** [`../../scripts/build_capture.py`](../../scripts/build_capture.py) (`extract_semantic_flags`, `unit_semantic_flags`) now parses all 7 families left-to-right with last-flag-wins across negating pairs and `-fpack-struct[=<n>|0]` / `-fno-pack-struct`, emitting `compiles[].semantic_flags`, `units.<name>.semantic_flags` (`flag`, `family`, `category`, `scope`, `files`), and non-test warnings without changing snapshot/cache digests when empty. Schema and validation updated in [`../../schemas/build_capture.schema.json`](../../schemas/build_capture.schema.json) and [`../../scripts/validate_artifacts.py`](../../scripts/validate_artifacts.py); [`../../scripts/generate_report.py`](../../scripts/generate_report.py) renders `### Semantic compiler flags` when non-empty.
  2. **Attribute-filtered parse-loss census (Part B):** [`../../scripts/phase0_model.py`](../../scripts/phase0_model.py) (`summarize_parse_warnings` using `fold_messages`) records `parse_jobs[].parse_warnings` and `units.<name>.parse.warnings` on `status == "ok"` parses (separating project files from snapshot headers, filtering benign GCC attributes and `-no-annot` `libc:frama-c` noise); validated in [`../../schemas/phase0_model.schema.json`](../../schemas/phase0_model.schema.json) / [`../../scripts/validate_artifacts.py`](../../scripts/validate_artifacts.py) and rendered under `### Phase 0 parse` in [`../../scripts/generate_report.py`](../../scripts/generate_report.py) only when `has_parse_loss` is true.
  3. **Tests & acceptance:** unit tests in [`../../tests/test_build_capture.py`](../../tests/test_build_capture.py), [`../../tests/test_phase0_model.py`](../../tests/test_phase0_model.py), [`../../tests/test_validators.py`](../../tests/test_validators.py), and [`../../tests/test_report.py`](../../tests/test_report.py) (`284 passed`), plus Docker verification on `minmea` (`benchmark_compare.py` 0 diff, identical `snapshot_digest`) and `oscs-jsmn` (`validate_artifacts.py run-dir` ok).
  4. **Deferred (Part C — open only if a real target uses a semantic flag):** layout/signedness stop gate in `build_capture.py`, and per-unit `-fwrapv`/`-fno-strict-overflow` propagation across Frama-C RTE/Eva/WP (`-no-warn-signed-overflow`), Phase 1 Clang sanitizer builds ([`../../scripts/fuzz_build.py`](../../scripts/fuzz_build.py)), and E-ACSL Clang backend codegen ([`../../scripts/eacsl_toolchain.py`](../../scripts/eacsl_toolchain.py)).

### Symptom: `"status": "unsupported_architecture"` (Exit Code 5 From `build_capture.py run`)
- **Cause:** x86_64 Linux is the only supported platform. Frama-C's machdep (`gcc_x86_64`), the harness layouts (8-byte pointers) and the E-ACSL and sanitizer builds assume it. This is a limit of the pipeline, not a defect of the target. The capture's architecture guard stops Phase 0 in two cases, and the checkpoint keeps the status until a capture passes:
  - **The host is not x86_64.** `architecture.host` in `workspace/reports/build_capture.json` is `aarch64` or another machine. The guard stops before the target is copied or built.
  - **The build produced other code than x86_64.** `architecture.unsupported` lists each object, executable or shared library that is not ELF64, little-endian, x86-64, with its sources, what the file is (`ELF32 i386`, `ELF32 x86-64 (x32 ABI)`, `ELF64 aarch64`) and what in its command line made it so. The file's header decides. The command line (`-m32`, `-mx32`, `-m16`, `--target=`, a cross compiler's name) decides only for a file that cannot be read (`decided_by: command_line`). The guard stops after the build and before units, flags or entry points are derived.
- **Fix:** `diagnostics.instructions` in the report gives the same steps.
  1. **arm64 host (Apple Silicon, Graviton):** run the pipeline on an x86_64 machine. The images can be built and run as `linux/amd64` under emulation (`DOCKER_DEFAULT_PLATFORM=linux/amd64`), but this is not tested and not supported: it is slow, and the sanitizer and LibFuzzer builds of Phase 1 may misbehave.
  2. **`-m32`, `-mx32` or `-m16` in the flags:** ask the user for a recipe without it (`CFLAGS`, a configure or CMake option), record it with `run_metadata.py set-build`, and rerun the capture. The run then covers the x86_64 build only. Behaviour that exists only with 32-bit `long`, `size_t` and pointers is not analysed: say so in the report.
  3. **Cross compiler (`CC=<triple>-gcc`, `./configure --host=`, `CMAKE_TOOLCHAIN_FILE`, `clang --target=`):** ask for a native recipe without it, so the build image's own compiler builds the target.
  4. **Only some outputs are foreign** (a 32-bit test, a BPF or WebAssembly object, firmware next to host tools): name the native make targets in the recipe, so the others are not built.
  5. **The target builds for another architecture only** (firmware, a Windows or macOS build): it is out of scope for now. No recipe makes it pass.
- **Not checked:** a file the build removed, or LLVM bitcode from an LTO build, has no readable header. When its command line names no other target, it counts under `architecture.unknown` with a warning and the capture continues. Other architectures are not planned yet.

### Symptom: The Build Capture Times Out (1800 s) on a Build That Works by Hand
- **Cause:** a parallel build under `bear` can sit idle until the capture's timeout. Since `47d7c89`, a parallel build that fails **or times out** is retried once with one job on a fresh copy (`build.attempts` in `build_capture.json`), unless the recipe sets `MAKEFLAGS` or `CMAKE_BUILD_PARALLEL_LEVEL` itself. Only a serial build that also times out ends as `needs_build_recipe`. The retry gets a full new timeout, so the worst case is twice `--timeout`.
- **Fix:** rerun the capture through the broker (no `-NoBroker`), which sizes the build's jobs from its lease, or raise `--timeout` for a build that is just slow. If the recipe pins the parallelism through `MAKEFLAGS`, it gets no serial retry: drop it or set `-j1` yourself.

### Symptom: `needs_build_recipe` With `configure: error: cannot run /bin/bash ././config.sub` or `/bin/sh: 0: Illegal option -` (Windows Checkout)
- **Cause:** the target's working tree has CRLF line endings (`core.autocrlf=true`, or a `.gitattributes` `text` rule with the platform's native `eol`). `#!/bin/sh\r` or `#!/bin/sh -e\r` cannot run in the container, so `autogen.sh`, `config.sub`, `configure.ac`, `aclocal.m4` and every script fail. The git index is LF; only the checkout is wrong. Found on nettle (`file config.sub` says "with CRLF line terminators") and libseccomp (`autogen.sh` shebang triggers `/bin/sh: 0: Illegal option -`). This is a target-side checkout issue, not a pipeline defect.
- **Fix:** check the target out as LF, then start a **new run**: `git config --local core.autocrlf false`, `git config --local core.eol lf` (the `eol` setting is needed when `.gitattributes` marks files `text`), then `git rm -rq --cached . && git reset -q --hard` on a clean tree. The overlay of the earlier run holds the CRLF files and `workspace_overlay.py init` refuses a changed target, so do not resume it. Alternatively put a `sed -i 's/\r$//'` over the text files at the start of the recipe's command: the build runs in a copy, so the target stays untouched.
- **Check first:** `file config.sub configure.ac` (or `git ls-files --eol`) before the first capture on a Windows host.
- **Also seen:** mpack run-3 (2026-11-17). `seed_harvest.py record` with the test command `tools/unit.sh more` gave `no_calls_recorded`, the warning "the test command exited 127", and the log `sh: 1: tools/unit.sh: not found`. The build passed only because the recipe runs `python3 test/unit/configure.py` explicitly. In a repro, the same CRLF `#!/bin/sh` script run as the capture's build command (under `bear intercept`) exited 2 with `tools/run.sh: 2: set: Illegal option -`, while a plain `sh -c 'tools/run.sh more'` exited 127 with `not found`.
- **Detection:** **fixed**: `90cc197`, `16c86eb` from `sup/crlf-script-check`, merged into `phase1-remediation` on 2026-11-17 (merge `031f9cb`).
  - `scripts/line_endings.py` lists CRLF shebang scripts and CRLF `configure`, `config.sub` and `*.sh` files.
  - `workspace_overlay.py init` reports them up front in `overlay_meta.json` (`crlf_scripts`, `warnings`).
  - A failed build adds `diagnostics.crlf_scripts` and a hint to `warnings` in `build_capture.json`.
  - A failing test command adds the same hint to `warnings` in `seed_harvest.json`, naming the script (e.g. "tools/unit.sh has CRLF line endings").
  - The pipeline gap was the late, opaque diagnosis. To check a target read-only, run `python scripts/line_endings.py <target>`; on mpack it finds 12 scripts, including `tools/unit.sh`.
- **Also seen:** libmodbus run-1 (2026-11-18), two symptoms in a row, each with `status: needs_build_recipe`, no `diagnostics.crlf_scripts` and no hint in `warnings`, although `workspace_overlay.py init` had flagged `autogen.sh`:
  1. Recipe `./autogen.sh && ./configure && make -j"$(nproc)"`, exit 2: `./autogen.sh: 22: Syntax error: end of file unexpected (expecting "then")`. Under `bear intercept` the `#! /bin/sh\r` script is read by dash (exit 2), which never sees a `then` because the line holds `then\r`. Without `bear`, `sh -c ./autogen.sh` exits 127 with `not found`.
  2. Recipe `sed -i 's/\r$//' autogen.sh run-coverage.sh tests/*.sh && ./autogen.sh && ./configure && make`: `configure.ac:87: warning: AC_CHECK_HEADERS(\` then `): you should use literals`, then ``./configure: line 14962: syntax error near unexpected token `as_ac_Header=`printf "%s\n" "ac_cv_header_$ac_header" | sed "$as_sed_sh"`'``. The CRLF `configure.ac` leaves a `\r` after the `\` of a multi-line `AC_CHECK_HEADERS([ \`, and autoconf copies it into the generated `configure`.
  - **Repro** (`framac-build:latest`, fixtures under `%TEMP%`, `docker run --rm --label framac.run=sup-crlf-fixer --network none`): a CRLF `autogen.sh` without blank lines before its `if ...; then ... fi`, run as `bear intercept --output /tmp/e.json -- sh -c "./autogen.sh && ./configure"`, gives `./autogen.sh: 9: Syntax error: end of file unexpected (expecting "then")`, exit 2. `bash ./autogen.sh` gives `./autogen.sh: line 9: syntax error: unexpected end of file`. Blank lines would add dash's `./autogen.sh: 2: \r: not found`, which the old rule did catch. A CRLF `configure.ac` with `AC_CHECK_HEADERS([ \`, `stdio.h \`, `stdlib.h \`, `])` gives, after `autoreconf -i && ./configure`, ``./configure: line 3233: syntax error near unexpected token `as_ac_Header=...'``, exit 2.
  - **Cause:** the CRLF checkout is target-side, not a pipeline defect. The pipeline gap was the missing hint. `failure_hint()` counted only exit 126/127, `Illegal option -`, `bad interpreter`, `cannot run /bin/sh`, and `not found`/`cannot run`/`No such file or directory` naming a CRLF script. A shell syntax error matched none of them. The scan also listed shebang scripts and named shell scripts only, so a CRLF `configure.ac` was never found. The real `build.log` of the run was not opened here; the diagnosis rests on the reported `first_error` and the repro.
  - **Fix:** **fixed**, `41c20e9`, merged into `phase1-remediation` by `c776343` after libmodbus run-1 ended, in [`../../scripts/line_endings.py`](../../scripts/line_endings.py).   - **Also seen: nanopb run-1 (2026-11-20, target-side, not a pipeline defect).** `workspace_overlay.py init` reported `crlf_scripts` count 19 (`generator/protoc-gen-nanopb`, `generator/nanopb_generator(.py)`, `generator/protoc`, `tests/fuzztest/ossfuzz.sh`, `tools/*.sh`, ...) and the warning. The recipe's build command (`cmake -S . -B build -DBUILD_SHARED_LIBS=ON -Dnanopb_BUILD_GENERATOR=OFF && cmake --build build`) runs none of them, so the capture succeeded. Only the test command (`scons`, whose protoc plugin is `generator/protoc-gen-nanopb` with a `#!/usr/bin/env python3\r` shebang) needs them: the recipe strips CRs from exactly those four files (`sed -i 's/\r$//' generator/protoc-gen-nanopb generator/nanopb_generator generator/nanopb_generator.py generator/protoc && cd tests && scons`), recorded with origin `agent_confirmed`. - **Cause:** generated headers stay in the build tree on the scratch volume, and the later analyses read `workspace/work`, which holds only the target's source tree.

### Symptom: A Package Header Reached Through a Symlink Under `/usr/include` Is in the Snapshot but Not Found by the Analyses
- **Seen on:** not seen on a target yet. Inferred while verifying O7 (`ot/o7-system-headers`, 2026-11-17) in `framac-build:latest`: `echo '#include <linux/types.h>' > a.c; gcc -M a.c` names `/usr/lib/linux/uapi/x86/asm/types.h`, while `gcc -M -fno-canonical-system-headers a.c` names `/usr/include/x86_64-linux-gnu/asm/types.h`.
- **Cause (pipeline gap):** gcc canonicalizes system header paths in its dependency output by default (`-fcanonical-system-headers`), so the capture's `cc -M` lists a header that sits behind a symlink under its real path. `build_snapshot` copies package and unowned headers to `<snapshot>/root/<that path>`. `target_env.include_flags` only adds the include directories the compile names and gcc's default system directories, so a header at `root/usr/lib/...` or `root/opt/...` is in the snapshot but on no include path.
- **Fix:** the libc headers Frama-C's libc lacks are mapped back to the path an `#include` finds (`build_capture.system_dir_links`, O7, commit `9da5f02`). **Open pipeline gap:** the `root/` export of package headers does not do this mapping yet. Applying `include_path` to those headers too, or capturing with `-fno-canonical-system-headers`, would close it. Either change moves files in the manifest, and so changes the snapshot digest and the cache keys.

### Symptom: A Unit's `parse.status` Is `gcc_fallback` in `phase0_model.json`
- **Cause:** Frama-C could not parse the unit with its build flags. Its functions and edges come from GCC's `-fcallgraph-info` instead, without loops, complexity, signatures or indirect-call candidates. `parse.error` holds Frama-C's first error, and the ledger flags the unit's functions (`bookkeeping.callgraph_fallback`).
- **Fix:** read `parse.error` and the log under `workspace/reports/phase0_model/`. The usual causes are the ones in [`./kernel-and-stubs.md`](./kernel-and-stubs.md) (host headers, compiler extensions); fix the cause, then rerun `phase0_model.py run`. ### Symptom: Frama-C Cannot Parse C23 `[[...]]` Attributes in the Target's Generated `config.h` (sudo: 19 of 25 Units Fall Back to GCC at `include/sudo_fatal.h:173`)
- **Seen on:** sudo 1.9.18 (commit `082045c68`), run-1 (`run-1-e7bc881eee3c`), 2026-11-21, build `./configure && make`. The first `phase0_model.py run` ended with `gcc_fallback` for 19 units: `[kernel] include/sudo_fatal.h:173: User Error: syntax error: ... before or at token: [` (lines 173-174, `sudo_noreturn sudo_dso_public void sudo_fatal_nodebug_v1(...)`).
- **Cause:** sudo's `config.h.in` (line 1600) defines `sudo_noreturn` as `[[__noreturn__]]` when `__has_c_attribute(__noreturn__)` holds, and `FALLTHROUGH` as `[[__fallthrough__]]`. The `gcc -E` that Frama-C runs reports `__has_c_attribute`, so the generated `config.h` uses the C23 attribute syntax, which the Frama-C 34.0~beta parser does not read. This is a pipeline gap (the Frama-C parse should preprocess with `__has_c_attribute` undefined or 0, or map these macros), not a target defect. My first guess, GCC's `__restrict__` spelling (`#define restrict __restrict__` in the same `config.h`), was not the cause: `fc_compat_types.h` maps `__restrict__` for the E-ACSL frontend only, and whether the plain Frama-C parse needs it too was not shown.
- **Fix:** **Open pipeline bug.** Worked around inside the run directory only, no pipeline file edited: in the scratch build tree's `config.h` and in `workspace/snapshot/generated/config.h`, `sudo_noreturn` became `__attribute__((__noreturn__))`, `FALLTHROUGH` became `__attribute__((__fallthrough__))` (and `restrict` became `__restrict`); the original is kept in the run's `repair/`. After the patch, `phase0_model.py run` parsed 17 of 25 units with Frama-C. The snapshot manifest digest was not recomputed. A pipeline fix should make the preprocessing for the Frama-C parse hide `__has_c_attribute` (for example in `fc_cpp_wrapper.py` or `fc_compat_types.h`).
- **Fixed (supervisor, merged live into `main` as `9950ee3`, branch `sup/sudo-c23-attributes`, commits `788c027` and `dd99d58`):**
  - **The fix:** [`../../scripts/fc_cpp_wrapper.py`](../../scripts/fc_cpp_wrapper.py) now puts `-include scripts/fc_cpp_no_c23_attributes.h` first on every `cc1 -E` command. That header is a `#pragma GCC system_header` that redefines `__has_c_attribute(x)` as 0, so feature-testing code falls back to `__attribute__((...))`.
  - **Why this form:** GCC 14 answers 202311 in every `-std` mode. `-U__has_c_attribute` breaks `#if defined(__has_c_attribute) && __has_c_attribute(x)`, and `-D...=0` warns "redefined" under `-Werror`.

  - **Reach:** Eva, WP, the Phase 0 model, the kernel AST and the E-ACSL frontend. `FRAMAC_CPP_REWRITE=off` turns it off.
  - **Tests:** four new tests in `tests/test_fc_cpp_wrapper.py`, plus `test_frama_c_and_eacsl_parse_code_that_feature_tests_c23_attributes` under `FRAMAC_DOCKER_TESTS=1`.
  - **Still open:** source that writes `[[...]]` without testing `__has_c_attribute` (`-std=c23`, `__STDC_VERSION__` checks) still fails to parse.
  - **Run 1:** its `config.h` copies stay hand-patched.

  - The model has only their prototypes (`external_decls`, from `toke.h` and `parse.h`). `seed_harvest.py` skips them with `signature '' not understood`.
  - The threat model's `plugins/sudoers/toke.c#sudoers_input` warning is probably the same gap.
- **Cause (diagnosed):**
  - Flex and bison write `#line` directives relative to the directory they generated in (`#line 3 "toke.c"`, `#line 1 "toke.l"`, `#line 1 "gram.y"`, `getdate.y`).
  - Frama-C (`errorloc.ml` `setCurrentLine`) ignores a directive whose file does not exist relative to its working directory, the tree root, and ignores its line number too: `ignoring non-existing file 'toke.l', referenced in a line directive`.
  - cpp names every later return-from-include marker after the same file, so Frama-C ignores those as well. The position stays in the last header entered, with lines counting on past its end.
  - Effects on run-1:
    - gram.c's 36 functions became `toke.h#...` (`sudoersparse` at line 800), and getdate.c's 12 became `include/sudo_compat.h#...`.
    - toke.c's 45 landed in Frama-C's libc `unistd.h`, which the model drops as not the project's.
    - 68 globals moved the same way.
    - A directive Frama-C does follow, because the file exists, puts definitions in the `.y`/`.l` file instead.
- **Fix:** **fixed** on branch `sup/sudo-line-directives` (`dd5193e`), merged live into `main` as `3774d95` during sudo run-1, at the user's request.
  - `scripts/phase0_model.py` parses a source with line directives from a copy with them blanked: same line numbers, a first `#line 1 "<original>"`, and `-iquote <its dir>`. The GCC fallback and the macro scan do the same. Parse jobs record `line_directives`.
  - `scripts/phase0_dump.ml` (dump schema 7) records each definition's `root`, the compiled file of its inclusion chain.
  - When a directive is still in play (one in a header), `attribute_definition` moves a definition whose location is not a C file, or lies past the end of the C file, to its root compiled source. The record gets `relocated_from`, and the model writes a warning.
  - Tests: `tests/test_phase0_line_directives.py`, with a Docker fixture.
  - Replayed read-only on run-1: toke.c gets 45 functions, gram.c 36 and getdate.c 12; none are left in `toke.h` or `sudo_compat.h`. The six entry-point warnings and the 25 "is toke.h#" warnings are gone; the DAG has no function in `toke.h`.
  - The run picks it up by rerunning Phase 0 from the build capture, because its scratch volume was removed.
  - **Still open:** E-ACSL, Eva and WP still parse the original sources, so their locations inside generated sources stay stale (`toke.h:NNN`). That affects consumers that match tool locations to model lines (`ledger.py` `_alarm_in_file`, `failure_identity._resolve_function_at_line`). The systemic fix would blank line directives in the overlay itself (`workspace_overlay.py`).
