# Resources, Caches, Make & Host Tooling

Issues encountered in container resource sizing (`resources.py`), content-addressed build/proof caches (`cache.py`), loop seed generation (`loop_seeds.py`), Make orchestration (`pipeline_make.py`, `templates/pipeline.mk`), benchmark path scrubbing (`benchmark.py`), reference extraction (`extract_references.py`), wrapper invocations (`wrappers/framac-docker.*`), and Windows/host test infrastructure.

The full resource and cache design guide is [`../guides/resources-and-caching.md`](../guides/resources-and-caching.md) (Section 9 lists symptoms). See [`./README.md`](./README.md) for the master troubleshooting index.

## Quick Resource, Cache & Lock Checklist

- **A command prints "queue position N" and waits:** the measured pool is busy. `python3 scripts/resources.py status` (on the host) lists the leases. Leases of killed wrappers are released once their containers exit (`resources.py gc`).
- **A WP report has `"status": "analysis_error"`:** Frama-C was killed or timed out (`reason`: `oom_killed`, `timeout`, `crashed`). Nothing was proven or refuted. The recorded peak memory makes the next lease larger, and the scheduler retries once before marking the units `blocked`.
- **Suspected stale cache result:** re-run with `FRAMAC_CACHE=off` and compare, then `python3 /opt/framac-pipeline/scripts/cache.py clear`.
- **The shared cross-run store stays empty:** only the exact allowlisted commands (`python3 /opt/framac-pipeline/scripts/pipeline_make.py run build|eva|eva-tune|facts|wp-sweep|ingest`, `pipeline_make.py build-check` and `ingest`, `cache.py gc` and `stats`, with or without `$S/...`) may write it. Unrecognized commands, extra un-allowlisted options, or `FRAMAC_CACHE_RW=off` keep the store read-only (`FRAMAC_CACHE_MODE=ro` inside the container).
- **An ad-hoc command is OOM-killed at 1 GiB:** commands the broker does not recognise run as `light` (1 CPU, 1 GiB). Pass `-Class` / `--class` (for example `build` or `phase-dynamic`).
- **`RunLockTimeout`:** another container held the run's `ledger` or `merge` lock for longer than `FRAMAC_LOCK_TIMEOUT`. A holder whose heartbeat stopped (`FRAMAC_LOCK_STALE`, default 120 s) is broken automatically, and an interrupted merge is rolled back from `state/merge-journal.json` by the next merge.
- **Need the previous static behavior:** `FRAMAC_BROKER=off` (`-NoBroker`) for container sizing, `FRAMAC_SCHEDULER=waves` for Phase 3 dispatch.

## Resource Broker, Cache Keys & Make Orchestration

### Symptom: An Ad-Hoc `framac-docker.ps1` Container Keeps Running for Hours After Its Agent Finished, and Its Lease Never Returns to the Pool
- **Seen on:** c-ares run-1 (`run-1-9fd7f4f14232`), Phase 3, 2026-11-16.
  - `framac-fbdd997d6083` started at 19:58Z, running `python3 -` with `glob('/**/stdlib.h', recursive=True)`.
  - `framac-fb23319b0e17` started at 20:47Z, running `glob('/**/libc/stdio.h', recursive=True)`. It was still at about 98% CPU at 22:12Z, although its agent `prove-print_opt_u16_list` had finished at about 21:14Z.
  - No host python, docker or pwsh process referenced either container, and the broker's lease entries were `granted` and orphaned. The user stopped both containers by hand at 22:14:53Z.
- **Cause:** pipeline gap.
  - The agent's shell tool timed out, and the opencode host killed the PowerShell tree. On Windows that is TerminateProcess, so [`../../scripts/resources.py`](../../scripts/resources.py) `exec` (`_run_engine` / `_forward_signals`) never ran its `docker kill` handler, and the `docker run --rm -i` container kept running with no client.
  - The broker saw the holder's lease lock released while `<engine> ps` still listed the container. It marked the lease `orphaned` and kept it counted against the pool. No code path ever stopped such a container.
  - The recursive glob from `/` that never finishes is the subagent's own mistake.
- **Fix:** fixed and merged into `phase1-remediation` (2026-11-16), from branch `sup/c-ares-orphan-container-reap` (`a7ce719`, `c2d8c61`), verified by the supervisor.
  - `Broker._reap_orphan`: a reaping pass (exec acquire, rebalance, `resources.py gc`) kills an orphan's container with `<engine> kill framac-<lease>` once `FRAMAC_ORPHAN_GRACE_S` has passed since the orphan was first seen. The default is 60 s, and `off` restores the old behaviour. It retries every 30 s.
  - It kills only containers named after their own lease, and only on a fresh, definite `<engine> ps` answer, never when liveness is unknown. The lease stays counted until the container is gone, then it is dropped.
  - Tests: the orphan tests in `tests/test_resources.py`, and [`../../tests/test_orphan_container_reap_docker.py`](../../tests/test_orphan_container_reap_docker.py) (gated on `FRAMAC_DOCKER_TESTS=1`).
  - Workaround for a run on an older checkout without the fix: `docker kill framac-<lease>` for an orphan whose agent has finished. The broker drops the lease on its next pass.
- **Still open:** ad-hoc wrapper commands have no default wall-clock cap. A cap in `exec` would also apply to the Make, Eva and fuzz phases, which decide results.

### Symptom: `build-check` E-ACSL Build OOM-Killed: Two Whole-Program Builds Admitted at 2 GiB Each
- **Seen on:** nginx 1.31.9 run-3, `pipeline_make.py build-check`, 2026-11-19.
  - Container `framac-df5a91d5be63` had a 17 GiB limit (`HostConfig.Memory` 18253611008, `MemorySwap` equal), 32 host CPUs and a 30-CPU pool.
  - Make ran `resources.py run --class build --key nginx__ngx_event_openssl ... -- run_eacsl_fuzz.py build ...` and the same for `nginx__ngx_files` at the same time.
  - Each E-ACSL instrumentation is a whole-program Frama-C, because the two `SOURCES_` lists hold 163 and 161 of the unit's 165 files. Even the 20-function cluster gets them; that unit-split gap is tracked separately. On run-5 the same whole-program instrumentation also ran out of time: `nginx__ngx_bpf` (23 functions, 135 of 137 files) was killed at the fixed 3600 s build limit. See "`/home/opam/.opam/5.5/bin/e-acsl-gcc exceeded the 3600 s build time limit` on a Large Whole-Program Slice" in [`./eacsl-and-fuzzing.md`](./eacsl-and-fuzzing.md).
  - At 15:01:24 the container was at 98.7% (16.78/17 GiB), and the two Frama-C processes held 8.76 GB and 8.39 GB RSS.
  - Docker logged an `oom` event at 15:01:48, and the cgroup OOM killer took a Frama-C. The container's own record (`phase-static`, 14:15:31Z) says `oom_kills: 2`, `peak_mb: 17408`.
  - The job history then said `peak_mb` 17173 (rusage) for the openssl key and 8809 for the files key. Both records had `oom_killed: false` and `mem_mb: 2048`.
  - **Attribution (from the per-key peaks):** at 15:02:15 the surviving Frama-C was at 9172 MiB and growing, above the files key's final 8809 MiB. So the first kill took the `nginx__ngx_files` Frama-C. The openssl Frama-C then grew alone to the container limit (17173 MiB) and was the second kill. The supervisor's live note, which named openssl first by process-id order, was wrong.
  - **Consequence:** the openssl whole-program E-ACSL instrumentation alone needs more than 17 GiB. Serializing the two builds (the fix below) is necessary but not enough on this pool. **Open:** a larger build-check container (the host has about 39 GiB), or smaller slices (the unit split), is still needed.
  - **The first-build estimate is too low for E-ACSL (open pipeline bug, found when preparing run-4):** `first_build_estimate` (below) asks 1.25 × the scaled parse peak, which is 12931 MiB for openssl. The build had reached 17173 MiB, at least 1.66 × that peak, when it was killed. Its full need is unknown.
    - In a container larger than about 26 GiB, the two estimates fit together, so both whole-program builds would be admitted again and would overrun it.
    - The 2 × doubling after an OOM kill corrects this only from the second run of a key with history.
    - **Workaround for a run:** start the builds with the wrapper's `-Memory` fixed grant (for example `-Memory 32g` on this host) and run `pipeline_make.py run build --jobs 1` before `pipeline_make.py build-check`. build-check then finds the build reports up to date.
    - **Fix:** none yet. Measure E-ACSL's instrumentation overhead over the parse peak on a few targets, and use it instead of the generic 1.25 margin.
    - **Run-4 (2026-11-19):** the broker logged `12932 MiB from Phase 0's parse (163/165 of parse p0-8e61d9631d20a21d (13090 MiB from its history))` for `nginx__ngx_event_openssl`, run with `-Memory 32g` and `run build --jobs 1`. The user stopped the run after about 11 minutes of that build, with no `oom` event. No `.build.json` was written and the peak was not measured, so the real need is still unknown.
    - **Run-5 (2026-11-19, nginx without OpenSSL):** the broker logged `build of nginx__ngx_bpf: 3607 MiB from Phase 0's parse (135/137 of parse p0-f2f1fa9467361a0d (3660 MiB from its history))`, from a parse peak of 2928 MiB. The supervisor read the build container at 10.68 GiB (`docker stats`, 100% of one CPU) 35 minutes into the E-ACSL instrumentation: at least 3.0 × the lease and 3.7 × the parse peak, still growing. `-Memory 32g` covered it, and there was no `oom` event. The attempt was then killed at the 3600 s build limit (see "`e-acsl-gcc exceeded the 3600 s build time limit`" in [`./eacsl-and-fuzzing.md`](./eacsl-and-fuzzing.md)), and the run's task was cancelled before `resources.py` wrote a record, so this is again a lower bound with no history entry. The sanitizer builds that followed peaked at 226 and 360 MiB against the same 3607 MiB lease.
- **Cause:** pipeline bug in [`../../scripts/resources.py`](../../scripts/resources.py), in three parts.
  - **Lease size.** `CLASSES["build"]` is 2048 MiB with no per-CPU memory, and `history_estimate` cannot help the first build of a key. So the broker granted 2 GiB to each job and admitted both. Phase 0 had already measured 10471 MiB for the whole-unit parse of the same files: the model container's record `state/resource-history/phase-static/20261119T121611091611Z-0b01b5a0.json`, written 1.1 s after the model ended. That record has a null key, so nothing linked it to the unit.
  - **Missing parse history.** The parse leases (`resources.py run --class parse --key p0-<job>`) ran with the scratch tree as their cwd, and `cmd_run` read and wrote history only in the cwd. No `parse` record was ever written: run-3 has no `state/resource-history/parse/`.
  - **OOM detection and retry.** `_oom_killed` required rc -9/137. Under engine `auto` the killed E-ACSL compile fell back to the sanitizer build, so the job exited 1, the retry never fired and the record said `oom_killed: false`. Even if the retry had fired, it asked for 2 × the lease (4096 MiB), far below the need.
  - **Hidden in the report.** `build.json` hid the OOM: it reports only the last attempt (`eacsl_instrumentation_failed` from the post-repair attempt, which stopped at once on the missing `objs/ngx_modules.c`). That reporting half is handled on branch `sup/nginx-generated-sources`.
- **Fix:** fixed on branch `sup/nginx-build-memory` (commits `c35dfb0` and `090c0f3`), merged into `phase1-remediation` in `e8ccd54` and into main in `fd40b66`, all in [`../../scripts/resources.py`](../../scripts/resources.py).
  - **Phase 0 estimate.** `first_build_estimate`: a `build` job asks for 1.25 × the parse peak of the parse job(s) its `--sources` come from, scaled by the share of each job's sources it compiles.
    - The lease takes the larger of this estimate and the key's own history. An attempt that aborted in seconds (run-3's missing `objs/ngx_modules.c`) records a tiny peak, which must not size the next whole-program build back down to 2 GiB. The cost: a build that really needs less still waits for its estimate.
    - The peak comes from the job's `parse/p0-<job>` history, else from the model container's `phase-static` record. That is the first record within 120 s after `generated_at` + `seconds`. It is split across parse jobs by number of sources, so later containers, such as build-check's own OOM record, never count.
    - Run-3 data gives 12931 and 12772 MiB. Together they exceed the 17408 MiB pool, so the second build queues. A demand above the pool is granted alone with the existing "clamped to the pool" warning.
    - The 1.25 is `history_estimate`'s margin over a measured peak. The observed 8.39 and 8.76 GB, read at kill time, are 0.82-0.86 of the scaled parse peak: lower bounds, not a measured E-ACSL factor.
    - Small units keep the class's 2048 MiB while the scaled parse peak is at most 1638 MiB. Above that, the first build asks for more: a whole-unit build of a target whose model container peaked at 2050 MiB asks for 2563 MiB.
  - **History location.** `history_run_dir`: `run` uses the cwd when it is a run dir, else `/framac-run`, so parse leases now record `parse/p0-<job>`.
  - **OOM attribution.** `oom_evidence` charges an `oom_kill` delta during the job in three cases: the job was SIGKILLed, it held the only lease (`alone`), or it overran its own gated lease (`overran_lease`). Ungated `light` leases never qualify for `overran_lease`. A job within its lease beside others is not charged, because the kill may be a neighbour's. Records add `oom_evidence` and `oom_kills_during`, so a kill that hit a grandchild doubles the next estimate.
  - **Retry.** `retry_memory`: the one retry asks max(2 × lease, 1.25 × peak), capped at the pool. Only a charged job that failed (rc != 0) is retried. One that exited 0 (for example a successful sanitizer fallback) is kept, and its record says `oom_killed`.
  - Tests: [`../../tests/test_resources_build_memory.py`](../../tests/test_resources_build_memory.py). `test_first_builds_of_two_whole_unit_modules_run_one_at_a_time` and the rc-1 case of the OOM retry test failed on `973e519`: both builds got 2048 MiB, and the rc-1 OOM was neither retried nor recorded.
- **Still open:**
  - The 17173 MiB rusage peak of the openssl job exceeds what it could hold beside the files job. One reading fits both `oom_kills: 2` and the two peaks: the first kill took the files Frama-C at about 8.8 GB, then the openssl Frama-C grew alone to the 17 GiB limit and was killed too. If so, the openssl E-ACSL instrumentation alone needs more than this 17 GiB container. The fix then serializes the builds, but the build still fails until the build-check container gets more memory. Not verified, because the compile log keeps only the last attempt.
  - Leases are admission only. A retry sized from the observed peak can still be admitted beside a neighbour whose lease is far below its real use, as in run-3, where both jobs held 2 GiB leases while using about 8.5 GB each. The Phase 0 estimate removes that case for builds, but not for other classes.
  - `eva` (also 2048 MiB fixed) has no Phase 0 estimate. A whole-unit Eva on such a module would meet the same first-run gap.
  - **Verified on nginx run-4 (2026-11-19):** the parse lease wrote `state/resource-history/parse/` inside the model container (key `p0-8e61d9631d20a21d`, `peak_mb` 10472, lease `mem_mb` 2048, wall 1191 s, rc 0, no OOM), and the first openssl build took its estimate from it (above).
  - Not verified on a real run: a two-module build-check in Docker; the 120 s record window on other hosts; the `overran_lease` path end to end (the Windows test host has no `os.wait4`, so the tests inject peaks through the fake cgroup's `memory.peak`).

### Symptom: A Module's E-ACSL Build Runs in Full Again Although Nothing Changed, With `"cache": {"hit": false, "key": null}`; `run fuzz` Takes Half an Hour for Campaigns of 30 s
- **Seen on:** c-ares run-1 (2026-11-16), found while reassessing [`../plans/fuzz-budget-design.md`](../plans/fuzz-budget-design.md). `run fuzz` took 2,026 s for seven campaigns with 274 s of wall limits together. The records in `state/resource-history/` give the order of events:
  - `run build` (348 s) ran seven build leases of 155 to 188 s with a largest process of 81 MiB each. A full E-ACSL build of these modules peaks at 4.2 to 4.3 GiB, so these were cache restores. This is inferred from the peaks: the `build.json` files of that step were overwritten by the next one.
  - `run fuzz` ran `build-%` again for every module, because `fuzz-%` depends on the phony `build-%`. Six were restored in 154 to 200 s. `libcares_a__channel`, restored three minutes earlier, was built in full: 882 s, 4,327 MiB.
  - The campaign of `libcares_a__channel` then built it in full once more inside its `fuzz` lease (986 s for 1.8 s of fuzzing), and so did the campaign of `ahost` (1,046 s for a 30 s campaign), although `build-ahost` had been a cache hit.
  - All three full builds report `"cache": {"hit": false, "key": null}`: `workspace/build/libcares_a__channel.build.json`, and `compile.cache` in `workspace/reports/fuzz/ahost.json` and `workspace/reports/fuzz/libcares_a__channel.json`. The other modules report the same key in both steps.
- **Cause:** **Open pipeline bug.** `cache.memoize` in [`../../scripts/cache.py`](../../scripts/cache.py) gives a build no key when `dependency_manifest` returns `None`, and the build then runs uncached. `dependency_manifest` runs `gcc -M -MG` and then `clang -M -MG` over all sources of the module, each with a timeout of `DEPS_TIMEOUT_S = 120`. A c-ares module has 95 to 97 sources. Measured on 2026-11-16 in a separate container with 2 CPUs, the run directory mounted read-only and the live run busy on the same host:
  - `gcc -M -MG` took 242 s and `clang -M -MG` 41 s, both with exit code 0.
  - `cache.dependency_manifest` returned `None` after 120.0 s, the timeout of the `gcc` scan.

  This is not the skip rebuild of "Multi-Round Dispatch Fuzzing Spends Over Half Its Wall-Clock Time in Single-Threaded `frama-c -e-acsl` Stage 1 Rebuilds" in [`./eacsl-and-fuzzing.md`](./eacsl-and-fuzzing.md), which also builds without a key: the only round of `libcares_a__channel` skipped at run time (`runtime_skip: true`, one round), `ahost` runs in fork mode, and `build-%` has no skip rebuild.

  So the scan is close to its limit on this target even when it succeeds (hence 154 to 200 s for a cache hit), and it can pass it. What was not checked:
  - **What makes the scan's time vary.** It stayed under 120 s per tool on the restores and took 242 s today. CPU load is one candidate, the Windows bind mount of the run directory another. The second full build of `libcares_a__channel` started when only one other lease was running, a single Frama-C build, so many fuzz workers are not needed for a miss.
  - **Whether run-1's three misses were timeouts.** The scan was timed today, not during run-1, so the timeout is the measured explanation for a missing key, not a recorded one. Nothing in a report says why a key is missing.
- **Effect:** one timed-out scan costs a full E-ACSL build, about 15 minutes and 4.3 GiB on c-ares, and it can happen inside a `fuzz` lease, where the broker reserved memory for fuzz workers. Nothing reports it: the build succeeds.
- **Fix:** none yet. Candidates, none tried:
  - Record why a key is missing (`timeout`, `tool_failed`, `no_sources`) in the `cache` field, and warn.
  - Scan the sources in parallel or one command per source with the per-file results reused, so the time does not grow with the whole module in one process.
  - Size the timeout from the number of sources, or let a slow scan finish: a full build costs far more than the scan.
  - Do not build inside the campaign at all (`P7f` of the design document), which removes the two rebuilds inside `fuzz` leases but not the one in `build-%`. `P7g` of the same document carries the first three candidates.
- **Workaround:** none used. The run finished; the time is lost.

### Symptom: A "standard analysis" of a benchmark target takes its harness, build recipe and known bugs from `benchmark/manifest.json`
- **Seen on:** minmea run-1, 2026-11-14 (opencode session). Asked to "run a standard analysis" of `targets/minmea`, the agent read `benchmark/manifest.json`, copied its `call_expr` into the harness (`--entry-style custom`), copied the threat model from `benchmark/assets/minmea/`, and recorded the manifest's build recipe with `--origin agent_confirmed` without asking the user. After fuzzing it compared the crashes with the manifest's bug list ("found 2 of 3 known bugs").
- **Cause:** pipeline gap in the skills, not in a script. Nothing in [`../../skills/framac-verify/SKILL.md`](../../skills/framac-verify/SKILL.md) or [`../../skills/framac-slice/SKILL.md`](../../skills/framac-slice/SKILL.md) says that `benchmark/` holds ground truth and pinned harnesses that a normal run must not read, and the agent argued that a checked-in recipe counts as given by the user. The run is therefore not blind, and its harness was not produced by the pipeline's own generator (`--api`).
- **Fix:** **Open pipeline gap:** state in the skills that `benchmark/` is off limits outside `benchmark.py` runs, and that a recipe from the manifest still needs the user's confirmation. No workaround was applied to the run.

## Wrappers, Host Environment & Shared Infrastructure

### Symptom: Wrapper Exits With Code 2: `-NoInnerSandbox` / `--no-inner-sandbox` (or `-AllowDegradedSandbox` / `--allow-degraded-sandbox`) "is no longer supported"
- **Cause:** The bubblewrap layer was removed. The hardened container, with Docker's default seccomp and AppArmor profiles, is the only isolation boundary, and target-controlled binaries run under [`../../scripts/sandbox_exec.py`](../../scripts/sandbox_exec.py) (rlimits, env allowlist, timeout). The legacy flags fail hard rather than being silently ignored.
- **Fix:** Remove the flag from the command line or script. No replacement flag is needed.

### Symptom: PowerShell Splits Frama-C or Docker CLI Flags Containing `.` or `=`
- **Cause:** Windows PowerShell parses unquoted arguments containing `.` or `=` (like `-wp-model=Typed+ref` or `-report-csv=out.csv`) into multiple tokens.
- **Fix:** Always invoke container commands through [`../../wrappers/framac-docker.ps1`](../../wrappers/framac-docker.ps1) and double-quote any CLI flag containing `=` or `.`.

## Test Suite & Windows Checkout Issues

### Symptom: `test_sh_new_run_allocation_is_atomic_under_concurrency` fails on Windows with `child_copy: cygheap read copy failed ... Win32 error 299` or return code `3221225794`
- **Seen:** 2026-11-09, full `python -m pytest tests -n auto` in the formal-discovery Tier 4 worktree while five other sessions ran their own suites on the same Windows host. Failed twice in the full suite; `tests/test_run_identity_wrappers.py` passes alone (`-n 0`).
- **Cause:** not a pipeline defect. The test starts many Git Bash (`bash.exe`) processes at once; under heavy host load Cygwin's `fork` fails (Win32 error 299, or `0xC0000142` STATUS_DLL_INIT_FAILED as the return code), so `mkdir` in `framac-docker.sh`'s run allocation never runs. The atomicity being tested is not involved.
- **Forms seen** (2026-11-17, 100 stress rounds of 16 to 24 concurrent processes on this host, branch `ot/o11-o12-small`): bash exits 0 but prints `child_copy: cygheap read copy failed ... Win32 error 299` and `dofork: child -1 - forked process <pid> died unexpectedly, retry 0, exit code 0xC0000142, errno 11` (Cygwin retried; sometimes the names are still right, sometimes a number is skipped); `mkdir` itself fails the same way and bash exits 127; bash exits 2 after the `dofork` message. No duplicate allocation in any round.
- **Fix:** none needed in the pipeline. The test gap is fixed in `65e9a95` and `9dd0ef2` (O12 in [`../plans/open-topics-remediation-plan.md`](../plans/open-topics-remediation-plan.md)): [`../../tests/test_run_identity_wrappers.py`](../../tests/test_run_identity_wrappers.py) (`_judge_allocations`) first fails on a run directory claimed twice among the processes that succeeded; passes when every process got one of the expected names (a fork Cygwin retried); otherwise skips with `Git Bash could not fork in <k> of 8 processes ...` when any process returned `0xC0000142` or printed `Win32 error 299` / `cygheap read copy failed`; anything else fails as before. Unit tests in the same file simulate both halves (fork failure gives a skip; a duplicate fails with or without a fork failure). A skip still means the allocation was not exercised: re-run the file alone (`python -m pytest tests/test_run_identity_wrappers.py -n 0`) when the host is quieter. One full-suite run (`-n 8`) on the first version of the fix failed this test with a message that was not captured; nine later full runs and the stress rounds did not reproduce it, and every abnormal process seen was a fork failure the test recognizes.

### Symptom: Phase 3 Subagents Start Their Own Containers With `docker run` and `docker exec` Into Other Agents' Containers, Outside the Wrapper and the Resource Broker
- **Seen on:** minmea, run-1, 2026-11-14 (supervisor, from `docker ps` and a copy of the opencode session database). `breaker-minmea_check` started `docker run -d --name breaker-minmea-check ... framac-analysis:latest sleep 1800` with flags it wrote itself (`--network none --cap-drop ALL --pids-limit 4096 -m 8g --cpus 3`, the run directory mounted read-write) and then used `docker exec`. `breaker-minmea_parse_rmc` ran `docker run --rm --network none --cpus 1 --memory 1024m ...` by hand. `breaker-minmea_checksum` ran campaigns with `docker exec framac-e0904f6850c4 ...` and `docker exec framac-3dffc44c936a ...`, containers the wrapper had started for other agents' commands, and tried names that did not exist (`framac-breaker-gga`, `framac-breaker-checksum`). Several breakers also ran `docker inspect` on wrapper containers to copy their mounts and environment.
- **Cause:** **Open pipeline gap:** the subagents run on the host with the same Docker access as the parent, and nothing but the brief's wording makes them go through `wrappers/framac-docker.ps1`. A container started by hand has no `framac.run` label, takes no lease from the host broker (its CPUs and memory are not counted in the pool), is not removed by the wrapper, and has whatever mounts and limits the agent typed. A `docker exec` into another command's container runs inside that command's cgroup and time limit, so its work is charged to the wrong job and dies when that command ends. The run's `REPORT.md` still states `Execution: sandboxed, local only (outer: docker-hardened, inner: rlimits)`. In this run every hand-written command the supervisor saw kept `--network none`; that was the agent's choice, not something the pipeline enforced.
- **Fix:** none yet. Options: state in the breaker, prover and verifier briefs that the wrapper is the only allowed way to reach Docker, and why; give subagents a tool allowlist that excludes raw `docker`; have the report's execution line derive from what ran (containers without the `framac.run` label during the run) instead of from the policy.
- **Status (2026-11-19):** the brief side is fixed (`24c99a5`, now on `main`). `skills/framac-wp/run_commands.md`, spliced into the prover, breaker, verifier, architect and stub author briefs, says the wrapper is the only way to reach Docker and why, forbids `docker run`, `docker exec` and `docker inspect` by hand, and forbids `ulimit -c 0`. ### Symptom: `pipeline_make.py run fuzz` (Single-Module Target) Uses Only ~20–30% of Host CPU on Multi-Core Windows / Docker Desktop Hosts
- **Seen on:** QCBOR, run-6, module `libqcbor_a`, 2026-11-14 (AMD Ryzen 9 5950X, 32 logical CPUs, 48 GiB host RAM). Host CPU stayed around 22–36% (~7 active LibFuzzer workers) throughout `pipeline_make.py run fuzz`.
- **Cause:** Two stacked pipeline/host memory-sizing caps, plus an open sub-lease bug inside `job_budget()`:
  1. **Host broker pool memory capped by Docker Desktop's WSL2 VM default (50% of host RAM):** Docker Desktop reports `MemTotal = 23991 MiB` (~23.4 GiB, WSL2's default 50% of 48 GiB). After the 10% host reserve (`2399 MiB`), the host broker pool (`resources.py status`) is `30 CPUs, 21591 MiB`. When `pipeline_make.py run fuzz` acquires a `phase-dynamic` container lease (`mem_base_mb = 2048`, `mem_per_cpu_mb = 1536`, elastic upper bound `pool // 2 = 15` CPUs), `_fit()` lowers CPUs from 15 until `2048 + 1536 * cpus <= 21591`, granting the container `--cpus 12 --memory 20480m` (leaving only `1111 MiB` free in the pool, which also blocks concurrent `phase-static` jobs needing at least `4096 MiB`).
  2. **Per-worker LibFuzzer memory headroom (`2560 MiB` per worker) caps workers inside the container:** QCBOR has a single fuzzable module (`libqcbor_a`), so only one `run_eacsl_fuzz.py campaign` runs inside `make -j12`. `fuzz_workers()` computes `min(cpus, (mem_mb - 512) // 2560)` for the fixed `-rss_limit_mb=2048` (`1.25 * 2048 = 2560 MiB`), capping `libqcbor_a` to `(20480 - 512) // 2560 = 7` LibFuzzer workers (`7 / 32 = 21.9%` of logical CPUs, ~30–36% total host CPU with OS/hypervisor/9p I/O overhead). In addition, the run directory is on the Windows filesystem (`C:\Users\...\framac-pipeline\QCBOR\run-6`), mounted over 9p (`/framac-run`), slowing corpus sync I/O across workers.
  3. **Open pipeline bug in [`../../scripts/resources.py`](../../scripts/resources.py) (`job_budget` / `enforced_memory_mb`):** Inside a container started by the host broker, `FRAMAC_CGROUP_ENFORCED=1` is set on the outer container environment (`build_engine_argv`, line 3059) and inherited by in-container sub-leases (`cmd_run`, line 2814), which set `FRAMAC_SUBLEASE_ID` and smaller `FRAMAC_JOB_CPUS` / `FRAMAC_JOB_MEM_MB` without creating a child cgroup. Because `job_budget()` (lines 1336, 1347) ignores `FRAMAC_JOB_CPUS` and `FRAMAC_JOB_MEM_MB` whenever `FRAMAC_CGROUP_ENFORCED == "1"` and a container-level cgroup limit exists, sub-leased tools inside `make -j` (`fuzz_workers()`, `wp_parallelism()`) size themselves from the outer container's whole cgroup (`12 CPUs, 20480 MiB` -> 7 workers) instead of their sub-lease (`FRAMAC_JOB_CPUS=6, FRAMAC_JOB_MEM_MB=15872` -> 6 workers). On multi-module targets running parallel Make recipes, each parallel recipe will oversubscribe the container's CPUs and memory. Also, elastic `phase-dynamic` / `phase-static` grants (`_cpu_bounds`, line 1414) cap `alone` only for `wp`, limiting a sole `run fuzz` container to `pool // 2` CPUs even when idle memory is abundant.
- **Fix:**
  - **Host configuration (not a pipeline bug):** Increase `memory=` in `%USERPROFILE%\.wslconfig` (for example `memory=40GB` on a 48 GiB machine, followed by `wsl --shutdown` and restarting Docker Desktop) so Docker Desktop's VM exposes enough RAM for 14–15+ fuzz workers, and place run directories inside the WSL2 ext4 filesystem rather than `C:\...` to avoid 9p corpus overhead.
  - **Seen again (still open):** c-ares run-1, 2026-11-16, on a multi-module target. The seven fuzz sub-leases got 1 to 7 CPUs and 3,072 to 18,432 MiB (`state/resource-history/fuzz/`), yet every fuzz report has `sizing.workers: 9`, which is `(25088 - 512) // 2560` for the whole container (15 CPUs, 25,088 MiB, `FRAMAC_CGROUP_ENFORCED=1`). A campaign with a 1-CPU lease ran 9 workers, so the broker's "in use" CPU figures understated what ran, and each campaign's wall time (`fuzz_budget / workers`) used a worker count its lease did not grant. Found while reviewing [`../plans/fuzz-budget-design.md`](../plans/fuzz-budget-design.md) (P7e); the run was only read.
  - **Seen again, 9p corpus I/O now dominates (QCBOR run-2, 2026-11-23, `run-2-d574bb040623`):** the container had `NanoCpus=15e9` and 7 workers, but `docker stats` showed 70-106% CPU for the whole container and each worker about 11% of a core (1 CPU-minute in 9 minutes); `/proc/<pid>/stat` sampled every 0.5 s put the workers in state `D` most of the time, `wchan` `p9_client_rpc`, `d_alloc_parallel` or `walk_component` (lookups on the `/framac-run` 9p mount, `aname=drvfs;path=C:\`). Throughput fell to about 2.5k exec/s per worker (run-1 of the same target and harness family: about 5.8k exec/s on about 6.8 cores). With `-jobs=7 -workers=7` each worker rescans that directory to pick up the others' units (`Loaded 1024/43261 files from /framac-run/workspace/corpus/libqcbor_a`, 18 times in the first 9 minutes), and every rescan is a 9p lookup per file. The run is alive, not stalled, but each worker's `-max_total_time` is wall clock, so the campaign gets far fewer executions than its CPU budget. **Open pipeline bug:** `scripts/run_eacsl_fuzz.py` (`_run_fuzz_campaign_once`, `corpus_dir` passed straight to libFuzzer) keeps the live, shared corpus on the run mount. Keeping the working corpus on container-local scratch (the scratch volume or `/tmp`) and syncing new units back to `workspace/corpus/` at the end of the campaign would remove the 9p cost; moving the run directory into the WSL2 filesystem (see above) also would. Nothing was changed in the live run.
  - **Open pipeline bug:** In [`../../scripts/resources.py`](../../scripts/resources.py), `job_budget()` and `enforced_memory_mb()` must honor `FRAMAC_JOB_CPUS` and `FRAMAC_JOB_MEM_MB` (taking `min(grant, cgroup)`) whenever `FRAMAC_SUBLEASE_ID` is set (or unconditionally take the minimum of `grant` and `cgroup`, since a resized container only grows under `rebalance_grants` and never shrinks). ### Symptom: Every `abort()` (or Other Core-Dumping Signal) in a Container Takes Minutes on a Docker Desktop / WSL2 Host; E-ACSL Test Binaries and Crashing Fuzz Inputs Run Far Slower Than Their Work
- **Seen on:** the Frama-C upstream filing audit, 2026-11-15, image `framac-master-audit:3dff90f` (a local build of Frama-C `master` `3dff90fc70`), on the same 32-CPU Docker Desktop / WSL2 host as above. One `kill -ABRT` of a test binary took 156 s; E-ACSL's `format/printf.c` ptest, whose binaries abort on purpose, ran for more than 40 minutes without finishing.
- **Cause (host configuration, measured by the audit agent):** the WSL2 kernel's `core_pattern` is a pipe (`|/wsl-capture-crash ...`). For a piped `core_pattern` the kernel ignores `RLIMIT_CORE = 0` and still streams the core to the helper; only `RLIMIT_CORE = 1` makes it skip the pipe dump. With `prlimit --core=1:1` the same abort took 10 ms. `ulimit -c 0` does not help.
- **Pipeline impact (fixed, see "Pipeline fix" below):** [`../../scripts/sandbox_exec.py`](../../scripts/sandbox_exec.py) sets `RLIMIT_CORE` to `0` (line 121), so on such a host every E-ACSL abort and every crashing fuzz input inside the sandbox pays the pipe dump. This is not yet measured on a pipeline run. Candidate fix: set `RLIMIT_CORE` to `1` (a 1-byte limit also writes no useful core file under a file `core_pattern`), with a test, after checking that nothing reads core files.
- **Measured for the pipeline's binaries (2026-11-16, `framac-analysis:latest`, same host, a container of its own with 2 CPUs, 5 runs each; for [`../plans/fuzz-budget-design.md`](../plans/fuzz-budget-design.md)):**
  - **A binary with its own `main` pays the pipe dump.** An E-ACSL binary whose check fails: 852 ms with `RLIMIT_CORE` 0 (what the sandbox sets), 866 ms with no limit, 14 ms with `RLIMIT_CORE` 1. A plain `abort()`: 129 ms against 13 ms. Far less than the audit's 156 s, but still 60 times the cost with the limit at 1.
  - **A libFuzzer binary does not.** libFuzzer catches the signal and exits with code 77, so no core is written: a failing input on minmea's E-ACSL and sanitizer fuzz binaries took about 435 ms with the limit at 0, at 1 and unset, against 85 ms for a passing input.
  - **Those 350 ms are stack symbolization.** With `symbolize=0` in `ASAN_OPTIONS` and `UBSAN_OPTIONS` the same failing input took 94 ms (E-ACSL build) and 88 ms (sanitizer build), and the stack frames have no function names. This is not a host defect and not a pipeline bug; it is the price of each crash in a campaign or a replay.
  - Which pipeline steps run a binary with its own `main` inside the sandbox was not listed.
- **Workaround used in the audit:** run E-ACSL tests and binaries under `prlimit --core=1:1`.
- **Upstream ptests (2026-11-16, filing packages 30 and 31):** the E-ACSL `format/` `dev` ptests that "hung" on `master` were paying this dump on every expected abort. With `ulimit -c 1` in the shell before `dune build`, `printf.c` alone finished its `dev` run in 12-14 minutes; two such runs in parallel containers both hit a 30-minute timeout.
- **Pipeline fix (fixed 2026-11-16, commit `21a1144`, now on `main`):** [`../../scripts/sandbox_exec.py`](../../scripts/sandbox_exec.py) sets `RLIMIT_CORE` to `CORE_LIMIT_BYTES = 1` instead of `0`; test `test_preexec_sets_core_limit_to_one_byte`. Measured with `run_sandboxed` on an aborting binary (`framac-analysis:latest`, 2 CPUs, 5 runs, WSL2 pipe pattern): median 2072 ms (max 3777 ms) with the limit at 0, 11 ms (max 12 ms) at 1, no core file either way.
- **Measured again (2026-11-17, `framac-master-audit:9540804`, same host after its disk-full incident):** an abort takes 6 ms with the containers' default core limit of 0, and E-ACSL's `format/` `dev` ptests finish in about 11 s. `core_pattern` is still the `|/wsl-capture-crash` pipe; why the dump is now skipped was not diagnosed. The containers' hard core limit is 0, so `ulimit -c 1` fails there with `Operation not permitted`; it is harmless now. To set the limit anyway, start the container with `docker run --ulimit core=1:1`.
- **Host fix (the owner's to apply):** with a file pattern, the containers' default `ulimit -c 0` blocks the dump entirely. Live until the VM restarts: `docker run --rm --privileged alpine sysctl -w kernel.core_pattern=core`. Persistent: `kernelCommandLine = sysctl.kernel.core_pattern=core` under `[wsl2]` in `%USERPROFILE%\.wslconfig`, then `wsl --shutdown`; not yet verified that WSL keeps it instead of resetting it at start-up (check with `docker run --rm alpine cat /proc/sys/kernel/core_pattern`). It applies to every WSL2 distro and container on the host, and WSL's own crash reports stop.

### Symptom: `sandbox_exec.py run` Fails With `FileNotFoundError: [Errno 2] No such file or directory: 'workspace/harnesses/fuzz_<module>.e-acsl'` on a Relative Binary Path

The run directory is `/framac-run`, not that scratch directory, so `Popen` raises an uncaught `FileNotFoundError` traceback instead of a clean error naming the missing path. The replay path avoids it because it passes absolute paths and an explicit cwd.
- **Fix:** **Open pipeline gap** (not patched in the run). Workaround used: pass `--cwd /framac-run` and absolute `/framac-run/...` paths for both the binary and the input. Suggested pipeline change: resolve `argv[0]` (and input paths) against the invocation directory before changing `cwd`, or default the `run` subcommand's cwd to the container's `/framac-run`, and turn the `FileNotFoundError` into a diagnostic that prints the path it tried.

### Symptom: After an Eva Step Restart, a Finished Shard Misses Its Own Cache Entry and Is Recomputed

- **Seen on:** QCBOR v2.0-beta-1 run-2, 2026-11-23, module `libqcbor_a`, 8-shard plan. Shard 1 finished `ok` in 5177.1 s (2212 properties) under the old code. Its entry was published at `state/cache/eva/5a/<key>/` at 14:18:57: all 8 files present with their manifest sizes, `schema` 1, `key` equal to the directory name. The driver then stopped the Eva step to pick up `03523de` and reran `gen` and `eva` at 14:19:46. Each `evashard-<mod>--<i>` rule (`templates/pipeline.mk`) deletes `shard<i>.json` and reruns `run_eva_slice.py`, relying on the content cache ("cached by content"). Shard 1 ran `frama-c` again instead of restoring, which redoes about 86 min of work.
- **What was checked:** the cached `key.json` `command` equals the new shard 1 `frama-c` command token for token once output paths are masked as `<out>/...` (the case list `-DFRAMAC_EVA_SHARD_CASE_*` included). `sources` and `cwd` are the same, and all 140 `deps` digests still match the files on disk. So either the new run computed a different key from material that `key.json` does not show (`timeout_fallback`, `security_props`, or a changed dependency list), or `lookup`/`restore` in [`../../scripts/cache.py`](../../scripts/cache.py) returned nothing.
- **Cause (confirmed 16:10):** the recomputed shard 1 finished `ok` at 16:04 (6055.8 s, the same 2212 properties and 255 Unknown) under a **different** key: `16c21665...` against the first run's `5a64409b...`. The two entries' `key.json` files are identical (same `command`, `cwd`, `deps`, `kind`, `sources`). The difference is outside `key.json`: `make_key` in [`../../scripts/cache.py`](../../scripts/cache.py) hashes the material together with `scripts_digest()`, the sha256 of **every file under `scripts/` and `templates/`**. Commit `03523de` changed `scripts/resources.py`, `scripts/eva_shards.py`, `scripts/pipeline_make.py` and `templates/pipeline.mk`, none of which changes what Eva computes, so every Eva cache key changed. The wrappers bind-mount `scripts/` and `templates/` live from the checkout, so any commit to them during a run invalidates every cached result the run has made. The next step that relies on the cache redoes the work (here 101 min of shard 1, after 86 min the first time).
- **Status:** **Open pipeline gap** (design: coarse invalidation; not patched). Options: key Eva entries on the files that can change an Eva result (`run_eva_slice.py` and the modules it imports, `templates/fc_stubs`, `templates/acsl`) instead of the whole tree; or record the scripts digest in `key.json` and fall back to an entry whose only difference is the digest of files outside that set. Workaround: do not commit to `scripts/` or `templates/` of the checkout a live run mounts before restarting a cached step; make fixes in a worktree and restart after the step has finished.
