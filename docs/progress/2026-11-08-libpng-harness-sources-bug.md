# Bug report: `generate_harness.py` builds wrong source lists on libpng

Date: 2026-11-08 · Pipeline commit: `4c3b657` (phase1-remediation) · Profile: standard
Target: libpng `a70313dbb` (CMake, LF checkout) · Run: `~/framac-pipeline/libpng/run-2`

## Summary

Phase 0 stops at Step 4 (harness generation). For libpng, `generate_harness.py` writes harnesses whose
`sources` cannot be compiled and linked as intended, and the auto-prelude is skipped. Two symptoms, possibly
two causes. Nothing downstream (reach gate, ledger seed, build-check, fuzz, Eva) has run.

## Environment / state at failure

Phases done before the failure, all clean: `build_capture.py run` (status ok), `phase0_model.py run`
(11 units `ok`, 1081 functions, 2892 edges, no GCC fallback), `build_callgraph_dag.py`, `security_props.py run`
(no threat model, Layer 3 only). `seed_harvest.py record` returned `no_test_units` (see "Related").

DAG modules: 8 executables (`png_fix_itxt`, `pngfix`, `pnggetset` [Tier 3], `pngimage`, `pngreadend`,
`pngstest`, `pngtest`, `pngunknown`, `pngvalid`) plus 9 sub-modules of the unit `libpng18_a`
(`libpng18_a__png`, `__pngwutil`, `__pngwrite`, `__pngset`, `__pngget`, `__pngget_2..5`).
`libpng18_a` itself is not an entry in `callgraph_dag.json["modules"]`; only its sub-modules exist.

## Symptom 1 — executable harness pulls in every other executable's source

Command:

```
generate_harness.py --module pngfix --sources contrib/tools/pngfix.c --entry-fn main --max-size 1500 \
  --cppflags='-Iworkspace/work -Iworkspace/work/build -Iworkspace/work/contrib/tools' --out-dir workspace/harnesses
```

Expected `sources`: `["contrib/tools/pngfix.c"]` (the module's `required_sources`).

Actual `sources`:

```
contrib/tools/pngfix.c
workspace/work/contrib/libtests/pnggetset.c   pngimage.c   pngreadend.c   pngstest.c   pngunknown.c   pngvalid.c
workspace/work/contrib/tools/png-fix-itxt.c
```

Seven other programs, each defining its own `main`, end up in one harness. With `-Dmain=__framac_target_main`
applied to all of them this cannot link (duplicate symbols), and it would analyse unrelated code.

Facts gathered:
- `callgraph_dag.json` is correct for this module: `modules.pngfix.required_sources == ["contrib/tools/pngfix.c"]`,
  `functions["contrib/tools/pngfix.c#main"].module == "pngfix"`, `.lexer_module == "contrib"`.
- `lexer_modules` has **no** `contrib` entry, so the lexer-module override in `_merge_dag_harness_sources`
  ([scripts/generate_harness.py:1435](../../scripts/generate_harness.py)) does not explain the extra files.
  My first hypothesis (directory-grouped lexer module) is therefore **not supported by the data**.
- `main` is defined in 8 files, so the DAG keys are `file#main`; `_colliding_keys('main')` is the code path in
  play ([generate_harness.py:1376](../../scripts/generate_harness.py)). The extra files all contain a `main`,
  which points at the `main` identifier resolution (or another step that handles `argv` style), but I did not
  find the line that appends them. Not root-caused.

Suggested first check: run with the merge disabled (`--include-source` skips `_merge_dag_harness_sources`) and
diff the `sources`; then trace where else `sources` is extended for `entry_style == argv`.

## Symptom 2 — library cluster harness: inconsistent sources, prelude skipped

Command:

```
generate_harness.py --module libpng18_a__png --api --header workspace/work/png.h \
  --cppflags='-Iworkspace/work -Iworkspace/work/build' --max-size 1500 --out-dir workspace/harnesses
```

(a) Without `--header`, the call fails: `unresolved identifiers after automatic prelude resolution: png_uint_32`.
`--api` does not derive the unit's public header (`png.h`) on its own.

(b) With `--header`, `sources` come out as

```
png.c  pngmem.c  workspace/work/pngerror.c  workspace/work/pngread.c  workspace/work/pngwrite.c  workspace/work/pngwutil.c
```

Two entries lack the `workspace/work/` prefix the rest carry. The set equals `lexer_modules.png.required_sources`
(`png.c pngerror.c pngmem.c pngread.c pngwrite.c pngwutil.c`), i.e. the lexer module's closure, as the code
comment at line 1432 intends. `header` is recorded as `png.h`, not the path given.

(c) `prelude_status: skipped`, reason `clang fatal error: workspace/work/png.h:243:13: fatal error: 'pnglibconf.h'
file not found`. `pnglibconf.h` is generated by the build and lives in the snapshot
(`workspace/snapshot/generated/build`), which is not on the harness `cppflags`. The recorded cppflags also gained
`-Iworkspace/work/{arm,intel,mips,powerpc}`.

(d) `png_access_version_number` was chosen as `entry_fn` for a 12-case dispatch harness; harmless but arbitrary.

## Impact

Blocks Phase 0 for libpng (and likely any multi-executable CMake project). No harness can be trusted until fixed,
so no fuzzing, Eva or WP result exists for this run.

## Related observations (not blocking)

- `seed_harvest.py record` → `no_test_units` although a `test_command` is recorded. `pngtest`, `pngvalid`, etc.
  are not classed as test units: the name rule splits on `_ - .` only, so `pngtest` is one word. No seeds recorded.
- Target checkout had CRLF line endings (`core.autocrlf=true`), which broke libpng's `options.awk`. Worked around
  by re-checking out as LF. `build_capture` could detect `\r` in build scripts and say so in `diagnostics`.
- No `THREAT_MODEL.md`: trust from default rules only.
