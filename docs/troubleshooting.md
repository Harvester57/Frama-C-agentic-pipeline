# Troubleshooting Guide

Common issues encountered when running Frama-C (`RTE`, `Eva`, `WP`, `E-ACSL`) and Clang LibFuzzer on real-world C codebases, and how to resolve them.

If a symptom is not listed here, look it up in the upstream manuals in [`./references/README.md`](./references/README.md). Grep [`./references/INDEX.md`](./references/INDEX.md) or the manual itself, then read only the matching lines.

---

## 0. Frama-C 34 (Selenium) Upgrade Notes

Behavior changes since Frama-C 33 that the pipeline already accounts for:

- **Empty named behaviors are forbidden.** `behavior b: ;` in a function or statement contract is now a fatal `[kernel:annot-error] ... unexpected token ';'` (verified on the dev image). `acsl_ast.py` (`verify_acsl_only` / `find_empty_named_behaviors`) rejects them mechanically before splicing, and `run_wp_function.py` maps the kernel error to a repair hint.
- **ACSL clause order relaxed.** ACSL extensions may now precede `requires`, and `terminates`/`decreases` may sit anywhere between `requires` and `behavior` (verified: `assigns \nothing; terminates x > 0;` parses). The `exits`/`assigns`/`ensures` order is still enforced. The prover brief's recommended order remains valid.
- **Array-to-pointer decay removed in comparisons.** The kernel no longer implicitly converts an array to a pointer in `==`/`!=`/`<`/... comparisons, so array operands keep their array type. `kernel_ast_dump.ml` now matches both pointer and array operands when setting the `pointer_compare` feature.
- **New unsequenced-effect warnings (UB CC.35, upstream #@1219 fixed).** Local definitions with unsequenced side effects (e.g. `int x = i++ + i;`) now produce a `[kernel]` warning. Warnings do not change `-report-csv` statuses; no parser change needed.
- **Fine-grained `-rte-initialized` configuration fixed.** The option-hook bug that blocked per-function exclusion for `static` functions is fixed: `-rte-initialized=@all,-s` now emits zero initialization assertions for a `static` function `s` (verified with `-print` on the dev image). Prefer per-function exclusion over a global `--no-rte-initialized` (which is recorded in `reduced_checks`).
- **GCC machine modes partially supported.** `__attribute__((mode(<MODE>)))` is now converted to integer types (partial support), so targets using machine modes parse instead of failing with a syntax error.
- **`FRAMAC_TESTING` env var.** Frama-C 34+ exposes `FRAMAC_TESTING` (`Cmdline.inside_tests`) to mark test executions and guard extra verifications. Set it only for the repo's own test invocations of `frama-c`, never for production pipeline runs.
- **Base image is now 35.0~~dev (Bromine).** The pinned `framac/frama-c:dev` digest in the `Dockerfile` reports `35.0~~dev (Bromine)`. As of the master archive used for the upstream mining (2026-11-06), the Changelog's `<next-release>` section is still empty, so no 34→35 behavior changes need porting yet — but re-check `Changelog`/`Changelog_detailed.md` in the master archive on every base-image bump and port any `-`/`!` entries here. Upstream reference snippets mined from that archive live in [`./upstream/sources/`](./upstream/sources/README.md).

## 1. Phase 0: Build Capture, Frama-C Model & Gates

### Symptom: `"status": "needs_build_recipe"` (Exit Code 3 From `build_capture.py run`)
- **Cause:** the target's build failed, built no C file, or has no recipe. Phase 0 has no inventory without a build, so it stops here. The checkpoint keeps the same status until a capture succeeds.
- **Fix:**
  1. Read `diagnostics` in `workspace/reports/build_capture.json`: `first_error` with its context, `missing_headers`, `candidate_packages` (a heuristic from headers, pkg-config modules, CMake packages and commands) and `packages_not_installed`.
  2. Ask the user for a corrected command, packages or flags. Never record a recipe the user has not given or confirmed.
  3. Record it with `run_metadata.py set-build ... --package <pkg>` and rerun the capture with `-BuildImage -Scratch -TargetPackages "<pkgs>"` (`--build-image --scratch --target-packages`). A success clears the status.
- **Without a recipe at all:** `build_capture.py propose` prints one guessed from the build files, as a starting point for the user.

### Symptom: The Build Capture Times Out (1800 s) on a Build That Works by Hand
- **Cause:** a parallel build under `bear` can sit idle until the capture's timeout. Since `47d7c89`, a parallel build that fails **or times out** is retried once with one job on a fresh copy (`build.attempts` in `build_capture.json`), unless the recipe sets `MAKEFLAGS` or `CMAKE_BUILD_PARALLEL_LEVEL` itself. Only a serial build that also times out ends as `needs_build_recipe`. The retry gets a full new timeout, so the worst case is twice `--timeout`.
- **Fix:** rerun the capture through the broker (no `-NoBroker`), which sizes the build's jobs from its lease, or raise `--timeout` for a build that is just slow. If the recipe pins the parallelism through `MAKEFLAGS`, it gets no serial retry: drop it or set `-j1` yourself.

### Symptom: `build-check` Fails for Most Modules of a Target
- **nettle getopt (fixed, `scripts/build_callgraph_dag.py`, commit d71b255):** 9 executable modules failed with `lib/getopt.c:45: fatal error: gettext.h: No such file or directory`.
  - **Cause:** Frama-C parses with its own libc, which has no `__GLIBC__`; the build and every harness build use glibc. nettle's root `getopt.c` includes `lib/getopt.c` only when `ELIDE_CODE` is unset, and sets it under `__GLIBC__ >= 2`. The glibc build therefore compiled `getopt.c` to an empty object: in `build_capture.json` it has `headers: []` and `defined_functions: []`, and `lib/getopt.c` is no compiled source. The model took the other branch and put `_getopt_internal`, `getopt_long`, and the rest in `lib/getopt.c`. The DAG took `required_sources` from the model's defining files, so the argv harnesses compiled `lib/getopt.c` on its own.
  - **Fix:** a module's `required_sources` now hold only compiled sources (`compiles[].source`). Any other file becomes the compiled source whose `cc -M` list (`compiles[].headers`) includes it, or is dropped when none does. A function the real build does not define carries `model_only` with the reason, and the DAG lists these per file under `model_only_functions` with a warning. A function is marked when no compile compiles or includes its file, or when it is non-static and no object of its units defines it (statics are never marked: the compiler may inline them). Marked functions are never harness sources or reach-gate entry points (`harness_reach.built_entries`). Eva and WP may still analyse them; the ledger shows `bookkeeping.model_only` and REPORT.md lists them. `build_capture.py` now records `compiles[].probe_errors`, so an empty `headers` or `defined_functions` list is no longer confused with a failed probe. A capture that predates it trusts only non-empty symbol lists. `build_only_functions` no longer reports the functions of an included `.c` (nettle's `eccdata.c` including `mini-gmp.c`).
  - **Check:** after `build_callgraph_dag.py`, no `required_sources` names a file outside `compiles[].source`. Each `model_only_functions` warning names code only Frama-C's configuration compiles. Report it to the user: Eva and WP results there describe code the shipped binary does not contain.

### Symptom: A Unit's `parse.status` Is `gcc_fallback` in `phase0_model.json`
- **Cause:** Frama-C could not parse the unit with its build flags. Its functions and edges come from GCC's `-fcallgraph-info` instead, without loops, complexity, signatures or indirect-call candidates. `parse.error` holds Frama-C's first error, and the ledger flags the unit's functions (`bookkeeping.callgraph_fallback`).
- **Fix:** read `parse.error` and the log under `workspace/reports/phase0_model/`. The usual causes are the ones in Section 2 (host headers, compiler extensions); fix the cause, then rerun `phase0_model.py run`. Eva and WP will fail on that unit the same way until it parses. Fuzzing still works.

### Symptom: The Model Fails With the Dump Module (`kernel_ast.py` Compile Error)
- **Cause:** the image's Frama-C changed in a way `scripts/phase0_dump.ml` does not compile against.
- **Fix:** run `python3 /opt/framac-pipeline/scripts/phase0_model.py selftest`. The image build runs it too, so a Frama-C upgrade that breaks the dump module fails the image build first.

### Symptom: Every Unit Records `no_threat_model` (or `invalid_threat_model`)
- **Cause:** the target has no `THREAT_MODEL.md` with a fenced `framac-threat-model` JSON block (or the block does not validate against `schemas/threat_model.schema.json`).
- **Fix:** `python3 /opt/framac-pipeline/scripts/trust.py check-threat-model [PATH]` lists the errors (exit 2) or reports the missing block (exit 1). Put a corrected copy at `workspace/THREAT_MODEL.md` (it wins over the target's own), then run `trust.py run`, rebuild the DAG and rerun `security_props.py run`. Without a threat model, trust follows the default rules and only Layer 3 properties are generated.

### Symptom: The Reach Gate Fails (`harness_reach.py check` Exit 1, or `make` Stops at `reach-gate`)
- **Cause:** a harness does not reach one of its module's API entry points, a Tier 1A/1B/2 module has no harness (`no_harness`), or a harness changed after the check ran (its digest no longer matches `phase0_gates.json`).
- **Fix:** add a `--dispatch-case` per unreached entry point and rerun `check`, or record a reason with `harness_reach.py exempt` (`/framac-slice` Step 4b). A sub-module is checked only against the unit's entry points in its own scope; entry points no harness's scope holds are reported as the unit's gaps.

### Symptom: `dynamic: entry points never executed by the corpus` in `phase0_gates.json`
- **Cause:** after `coverage-<mod>`, `reach-dynamic-<mod>` found an entry point the gate holds the module to that no input executed. Fuzz and Eva of that module stop at the gate until it is fixed.
- **Fix:** read `executions: 0` in `workspace/reports/coverage/<mod>.json`. If the harness never calls the function, add a case. If it does, the corpus is stuck behind an input check: try, in order, recorded seeds, a dictionary (`params set --fuzz-dict`), a larger budget (`params set --fuzz-budget`), and a dispatch case that calls the function directly. The gap stays while the harness is unchanged.
- **Exemptions:** exempt only an entry point that cannot be driven from bytes (a live socket, a real file descriptor, process-global state). "30 s of fuzzing did not get deep enough" is not a reason: try the steps above first, and exempt only what still cannot be driven.
- **After a repair:** rerun the reach gate (`pipeline_make.py run reach-gate`) before rerunning the module. `build-<mod>` and `fuzz-<mod>` refuse a harness whose digest changed since the gate ran. A whole-run `reach-gate` exits 1 while another module still has a gap, but it still records this module's row.
- **No row for the module:** a module whose coverage could not be measured (coverage status `no_inputs`, `compile_error` or `coverage_error`, or no coverage report) gets no row. It is listed with its reason under `unmeasured` in `workspace/reports/harness_reach_dynamic.json`; `harness_reach.py dynamic` exits 2 and `reach-dynamic-<mod>` fails, but the gate is not reopened: fuzzing and Eva of the module continue. The usual cause is that every input crashes, so the corpus stays empty (qlz: a misaligned store at `quicklz.c:161`). Then the crash is the finding: verify it. There is nothing to repair in the harness, and the module's reach stays unmeasured; do not exempt entry points for it.

### Symptom: `llvm-cov` Fails With `truncated coverage data` in `workspace/reports/coverage/<mod>.json`
- **Cause:** a source includes a header inside a function body (CryptoLib `crypto.c:1674`, `#include <malloc.h>`). LLVM 19 then writes a coverage mapping `llvm-cov` cannot read.
- **Fix:** none needed. `run_eacsl_fuzz.py coverage` rebuilds once with those headers included first (`-include`), so the in-body include expands to nothing behind its include guard, and lists them in the report's `pre_included`. If the report still carries the error, no such header was found or one does not preprocess on its own with the unit's flags.

### Symptom: A Harness Misses a Build Flag (`-include config.h`, a Quoted `-D`, `-std=`)
- **Cause:** harnesses take the unit's flags from the DAG. The unit's `-include` files are kept apart (`force_includes`) and applied by `generate_harness.py`. Quoted `-D` values (`-DLOG_PATH="log.txt"`) and the build's `-std=` are not copied, because later stages split and re-join flag strings (and a C89 `-std` rejects the C99 harness).
- **Fix:** state such flags in the harness's `--cppflags` yourself.

### Symptom: A File Compiled by Several Units With Different Flags Is Analysed in One Configuration Only
- **Cause:** a source file belongs to the first unit that compiles it, with that unit's flags (qlz's four executables build `quicklz.c` with different settings).
- **Fix:** none automatic yet. To analyse another configuration, write a harness whose flags state it.

### Symptom: No Seeds, or a Harness Case Without Seeds
- **Cause:** the recipe has no test command; the tests call the API through header `static inline` functions or nested library calls, which the `-Wl,--wrap` recorders do not see; or the harness's case layout (overlapping slots, structs deeper than one `{ptr, len}` level) cannot be filled.
- **Fix:** read `workspace/reports/seed_harvest.json` and `workspace/reports/seeds/<mod>.json`. Seeds are an improvement, never a requirement: the campaign runs from its own corpus without them.

### Symptom: `seed_harvest.py record` Returns `no_test_units` Although the Recipe Has a Test Command
- **Cause:** only executables the name rule calls tests were relinked with recorders. libpng's `ctest` runs `pngtest`, `pngvalid`, `pngstest`, ..., none of which the rule recognizes (libpng `a70313dbb`, run-3; `docs/progress/2026-11-09-libpng-harness-generation-bugs.md`, defect D).
- **Fix:** **fixed** in `scripts/seed_harvest.py` (`record`): with a test command every executable is relinked and the test command decides which ones run; `test_units` still lists the ones named as tests, and `executables` lists all of them.

### Symptom: A Harness Line Like `break int main(void);`, or `too many arguments to function call, expected 0, have 2` on `main`
- **Cause:** the `main` prototype synthesizer read a statement keyword from a preceding macro continuation (`png-fix-itxt.c`'s `GETBREAK`) as the return type; and the default `argv` entry style calls `main(2, argv)` on a `main(void)` (libpng `pngfix-itxt`, `pnggetset`; defects B and C of the report above).
- **Fix:** B is **fixed** in `scripts/generate_harness.py`: preprocessor continuations are stripped and statement keywords cut from the head. C is handled by failing early (`_check_argv_entry`) with what to do: exempt the module with `harness_reach.py exempt`, or give `--entry-style` with `--call-expr`. **Open pipeline bug:** there is no stdin-fed entry style yet, so programs that read stdin cannot be harnessed.

### Symptom: `--api` Harness Fails With `unresolved identifiers after automatic prelude resolution: jmp_buf, FILE`, or Leaves Partial `harness_<mod>.{c,json}` After Exit 1
- **Cause:** the auto-prelude knew no header for standard-library names the target's headers use without including them; a failed generation left its half-written files, which `gen` and the reach gate can pick up; the case probe stopped at clang's 20-error cap, so more failing cases needed several rounds (libpng `pngwutil`, `pngset`, `pngget*`; defect E and "partial files" of the report above).
- **Fix:** **fixed** in `scripts/generate_harness.py` and `scripts/api_harness.py`: the prelude includes the standard header of such names (`_STD_HEADER_OF`); generation restores the previous harness files on any failure (`harness_files_kept_on_failure`) and fails on a harness that still does not compile after the prelude (`fail_on_compile_error`); the probe lifts the error cap and fails on errors outside the cases instead of dropping cases for them. **Open pipeline bug:** `--api` still does not default `--header` to the unit's `public_headers` from the build capture; give `--header` by hand.

### Symptom: Every `--api` Case of a Module Is Dropped (`no API case compiles`) on Opaque Handles (`png_const_structrp`)
- **Cause:** the generator declared an opaque struct, reached through a pointer typedef, as a by-value stack object (libpng `pngget*` clusters; defect A of the report above).
- **Fix:** **open, not re-verified on libpng.** `18bc5e9` (initializer calls for struct pointers, layout probing) may cover it; re-run Phase 0 Step 4 on libpng to check before closing.

### Symptom: Harness Linking Fails With `undefined reference to '<internal_helper>'` (e.g. `syscall_iterate`)
- **Cause:** `scripts/api_harness.py` collected source files defining only the public entry points called by the harness case, omitting internal helper translation units (e.g. `src/syscalls.perf.c` generated by gperf or auxiliary module sources) required by those API functions.
- **Fix:** **fixed** in `scripts/api_harness.py`. When building `--api` harness sources, the generator unions `dag.get("modules", {}).get(module, {}).get("required_sources")` into the harness compilation units so all internal helper sources of the module are linked into the harness binary.

### Symptom: A Generated Header (`config.h`) Is Missing in Eva, WP or the E-ACSL Build
- **Cause:** generated headers stay in the build tree on the scratch volume, and the later analyses read `workspace/work`, which holds only the target's source tree.
- **Fix:** **fixed** (`47d7c89`). The capture exports the headers the build generated to `workspace/snapshot/generated/` (`generated` in `build_capture.json`, `generated_dirs` in the snapshot manifest), and `target_env.with_include_flags` adds `-idirafter` for them to every Frama-C parse, the E-ACSL build, the harness probe and the sanitizer builds. If one is still missing, check that the run's capture predates `47d7c89` (rerun it) or that the header is listed under `generated`. Only as a stop-gap, copy it into `workspace/harnesses/include/`.

### Symptom: `needs_build_recipe` With `configure: error: cannot run /bin/bash ././config.sub` or `/bin/sh: 0: Illegal option -` (Windows Checkout)
- **Cause:** the target's working tree has CRLF line endings (`core.autocrlf=true`, or a `.gitattributes` `text` rule with the platform's native `eol`). `#!/bin/sh\r` or `#!/bin/sh -e\r` cannot run in the container, so `autogen.sh`, `config.sub`, `configure.ac`, `aclocal.m4` and every script fail. The git index is LF; only the checkout is wrong. Found on nettle (`file config.sub` says "with CRLF line terminators") and libseccomp (`autogen.sh` shebang triggers `/bin/sh: 0: Illegal option -`). This is a target-side checkout issue, not a pipeline defect.
- **Fix:** check the target out as LF, then start a **new run**: `git config --local core.autocrlf false`, `git config --local core.eol lf` (the `eol` setting is needed when `.gitattributes` marks files `text`), then `git rm -rq --cached . && git reset -q --hard` on a clean tree. The overlay of the earlier run holds the CRLF files and `workspace_overlay.py init` refuses a changed target, so do not resume it. Alternatively put a `sed -i 's/\r$//'` over the text files at the start of the recipe's command: the build runs in a copy, so the target stays untouched.
- **Check first:** `file config.sub configure.ac` (or `git ls-files --eol`) before the first capture on a Windows host.

### Symptom: `fatal error: elf.h: No such file or directory` or `linux/audit.h: No such file or directory` During Frama-C Model Parse
- **Cause (pipeline bug, fixed):** Frama-C parses with `-nostdinc`, so GCC does not search the system include directories (`/usr/include`, `/usr/include/x86_64-linux-gnu`). `build_capture.py` excludes libc and linux headers from the snapshot because they are present in the analysis container image. However, `augment_framac_cppflags` did not append the container's system include directories via `-idirafter`, making host system headers that `__fc_libc` does not define unreachable. Found on `libseccomp` run-2.
- **Fix:** `scripts/framac_common.py` (`augment_framac_cppflags`): appends `-idirafter /usr/include/x86_64-linux-gnu` and `-idirafter /usr/include` if they exist on the filesystem and are not already present. **Uncommitted** on `phase1-remediation` as of 2026-11-09. Verified on the analysis image: `<elf.h>`, `<linux/audit.h>` and `<linux/seccomp.h>` parse after Frama-C's libc, and without the two options `elf.h` is not found. (Frama-C's cpp runs with `-undef`, so `<linux/types.h>` skips its `__int128` typedefs.)
- **Caveats (open):** the headers come from the **analysis** image, not from the build image the target was built in, so `linux-libc-dev` versions can differ. The cleaner home is `target_env.py`, which owns the include order (the docstring of `augment_framac_cppflags` was not updated). The "already present" test is a substring test, so a flag such as `-idirafter /usr/include/foo` in the unit's flags suppresses `-idirafter /usr/include`. Functions declared only by these glibc headers have no ACSL contract: Eva lists them under `repair_hints`, WP marks them `unsound_proof`.

### Symptom: `User Error: Unable to compute offset .arr[i] in type struct s: Index is not constant`
- **Cause:** Frama-C's `<stddef.h>` (and gcc's, in E-ACSL host-header builds) defines `offsetof` as `__builtin_offsetof`, which the kernel folds to a constant at parse time. GCC also accepts a non-constant array index in the member designator (`offsetof(type, member[i])`); Frama-C aborts on it. Found on `libseccomp` (`src/arch.c:54`, `default_arg_offset(x)` is `offsetof(struct seccomp_data, args[x])`, used at `src/arch.c:267`). Frama-C limitation, candidate for an upstream report.
- **Rejected workaround:** the libseccomp run redefined `offsetof` for every target as `((size_t)&(((type *)0)->member))` in `fc_compat_types.h` (and in an untracked `templates/fc_stubs/eacsl/stddef.h`). Reproduced on the analysis image (Frama-C 35.0~~dev), 2026-11-09: the kernel no longer folds it (`(size_t)(& ((struct s *)0)->arr)` instead of `4UL`); Eva with `-warn-invalid-pointer` reports `\object_pointer(&((struct s *)0)->arr)` **invalid** and the function becomes `NON TERMINATING`; WP can no longer prove `\result == 4`; `_Static_assert` on an offset stops the parse. Both overrides are removed; `test_no_fc_stub_redefines_offsetof` keeps them out.
- **Fix (pipeline, uncommitted as of 2026-11-09):** new `scripts/fc_cpp_wrapper.py`, a gcc `-wrapper` that `augment_framac_cppflags` (model, Eva, WP, kernel AST) and `build_eacsl_flag_sets` (E-ACSL frontend only) pass to the preprocessor. After `cc1 -E` succeeds, it rewrites in the `.i` file only the `__builtin_offsetof(T, D)` whose designator has an index that is not an integer literal: `__builtin_offsetof(T, m[i])` becomes `(__builtin_offsetof(T, m) + (__typeof__(sizeof(0)))(i) * sizeof((((T *)0)->m)[0]))` (nested designators through `__typeof__`). Constant offsets stay folded, comments, literals and directives are untouched, the line count is kept, line markers gcc puts inside a system-header macro expansion are skipped, and each rewrite is logged as `[fc-cpp] <file>:<line>: offsetof with a non-constant index rewritten: ...`. Any failure leaves the output alone; `FRAMAC_CPP_REWRITE=off` disables it. Verified on the analysis image: Eva 0 alarms with `-warn-invalid-pointer`, WP 11/11 including `\result == 16 + 8*a`, the E-ACSL build and run pass (`test_frama_c_and_eacsl_accept_a_non_constant_offsetof_without_losing_precision`, `FRAMAC_DOCKER_TESTS=1`).
- **Caveats:** the wrapper is offered only on POSIX hosts where it is executable and its path has no space or comma (gcc and Frama-C split on them); commit it with mode 100755. The cache key covers it (keys hash all of `scripts/`).

### Symptom: `User Error: syntax error` on ioctl Invocations Passing Struct Types
- **Cause (pipeline gap, fixed):** Frama-C's `__fc_libc` `<sys/ioctl.h>` does not define the Linux ioctl encoding macros (`_IO`, `_IOR`, `_IOW`, `_IOWR`). `_IOWR(magic, nr, struct foo)` was then a call to an undeclared function with a type-name argument: a syntax error. Found on `libseccomp` (`src/system.c:522`).
- **Fix (uncommitted as of 2026-11-09):** `templates/fc_stubs/fc_compat_types.h`, in the `__fc_libc` branch only (E-ACSL builds take glibc's own `<asm-generic/ioctl.h>`, so no redefinition warnings): the generic-layout `_IOC*` constants, `_IOC`, `_IOC_TYPECHECK`, `_IO`/`_IOR`/`_IOW`/`_IOWR` and the `_IOC_DIR`/`_IOC_TYPE`/`_IOC_NR`/`_IOC_SIZE` decoders, guarded by `#ifndef _IOC`. Listed under "Libc contract overrides" in `templates/fc_stubs/README.md`. A `-I` override of `<sys/ioctl.h>` with `#include_next` is not an alternative: Frama-C puts its own libc `-I` before `-cpp-extra-args`, so the force-include is the only place. Values are x86_64's (generic layout); architectures with their own layout (powerpc, mips, sparc) would need theirs.

### Symptom: The Core Library Is `gcc_fallback` Because of a Build Variant Only the Compiler Accepts (nettle `fat-x86_64.c`)
- **Cause:** nettle's default build includes the runtime-CPU-dispatch ("fat") layer, whose `DEFINE_FAT_FUNC` macro expands to `return f(...)` inside `void` functions. GCC accepts it, Frama-C stops with `fat-x86_64.c:270: Return statement with a value in function returning void`. `libnettle.a` and `libnettle.so` then take the GCC call graph, which has **no signatures**: `generate_harness.py --api` cannot call any of its functions (`signature '' not understood`, 0 of 55 cluster harnesses), Eva and WP are blocked, and fuzzing falls back to the sanitizers.
- **Fix:** change the recipe so the analysed build is the portable one, with the user's confirmation: `./configure --disable-fat --disable-assembler`. The fix drops the dispatch layer and the assembly routines, so those code paths are not analysed; say so in the report. Then start a new run (capture, model, DAG). Look for the same pattern (`ifunc`, CPU-dispatch layers, `--disable-asm`/`--disable-assembler` flags) whenever a library's unit is `gcc_fallback` with a `return`-in-`void` or inline-asm error.

### Symptom: `--api` Says `no API entry point the generator can call: {}` for an Executable Module
- **Cause:** an executable's only API entry point is `main`, which `--api` does not drive (no signature it can fill from bytes).
- **Fix:** use the argv style: `generate_harness.py --module <m> --unit <unit> --sources <required_sources...> --header none --entry-fn main --entry-style argv --cppflags='<DAG cppflags>'`. Modules that take no attacker input (table generators such as nettle's `desdata`/`eccdata`, benchmarks) get `harness_reach.py exempt --module <m> --reason '<why>'`.

### Symptom: `--api` Skips Cases With `invalid application of 'sizeof' to an incomplete type` or `call to undeclared function`
- **Cause:** the harness was generated with `--header none`, so it includes no project header. The auto-prelude only searches for headers that define identifiers the module header uses, and there is none. Internal headers (`aes-internal.h`, `ghash-internal.h`...) are not found either. Found on nettle: 22 of 35 libnettle clusters failed outright and libhogweed skipped 109 cases.
- **Fix:** pass the headers explicitly, one `--extra-include <hdr>.h` each (the public headers of the unit and the internal ones its API uses), and regenerate. On nettle this took the gaps from 245 to 70.

### Symptom: `--api` Skips Cases With `pointer to an anonymous struct` (GMP `mpz_t`)
- **Cause:** `mpz_t` is `__mpz_struct[1]` with an anonymous struct, which the layout probe cannot fill. Every bignum API (RSA, DSA, ECC, PKCS#1, PSS, key parsers) is skipped and shows up as a reach gap (nettle libhogweed: 62 gaps after the header fix).
- **Fix:** write a dispatch sub-module by hand, which is the documented route for contracts the model does not know: a freely named sub-module (`libhogweed_a__mpz`) with `--scope-file` for the defining sources, `--entry-style dispatch` and one `--dispatch-case` per API family. Build the `mpz_t` values from `fuzz_buf` (`mpz_import`, `nettle_mpz_set_str_256_u`), initialise and clear everything, never `return`, and give sign/decrypt cases a fixed valid private key plus a deterministic random callback (a harness that violates the contract is rejected as harness-induced). A sub-module is checked only for its own scope, so the **unit's** harness still lists those entry points as gaps: record `harness_reach.py exempt --module <unit harness> --function <fn> --reason 'covered by sub-module <name>'` for exactly the functions the sub-module reaches, and check the sub-module's `entry_points_reached` equals its `entry_points`.

### Symptom: `validate_artifacts.py` Fails With `$.api_cases: one layout per dispatch case`
- **Cause (pipeline bug, fixed):** `api_harness.generate` drops the cases clang refuses, one probe round at a time, for at most `MAX_PROBE_ROUNDS` rounds. Clang stops after 20 errors by default, so a module with more refused cases than a few rounds can clear (nettle libhogweed: 88; `libnettle_a__sha256`: 5 more) ends with `api_cases` already filtered but `harness_<mod>.c` and `dispatch_cases` still holding a case that does not compile. The harness then fails to build, and the reach gate counted the broken case as reaching its function.
- **Fix:** `api_harness.probe_cases` lifts the error cap (`-ferror-limit=0` for clang, `-fmax-errors=0` for gcc), so one round finds every refused case, and the probe loop now runs until no case is refused (`MAX_PROBE_ROUNDS` is gone); the harness is rewritten after every drop, so the harness on disk and the sidecar always list the same cases (phase1-remediation `7b2a7ef`). If a run predates the fix, regenerate every sidecar the validator names. Expect the reach gate to report new gaps afterwards: the dropped cases never really reached their functions.

### Symptom: Seed Recording Records 0 Calls With a `make check` Test Command
- **Cause:** `seed_harvest.py record` relinks only the units it classifies as test executables (nettle: just `testsuite/sha1-huge-test`); a suite of many separate test programs built by `make check` is not instrumented, and header `static inline` calls are never recorded.
- **Fix:** the relink part is **fixed** (phase1-remediation `7b2a7ef`, `seed_harvest.py record`): with a test command every executable is relinked and the test command decides which ones run. Programs that `make check` builds only during the test run are not units of the capture, so they are presumably still not relinked (not re-verified on nettle); header `static inline` calls are never recorded. Seeds stay optional (see "No Seeds" above): fuzzing starts from its own corpus.

### Symptom: `build-check` Fails for Most Modules of a Target (nettle run-3: 39 `build_failed`, 2 `eacsl_fallback`, 5 `eacsl`)
Diagnosed on nettle (`./configure --disable-fat --disable-assembler`, Frama-C 35.0~~dev) from `workspace/harnesses/fuzz_<mod>.compile.log`. Five independent causes. The two E-ACSL build failures are fixed, `build-check` now names the two E-ACSL failures that have no source-level fix, and `lib/getopt.c` is fixed in the DAG (commits `9b3d2f3` and `d71b255`, details per bullet). The first four were reduced to minimal reproductions on the analysis image on 2026-11-09; none of the four has an upstream draft in `docs/upstream/` yet.

- **Fixed pipeline bug: `first_error` blamed memory or showed noise.** For the 19 `register` clusters and the two GMP modules, `build_check.json` showed `e-acsl-gcc: fatal error: aborted by Frama-C (Frama-C stopped without an error message: most likely killed for lack of memory)`, a false diagnosis: `[kernel] Failure: ...` and `[kernel] Unexpected error (...)` did not count as error lines, so only e-acsl-gcc's wrap-up matched. For `camellia256_set_decrypt_key` it showed GNU ld's `DWARF error: mangled line number section` (ld goes on linking after it) instead of the `undefined reference`. **Fix:** `pipeline_make._first_build_error` takes the first real error line of the last failed command (compiler, linker, `User Error`, `Failure:`, `Unexpected error`, `undefined reference`) and skips warnings and the ld DWARF lines. Failing that, it takes the start of an OCaml backtrace (`Raised at`). Only when e-acsl-gcc's `aborted by Frama-C` wrap-up is all that is left does the excerpt suggest a lack of memory. Checked against every failing run-3 log (commit `9b3d2f3`).
- **Fixed pipeline bug (E-ACSL): `Taking the address of a register variable with &[ i ]` (19 libnettle clusters, e.g. `libnettle_a__arcfour`, `arctwo`, `md5`, `sha256`).**
  - **Cause:** E-ACSL's full memory tracking, not the target. Under `-e-acsl-full-mtracking` (always on for fuzz builds), E-ACSL registers every local with `__e_acsl_store_block(&local, ...)`, and `Cil.mkAddrOf` aborts when the local is `register` (nettle `arcfour.c:78`, `register uint8_t i, j;`). Reproduced: a plain `register unsigned i` loop counter parses in the kernel and instruments without `--full-mtracking`, and aborts with it. Every target with a `register` local is hit. E-ACSL bug, candidate for an upstream report.
  - **Fix:** `eacsl_toolchain.build_eacsl_flag_sets(full_mtracking=True)` adds `EACSL_FULL_MTRACKING_DEFINES` (`-Dregister=`) to the E-ACSL frontend (`-E`) whenever `uses_full_mtracking` holds, that is for every two-stage build. The build report lists it in `compile.full_mtracking_defines` and the compile log says why. Removing `register` from a local whose address is never taken does not change its behaviour. The harness `--cppflags` never get it, because they also reach Eva and WP (a test checks that no other script or template carries it). A global register variable (`register T x asm("reg")`) would change meaning, but Frama-C does not parse those anyway. Verified in framac-analysis: the canary selftest passes, the reproduction builds and runs, and nettle `arctwo` now instruments and compiles from run-3's sources; it then stops at link time on the open data-table bug below (commit `9b3d2f3`).
  - **Run-3 note:** the `arcfour` sidecar in run-3 still carries the experiment `-Dregister= '-D_Alignas(x)='` in its cppflags. Frama-C runs the preprocessor through `sh`, which fails on the parenthesis (`sh: 1: Syntax error: "(" unexpected`, then `User Error: failed to run: gcc -E`). Regenerate that harness without both flags.
- **Fixed pipeline bug (upstream Frama-C printer): `error: expected ';' at end of declaration list` in `fuzz_<mod>.instrumented.c` (every cluster that includes `nettle-types.h`: `xts`, `version`, `umac_l2`, `poly1305_internal`, `chacha_poly1305`, and `arcfour` once the `register` error is gone).**
  - **Cause:** nettle writes `alignas(16) uint64_t u64[2];` inside `union nettle_block16` and `struct aes128_ctx` (valid C). Reproduced with plain `frama-c -print`: the kernel prints `uint64_t u64[2] _Alignas(16) ;`, with the specifier after the declarator, which clang rejects. Frama-C prints the alignment of struct/union members in the wrong place (also `char c _Alignas(_Alignof(uint64_t)) ;` and, before other attributes, `uint64_t x _Alignas(16)  __attribute__((__unused__));`). Globals and locals print it before the declarator, which is valid. The E-ACSL output inherits the members' form.
  - **Fix:** `eacsl_toolchain.rewrite_trailing_alignas`, run between the two E-ACSL stages in `run_eacsl_fuzz.py` like `compile.formal_inits`. It turns an `_Alignas(N)` that ends a declarator (only attributes, then `;`, `,` or `=`, follow it) into `__attribute__((__aligned__(N)))`, which clang accepts after the declarator and which keeps the alignment. Frama-C prints an `aligned` attribute in that place itself. The build report counts the rewrites in `compile.alignas_rewrites`. Verified in framac-analysis: `_Static_assert(_Alignof(union blk) == 16, "")` holds on the rewritten file, the reproduction runs, and nettle `xts` and `chacha_poly1305` now compile from run-3's sources (3 and 2 rewrites); they then stop at link time on the open data-table bug below (commit `9b3d2f3`). Never use `-D_Alignas(x)=`: it drops the 16-byte alignment, changes the layout of the instrumented build, through the harness `--cppflags` would also change Eva's alignment checks, and breaks Frama-C's preprocessing command (see the run-3 note above). The printer bug is still to be filed upstream.
- **Open pipeline bug (E-ACSL), now named by `build-check`: `E_ACSL__Rtl.Symbols.Unregistered("__gmpz_clear")` (`libhogweed_a`, `libhogweed_a__mpz`).**
  - **Cause:** two conditions together. The target includes `<gmp.h>` (which declares `__gmpz_*`), **and** E-ACSL emits GMP code of its own for an assertion or RTE check whose integer range exceeds 64 bits (e.g. `a * b` on two `unsigned long`). E-ACSL then cannot find its own `__gmpz_clear` in its runtime symbol table. Reproduced: `<gmp.h>` with `mpz_*` calls alone instruments fine, as does the GMP-needing assertion without `<gmp.h>`; together they abort. Status shows as `build_failed` for the unit and `eacsl_fallback` for the mpz sub-module. E-ACSL bug, candidate for an upstream report.
  - **What build-check does:** no source-level fix exists (E-ACSL's GMP use cannot be turned off). The row gets `reason_code: eacsl_gmp_symbol_unregistered`, a `reason`, and as `next_step` the exact command, `python3 $S/pipeline_make.py params set --module libhogweed_a --fuzz-engine sanitizers`; the `fuzz-<mod>` gate message repeats it. The module still fails until someone runs the command: `build-check` never switches engines itself (commit `9b3d2f3`, `pipeline_make.KNOWN_EACSL_FAILURES`).
  - **Workaround:** run that command (and the same for `libhogweed_a__mpz`), then rerun `build-check`, which accepts a recorded sanitizers choice. The module loses the E-ACSL checks (sub-object overflow, `\initialized`), and the report must say so. Eva and WP are unaffected.
- **Open pipeline bug (E-ACSL), now named by `build-check`: `block-internal.h:49: implicit cast: cast from union nettle_block16 to void *` (`libnettle_a__sm4` as `eacsl_fallback`; `ccm`, `gcm`, `gcm_2`, `gcm_camellia128`, `drbg_ctr_aes256`, `twofish` through `block-internal.h`, and `aes128_set_decrypt_key`, `nist_keywrap` through `ocb.c:61`, `cmac_2` through `cmac.c:54`, all `build_failed`).**
  - **Cause:** a **`static const` union** (`static const union nettle_block16 zero_block;` in `block16_zero`, `ocb_set_key` and `cmac128_set_key`), initialized or not, local or at file scope. Reproduced: `= {{0}}` fails too, and so does the same declaration at file scope. A `static const` struct and a non-`const` `static` union (local or file scope) instrument fine. The rejected cast comes from E-ACSL's handling of that variable, not from the kernel (`frama-c -print` is clean). E-ACSL bug, candidate for an upstream report.
  - **What build-check does:** the row gets `reason_code: eacsl_static_const_union`, the `reason` and the `params set --module <mod> --fuzz-engine sanitizers` command as `next_step`, as for GMP above, and the module still fails until someone records the choice.
  - **Workaround:** none from flags; run the `next_step` command. Moving the variable to file scope does not help. A shadow-tree patch that drops `const` from that one declaration instruments. The object is still zero and never written, but E-ACSL then no longer treats it as read-only; state it in the report.
- **Fixed pipeline bug: `lib/getopt.c:45: fatal error: gettext.h: No such file or directory` (9 executable modules: `base16dec`, `base16enc`, `base64dec`, `base64enc` and the tools).** Fixed in `scripts/build_callgraph_dag.py` (commit `d71b255`); see the nettle getopt entry in Section 1. The nettle harnesses of run-3 must be regenerated to pick it up.
- **Open pipeline bug: `undefined reference to '_nettle_aes_encrypt_table'` / `'_nettle_camellia_table'` at link time (`camellia256_set_decrypt_key` in run-3; `xts`, `arctwo`, `chacha_poly1305` once the `register` and `_Alignas` fixes let them compile).**
  - **Cause (partly diagnosed):** the harness sources lack the file that defines a constant **data** table (nettle `aes-encrypt-table.c`, `aes-decrypt-table.c`, `camellia-table.c`). `run_eacsl_fuzz.build_module_binary`'s link repair maps undefined symbols to files through the DAG, which knows functions only: for `xts` it added the AES function files and then stopped on the tables. ## 2. Frama-C Kernel Parsing & Preprocessing Errors

### Symptom: `[kernel] user error: syntax error` on GCC/Clang Intrinsics or System Headers (`_Float128`, etc.)
- **Cause:** The target C file or its `-I` flags pulled in host `/usr/include` headers containing glibc/compiler-specific extensions (`_Float128`, `__builtin_va_arg_pack`, inline assembly `__asm__`, or SIMD intrinsics) instead of Frama-C's standard library (`__fc_libc`).
- **Fix:**
  1. Never pass `-I/usr/include` or `-I/usr/local/include` in harness flags. Frama-C must use its portable `__fc_libc` headers: the target's own system headers reach it from the snapshot through `-idirafter`, searched after Frama-C's libc.
  2. If the target requires third-party system headers (e.g., `<bsd/string.h>`, `<openssl/evp.h>`), add the `-dev` package to the build recipe and rerun the build capture (`--build-image --target-packages "<pkg>"`, `-BuildImage -TargetPackages` in PowerShell). The capture copies the headers and libraries to the run's snapshot (`workspace/snapshot/`), and the analysis image reads them from there (`-idirafter`, after Frama-C's libc). The analysis image itself never gets target packages. Check `snapshot.headers` in `workspace/reports/build_capture.json`.
  3. Ensure `-machdep gcc_x86_64` (already the default in `run_eva_slice.py`, `run_wp_function.py`, and `run_eacsl_fuzz.py`, which every Make recipe calls) is active so GNU C extensions supported by Frama-C are enabled.
  4. Guard hardware inline assembly or unsupported compiler intrinsics with `#ifndef __FRAMAC__ ... #else ... #endif` in the `workspace/work/` shadow tree.

### Symptom: `[kernel:annot-error] unbound logic variable alse` or `orall`
- **Cause:** An ACSL annotation containing `\false`, `\forall`, `\at`, or `\base_addr` was written through an unescaped Python or shell string, turning `\f` into ASCII `0x0c` (form-feed), `\a` into `0x07`, or `\b` into `0x08`.
- **Fix:** Always use raw Python strings (`r"..."`) or file-editing tools when writing ACSL annotations. `acsl_ast.py` (`check-acsl-only`) automatically flags control characters (`\x07`, `\x08`, `\x0c`) inside ACSL comments.

## 3. E-ACSL + LibFuzzer Build & Runtime Issues

### Symptom: `e-acsl-gcc` Fails on `__fc_builtin.h`, `__fc_libc/stdlib.h` (`\old(endptr)`), or Unknown Legacy Flag `--rte=`
- **Cause:**
  1. `e-acsl-gcc` runs `frama-c -no-frama-c-stdlib` so its second pass can compile `instrumented.c` with host `clang` against host glibc. If a harness guards `#include "__fc_builtin.h"` only with `#ifdef __FRAMAC__`, `e-acsl-gcc` enters that block and fails because `__fc_builtin.h` is not on the host include path, and host `<math.h>`/`<stdlib.h>` expose `_Float128` prototypes on glibc >= 2.26.
  2. Frama-C 33+ installs `e-acsl-gcc` (no `.sh`). Its `-h` lists only the short flags (`-F`, `-G`, `-E`, `-e`, `-l`, `-n`, `-C`, `-M`), though long options such as `--rte=all` are still accepted. Running `-rte` across all functions without `-rte-select` instruments unused inline helpers.
- **Fix:** `harness_dual.c.template` guards `#include "__fc_builtin.h"` and `eva_main()` with `#if defined(__FRAMAC__) && !defined(__FRAMAC_EACSL__)`, and `run_eacsl_fuzz.py` automatically passes `-D__FRAMAC_EACSL__ -D_Float128=double -U__SIZEOF_INT128__` (host `<linux/types.h>` declares `__int128` typedefs, which Frama-C rejects, only when that macro is defined) along with `-rte-select` and `-e-acsl-functions` scoped to the functions defined in the target slice `.c` files. Full compiler diagnostics are saved to `<out-bin>.compile.log`. If `e-acsl-gcc` still fails in `campaign` mode, `--engine auto` falls back to native `clang -fsanitize=fuzzer,address,undefined`.

### Symptom: `frama-c` (Eva / WP) Cannot Find `<bsd/string.h>`, `<json-c/json.h>`, `<netinet/ip_icmp.h>`, or `__int32_t`
- **Cause:** `frama-c` runs with `-frama-c-stdlib` (`-nostdinc`), searching only `__fc_libc` and explicit `-I` flags so host `/usr/include` does not shadow `__fc_libc`.
- **Fix:** `run_eva_slice.py` and `run_wp_function.py` automatically append `-I/opt/framac-pipeline/templates/fc_stubs -include fc_compat_types.h`, providing bodyless ACSL-annotated prototypes for `bsd/string.h`, `json-c/json.h`, `netinet/ip_icmp.h`, and glibc `__int8_t`..`__uint64_t` typedefs while keeping external specifications `Considered valid` (`STATUS_ASSUMED`) in the ledger.

### Symptom: Selftest `compiled: false` With `undefined reference to 'main'` / `fail to compile/link un-instrumented code`
- **Cause:** by default `e-acsl-gcc` instruments **and** links the original sources. A libFuzzer harness has no `main()`, so that link fails and `e-acsl-gcc` exits 1, even though the instrumented file was written.
- **Fix:** `run_eacsl_fuzz.py` passes `-n` (instrument only) in stage 1.

### Symptom: Every Input Crashes in `shadow_alloca` (`e_acsl_segment_tracking.c`), or Valid Stack Accesses Fail `\valid`
- **Cause:** E-ACSL initializes its runtime at the top of `main()`, and a harness has none. Without full memory tracking, its memory analysis leaves a caller's stack buffer untracked, so a callee's valid write fails `\valid`. With full tracking but no runtime initialization, the runtime segfaults on the first tracked stack block.
- **Fix:** automatic. Fuzz builds use `-e-acsl-full-mtracking` and link [`../templates/eacsl_runtime/fuzz_init.c`](../templates/eacsl_runtime/fuzz_init.c), whose `LLVMFuzzerInitialize` calls `__e_acsl_memory_init` and `__e_acsl_globals_init`. Do not define `LLVMFuzzerInitialize` in a harness (`reason: eacsl_init_hook_conflict`). The selftest's `benign_input_clean` check catches either regression.

### Symptom: E-ACSL Reports `rte: initialization` on Benign Inputs
- **Cause:** E-ACSL builds pass `-rte-initialized @all`, so every read must be of initialized memory, and memory written outside instrumented code is never marked initialized. The usual culprits:
  1. target code reads libFuzzer's `data` directly instead of the harness copy `fuzz_buf`, for example in a hand-written or `custom` harness;
  2. an external library behind `fc_stubs` fills a buffer;
  3. `read`/`recv` fill a buffer.
- **Fix:**
  - Pass `fuzz_buf` (generated harnesses do), or copy the input into the harness's own buffer with `memcpy`, which E-ACSL marks initialized.
  - If a library-filled buffer is the cause, initialize it before the call (`= {0}` / `memset`) or rerun with `--no-rte-initialized`. That opt-out is recorded in `reduced_checks`, and Eva still reports uninitialized reads statically.
  - Per-function exclusion (`-rte-initialized=@all,-f`) works for `static` functions too since Frama-C 34 (option-hook bug fixed; in Frama-C 33 it only worked for non-`static` functions).
  - The crash verifier classifies such reports as `harness_induced`.

### Symptom: Every Input Fails `\initialized(&__retres)` in a `__gen_e_acsl_<fn>` Wrapper
- **Cause:** an E-ACSL gap in Frama-C 33. The wrapper that checks a function contract registers its `__retres` with the runtime but never marks it initialized after `__retres = <fn>(...)`. Under `-rte-initialized`, any `ensures` that reads `\result` then fails on the first input.
- **Fix:** automatic. Between instrumentation and compilation, `run_eacsl_fuzz.py` inserts the missing `__e_acsl_initialize` after each such assignment; the build report counts them in `compile.wrapper_result_inits`. This is sound, because the callee's own return value is still checked for uninitialized reads. A report of this failure means the build ran without that step: rebuild it, and never weaken a contract to get past it.

### Symptom: Every Call Fails `\initialized` on a Formal Parameter (`\initialized(&s.len)`, often at a Function's First Statement)
- **Cause:** an E-ACSL gap, reproduced on Frama-C 35. Each function registers its formals with `__e_acsl_store_block` but never marks them initialized, although the caller has just written them. Under `-rte-initialized`, the first read of a by-value struct field, or of a scalar formal through its address, fails whatever the caller passed. The assertion is blocking, so nothing after it in that function is ever checked. In QCBOR run-5, 13 of 29 crash candidates were this artifact, and it hid a real signed overflow a few lines below one of them.
- **Fix:** automatic. Between the two stages, `run_eacsl_fuzz.py` inserts `__e_acsl_full_init` after each formal's registration; the build report counts them in `compile.formal_inits`, and the selftest canary reads a by-value struct and an address-taken scalar formal on every input. Locals are untouched, so uninitialized locals are still reported. The cost: E-ACSL no longer reports a struct passed by value with uninitialized members. A report of this failure means the build ran without that step: rebuild it rather than using `--no-rte-initialized`. Upstream report (draft, not filed): [`frama-c-eacsl-formal-params-initialized.md`](./upstream/frama-c-eacsl-formal-params-initialized.md).

### Symptom: `implicit cast: cannot cast from __e_acsl_mpz_t to size_t` (E-ACSL silently in GMP-only mode)
- **Cause:** `e-acsl-gcc` splits the values of `-e`/`-E`/`-F`/`-l` on spaces and re-parses the tokens. A standalone `-g` inside `-e` is read as its own `--gmp` option (`-e-acsl-gmp-only`).
- **Fix:** `run_eacsl_fuzz.py` normalizes every passthrough value: `-g` becomes `-gline-tables-only`, `-I dir` becomes `-Idir`, and other standalone single-letter tokens or paths with spaces are refused (`reason: eacsl_argv_unsafe`). `run_eacsl_fuzz.py selftest` checks that the compile log never contains `-e-acsl-gmp-only`.

### Symptom: Campaign Reports `engine_used: eacsl` but E-ACSL Never Fires, or the Guardrail Always Passes
- **Cause:** `e-acsl-gcc -O <out>` writes the instrumented executable to `<out>.e-acsl`; `<out>` is a plain build.
- **Fix:** the script selects `<out>.e-acsl` and refuses any binary without E-ACSL instrumentation (`reason: eacsl_binary_not_instrumented`). The guardrail refuses uninstrumented binaries (`guardrail_error`) instead of reporting `passed_dynamic_oracle`.

### Symptom: `redefinition of 'timeval'` / `'timespec'` or Conflicting `fd_set` Types When Compiling the Instrumented File
- **Cause:** the instrumented file printed by Frama-C is self-contained (it has no `#include` lines and already contains every typedef). Force-including headers that pull in host system headers into its compile duplicates those typedefs.
- **Fix:** `run_eacsl_fuzz.py` builds in two stages. All preprocessor flags (`-I`, `-D`, `-include`) go to instrumentation (`-E`) only; the instrumented file is compiled with codegen flags only (`e-acsl-gcc -C -e ...`). `fc_compat_types.h` is empty whenever `__FRAMAC__` is undefined. Boundary stub headers need no E-ACSL-specific branches.

### Symptom: `syntax error` on `__int32_t`, `u_short` (E-ACSL Host-Header Mode)
- **Cause:** E-ACSL runs Frama-C with `-no-frama-c-stdlib`, so the glibc-internal and BSD aliases must come from host headers.
- **Fix:** in host-header mode `fc_compat_types.h` includes glibc `<sys/types.h>`, so the aliases are identical to glibc's by construction. Do not hand-write `__intN_t` typedefs: `__int64_t` is `long` on LP64 and `long long` on ILP32.

### Symptom: `undefined reference to 'open_fallback_N'` at Link Time
- **Cause:** in host-header mode, the Variadic translation emits `<fn>_fallback_<N>` for variadic calls without a libc specification (`open`, `fcntl`, `ioctl`, ...), and the E-ACSL RTL does not define them.
- **Fix:** automatic. The script generates `<out-bin>_fallbacks/eacsl_fallbacks.c`, which forwards to the real function (or fails with `ENOSYS` when the signature or header is unknown, recorded as `mode: enosys`), compiles it to a link-only object, and retries the link once. Never add these definitions to the instrumented sources: each definition shifts the fallback numbering. `--no-variadic-translation` passes `-no-variadic-translation` to Frama-C instead (no fallbacks are emitted).

### Symptom: `call to undeclared function 'X'` or `invalid application of 'alignof' to an incomplete type`
- **Cause:** a [`../templates/fc_stubs/`](../templates/fc_stubs/) header lacks a prototype the target calls, or declares an opaque handle (`struct json_object`) as incomplete. E-ACSL emits `alignof` on pointed-to types.
- **Fix:** add the prototype and complete the handle with a single dummy member (see [`../templates/fc_stubs/README.md`](../templates/fc_stubs/README.md)). Tool JSONs list missing prototypes under `undeclared_functions`. For Eva/WP this is a soundness issue: Frama-C invents `int X()`.
- **Target-specific compat headers** (e.g. completing OpenSSL 3 opaque handles `EVP_PKEY`, `BIGNUM`, ... for the fuzz build) must be delivered **source-side**: pass them to `generate_harness.py --compat-include <header>` so the harness `#include`s them after the module header. Never add them to cppflags as `-include`: force-including a header that pulls in system headers re-registers libc properties per merged translation unit and the Frama-C kernel aborts with `trying to register twice property 'assumes nonnull_p'`.

### Symptom: Instrumentation Aborts With `no function 'X'`
- **Cause:** `-rte-select` / `-e-acsl-functions` named a function that is absent from the parsed AST (disabled by `#if`, or in a file that failed to parse).
- **Fix:** function discovery runs on preprocessed sources. Names Frama-C still rejects are dropped once and listed in `rte_select_dropped`.

### Symptom: A Crash Reproducer Is Large or Hard to Read
- **Fix:** `python3 /opt/framac-pipeline/scripts/pipeline_make.py run minimize` runs cvise (installed in the container image) on every unverified candidate's reproducer, under the sandbox, accepting only variants that still crash with the same fingerprint. Each crash artifact gets a `<artifact>.min` sibling; `workspace/reports/minimize/index.json` maps fingerprints to the reports. Crash verifiers should replay the `.min` first (`skills/framac-wp/crash_verifier_brief.md`).

### Symptom: E-ACSL Crash With `failure: null` or a Location Inside the E-ACSL Runtime (`unsafe_initialize`)
- **Cause:** heap corruption made the E-ACSL RTL crash before it printed the failing assertion.
- **Fix:** automatic. The crash input is replayed on a sanitizer build of the same slice; `attribution` and `failure_source: sanitizer_replay` give the precise file:line. The crash is still classified from the E-ACSL run.

### Symptom: Why Not `-L` / Frama-C's libc for E-ACSL?
- E-ACSL aborts on Frama-C libc specifications (`unbounded ranges are not part of E-ACSL`, `share/libc/string.h`). Host-header mode is the only supported E-ACSL mode.

### Symptom: Linker or Shadow Memory Conflict When Combining E-ACSL with AddressSanitizer (`-fsanitize=address`)
- **Cause:** E-ACSL embeds its own shadow-memory runtime (`rtl`) to track byte-level pointer validity (`\valid`), initialization (`\initialized`), and sub-object bounds. AddressSanitizer (`ASan`) also maps shadow memory and intercepts `malloc`/`free`. Running both in the same binary causes immediate `mmap` collisions or false aborts.
- **Fix:**
  - Compile E-ACSL fuzz binaries with `-fsanitize=fuzzer` **without** `-fsanitize=address` (as configured in `run_eacsl_fuzz.py`). E-ACSL's own runtime already detects out-of-bounds accesses, use-after-free, bad free, uninitialized reads, and sub-object overflows.

### Symptom: `e-acsl-gcc` Rejects Complex Unbounded Quantifiers (`\forall integer k; ...`)
- **Cause:** E-ACSL can only compile **bounded** quantifiers where the lower and upper bounds of the quantified integer variable `k` are syntactic integer expressions (e.g., `\forall integer k; 0 <= k < len ==> ...`).
- **Fix:** Always write explicit integer lower and upper bounds in `\forall` and `\exists` predicates (`0 <= k < n`), and use the `integer` type (or `size_t` / `int`) explicitly.

### Symptom: Wrapper Exits With Code 2: `-NoInnerSandbox` / `--no-inner-sandbox` (or `-AllowDegradedSandbox` / `--allow-degraded-sandbox`) "is no longer supported"
- **Cause:** The bubblewrap layer was removed. The hardened container, with Docker's default seccomp and AppArmor profiles, is the only isolation boundary, and target-controlled binaries run under [`../scripts/sandbox_exec.py`](../scripts/sandbox_exec.py) (rlimits, env allowlist, timeout). The legacy flags fail hard rather than being silently ignored.
- **Fix:** Remove the flag from the command line or script. No replacement flag is needed.

### Symptom: LeakSanitizer Reports `LeakSanitizer has encountered a fatal error` or `LeakSanitizer does not work under ptrace`
- **Cause:** LeakSanitizer (enabled by default with `-fsanitize=address` in the native LibFuzzer fallback) uses `ptrace` to stop threads while scanning. Docker's default seccomp profile allows `ptrace` on kernels >= 4.8; older hosts block it.
- **Fix:** Do not relax seccomp. Set `ASAN_OPTIONS=detect_leaks=0` (or pass LibFuzzer `-detect_leaks=0`) for the campaign and record in the run notes / agent result that leak detection was disabled, so missing leak coverage is visible.

## 4. Eva Abstract Interpretation Precision Issues

### Symptom: Eva Reports High `Unknown` (Orange) Alarm Counts (> 30%) on a Module Slice
- **Cause:** Loop widening or path merging occurred before precision could stabilize, or an external helper function had no ACSL contract (`builtins:missing-spec`).
- **Fix:**
  1. Check `workspace/eva/<mod>/eva.log` for `missing-spec` warnings. Add a contract stub to `external_stubs.h` for any unmodeled external function so Eva does not widen its return value to `[-inf, +inf]`.
  2. Run `pipeline_make.py run eva-tune`, then read `tuning` in `workspace/reports/eva/<mod>.json`. It tries slevel, unrolling and the other precision options as a fixed ladder, and says what helped and why any run was rejected ([`./resources-and-caching.md`](./resources-and-caching.md), Section 6). If nothing helped, look at the harness: a symbolic input length, for one, leaves every option with the same Unknowns.
  3. For a small fixed-bound parsing loop the ladder did not settle, add `//@ loop unroll 32;` above it in `workspace/work/`. Do not write `loop pragma UNROLL`: the kernel rejects it and the run fails.

### Symptom: An Eva Run Is Slow (or Hangs) on a Module Slice
- **Fix:** first read `cost_profile` and `timeout_fallback` in `workspace/reports/eva/<mod>.json`. `cost_profile` lists the five functions with the largest share of the run's time on their own (`self`) and with their callees (`inclusive`), read from `flamegraph.txt`; `timeout_fallback` names the cheaper settings a timed-out run was retried with (less precise: more Unknowns). Tune (Step 2a of `/framac-eva`) or stub the functions it names. To see more, the module's base and plain Eva runs write `workspace/eva/<mod>/flamegraph.txt` (`-eva-flamegraph`; tuning rungs and loop trials skip it, and a tuned module publishes its base run's profile when the report rests on a rung). Render it to `flamegraph.svg`/`flamegraph.html` with `python3 /opt/framac-pipeline/scripts/pipeline_make.py run flamegraph-<mod>` (it renders the existing file and never re-runs Eva; or `scripts/eva_flamegraph.py --dir workspace/eva/<mod>`), then read the widest bars: they name the functions where Eva spends its time. Cross-check `workspace/eva/<mod>/nonterm.log` and the report's `nonterm` field (`workspace/reports/eva/<mod>.json`): a non-terminating loop is the usual cause of a hang, and `-eva-slevel`/`-eva-auto-loop-unroll` tuning (Step 2a of `/framac-eva`) is the usual fix.

### Symptom: `repair_hints` in the Eva Report (recursive call, or function with neither code nor specification)
- **Cause:** ported from upstream `frama-c-script make-wrapper` (see [`./upstream/sources/make_wrapper_tips.md`](./upstream/sources/make_wrapper_tips.md)). `run_eva_slice.py` matches `detected recursive call` and `Neither code nor (specification|... assigns clause) for function X,` in `eva.log` and lists the matching pipeline action in `repair_hints`.
- **Fix:** follow the hint's `action`: add the defining file to the module sources (locate it via `build_callgraph_dag.py`'s function index), add a stub/contract in `templates/acsl/external_stubs.h`, or enable the recursion fallback with `pipeline_make.py params set --module <mod> --eva-recursion-fallback` (recorded in `reduced_checks`).

### Symptom: Eva Reports `undeclared_functions: ["syscall"]` and Aborts with `invalid user input`
- **Cause:** `system.c` invokes the Linux `syscall(...)` glibc wrapper. Frama-C's internal libc headers (`__fc_libc/unistd.h`) omit the `syscall` function prototype when `-nostdinc` is used for Eva and WP.
- **Fix:** Add `/*@ assigns \result \from number; */ long syscall(long number, ...);` to `templates/fc_stubs/fc_compat_types.h` under the `__fc_libc` block. Fixed in pipeline, **uncommitted** as of 2026-11-09; listed in `templates/fc_stubs/README.md`.
- **Caveat (open, by design):** a variadic contract cannot say what the call writes through its arguments, so Eva and WP assume `syscall` writes no memory: a buffer it fills (`getrandom`, `read` through `syscall`) keeps the caller's value. Results that depend on such a buffer are optimistic.

### Symptom: Eva Aborts on Global Initializers with `invalid pointer creation ... evaluation of initializer failed: Eva not started because globals initialization is not computable`
- **Cause:** Code generated by `gperf` (such as `syscalls.perf.c`) or traditional C code uses `(size_t)&((struct stringpool_t *)0)->member` for static offset tables. When Frama-C's `-warn-invalid-pointer` is active, Eva treats pointer arithmetic on `NULL` during static const global table initialization as an invalid pointer alarm, aborting before analysis starts.
- **Workaround used by the libseccomp run (replaced):** `--no-warn-invalid-pointer` in `eva_args` of `templates/pipeline.mk`. It was global, so every module of every target lost the invalid-pointer alarms (`p + n` past an object), not only gperf tables; it is removed again.
- **Fix (pipeline, uncommitted as of 2026-11-09):** `scripts/fc_cpp_wrapper.py` (the preprocessor `-wrapper`, see the `offsetof` entry in Section 1) rewrites the idiom behind an integer cast, `(int)(size_t)&((struct stringpool_t *)0)->str5` into `(int)(size_t)__builtin_offsetof(struct stringpool_t, str5)`, which the kernel folds to the same constant gcc computes; a non-constant index goes through the same arithmetic as `offsetof(T, m[i])`. Each rewrite is logged as `[fc-cpp] <file>:<line>: null-pointer offset idiom rewritten: ...`. `-warn-invalid-pointer` stays on. Verified on the analysis image with a gperf-style table: the rewrite off reproduces `Eva not started because globals initialization is not computable`, on gives `0 alarms` (`test_frama_c_and_eacsl_accept_a_non_constant_offsetof_without_losing_precision`, `FRAMAC_DOCKER_TESTS=1`).
- **Limits:** only `(I)&((T *)0)->D` with an identifier-only cast and a null pointer written `0`, `(0)` or `((void *)0)` is rewritten. Without an integer cast (a pointer result), behind a pointer cast, or with any other null-based arithmetic (`(char *)0 + n`, `container_of` variants), Eva still reports the invalid pointer: triage those, or stub the code. libseccomp needs a re-run to confirm the whole module now starts.

## 5. Deductive Verification (`WP`) Issues

### Quick Symptom-to-Fix Reference

| Symptom in `wp.log` / `run_wp_function.py` | Root Cause | Exact Fix |
| :--- | :--- | :--- |
| Every goal after a loop fails, even for untouched variables | Missing `loop assigns` (WP havocs all memory on every iteration) | Write `loop assigns` (**Step A**) before any `loop invariant` (**Step B**). |
| `loop invariant` is `Valid` for `established`, `Unknown` for `preserved` | Invariant is not inductive across `i -> i + 1` or omits modified variables | Conjoin loop counter bounds (`0 <= i <= n`) with accumulator/pointer relationship (`offset == i * sizeof(elem_t)`), constrain all variables modified in the loop body, or drill down with `--prop <clause_name> --dump-goal` (`vc_goal_dumps`). |
| `loop invariant` fails `established` on `0 <= i <= n` | `n` can be negative on entry | Add `requires n >= 0;` (or use unsigned `size_t`). |
| `[wp] warning: Missing assigns clause` | Loop or callee lacks `assigns` (`run_wp_function.py` flags this as `unsound_proof`) | Add explicit `loop assigns ...;` and callee `assigns ...;`. |
| `[wp] warning: Memory model hypotheses for function ...` | `-wp-check-memory-model` detected raw `\separated` missing on pointer arguments | Add `requires \separated(p + (0 .. n-1), q + (0 .. m-1));` to the function contract. |
| `[rte:annot] warning: ... Through function pointer ... cannot generate ...` | Indirect call `fp(...)` without `calls` specification | Add `//@ calls f1, f2;` above the call or `//@ assert fp \in {&f1, &f2};`. |
| `Instance of 'Pre-condition ...' status: Unknown` at call site | Caller has not proven callee's `requires` | Add an intermediate `//@ assert ...;` before the call or strengthen the caller's loop invariant / `requires`. |
| `while (count--) { ... }` fails `rte:unsigned_overflow` | Post-decrement wraps `0U -> UINT_MAX` on loop exit | Use `--no-warn-unsigned --wrap-lines <lines>` (the declared lines are recorded in `reduced_checks` as an assumption; any other unsigned overflow goal not fully proved leaves the function unproven) or bound a non-wrapping counter. |
| Pointer cast `(uint32_t *)byte_buf` or `(void *)attr + 4` stays unproven under `Typed` | Type reinterpretation across pointer types, which the `Typed` memory model does not support | Do not switch to `Typed+cast`: the WP manual calls that model unsound, and `run_wp_function.py` records any proof under it as `unsound_proof`. When such goals stay unproven, `run_wp_function.py` re-runs the function once under `Typed+cast` as a diagnostic (`cast_model_probe`, never credited). If that probe proves every goal, the report sets `wp_cast_limitation` and `next_synthesis_focus: wp_typed_cast_limitation_stop_now`: stop, since a stronger contract will not help (on libmnl, `Typed+nocast`, `Bytes` and cast-free contracts left the same goals unproven). The unit stays unproven by WP: report it as a WP memory-model limit. |
| Address taken `&local_var` passed to helper | Stack variable address taken | Pass `--wp-model Typed+ref` (the default in `run_wp_function.py`). |
| `syntax error` on `terminates` or `exits` | Wrong ACSL clause order in function contract | Order clauses strictly: `requires` -> `terminates` / `decreases` -> `exits` -> `assigns` -> `ensures` -> `behavior`. |

### Symptom: `unsound_proof` With `Neither code nor specification for function X`

- `X` is called but has neither a body nor a contract. Frama-C generates a default contract and WP would trust it, so the proof does not hold.
- Add a contract to the prototype through `strengthening_requests`, or use a stub from `templates/acsl/external_stubs.h` for an external function.
- `Neither code nor explicit exits and terminates for function X` is a different message: `X` has a specification, and this one is harmless.

### Symptom: A Unit Stays Uncovered With `wp_trivial_clause_only` or `wp_limits_unmet`

- `wp_trivial_clause_only`: every `L4_*`, `L5_*` or `L6_*` clause of that class holds whatever the function does. Write a clause that constrains the output or state.
- `wp_limits_unmet`: the report has no `limits`, or its contract check did not pass. Re-run with the current `run_wp_function.py`; reports written before verdict limits existed are not credited.

### Symptom: `workspace/reports/kb/evolved.json` and `obstructions.json` Never Appear in a Run

- **Seen:** while implementing formal-discovery Tier 1 (dead-end ledger), 2026-11-09, by reading the code; no target run yet.
- **Cause:** `spec_kb.mine_run` (CLI `spec_kb.py mine --run-dir .`) is the only writer of the evolved KB and of the obstruction store, and no script, Make target, scheduler step or skill called it. Both stores therefore stay empty unless someone runs it by hand, and the "evolved" half of the spec KB has never fed a brief or a repair hint in an unattended run.
- **Workaround in place:** the Tier 1 "Known Dead Ends" section does not depend on mining: `prepare_agent` reads earlier provers' refutations of the same function from their scratch (`prover_candidates.refuted_clauses`), and `spec_kb.obstructions_for` reads callee rejections live from `workspace/reports/strengthen_requests.json`. Only cross-function persistence (the stored items) needs `mine`.
- **Fix:** **Fixed** on branch `formal-discovery-tiers`: `wp_scheduler.cmd_complete` now calls `spec_kb.mine_after_complete` after every result it accepts (not on a stale or repeated `complete`), under its own `spec-kb` run lock; `FRAMAC_SPEC_KB=off` mines nothing, and a mining failure is recorded in the command's `errors` without failing it. `mine_run` was not idempotent (each call re-scored every agent, so mining after each task would have counted an agent once per later task): it now records `mined_agents` in `evolved.json` and skips them, and in the scheduler's `finished_only` mode leaves an agent without `result.json` for a later call. Tests: `test_mine_run_counts_each_agent_once`, `test_finished_only_leaves_a_running_agent_for_later`, `test_mine_after_complete_fills_both_stores_unless_switched_off`, `test_complete_mines_the_spec_kb_and_a_mining_failure_is_only_an_error`.

### Symptom: A Prover's Merge Is Refused With `agent modified content outside assigned function '<fn>'` After It Added a Ghost Lemma Function
- **Fixed pipeline bug** (found 2026-11-09 while reviewing [`./formal-discovery-plan.md`](./formal-discovery-plan.md); reproduced on `acsl_ast.splice_prover_changes` with a `/*@ ghost /@ requires ...; decreases n; ... @/ void lem(int n) {...} */` block placed directly above the prover's function; fixed by Tier 3, [`./formal-discovery/tier-3-rule3-ghost-lemma.md`](./formal-discovery/tier-3-rule3-ghost-lemma.md)). Runs made before the fix still show the old message.
- **Cause:** [`../skills/framac-wp/prover_brief.md`](../skills/framac-wp/prover_brief.md) Step B item 3 ("Inductive Lemmas Without Coq") told the prover to replace a global `lemma` with a recursive `/*@ ghost ... */` C function carrying `decreases` and `ensures`. Such a function can only live at file scope, and `acsl_ast._compute_span_start` deliberately leaves top-level ACSL declarations (`ghost` included, via `_TOP_DECL_KWS`) outside the function span, so `splice_prover_changes` raised `ScopeViolationError` for exactly the construct the brief asked for. `verify_acsl_only` passes (the block is pure ACSL), so the prover saw no warning until `merge-agent`. A prover could reach `all_proven` in its scratch (WP under `-wp-fct` takes the ghost function's contract as a hypothesis and never proves the ghost function itself), then lose the whole attempt at merge. A second defect hid the declaration's name: `_parse_acsl_inner_segments` cut a ghost function at the first `;` of its `/@ ... @/` contract and `_extract_decl_name` returned the first parameter (`n`) instead of `lem`.
- **Fix:** (1) the brief's rule now forbids file-scope ghost functions as well as global `lemma`s and tells the prover to stop with `stalled_after_k_retries` and `proof_gap: {"predicate": ..., "reason": "inductive lemma required: ..."}`; (2) [`../scripts/prover_candidates.py`](../scripts/prover_candidates.py) `note_oracle` diffs the top-level declarations of `scratch/work` against `scratch/base` after every oracle run and reports `scope_violation_pending: ["ghost lem", ...]` in the first `candidate` block, with `next_synthesis_focus: "remove_top_level_acsl_declarations"`, `next_action: "continue"` even when `all_proven`, and the candidate never kept as best; (3) [`../scripts/acsl_ast.py`](../scripts/acsl_ast.py) `splice_prover_changes` names the added declarations (`agent added top-level ACSL declaration(s) outside '<fn>': ghost lem; ...`), and the segmenter treats a ghost function's `/@ ... @/` contract as part of the declaration; (4) [`../scripts/ledger.py`](../scripts/ledger.py) tags such a `proof_gap` with `details.gap_kind: "inductive_lemma_required"` and [`../scripts/generate_report.py`](../scripts/generate_report.py) counts those functions under "Open units: prover-limited vs spec-limited". Provers still cannot contribute lemmas: that is Tier 7 of the plan.

### Symptom: Implementation Mutants Fail With `acsl_syntax_error` (`return attr->=nla_len;`, `<==`, `>==`)
- **Fixed pipeline bug** (found 2026-11-09 by the formal-discovery Tier 4 A/B on libmnl run 1: 6 of 15 implementation mutants; also present on `phase1-remediation`; fixed on branch `formal-discovery-tiers`).
- **Cause:** [`../scripts/mutation_check.py`](../scripts/mutation_check.py) `impl_mutants` applies `_REL_OP_FLIP` with `body_text.replace(op, flipped, 1)`, a plain substring replace with no token boundaries, so `>` matches inside `->` and `<` inside `<=`. With the corrected criterion these mutants are `not_applicable` and leave the denominator, but the function then gets no real implementation mutant.
- **Fix:** `mutation_check._c_operators` regroups the single-character `c_token`s of `acsl_ast.tokenize_c_acsl` into C operators by maximal munch (`->`, `>>`, `<=`, ...), skipping comments, strings and ACSL, and `impl_mutants` flips only a whole `<`, `<=`, `>` or `>=`. Test: `test_impl_mutants_flip_only_whole_relational_operators`.

### Symptom: `mutation_check.py --run-dir` Scores Every Mutant `not_applicable` on a Target With Include Paths
- **Fixed pipeline bug** (fixed on branch `formal-discovery-tiers`; found 2026-11-09 by the Tier 4 A/B on libmnl: every mutant failed with `fatal error: libmnl/libmnl.h: No such file or directory`, reported as `acsl_syntax_error`).
- **Cause:** `run_mutation_check` passes the hard-coded cppflags `"-I."` to `check_function` instead of the module's WP flags. A preprocessing failure is also classified as `acsl_syntax_error`, which is misleading.
- **Fix:** `run_mutation_check` resolves each function's module from `coverage-ledger.json` and uses `pipeline_make.build_plan(run).wp_cppflags_for(module)`, as `wp-sweep` does; each function records `cppflags_source`. A function whose module flags cannot be resolved is listed under `skipped` instead of being checked with wrong flags; a directory with no ledger modules keeps the old `-I.` (`cppflags_source: default ...`). A preprocessing failure is no longer hidden behind `acsl_syntax_error` (also fixed on this branch): `run_wp_function` still reports that status, but every `not_applicable` mutant now carries a `failure` (`preprocessing_failed` when an error is a C preprocessor diagnostic or `failed to run: ... -E`, else the WP status), functions and totals count `preprocessing_failed`, a function whose every mutant failed to preprocess gets an `error` instead of a score, and the report's "Specification quality" section names those functions. Tests: `test_a_preprocessing_failure_is_named_and_leaves_the_function_unscored`, `test_an_acsl_error_is_not_a_preprocessing_failure`, `test_report_lists_functions_whose_mutants_failed_to_preprocess`.

### Symptom: A Proof-Carry Replay Rejected After Its Merge Leaves the Cached Contract in `workspace/work/`
- **Fixed pipeline bug** (fixed on branch `formal-discovery-tiers`; found 2026-11-09 by the formal-discovery Tier 6 A/B on a copy of libmnl run 1: `mnl_cb_noop` was rejected with `ledger ingest-wp failed`, its contract stayed in `workspace/work/src/callback.c` and its units stayed `planned`).
- **Cause:** [`../scripts/proof_carry.py`](../scripts/proof_carry.py) `replay` calls `reject()` after `merge_agent_overlay` has already spliced the tree (the `merged without a parent WP report` and `ledger ingest-wp failed` paths). `reject()` only removes the agent; the module docstring promises that anything else rolls back.
- **Fix:** `replay` snapshots the function's file, its header and its canonical `workspace/reports/wp/<fn>.json` before any merge and restores them on every rejection after that point (`_snapshot_files` / `_restore_files`), including a prover merge that fails after the header declarations were merged. A `mark-carried` failure after a successful `ingest-wp` is not rolled back: the units are already credited by the fresh report. - **Fixed pipeline gap** (fixed on branch `formal-discovery-tiers`; found in the Tier 6 A/B, 2026-11-09: `mnl_attr_get_str` was rejected at replay with `frame-preservation check failed: projected frame clause missing or weakened: 'assigns \nothing;'`, because run 1's swept contract predates the frame skeleton).

### Symptom: E-ACSL Fails With `labels pre-analysis was not performed on construct \old(b)` on a Guardrail Build
- **Open, toolchain (Frama-C 35.0~dev regression)**, diagnosed 2026-11-09. Seen in the Tier 6 A/B: the parent guardrail of `mnl_nlmsg_batch_is_empty` returned `compile_error`, so its merge was refused (`parent guardrail returned status='compile_error'`). The same contract passed under run 1's Frama-C 34 image.
- **Cause:** E-ACSL in 35 aborts on any `p1 <==> p2` whose operands contain a labelled term: `\old(...)`, `\at(..., L)`, or a formal parameter in an `ensures` (the kernel reads it as `\old(formal)`). The contract here was `ensures empty_iff_zero: (\result != 0) <==> (b->buflen == 0);`. The `Piff` translation now deep-copies its operands and skips the labels pre-analysis on the copies. A 6-line reproducer fails on `framac-analysis:latest` (35) and builds and runs on `framac-pipeline:fc34-20261105`. Upstream draft with the failing shapes and the 34/35 source diff: [`./upstream/frama-c-eacsl-iff-labelled-term.md`](./upstream/frama-c-eacsl-iff-labelled-term.md) (Issue 14, not filed).
- **Impact:** a WP-proven contract of this shape can never pass the parent guardrail on 35, so the prover's merge is refused, or a carry-forward replay rejected. In libmnl run 1, 4 merged contracts have it: `mnl_nlmsg_batch_is_empty`, plus three header `ensures` of the form `... ==> (\result <==> ...)` (`ok_iff`, `seq_track`, `pid_track`).
- **Fix:** **Open, toolchain**, with no pipeline workaround yet. Writing the equivalence as `(p1 ==> p2) && (p2 ==> p1)` avoids it. Options: tell provers to do that (prover brief), rewrite `<==>` in the guardrail build only, or patch E-ACSL in the image (patch not written or validated).

### Symptom: `wp_scheduler.py` Rejects Verifier Results with `$.record.linked_units: fewer than 1 items`
- **Cause:** `schemas/findings.schema.json` globally enforced `minItems: 1` on `linked_units`. When a crash or leak candidate originates from an external standard library stub (such as `FRAMAC_SHARE/libc/stdlib.h#free`) or generated harness code (`harness_<module>.c#unknown_function`), there are no target units in `coverage-ledger.json`, leading `scripts/ledger.py scaffold-verifier` to emit `linked_units: []`, which tripped the schema check and caused the scheduler to discard the result as invalid.
- **Fix:** Added `linked_units_nonempty` (`minItems: 1`) for `confirmed` findings in [`../schemas/findings.schema.json`](../schemas/findings.schema.json) while permitting empty `linked_units` for `rejected` candidate records. (Status: fixed).

### Symptom: `ingest-verifier refused the result: deferred unit must not hide evidence (use 'blocked' for partial work)`
- **Cause:** When `cmd_scaffold_verifier` scaffolded a `rejected` result for a function containing `deferred` units (e.g., functions skipped from WP prover dispatch via `shell_unverifiable_wp` or bounded profile), it populated `linked_units` with all non-out-of-scope function units. During ingestion, `cmd_ingest_verifier` added non-discharging reject evidence to each linked unit. Because the units were in status `deferred`, `validate_artifacts.py` rejected the ledger update under the invariant that `deferred` units cannot carry evidence.
- **Fix:** Updated `cmd_scaffold_verifier` in [`../scripts/ledger.py`](../scripts/ledger.py) so non-confirmed (rejected/needs_validation) candidate scaffolding links only the candidate's actual `linked_units` rather than all function units. In addition, updated `cmd_ingest_verifier` defensively so that if any unit in `NO_EVIDENCE_STATES` (`deferred`, `out_of_scope`, `not_applicable`) receives non-discharging evidence, its status transitions to `blocked` to maintain ledger validity. (Status: fixed).

### Symptom: `refusing to write invalid ledger: $[index].unresolved[N]: duplicate item`
- **Cause:** When multiple unproven goals on a function had identical annotations or lines (such as multiple pointer accesses or overflows on the same source line), `cmd_ingest_wp` in `scripts/ledger.py` appended them to `u["unresolved"]` without deduplication, violating the `coverage-ledger.schema.json` `uniqueItems: true` constraint.
- **Fix:** Deduplicated `u["unresolved"]` with `list(dict.fromkeys(...))` in [`../scripts/ledger.py`](../scripts/ledger.py) during WP report ingestion. (Status: fixed).

## Resources, Caches and Scheduling

The full guide is [`./resources-and-caching.md`](./resources-and-caching.md) (Section 9 lists symptoms). The most common ones:

- **A command prints "queue position N" and waits:** the measured pool is busy. `python3 scripts/resources.py status` (on the host) lists the leases. Leases of killed wrappers are released once their containers exit (`resources.py gc`).
- **A WP report has `"status": "analysis_error"`:** Frama-C was killed or timed out (`reason`: `oom_killed`, `timeout`, `crashed`). Nothing was proven or refuted. The recorded peak memory makes the next lease larger, and the scheduler retries once before marking the units `blocked`.
- **Suspected stale cache result:** re-run with `FRAMAC_CACHE=off` and compare, then `python3 /opt/framac-pipeline/scripts/cache.py clear`.
- **The shared cross-run store stays empty:** only the exact allowlisted commands (`python3 /opt/framac-pipeline/scripts/pipeline_make.py run build|eva|wp-sweep|ingest`, with or without `$S/...`) may write it. Unrecognized commands, extra un-allowlisted options, or `FRAMAC_CACHE_RW=off` keep the store read-only (`FRAMAC_CACHE_MODE=ro` inside the container).
- **An ad-hoc command is OOM-killed at 1 GiB:** commands the broker does not recognise run as `light` (1 CPU, 1 GiB). Pass `-Class` / `--class` (for example `build` or `phase-dynamic`).
- **`RunLockTimeout`:** another container held the run's `ledger` or `merge` lock for longer than `FRAMAC_LOCK_TIMEOUT`. A holder whose heartbeat stopped (`FRAMAC_LOCK_STALE`, default 120 s) is broken automatically, and an interrupted merge is rolled back from `state/merge-journal.json` by the next merge.
- **Need the previous static behavior:** `FRAMAC_BROKER=off` (`-NoBroker`) for container sizing, `FRAMAC_SCHEDULER=waves` for Phase 3 dispatch.

### Symptom: `test_sh_new_run_allocation_is_atomic_under_concurrency` fails on Windows with `child_copy: cygheap read copy failed ... Win32 error 299` or return code `3221225794`

- **Seen:** 2026-11-09, full `python -m pytest tests -n auto` in the formal-discovery Tier 4 worktree while five other sessions ran their own suites on the same Windows host. Failed twice in the full suite; `tests/test_run_identity_wrappers.py` passes alone (`-n 0`).

- **Fix:** none needed in the pipeline. Re-run the file alone (`python -m pytest tests/test_run_identity_wrappers.py -n 0`) when the host is busy. **Open test gap:** the test could skip or retry on a Cygwin fork failure instead of reporting it as an allocation race.
